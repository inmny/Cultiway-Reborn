# 生成 Cultiway 更新日志

面向玩家的中文更新日志。读起来要像「这版本加了什么好玩的东西」，而不是「这版本改了哪些代码」。

## 工作流

### 1. 定位版本区间

读 `mod.json` 拿到当前版本号，再用下面的命令找到用户指定起始版本对应的 commit：

```bash
# 列出每次改动 mod.json 的 commit 及其版本号
git log --all --pretty=format:"%H %s" --follow -- mod.json | while read hash msg; do
  v=$(git show $hash:mod.json 2>/dev/null | grep version | head -1)
  echo "$hash | $msg | $v"
done | head -20
```

用户说「从 0.0.26 至今」，就把 0.0.26 那一行对应的 hash 作为 `<起始commit>`。

### 2. 收集提交

```bash
git log --pretty=format:"%h %s" <起始commit>..HEAD
```

建议把结果写到临时文件再读，避免输出被截断。读完即删，不要污染工作区。

### 3. 识别「本次新增的系统」（关键步骤）

折叠规则的前提是先判断哪些系统是**本版本区间内新增的**。用两条证据交叉验证：

**证据 A：目录从无到有**

```bash
# 看起始版本到 HEAD 之间，Source/ 下哪些路径是新增的
git diff --name-status <起始commit> HEAD -- Source/ | grep "^A" | awk '{print $2}'
```

如果某个子系统目录（如 `Source/Core/SectLib`、`Source/Content/Artifact*`）的文件**几乎全部**是新增的 → 强信号：这是新增系统。

**证据 B：提交关键词聚类**

扫描提交信息，如果某个模块关键词（见下方词典）在本区间内**首次密集出现**，且早于本区间的历史里基本没有 → 强信号：这是新增系统。

**判定原则**：两条证据任一命中即可标为「新增系统」；都命中则几乎确定。拿不准时，按「已有系统」处理（保守，不滥用折叠）。

### 4. 按模块聚类提交

用下方「模块词典」把提交归到对应模块。无法归类的基础设施重构、代码整理归到「重构与整理」；跨模块的 UI 框架升级归到「UI」。

### 5. 应用折叠规则（核心）

对每个模块判定状态后，按下表处理：

| 模块状态 | 功能（feat） | 优化（optim/adj） | 重构（refactor） | Bug（fix/bugfix） |
|----------|--------------|-------------------|------------------|-------------------|
| **新增系统** | 写进该系统板块 | **折叠**，不单独列 | **折叠** | **折叠** |
| **已有系统** | 写进该系统板块 | 可选简述 | 可选简述 | 写进「Bug 修复」 |

**为什么这样**：新系统在首个版本必然伴随大量自身迭代和修复。如果把它们单独列到「Bug 修复」会让玩家误判「这系统质量差」，且这些 bug 对玩家毫无意义（他们没玩过上一版）。

**折叠≠删除**：被折叠的条目要**融进该系统板块的功能描述**，用一句话概括「建立了完整的 XX 体系」即可，不必逐条罗列。

**例外**：即使是新增系统，如果某个 bug/优化对**玩家体验**有显著独立价值（如性能从卡顿到 60fps、修复会导致存档损坏的崩溃），可以单独提及，但措辞要正面（写成「优化了 XX」「提升了稳定性」），不要写成「修复 XX 的 bug」。

### 6. 输出

按下方「输出格式」生成。语言：简体中文。面向玩家，突出玩法影响，不要堆代码细节。

## 模块词典

用于聚类提交。关键词命中即归入对应模块。

**玩法系统**
- `宗门` / `Sect` —— 驻地、职级、师徒、藏经阁、事务、日志、特质、贡献
- `法器` / `法宝` / `Artifact` —— 炼器、atom、外观、能力、飞剑、百宝阁
- `功法` / `Cultibook` —— 修炼方式、品阶、主修、LLM 生成、转修
- `境界` / `Realm` / `突破` / `Breakthrough` —— 视觉、金丹、元婴、突破异象
- `寻路` / `Pathfinding` —— 乘船、火车、铁路、码头、portal
- `地理区域` / `GeoRegion` —— 分区、自动命名、地图模式
- `丹药` / `Elixir` —— 生成、升级、评级
- `法术` / `技能` / `Skill` —— 轨迹、词条、齐射、连射、Power Level
- `修炼体系` / `Cultisys` —— 境界管理、灵气、灵根雨、升级雨
- `灵根` / `ElementRoot` —— 阴阳混沌、灵根雨
- `万法阁` / `魔网` / `Wanfa`
- `师徒` / `Master` / `Apprentice`

**内容 / 种族**
- `东方人族` —— 城墙、命名、服饰
- `奇幻生物` / `阵营` —— 恐虐、奸奇、青帝、万变魔君
- `骑士` / `Knight`
- `群系` / `Biome`

**基础设施**
- `UI` / `界面` / `Window` —— 统一界面、Foundation、Controls
- `语义` / `Semantics` —— 语义资产框架
- `系统开关` / `SystemSwitch` —— 各功能开关
- `日志` / `Log` —— 玩法日志、调试日志（注意区分：宗门日志归宗门）

## 输出格式

```markdown
# 修仙[重制] 更新日志 — <目标版本号>

> 预览版，存档无效，无优化

## <emoji> <新增系统名>（全新 / 重大重构）

<2-4 句话概述这个系统是什么、玩家能做什么。然后列功能点。>

- **<子模块>**：<具体功能>
- ...

## <emoji> <已有系统名>

- <功能点>
- <功能点>

## <emoji> UI / 视觉
...

## 🐛 Bug 修复
<只列「已有系统」的 bug，以及跨模块的崩溃/卡死。新增系统的 bug 不在这里。>

---

**完整提交数**：<N>（`<起始commit短hash>` 之后到 `<HEAD短hash>`）
```

### emoji 建议

宗门 🏛️｜法器 🗡️｜功法 📜｜境界 🌟｜寻路 🧭｜法术 ✨｜丹药 💊｜地理 🗺️｜UI 🪟｜修炼 🧠｜灵根 🌱｜Bug 🐛

## 反面示例

**错误**（把新增系统的 bug 单独列出）：

```markdown
## 🏛️ 宗门系统（全新）
- 创建宗门、职级、师徒...

## 🐛 Bug 修复
- 修复宗门 object 复用时字段缺值
- 修复外门弟子也能收徒入宗
- 修复宗门建筑会被城市建筑强行覆盖
```

玩家看到会想：「这新系统一堆 bug」。

**正确**（折叠进系统描述）：

```markdown
## 🏛️ 宗门系统（全新）
从零搭建了完整宗门体系，含创建、职级晋升、师徒、藏经阁、驻地、地图模式、日志。
- **组织**：外门/内门/执事多层职级，带徒入宗权限
- ...
```

## 完成后

- 收尾不要长篇总结。最后只附「完整提交数」一行。
- 不要主动建议写入 `CHANGELOG.md`，除非用户要求。
- 删除所有临时文件。
