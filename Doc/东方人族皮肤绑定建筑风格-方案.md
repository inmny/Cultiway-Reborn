# 东方人族文化皮肤绑定建筑风格 — 实现方案

## 一、现状调研结论

| 机制 | 现状 |
|---|---|
| 皮肤存储 | 文化级 `culture.data[SkinID_int]`（10 种风格：1 通用 / chunqiu / tang / song / yuan / ming / qing / modern / fusang / chaoxian），`EasternHumanSkinStyles.CycleNext` 循环切换并刷新单位贴图 |
| 单位换肤 | `PatchAboutCultureSkin` 在 `ActorTextureSubAsset` 贴图路径层按 `skin_citizen_male_tang` 等目录选择 |
| 建筑贴图 | 东方建筑资产 `main_path = "buildings/civ_main/Cultiway.EasternHuman/"`，NML 启动时按相对路径扫描 `GameResources/**` 全部图片，精灵以路径为键（`SpriteTextureLoader.getSprite("walls/...")` 已有先例），**路径键不会重名冲突** |
| 建筑渲染 | `Building.calculateMainSprite()` 选 `animData.main`，**原版预留了逐建筑覆盖钩子 `asset.get_override_sprites_main(Building)`（delegate Sprite[]），原版代码从未使用**，返回 null 则回落默认 |
| 缓存 | `calculateColoredSprite` 以主精灵 hash 为缓存键，主精灵一变即自动重算染色（王国色）缓存，无需手动刷新 |
| 已有联动 | modern 皮肤门控东方大厅 3→4 级升级（`PatchBuilding.canBeUpgraded`），保持不变 |

## 二、总体思路

**不改建筑资产、不克隆资产、不补丁渲染管线**——利用原版预留的
`BuildingAsset.get_override_sprites_main`，在渲染取帧阶段按"所属文化当前皮肤"返回
风格变体精灵数组；变体贴图按风格目录预置于资源目录（NML 自动扫描加载），
缺图自动回落默认贴图。

```
放置/渲染建筑 → calculateMainSprite()
  → get_override_sprites_main(building)
      → 读 city.culture 的 SkinID → 风格 key（如 "tang"）
      → 组装路径 cultiway/building_skins/tang/hall_Cultiway.EasternHuman_2/main_0
      → SpriteTextureLoader.getSprite(...)（缓存 Sprite[]）
      → 目录/文件缺失 → 返回 null → 原版回落通用贴图
```

## 三、资源目录规范

```
GameResources/cultiway/building_skins/
  chunqiu/hall_Cultiway.EasternHuman_0/main_0.png ...
  tang/hall_Cultiway.EasternHuman_0/main_0.png ...
  song/...  yuan/...  ming/...  qing/...  fusang/...  chaoxian/...  modern/...
```

- 每个风格目录内的 `<建筑id>/` 子目录**文件名与像素尺寸必须与基础目录
  `buildings/civ_main/Cultiway.EasternHuman/<建筑id>/` 完全一致**（main_N 同名同尺寸）。
- ⚠️ 语义注意：`main_N.png` 与 `main_M.png` 是**同一建筑的不同随机外观变体**（游戏为每栋建筑随机固定一个变体）；
  `main_N_0.png、main_N_1.png...` 才是同一外观的动画帧。运行时会按建筑已选定的变体条目
  （`animData_index`）返回该条目的风格帧，**绝不会把不同变体拼进同一数组**（否则建筑外观会来回轮播）。
- ⚠️ 历史命名怪癖：部分基础素材的动画帧为 `main_N _K.png`（`main_N` 与后缀间多一个空格，如风车叶片
  `main_0 _0.png..main_0 _3.png`）。运行时两种命名都会探测，且**多帧动画条目优先于单帧文件**——
  风格包中风车要播放动画，必须包含 `main_0 _0.._3` 全部帧文件（仅有 `main_0.png` 会显示为静止）。
- 风格 `1`（通用）不建目录，直接使用现有基础贴图。
- **目录级判定，不与通用贴图混用**：只要 `building_skins/<风格>/<建筑id>/` 下有该建筑的贴图，
  该建筑就整体只使用风格包贴图——风格包内缺失的变体条目用包内其他变体顶替；
  目录下无任何贴图时才回落通用贴图。
- 美术管线复用树木流程：以基础贴图为结构参考 → AI 按朝代风格生成 → 抠图 →
  块平均像素化到与原文件相同的精确尺寸（逐文件一一对应，多帧条目需产出全部帧）。

覆盖范围（东方建筑共 21 个）：
- 优先 P1：`hall_0..2`、`house_0..5`（9 个，视觉主体）
- P2 功能建筑：`watch_tower / market / temple / library / barracks / windmill_0 / windmill_1 / tent`
- P3 水系与特殊：`docks / fishing_docks`；`hall_3 / house_6 / house_7` 仅 modern 需要

## 四、代码改动点

| # | 位置 | 内容 |
|---|---|---|
| 1 | 新建 `Source/Content/Const/EasternHumanBuildingSkinSprites.cs` | 静态缓存 `Dictionary<(int styleIndex, string buildingId), Sprite[]>`；`OverrideMain(Building)`：读城市文化 SkinID → key → 逐张 `getSprite` 组装数组；任何一张缺失即尝试继续，全缺返回 null |
| 2 | `Buildings.SetupEasternHumanBuildings` 末尾 | 对全部东方建筑资产设置 `asset.get_override_sprites_main = EasternHumanBuildingSkinSprites.OverrideMain` |
| 3 | （可选 v1.1）`PatchAboutCultureSkin` 或新前缀补丁 | `calculateMainSprite` 废墟分支同样应用 override（取 `ruin_N`），让废墟也随风格变化；v1 先不做，废墟共用默认版 |
| 4 | 无需改动 | 皮肤切换（CycleNext）：渲染每帧读当前皮肤，建筑自动换装；染色缓存按精灵 hash 自动失效 |

风格 key ↔ SkinID 映射复用 `EasternHumanSkinStyles`（新增 `KeyOf(int index)` 查询）。

## 五、边界与兼容

- **多文化并存**：皮肤是文化级数据，两个东方文化可同时各用不同风格，互不影响（override 逐建筑读所属文化）。
- **非东方种族**：override 只挂东方建筑资产，人类/鬼族建筑不受影响；鬼族虽也有 CultureSkin 特质，本方案不覆盖（后续可复用）。
- **存档兼容**：SkinID 持久化于文化数据；风格目录缺失自动回落；新增目录对旧存档无副作用。
- **性能**：渲染期每建筑每帧一次字典查询 + 哈希比较，开销可忽略；精灵由 NML 启动时统一加载。
- **小地图/建造中贴图**：v1 不分风格（mini/construction 共用），如需再扩展。

## 六、验证清单

1. 神力循环切换皮肤 → 同城建筑逐帧变为对应风格，无残留旧帧（染色缓存失效验证）。
2. 两个东方文化分别设不同皮肤 → 两城建筑风格同时保持独立。
3. 删除某风格某建筑的贴图文件 → 该建筑回落通用贴图，无报错。
4. 大厅 modern 升级门在切换皮肤后行为正确（modern 可升，其他禁止）。
5. 建筑废墟/受损显示正常（v1 共用废墟贴图）。
