# 第4阶段-遗迹战利品与争夺

本阶段把“机缘收益”升级为遗迹中真实存在、可拾取、可遗落、可争夺并能带回主世界的 typed 战利品，同时允许两支队伍进入同一共享 Runtime。机缘归属由谁真正调查、拾取并活着带回决定，不使用抽象积分、唯一 Winner 或阶段末统一发奖。

本阶段还加入第二种机械结构不同的开放遗迹“远古战场”，开始验证“各式遗迹”由地貌、遗构、危险、守卫和机缘组合形成，而不是给古修道场换一套颜色。

## 具体说明

### 设计边界

- 阶段验收只要求两类实体战利品：Ingredient 与 MagicScroll；Artifact、Elixir、Talisman、装备和制造进程后移到具体遗迹真正需要时。
- 主世界携带物仍不进入小世界；本阶段只处理遗迹中新生成并带出的物品。
- MagicScroll 在遗迹内不能阅读、学习或消耗；它作为物品带回后继续使用主世界现有语义。
- 多队伍上限先固定为两队、每队 1-3 人；扩大容量留到阶段 5 实测。
- 队伍之间只有 Allied、Neutral、Hostile 三种入场时快照；不在 Runtime 中运行完整王国/宗门外交。
- Neutral 只竞争机缘，不主动互相攻击；Hostile 才允许 Projection 对 Projection 战斗。
- 不建立通用跨世界库存框架、任意 ECS 组件序列化或六类 PortableItem 基类层级。
- 遗迹仍全部属于当前会话，RuinLootId 不跨加载恢复。

本阶段分三道独立闸门，必须按顺序通过：

- **4A（步骤 1-3）**：单参与者 typed loot 生成、携带、遗落、Prepare/Commit/Rollback 与防复制。未通过前不实现队伍或第二遗迹。
- **4B（步骤 4-5）**：在 4A 稳定合同上加入两队、Knowledge 隔离、Neutral/Hostile 和原子竞逐。未通过前不写远古战场内容。
- **4C（步骤 6-7）**：只使用 4A/4B 已验证的 loot、Admission、战斗和清理合同实现远古战场，再完成跨 Archetype 验收。

### 步骤 1：建立机缘表与创建时确定的收益载荷

#### OpportunityTable

新增 `RuinOpportunityTableAsset`：

```text
Id
Entries[]
  OpportunityKindId
  CompatibleLandmarkKinds[]
  Weight
  MinRealm / MaxRealm
  HazardBudget
  GuardianBudget
  OutcomeFactoryId
  VisualProfileId
```

`OutcomeFactoryId` 必须引用已注册的强类型 factory；不存在时具体内容配置注册失败。禁止把物品组件写成 JSON 或键值 payload。

首批 OpportunityKind：

| Kind | 典型地点 | 收益 | 是否生成地面物 |
| --- | --- | --- | --- |
| HerbRemnant | 药圃、灵脉渗出点 | Ingredient | 是 |
| InheritanceTrace | 残碑、道台、尸骸执念 | MagicScroll | 是 |
| DaoInsight | 道台、战痕、阵眼 | InsightOutcome | 否，返回结算数值 |
| WeaponFragment | 战场尸骸、断器堆 | Ingredient/后续 Artifact 素材 | 是 |

#### 创建时确定

所有有限机缘的最终收益在 Runtime 创建时由 GenerationRandom 确定并存为隐藏 typed payload：

- 调查成功率可以在交互时使用独立 AttemptSeed。
- 收益种类、品质、数量和 RuinLootId 不因进入者、相机、重试或打开时刻重抽。
- 未 Exposed 前 payload 不进入 ReadModel、AI Knowledge 或 Tooltip。
- 同一 Opportunity 即使多队同时调查，也只有这一份 payload。

`RuinOpportunityState` 增加 `PayloadId`，实体 payload 存在 Runtime 专用 repository；State 不复制全部物品字段。

#### 价值评估

AI 只能看到收益区间：

- Clued：只知道类别倾向与粗略价值档。
- Exposed：知道物品类型和品质范围。
- Claim 后：持有者知道完整 typed payload。

AI 不读取隐藏精确数值来抢夺，玩家也只有公开发现后才能看见对应信息。

### 步骤 2：实现 Ingredient 与 MagicScroll typed 战利品

#### 先审计现有组件

实现前分别读取现有 Ingredient 与 MagicScroll 的创建、显示、持有、使用和销毁路径，列出构成固有身份的最小组件。不得照搬旧文档中并不存在的 `IngredientSnapshot` 或 `MagicScrollSnapshot` 类型。

只捕获物品自身定义，不捕获：

- 当前主世界 EntityId。
- holder、city、Actor 或 EntityStore 引用。
- UI cache、Renderer、临时选择状态。
- 制造过程或不属于该物品类型的组件。

#### typed 值

按真实组件审计结果建立两个独立值类型：

```text
RuinIngredientLootValue
  RuinLootId / ShapeId / NameData
  PowerLevel / CreatedTime
  IngredientSemanticFields...

RuinMagicScrollLootValue
  RuinLootId / ShapeId / NameData
  PowerLevel / CreatedTime
  SkillBlueprintValue / ScrollSemanticFields...
```

这里的 `...Fields` 必须在实现前替换为代码中真实存在且构成物品语义的字段，不允许把整个 Component bag 塞进字典。

#### 显式工厂

重构现有物品创建入口为明确目标 Store：

```text
IRuinLootMaterializer<TValue>
  Validate(targetContext, value)
  Create(targetContext, value) -> Entity
  Verify(entity, value)
```

- MainWorld targetContext 明确包含主世界 Store 和 holder adapter。
- SubWorld targetContext 只用于地面战利品实体，不调用绑定全局 Store 的 `SpecialItemUtils` 隐式路径。
- Ingredient 与 MagicScroll 各有 handler，不用反射或运行时字段复制。
- MainWorld 原有创建路径改为调用同一 typed builder 时，必须先用 fixture 证明结果不变。

### 步骤 3：实现战利品生成、携带、遗落与原子返回

#### 生命周期

```text
HiddenPayload
-> SpawnedOnGround
-> Carried(ParticipantId)
-> Dropped
-> Settling
-> SettledMainWorld
   \-> DestroyedByCollapse
```

- Opportunity 调查成功后，在其真实 tile 生成 `RuinLootEntity`，不自动放入调查者背包。
- 拾取要求同格/邻接、可携带容量和原子 owner 变更。
- Carried loot 仍是 Runtime Entity/typed value；Projection 只保存 RuinLootId 列表。
- 死亡、主动丢弃或持有者清理时回到 Dropped，位置明确。
- Collapsed 可以销毁仍在地面的 loot；已进入 Settling 的 loot 先完成或回滚，再处理崩塌。

#### 容量

首版每名 Projection 最多携带：

- 3 个普通 Ingredient loot，或
- 1 个 MagicScroll + 1 个 Ingredient。

容量由 loot category slot 表达，不引入重量、背包格、装备栏或玩家整理 UI。AI 在容量不足时按已知价值决定替换或放弃，替换会把原 loot 丢在当前格。

#### 原子返回

每个 RuinLootId 维护唯一 `RuinLootOwnershipState`，所有状态变化由 Runtime command 执行。返回事务扩展阶段 1 的同一原子提交协议：

1. `PrepareLootSettlementCommand(ParticipantId, Revision)` 在 Runtime tick 边界把持有者所有 loot 从 Carried 改为 Settling，冻结拾取并发布 Token/快照。
2. `SubWorldExpeditionService` 按 RuinLootId 排序，仅把 `SourceActorId/HolderId`、typed loot values、仅含标量/不可变 typed value 的 ActorOldValues、`MaterializerKey` 与纯数据参数写入 `SettlementStagingRegistry`；不保存对象引用，不提前 Create Entity 或修改主世界字段。
3. `CommitLootSettlementCommand(Token, StagingId)` 在 Runtime 预校验后进入不可重入主线程提交段；commit port 此时才按 ID/Key 重新解析 Actor、holder adapter 与 materializer，同步 Validate/Create/Verify 并返回可逆 Receipt。
4. Promote 成功后，Runtime 在同一调用内以无分配、无外部回调的代码把源 loot 标记 SettledMainWorld、更新 settlement ledger 并销毁 Runtime loot Entity。
5. MainWorld 或 Runtime 最终提交任一步失败时，port 在退出提交段前按 Receipt 删除目标 Entity、恢复 Actor 字段，Runtime 同步恢复 Prepared/Carried；外界没有可见或可保存的半份 loot。
6. 两边成功后才发布 Commit 事件、清理 Binding/StagingRecord。Commit 前取消或清理使用 `RollbackLootSettlementCommand(Token)`；Projection 保持完整可重试。

`SettledMainWorld` RuinLootId 进入 Runtime settlement ledger，后续命令不能再次处理。ledger 只存在到 Runtime 销毁，不做跨会话持久化。用途层不能绕过命令直接改 ownership、ledger、Opportunity 或源实体。

#### 主世界来源追踪

物化后的物品只保留可长期解释的 `RuinOriginContentId`，用于 Tooltip 表达来源类别。`RuinLootId -> MainWorldEntityId` 的防重映射留在当前 Runtime settlement ledger/Debug 索引中，不写入可能随主世界物品保存的数据；重新加载后不会出现失效 Runtime ID。

### 步骤 4：实现两队并存、独立知识与关系快照

#### 4B 闸门

开始本步前，4A 的单参与者 typed loot 往返、死亡遗落、物化失败回滚和重复领取测试必须全部通过。

#### 队伍

`RuinExpeditionParty`：

```text
PartyId
MemberParticipantIds[]
SourceAffiliationId?
EntryTick
KnowledgeState
RelationSnapshotByPartyId
```

- 同一 Actor 只能属于一支当前远征队。
- 队伍共享 ObservedTiles、Clues 和 KnownHazards；新成员加入时获得当前队伍知识。
- 不同队伍的 Knowledge 独立；物理实体状态、守卫生命和地面 loot 全局共享。
- 首版队伍在入场时固定，内部不合并、拆分或招募。

#### 关系快照

主世界适配器在第二队进入前根据现有关系得出：

- Allied：共享公开目标和守卫仇恨，禁止互伤；Knowledge 不自动合并，除非两个队在感知范围内完成一次信息交流事件。
- Neutral：禁止互伤，独立调查并争抢同一 loot。
- Hostile：允许互相感知、仇恨和战斗；仍受同一 shared resolver 与死亡规则。

关系在该队本次远征期间固定。主世界关系变化不热更新 Runtime，避免每 tick 回查世界对象；双方都退出后下次入场重新捕获。

#### 入口与出生

两队从同一 Site 的入口区域进入，但 SpawnPoint 必须寻找不同合法空格。入口附近设置短暂 `ArrivalSafetyTicks`：

- 只阻止 Projection 对 Projection 的攻击，不阻止守卫或危险。
- 任一队离开入口半径或主动攻击后立即结束。
- 不能在安全区内调查/拾取 Opportunity。

该规则避免实体重叠和加载即互杀，不创建永久安全屋。

### 步骤 5：实现机缘竞逐、原子领取与有限敌对

#### 原子命令顺序

同一 tick 的调查完成、Opportunity claim 和地面 loot pickup 统一按：

```text
TickIndex
-> CommandSequence
-> PartyId
-> ParticipantId
```

排序。第一个通过状态/距离校验的命令成功，后续收到明确 `AlreadyClaimed` 或 `LootUnavailable`，不得再次 roll 收益。

`CommandSequence` 由 Runtime 接收命令时分配，不使用线程到达顺序或渲染帧顺序。

#### 竞争 AI

AI 只在实际感知其他队伍后加入竞争因素：

- 估算对方到 Exposed Opportunity 的可见距离。
- 自己路线更短且风险可接受时提高 claim 优先级。
- 已持高价值 loot 时更偏向返程，不因发现竞争者无条件冒险。
- Neutral 不阻挡、攻击或跟踪对方隐藏位置。
- Hostile 可选择攻击持有高价值 loot 的已感知参与者，但仍比较战斗风险和返程收益。

没有抽象 Winner。一个 Site 中不同队伍可以各自带走不同机缘，甚至都空手或死亡。

#### Projection 对 Projection

复用阶段 3 战斗组件：

- Hostile 关系才创建合法攻击目标。
- Source Actor 的主世界 faction/sect 只在入场时转为 Runtime FactionId。
- 死亡者物理 loot 落地，击杀者不会自动获得；必须移动并拾取。
- Allied/Neutral 误伤在命令验证阶段拒绝，不依赖伤害 resolver 返回 0。
- 同归于尽按同 tick 已提交伤害规则结算，loot 分别落在各自死亡 tile。

### 步骤 6：实现远古战场并在验收后提取 Archetype

#### 4C 闸门

开始本步前，4B 的两队 Admission、Knowledge 隔离、Neutral/Hostile 关系、原子 claim 和 Projection 对 Projection 结算必须全部通过。远古战场不得引入一套新的 loot、队伍或清理语义。

#### 设计目的

`Cultiway.Ruin.Content.AncientBattlefield` 必须在玩法上区别于古修道场：

| 维度 | 残破古修道场 | 远古战场 |
| --- | --- | --- |
| 地貌 | 山脊、谷地、林地与道场遗构 | 焦土、裂谷、残垒、尸骸带与兵器散落区 |
| 信息来源 | 残碑、道痕、阵眼、药圃 | 战痕走向、尸骸姿态、残旗、兵器共鸣 |
| 主要危险 | 断裂阵带、灵气污染 | 煞气风暴、执念聚集区、游荡残魂群 |
| 机缘 | 灵植、道台感悟、传承卷轴 | 兵器残材、战法卷轴、战意感悟 |
| 守卫 | 残阵傀儡、少量残魂 | 成群残魂、战场执念投影 |
| 调查节奏 | 地标之间推理线索 | 沿战痕追踪事件中心，同时规避移动危险 |

它不是把 terrain 调色后复用同一 Landmark 表。至少新增：

- 2 个手工开放战场底图。
- `BattleTraceClue`：沿战斗方向提供带噪声的链式线索。
- `BalefulStormHazard`：按预生成路线缓慢移动的危险带。
- `CorpseRemnantOpportunity` 与 `BrokenWeaponOpportunity`。
- 一组残魂 patrol/聚集规则。

#### 开放性约束

- 战场没有房间和固定战线门。
- 移动危险带不能封死所有返程路线。
- 至少一个机缘可完全避战取得，至少一个高价值机缘明确受守卫威胁。
- 尸骸/兵器散点形成叙事方向，但不能是一条唯一导航线。

#### 内容边界

阶段 4 的战场奖励仍只有 Ingredient、MagicScroll 和 Insight；Artifact 只作为后续内容入口，不在本阶段临时伪造成 Ingredient。

### 步骤 7：完成重复游玩与防复制验收

#### 4A 验收：typed 往返

对 Ingredient 与 MagicScroll 分别验证：

- Runtime payload -> 地面 Entity -> Carried -> MainWorld Entity 后，所有固有字段与 typed value 相等。
- Sprite/Icon/Tooltip 与主世界正常创建的同类物品一致。
- Source Runtime Entity 在成功物化后不存在。
- 第 N 个 materializer 或 Runtime 最终提交失败时，主世界和 Runtime 不会各留一份，StagingRecord/Receipt/待确认 Entity 全部归零。
- Prepare 后触发保存或清理不会枚举出 staged loot；不可重入 Commit 调用只能完整成功或完整回滚。
- 死亡、主动丢弃、由后续单参与者拾取后仍保持同一 RuinLootId。

#### 4B 验收：竞争场景

至少运行：

1. 两支 Neutral 队同时调查同一机缘，只有一队成功 claim。
2. 两队分别取得不同机缘并安全返回，没有 Winner 结算。
3. Hostile 队在开放地貌相遇，一方死亡，另一方实际拾取后带回 loot。
4. 同 tick 双方互杀，loot 留在两个死亡 tile，第三支后续队可以拾取。
5. 结算期间遗迹崩塌，事务先完成或完整回滚，不复制物品。

#### 4C 验收：跨遗迹内容差异

先为远古战场实现具体的 `AncientBattlefieldGenerationConfig` 与 `AncientBattlefieldPlan`，并分别对古修道场和远古战场运行阶段 2 的 `RuinContentAcceptance`。只有两者都通过后，才比较并提取真正重复的字段为 `RuinArchetypeAsset`；不重复的线索、危险、机缘和守卫配置继续保留在具体内容类型中。

使用至少 20 个古修道场 Seed 和 20 个远古战场 Seed，必须得到以下可观察断言：

- 古修道场使用“残碑/道痕 -> 地貌调查”传播，战场使用“战痕链 -> 事件中心”传播；两套 Clue 计算路径不同。
- 古修道场危险主要是静态残阵/污染，战场至少有一条预生成路线移动的煞气危险；两者的避险路线选择分布不同。
- 每类遗迹至少有一种不依赖战斗的机缘应对，且对应交互类型不同。
- 守卫的活动锚点和巡游/聚集规则不同；不能只改数值倍率。
- 固定 Seed 的具体 Plan、Outcome 和公开状态可重复；不存在无路返回、全部机缘集中、隐藏坐标泄露或危险永久封口。
- 输出两类全图俯视诊断图、Opportunity 前置关系图和路线差异报告；两类前置关系图都必须为空，人工检查不得出现串联“战斗区 -> 奖励区”。

#### 压力与清理

- 每个具体遗迹配置连续创建/耗尽/销毁 25 次；共同字段抽取完成后再运行 Archetype 注册路径。
- 两队反复进入、退出、死亡和拾取后，Party、Knowledge、Threat、RuinLoot、settlement ledger、StagingRecord、PromotionReceipt、待确认 Entity、Binding 与 View 计数归零。
- `dotnet build Cultiway.csproj -c Debug` 无错误。

## 资源说明

| 资源 | 类型 | 建议路径 | 设计要求 |
| --- | --- | --- | --- |
| Ingredient 地面物 | 现有 ItemShape 世界 sprite | 复用现有资源 | 缩放稳定，不因名字长度改变布局 |
| MagicScroll 地面物 | 现有 Scroll sprite/icon | 复用现有资源 | 地面与主世界物品页使用同一视觉身份 |
| 拾取/遗落反馈 | 短时 VFX | `GameResources/cultiway/sub_world/ruins/common/loot/` | 只表达状态变化，不遮挡附近单位 |
| 远古战场 terrain 组合 | 原版焦土、岩地、坑洼等 | 先核对 `.GameSource/Assets` | 不复制基础 terrain，不用单色滤镜代替内容 |
| 尸骸、残旗、断兵 | 世界空间遗构 | `GameResources/cultiway/sub_world/ruins/battlefield/landmarks/` | 方向与聚集关系可读，避免均匀散点 |
| 煞气风暴 | 移动 Hazard VFX | `GameResources/cultiway/sub_world/ruins/battlefield/baleful_storm/` | 移动边界与方向清楚，不遮挡地图大部分内容 |
| 战痕线索 | 地表 decal/短时 VFX | `GameResources/cultiway/sub_world/ruins/battlefield/traces/` | 表现事件方向，不画玩家导航箭头 |
| 队伍关系 | 选中圈/生命条色 | 复用现有阵营色语义 | 颜色之外保留形状/图标差异，避免仅靠色觉 |

新增战场资源前必须核对原版废墟、尸骸、焦土、旗帜、武器和天气 VFX；原版能直接表达时优先复用。
