# 第2阶段-遗迹生成与探索

本阶段把第一阶段的单张开放古修道场扩展为可重复游玩的遗址生成与调查系统。Generator 仍只生成连续 Tile 地貌和物理 Actor/Building placement；观察、调查、危险和机缘在对应可运行系统实现时再加入，不作为生成步骤的预制能力计划。

本阶段继续使用具体的 `RuinedDaoGroundGeneratorAsset`。在阶段 4 实现第二种遗迹并确认实际重复以前，不增加 `GenerationConfig`、通用 Archetype、Plan、Bootstrap 或内容 Validator。

## 具体说明

### 设计边界

- 不生成矩形房间、走廊树、钥匙门或“入口到 Boss”的关键路线。
- Region 只是地貌与内容分布语义，不是带墙边界的玩法容器。
- 空间 ECS 类别只有 Actor 与 Building；Tile 留在稠密 Grid，Site 等非空间状态由实际用途 Service 管理。
- 每个物理遗构只有一个 Building 和一个 `LocalObjectId`。
- Terrain 继续直接使用原版 Asset ID，不复制定义。
- Generator 使用 `System.Random(seed)`，只决定地貌、placement 和视觉变体，不进入 Runtime 热路径。
- 不建立任意脚本、通用 Rule Module、FeatureSlot 解释器、目标 DAG、无类型配置包或预制能力仓储。
- 本阶段仍无战斗与死亡；危险效果在步骤 5 真正实现时确定。

### 步骤 1：扩展古修道场具体 Generator

直接扩展 `RuinedDaoGroundGeneratorAsset`，让它从一个手工布局增加到三个明确布局。每次生成仍直接返回：

```text
SubWorldGeneratedScene
  MapData
  SpawnPoints
  SubWorldActorPlacement[]
  SubWorldBuildingPlacement[]
```

Generator 继续用原版 `BuildingAsset.fundament` 清理地基，并为 Building placement 分配稳定 `LocalObjectId`。不创建 `RuinedDaoGroundPlan`、`GenerationSignature`、用途 Bootstrap、Repository 或 Validator；生成代码本身负责构造正确场景，通用 Runtime 负责物化 placement。调查、线索、危险和机缘所需的数据结构在对应玩法步骤根据真实读写流程设计。

### 步骤 2：实现手工布局族与 Seed 内容组合

#### 布局族

`RuinedDaoGroundLayoutFamily` 提供至少 3 个手工开放底图，每个底图都包含相同语义区域但地貌关系不同：

| 底图 | 地貌特点 | 路线差异 |
| --- | --- | --- |
| 山脊道场 | 入口在低处，遗构沿弧形山脊分布 | 山脊捷径危险，缓坡路线安全 |
| 谷地道场 | 废殿与药圃分列谷地两侧，道台在高处 | 中央残阵短路，两侧均可绕行 |
| 林中道场 | 遗构被林地和水洼分割 | 视线受限，但不存在唯一窄口 |

这里的“底图”是 terrain mask 与锚点池，不固定具体机缘内容。所有底图都保持连续开放视野，不绘制封闭室内结构。

#### Seed 组合顺序

Generator 使用调用内的 `System.Random(seed)` 按固定顺序：

1. 选择一个手工底图。
2. 选择对应底图的坍塌/植被 variation。
3. 从每类 Building anchor pool 中选出物理放置点并分配稳定 `LocalObjectId`。
4. 选择原版 Building 视觉变体。

三个手工底图和各自 anchor pool 都由代码直接写成合法布局，不做失败重试、回退地图或生成后 Validator。调查、危险和机缘系统需要的状态由对应步骤依据已经物化的 Building 建立，不混入地图 Generator。

#### 内容兼容

机缘系统在真正实现时根据宿主 Building 和地貌语义选择内容，例如：

- 灵植只进入药圃、湿地或灵脉渗出点。
- 石碑传承只进入残碑、道台或废殿遗构。
- 阵法机缘只进入阵眼、阵基或灵脉节点。
- 遗物只进入尸骸、断器或坍塌遗构。

该兼容关系属于机缘玩法本身，不由地图 Generator 随机安装，也不要求生成额外 Opportunity Entity。

### 步骤 3：形成开放通路与地标分散的布局

三个手工布局直接按以下规则编写，不新增 `RuinedDaoGroundValidator` 或运行时预检：

#### 通路

- Entry 本身可站立，周围至少有两个可离开方向。
- 每个 `OpportunityClaimKey(SourceLocalObjectId, SlotIndex)` 的宿主 Building anchor 从 Entry 可达，且原版 `fundament` 派生 footprint 不覆盖阻塞 Tile。
- 至少一半机缘槽的宿主 Building 存在两条不完全重合的可行接近路线。
- 任一 HazardController 的 Tile 覆盖被视为不可进入时，仍至少有一个未耗尽槽可达。
- 不允许一格宽的单一 chokepoint 同时控制全部机缘槽。
- 生成 schema 不提供 opportunity prerequisite 字段；每个槽只能依赖自身宿主的物理状态、可达性和 claim，不能依赖另一槽、守卫清空或门/区域解锁。
- 返回路径与进入路径使用同一通行规则验证，不假设单向传送。
- 固定 Seed 必须输出全图俯视诊断图、Building/能力分布，以及 Entry 到每个 claim key 的独立可达性结果；不创建“空前置图”来保留被禁止的 DAG 抽象。

“路线不完全重合”按去除 Entry 周围固定半径后的 Tile 集合差异判断，不要求严格图论边不相交，避免为小地图过度建模。

#### Building 与能力分散

- 首版每个宿主 Building 最多安装一个 Opportunity 槽；以后确有多槽需求时使用不同 SlotIndex，不创建子实体。
- 所有 Opportunity 槽不得集中在同一四分之一地图区域。
- EvidenceSource Building 与目标宿主不能在同一可见半径内，否则方向证据没有意义。
- 至少一个带显著 Landmark 能力的 Building 在入口初始视野中，用来给 AI 第一个调查方向。
- HazardController 的 Tile 覆盖不能完整覆盖 Entry、Exit 或所有安全返程路线。
- 不得由 Building、危险覆盖和守卫排列出“战斗区 -> 奖励区”串联；每个槽都要有不依赖清除其他槽/守卫的调查入口。

#### 证据可解

对每个初始 Unknown 的机缘槽：

1. 至少存在一个可达的 EvidenceSource Building。
2. 对应 `EvidenceRelationPlan` 生成的 bearing 与 distance band 覆盖目标宿主 anchor 及原版 `fundament` 派生范围。
3. Actor 在该范围内的 PerceptionRange 足以通过移动观察并把宿主写入 Knowledge。
4. 生成的 `EvidenceObservation` 不携带 TargetLocalObjectId 或精确 Tile，也不会把范围扩大到整张地图。

这些约束是具体布局和玩法实现的编码要求，不生成结构化 GenerationDiagnostics，也不在正式创建路径重复扫描 Generator 刚刚构造的数据。实际问题通过对应代码和端到端玩法测试修正。

### 步骤 4：完善观察、道痕、调查与参与者知识

#### 三层信息

遗迹信息分为：

| 层 | 示例 | 谁持有 |
| --- | --- | --- |
| 物理事实 | Tile terrain/危险覆盖、Building 位置、阵眼状态、机缘槽状态 | Runtime 的 Tile 环境与 Building 稳定组件 |
| 观察者知识 | 看过哪些格、知道哪些 Building/危险、有哪些 EvidenceObservation、调查失败记录 | Participant/Party `RuinKnowledgeState`；明确公开的事实复制到 Site MetaObject 的 Public Knowledge |
| 派生呈现 | 对当前参与者或公开上下文可显示的遗构、机缘、危险与 Site 摘要 | `RuinSiteReadModel`，从物理事实和对应 Knowledge 只读生成 |

玩家可以看到完整基础地貌和显著 Building，保持类似主世界的观察感；隐藏能力 payload、潜伏 Actor 和精确危险强度只在对应 Knowledge 允许后渲染。Site Public Knowledge 不自动写回新队伍的私有 Knowledge，ReadModel 也不能反向改写前两层。

#### 观察更新

`RuinPerceptionSystem`：

- 只在 Actor 跨格、视野属性变化或遮挡变化时重算。
- terrain 与大型 Building 参与视线阻挡。
- 观察带显著 Landmark 能力的 Building 只需进入其远距观察半径；调查则按 Building anchor、原版 `fundament` 派生范围和调查距离验证。
- 道痕/灵气感知向参与者 Knowledge 写入 `EvidenceObservation`，不等同于直接定位目标 Building。
- 已成为公开物理事实的 Building 对进入其可见范围的后续队伍正常可见，不需要创建或删除能力组件。

#### 调查结果

`InvestigateBuildingCommand(SourceLocalObjectId, InvestigationMode)` 在 Building 几何范围/调查距离验证后开始 Actor 持有的 `RuinInvestigationState`：

```text
ParticipantId
SourceLocalObjectId
InvestigationMode
StartTick
RequiredTicks
Progress
AttemptSeed
```

移动、受伤或主动撤离会中断进度。完成时使用固定 AttemptSeed 和 Actor 的明确调查快照，结果只能是：

- `RevealEvidence(EvidenceObservation)`
- `LocateOpportunitySlot(OpportunityClaimKey)`
- `StabilizeHazardController(SourceLocalObjectId)`
- `GainOutcome(OpportunityClaimKey)`
- `NoFinding`

同一参与者对同一 `(SourceLocalObjectId, InvestigationMode)` 只结算一次；不能通过原地反复点击刷 RNG。`RevealEvidence`、`LocateOpportunitySlot` 与 `NoFinding` 只写参与者 Knowledge；`StabilizeHazardController` 通过命令修改 Building/Tile；`GainOutcome` 通过统一 claim/slot 与 typed Outcome 命令处理。其他队伍仍可用自己的能力尝试。

### 步骤 5：实现遗构变化、危险场与长期物理状态

#### Building 与 Tile 物理状态

首批可变化物理对象：

- 残碑 Building：Landmark/EvidenceSource 能力始终存在；悟道槽按 `Available -> Reserved -> Exhausted` 变化，谁观察或调查过只写 Knowledge。
- 阵眼 Building：HazardController 按 `Active -> Stabilized` 或 `Destroyed` 变化。
- 药圃 Building：材料槽按 `Available -> Reserved -> Exhausted` 变化；需要表现部分采集时在同一能力内保存 RemainingAmount，不拆子实体。
- 道台 Building：若显化对所有参与者都造成真实变化，则单独保存 `Dormant -> Manifested -> Destroyed` 物理轴；谁已经定位它仍属于 Knowledge，机缘槽继续使用统一领取状态。
- 坍塌通路 Tile：`Blocked -> Cleared`；只在明确调查/破坏结果发生时改变。

能力组件只在对应玩法系统实现后创建。变化通过 Runtime command 提交；用途层和 View 不直接改组件，也不通过增加/删除组件表示发现或耗尽。

#### Tile 危险环境

`RuinHazardController` 支持首批两种无战斗危险：

| 类型 | 效果 | 可应对方式 |
| --- | --- | --- |
| ResidualFormation | 控制器覆盖 Tile 内每 tick 生命/灵气损失 | 绕行、快速穿越、调查阵眼稳定 |
| CorruptedWakan | 覆盖 Tile 内累积灵气扰动，降低后续调查效率 | 绕行或带着已有所得撤离 |

本阶段 CorruptedWakan 只写 Actor 的临时 `WakanDisturbance`，退出时清除，不新增永久 status。控制器 Building 保存 Kind、Intensity 和 `Active/Stabilized/Destroyed`；实际覆盖和 O(1) Tile 查询属于 Runtime 环境层/空间索引。后续队伍继承控制器与 Tile 的物理状态，但自己的 `KnownHazardCoverage` 仍需观察后建立。

#### Site ReadModel

`RuinSiteReadModel` 从真实 Building 能力、Tile 环境、Knowledge 和 claim 派生：

```text
KnownLandmarkCount
KnownOpportunitySlotCount
KnownExhaustedSlotCount
KnownActiveHazardControllerCount
ParticipantCount
HasUnsettledClaims
IsExhausted / Lifecycle / AdmissionAvailable
ExplorationSummary
```

查询必须显式传入 `Public`、`Participant(ParticipantId)` 或仅开发诊断可用的 `Debug` disclosure context。不同 context 可以得到不同 Known 数量；`IsExhausted/Lifecycle/AdmissionAvailable` 始终从全部物理槽、claims 和 Site 生命周期派生，不随观察者变化。SiteRecord 不保存第二份可写进度；入口 Tooltip/主世界 AI 只请求 Public，参与者面板请求对应 Participant，正式代码不能请求 Debug。

### 步骤 6：完善自主调查、记忆与返程决策

#### 候选行动

AI 每个 DecisionInterval 构造候选：

- ReturnToEntry
- ObserveArea
- InvestigateBuilding
- FollowEvidence
- ClaimOpportunitySlot
- StabilizeHazardController

每个候选目标只能是 Tile 范围、`SourceLocalObjectId` 或 `OpportunityClaimKey`，并包含明确输入：路径是否可达、实际路程、Knowledge 已知危险的具体效果、预期收益区间、信息增益、返程余量和当前所持收益。AI 不读取 Generator Plan、秘密 EvidenceRelation、未知 Building 或隐藏能力 payload。

首版不把危险压成每格固定分数，也不建立统一的线性效用公式。决策先排除生命、资源或返程条件无法承受的候选，再由具体行动按自身目标比较距离、收益和信息；性格只参与对应行动的选择规则，不作为通用风险倍率。正式 UI 不显示内部决策数值。

#### 返程条件

任一条件成立时 Return 候选强制优先：

- 生命低于个体安全阈值。
- 返程最坏估算会把生命降到安全阈值以下。
- 已取得价值达到 DesiredGainThreshold。
- 当前没有正效用候选，且连续两个决策周期没有新信息。
- Site ReadModel 已派生为 Exhausted、物理生命周期进入 Collapsing/Collapsed，或入口要求清退。

取得部分收益后继续探索是允许结果，不要求“拿到一个就走”；是否继续由个体阈值和剩余候选决定。

#### 记忆与防循环

Knowledge 记录最近 16 个目标与结果。AI 不得：

- 连续选择刚返回 NoFinding 的同一 `(SourceLocalObjectId, InvestigationMode)`。
- 在两个不可达观察点间无限切换。
- 对同一已知 HazardController 和覆盖版本每 tick 重复重算路线。
- 因 Renderer 不可见而清空记忆。

连续 8 个决策周期无位置进展时，取消当前候选并重建；三次恢复仍失败则返程并记录 `ExplorationStalled`。

### 步骤 7：完成多 Seed 与接续探索验收

#### 固定 Seed 套件

至少保存 20 个测试 Seed，覆盖三种底图与边界组合。每个 Seed 验证：

- MapData、BuildingPlacement、稳定能力 payload、Tile 危险覆盖、EvidenceRelation、Opportunity slots 与收益 signature 可重复。
- 入口到每个宿主 Building anchor 可达，且 `BuildingAsset.fundament` 派生 footprint 合法。
- 至少一半机缘槽有两条不同接近路线。
- 每个初始未知槽至少有一条可完成的 EvidenceRelation。
- AI 不通过隐藏 Building、TargetLocalObjectId 或秘密关系直接寻路。
- 所有参与者都可安全返回，除非其自己选择穿越已知高风险覆盖。

#### 古修道场内容合同

本阶段在 20 个 Seed 验收时建立第一版 `RuinContentAcceptance`，它是具体内容的验收合同，不是提前注册的通用资产：

- 每个机缘槽独立可调查、独立可取得、独立可放弃；生成 schema 不存在跨槽 prerequisite 字段。
- 不要求清空守卫、解除某扇门或完成另一个槽才能接近目标宿主。
- 至少两个槽各有两条不同接近路线；至少一个槽有明确非战斗应对。
- Tile 地貌、Building/能力分布、EvidenceRelation 和危险覆盖必须能从全图俯视诊断图读出空间关系；不能只靠运行时日志证明“开放”。
- EvidenceObservation 提供方向/距离/气息等调查信息，不直接暴露隐藏 Building 或精确坐标。
- 修士可以取得部分机缘后安全返回，后续参与者继承物理变化但不自动继承他人的私有 Knowledge。
- 同一 Seed 的 MapData、Actor/Building placement，以及从相同 Knowledge 派生的 ReadModel 和接续探索行为可复现。

阶段 4 实现远古战场后，先分别通过这份合同，再只抽取两种遗迹真正重复的字段；没有重复证据的字段留在具体配置中。

#### 接续探索

对每个 Seed 依次运行不同 Snapshot，直到其 3-5 个槽全部处理；每轮最多取得一个槽：

1. 第一轮保守修士取得一个低风险槽后返回。
2. 第二轮激进修士穿越危险覆盖、稳定阵眼并取得另一个槽。
3. 后续轮次使用不同风险/调查快照，分别依靠自己的 EvidenceObservation 找到剩余宿主 Building。

另保留一个恰好生成 3 槽的固定 fixture，断言第三名进入时只剩最后一个 Available 槽。所有轮次共用同一 Runtime，Building/Tile 物理变化和槽状态累积，各队 Knowledge 独立；全部槽耗尽前 Site ReadModel 不为 Exhausted。

#### 可见性差分

同一 Seed、Snapshot 和命令序列分别运行相机始终相交、始终 Culled、每 10 秒往返三种模式。验收分两层，不能把异步 worker 的 ready tick 误写成内容确定性：

- **真实 PathFinder**：只比较每次不可变请求得到的 Tile 序列，并审计 ViewVisible/Renderer 没有进入请求或决策输入；不同 worker publication trace 下不要求行动、竞争或最终状态相同。
- **记录/回放发布轨迹 fixture**：首次运行记录 request token 对应的 logical publication tick，后续由测试 path gateway 回放同一 trace。只有在相同 publication trace 下，三种可见性运行才比较逐 tick Position，以及各行动完成/结算里程碑的 Actor、Building、Tile、Knowledge、claims、Outcomes、显式 AttemptSeed/roll payload、ReadModel 和决策签名。

正式逻辑不得读取 ViewVisible；文档不要求真实异步 worker 在相同 wall-clock 或 local tick 恰好 ready，也不引入通用 Runtime `RandomState`。

#### 性能与清理

- `48x48`、12 个 Building（其中共含 5 个 Opportunity 槽和 2 个 HazardController）、1 个 Actor 的感知/AI/寻路不得每 tick 全图分配集合。
- 稳态逻辑和渲染准备目标为每帧 0 B GC；真实性能预算留到阶段 5 测量。
- 销毁 Runtime 后 Actor、Building、Tile 环境/空间索引、Knowledge、investigation、EvidenceObservation、claims 和 Site MetaObject 引用全部释放。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
