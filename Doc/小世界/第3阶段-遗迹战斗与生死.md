# 第3阶段-遗迹战斗与生死

本阶段在已经可调查的开放遗址中加入守卫、战斗、撤退、死亡和崩塌。战斗是遗迹环境的一部分：守卫巡游于废殿、阵眼和道台附近，修士可以观察、绕行、引开、交战或放弃某处机缘；不存在必须清空的房间或固定 Boss 门。

实现只覆盖当前遗迹实际需要的基础战斗能力。不得为了两类守卫先重写全部 SkillLibV3、所有技能、装备、状态和战术平台，也不得给小世界复制一套近似伤害公式。

## 具体说明

### 设计边界

- 本阶段仍只扩展残破古修道场这一具体内容配置，不提前依赖通用 Archetype 资产。
- 只支持一名远征参与者与遗迹守卫的敌对关系；组队、多队伍相遇和争夺留到阶段 4。
- 首批支持基础近战、基础投射攻击和一种无叠层控制效果；不承诺任意 SkillBlueprint 均可执行。
- 不读取或持有主世界 Actor/Entity；战斗热路径只使用 Runtime 组件与显式 Random。
- 不建立通用战术评分器。遗迹修士与守卫各有范围明确的 AI。
- 守卫可以守护某处机缘，但机缘仍可通过绕行、引开、等待或放弃来处理。
- 死亡、撤退和崩塌都是正常玩法结果，不以异常回滚成入场前状态。
- 相机、Renderer、粒子和声音不参与命中、伤害、仇恨或死亡结果。

### 步骤 1：锁定最小战斗能力与主世界 golden fixtures

#### 先核对真实调用链

实现前必须从现有 Cultiway 与原版源码定位：

1. 主世界普通近战攻击最终读取哪些 Actor 属性。
2. 防御、境界、元素/抗性、暴击和最低伤害在哪些函数结算。
3. Random 从哪里进入，哪些步骤依赖 World/Actor。
4. Actor 生命修改、死亡触发和 WorldLog 分别在哪个边界执行。
5. `SkillBlueprintCompiler` 已有输出中哪些能力能不依赖 `WorldTile/Actor` 表达。

文档中的 `CompiledSkillDefinition`、`ISkillExecutionPorts` 等旧名称不是现有类型，不能按旧计划直接实现。

#### Golden fixtures

先为主世界捕获至少 8 组固定输入/输出：

| 场景 | 覆盖 |
| --- | --- |
| 同境界普通近战 | 基础伤害 |
| 高境界攻击低境界 | 境界差 |
| 低境界攻击高防御 | 最低伤害/减伤 |
| 固定暴击与非暴击 | 显式 Random 输入 |
| 相克与非相克属性 | 元素/抗性阶段 |
| 基础投射攻击 | 距离不改变数值语义 |
| 生命正好归零 | 死亡阈值 |
| 过量伤害 | clamp 与最终结果 |

fixture 保存纯数值快照与最终结果，不依赖游戏对象地址。重构后主世界原调用点和 SubWorld resolver 对相同输入必须与 fixture 一致。

若现有普通攻击无法在不牵动大量世界行为的情况下抽取，本阶段暂停增加投射/技能，先完成唯一近战共享路径；不得先写“小世界简化公式”绕开问题。

### 步骤 2：建立共享基础攻击解析与 Projection 战斗快照

#### Shared Combat Core

只抽出已被 fixture 覆盖的确定性数值阶段：

```text
BasicAttackRequest
  AttackerCombatSnapshot
  DefenderCombatSnapshot
  AttackKind
  RandomRolls

BasicAttackResult
  IsHit
  IsCritical
  RawDamage
  FinalDamage
  AppliedTags
```

Shared Core：

- 不引用 Actor、WorldTile、EntityStore、MapBox、Unity Renderer 或静态 World。
- 不自行获取 Random；调用方先给定 roll。
- 不修改生命；只返回结果。
- 主世界原攻击适配器和 SubWorld 战斗 System 调用同一 resolver。
- 不覆盖本阶段没有 fixture 的状态扩散、建筑伤害、范围搜索或特殊技能。

#### Projection 战斗快照

进入遗迹时，在阶段 1 Snapshot 上增加：

```text
AttackPower
DefensePower
AttackRange
AttackIntervalTicks
CriticalProfile
ElementProfile
ResistanceProfile
SupportedCombatCapabilities[]
```

这些值在单次远征期间固定，除非 Runtime 内明确 Outcome/Status 修改 Projection 组件。战斗 System 不回查 Source Actor。

`SupportedCombatCapabilities` 首批只有：

- BasicMelee
- BasicProjectile（确有现成主世界定义可复用时）
- ShortStagger（守卫专属且有明确 shared status 语义时）

遇到未支持技能时 Projection 不携带该技能效果，也不创建同名简化版；Debug 诊断列出被排除的能力。

#### 战斗 tick 顺序

```text
Perception
-> Intent selection
-> Movement
-> Attack wind-up
-> Hit/Projectile arrival
-> Shared damage resolve
-> Health apply
-> Death mark
-> Opportunity/exit evaluation
-> Events
```

同一 tick 的多个伤害按 Attacker EntityId 排序提交；死亡标记后该 Entity 不再发起新攻击，但当前 tick 已产生的投射仍按明确规则结算。

### 步骤 3：实现开放遗址守卫、巡游、感知与仇恨

#### 首批守卫

| 守卫 | 活动方式 | 攻击 | 与地貌关系 |
| --- | --- | --- | --- |
| 残阵傀儡 | 在阵眼、断阵边缘和废殿之间巡游 | 近战 | 可被引离阵眼；阵眼稳定后感知范围下降 |
| 游荡残魂 | 沿道痕和尸骸锚点缓慢游荡 | 基础投射/近战后备 | 穿过普通危险场，不穿不可通行 terrain |

守卫由 `RuinedDaoGroundGenerationConfig` 的 `GuardianPlacementPlan` 放在兼容 Landmark/PatrolAnchor 上，不按“房间数量”生成。

#### 感知

守卫使用与 Projection 相同的地形视线基础，但有自己的：

```text
VisionRange
WakanSenseRange
HearingRange
AlertDurationTicks
PatrolAnchorIds[]
LeashDistance
```

- 只能对实际感知到的目标建立仇恨。
- 一次受伤会暴露攻击者并建立最低仇恨。
- 丢失目标后前往 LastKnownPosition，不追踪实时隐藏坐标。
- 超出 LeashDistance 且未受持续攻击时返回最近 PatrolAnchor。
- View culled 时不降低感知频率或改变巡游路径。

#### 仇恨

`RuinThreatState` 本阶段只服务单参与者对守卫：

- 对每个已感知敌人保存 ThreatValue、LastSeenTick 和 LastKnownTile。
- 伤害、接近受守护 Opportunity 和稳定其阵眼会增加 Threat。
- 同分按距离和 EntityId 选目标。
- 超时且无任何感知后逐步清空；不跨 Runtime 保存。

不实现全局阵营外交、Competitive、Winner 或任意脚本条件。

### 步骤 4：实现修士迎战、规避、脱离与撤退决策

#### 威胁评估

Projection 只评估已感知守卫：

```text
ThreatCost = EstimatedIncomingDamage
           * ExpectedCombatDuration
           + KnownHazardCostAlongFightArea

CombatUtility = GuardedOpportunityExpectedGain
              - ThreatCost * RiskAversion
              - ReturnRisk
```

估算使用公开的自身/敌人战斗组件，不模拟未来 Random。AI 不读取未发现守卫或隐藏机缘价值。

#### 行动选择

出现守卫时，AI 可以：

- Avoid：重新选择不进入其感知范围的观察点/机缘。
- Lure：进入感知边缘后撤向开阔地，尝试让守卫离开 Landmark。
- Fight：接近到攻击范围并持续战斗。
- Disengage：打断当前调查，沿已知低风险路线离开仇恨范围。
- Return：生命或返程余量不足时直接返回入口。

首版 Lure 只由简单两段意图实现，不建立通用战术规划器。若没有可靠逃生路径，AI 不选择主动引怪。

#### 战斗移动

- 近战目标选择可达的邻接攻击格，不要求占据目标格。
- 投射单位尽量维持 AttackRange 的 60%-90%，但不能每 tick 来回抖动。
- 被危险场覆盖的攻击格加入风险成本。
- 路径阻塞时重新规划；连续三次失败后放弃追击或返程。
- 同一实体的移动与攻击 wind-up 互斥，除非能力明确允许移动施法；首批均不允许。

#### 撤退阈值

任一条件满足时从 Fight 转为 Disengage/Return：

- 当前生命低于个体 CombatRetreatThreshold。
- 最近 5 秒净生命变化表明无法安全完成战斗。
- 出口路径被新危险切断且替代路线余量不足。
- 已持有高价值 Outcome，继续战斗效用为负。

这不是玩家按钮；玩家只能观察 AI 判断。

### 步骤 5：实现受伤、死亡、遗落物与返回结算

#### 生命与临时状态

Projection 生命是 Runtime 唯一战斗生命。每次伤害发布 `SubWorldDamageAppliedEvent`；UI 和 WorldLog 读取事件，不自行推导。

首批状态只有 `ShortStagger`：

- 明确 DurationTicks。
- 只暂停移动/攻击 wind-up，不停止感知和时钟。
- 同一状态重复命中取较长剩余时间，不叠层。
- 返回主世界时不携带；阶段内不创建通用 status registry。

危险场与战斗伤害都可以致死，阶段 2 的“最低保留 1”在本阶段删除，不保留兼容分支。

#### 死亡状态机

```text
Alive -> Dying -> DeadPendingSettlement -> Settled
```

1. Health 到 0 时进入 Dying，停止移动、调查和新攻击。
2. 当前 tick 已提交的伤害和投射结算完成。
3. Runtime 在同一 tick 按稳定 RuinLootId 处理 Outcomes/物理战利品，进入 DeadPendingSettlement。
4. Runtime 发布带 `DeathSettlementToken` 的 `ProjectionDiedEvent`；Projection 和死亡遗落物冻结，等待外部确认。
5. 主世界边界提交 `AcknowledgeProjectionDeathCommand(Token)`，不在命令外先杀死 Source Actor。Runtime 预校验 Token 与最终状态后进入不可重入主线程提交段，由 `IMainWorldDeathSettlementPort` 处理。
6. 会话内 `DeathApplicationLedger` 保存 `Token -> NotApplied / Applying / Applied / Faulted`。同一 Applied Token 直接返回成功，绝不再次调用死亡入口；只有 NotApplied 可以进入 Applying。
7. Port 在切换到 Applying 前完成 Actor/holder/死亡入口的全部可失败预检，然后调用现有死亡入口一次。无论返回还是抛错，都在 `finally` 中读取主世界 canonical dead/removed 状态。
8. canonical death 已生效则记录 Applied，入口异常只写诊断并被 port 转成 Applied 结果，不再向外重抛；Runtime 随即执行已预验证、无分配、无外部回调的 Settled/Binding 句柄清理。canonical death 明确未生效且审计证明没有不可逆副作用时才恢复 NotApplied；无法证明时记 Faulted，禁止自动重试并让阶段验收失败。

Source Actor 的正式死亡入口对每个 Token 最多调用一次；保存和 clearWorld 不能插入 Applying 调用。因为主世界死亡通常不可逆，Runtime 最终步骤必须在调用 port 前完成全部校验，并保证 Applied 路径不再失败。不能先删除 Actor 再读取 holder，也不能在 Runtime 和主世界各生成尸体奖励；用途层不能直接改 Runtime loot owner 或销毁 Projection。

#### 所得遗落

- `RuinInsightOutcome` 等未物化认知收益在死亡时消失，Opportunity 变为 Released，后续仍可尝试。
- `RuinIngredientOutcome` 转成 Runtime 内 `DroppedRuinLoot`，位置为死亡 tile，保留同一 RuinLootId。
- 原 Opportunity 保持 ClaimedPendingSettlement 并改由 DroppedRuinLoot 持有；后续拾取者取得后才可结算。
- 阶段 4 建立完整 typed loot 后沿用同一所有权状态，不重写死亡语义。

#### 活着返回

活着返回完整沿用阶段 1 的 `SettlementStagingRegistry + PrepareSettlementCommand -> CommitSettlementCommand/RollbackSettlementCommand`，结算快照增加最终生命和允许带回的伤势。Commit port 与 Runtime 最终状态在同一不可重入调用内成功或按 Receipt 完整回滚，之后才移除 Binding。

若 Prepare 后发现 Health 已为 0，取消普通返回 Token，转入上面的 DeadPendingSettlement/Acknowledge 流程。正常战斗死亡本身不是异常，不能通过 Rollback 复活。

### 步骤 6：实现遗迹失败、崩塌与持续世界状态

#### 单次远征结果

| 结果 | Site 变化 | Actor 变化 |
| --- | --- | --- |
| 带部分所得返回 | 仅对应节点 Exhausted | 生命/收益结算，恢复主世界 |
| 无所得撤退 | 守卫、危险与调查状态保持 | 生命结算，恢复主世界 |
| Projection 死亡 | 守卫和物理世界保持，所得按规则遗落 | Source Actor 正式死亡 |
| 所有机缘耗尽 | Site -> Exhausted | 当前参与者仍可返程 |
| 遗迹崩塌 | Site -> Collapsed | 能返回者强制返程，未返回者死亡 |

一名修士死亡不会重置守卫生命、巡游位置、已稳定阵眼或已耗尽机缘。后续修士进入的是同一事件现场。

#### 崩塌

首版只提供一种明确崩塌来源：调查破损主阵眼时选择/触发不可逆失稳结果。`RuinCollapseState`：

```text
Stable -> Warning(CountdownTicks) -> Collapsing -> Collapsed
```

- Warning 通过全图可感知震动/灵气事件通知所有参与者，AI 立即把 Return 设为最高优先级。
- 倒计时按 Runtime LocalTime 推进，不按真实帧。
- Collapsing 时按预生成 CollapseWavePlan 逐步把明确 tile 改为阻挡/危险；每次变化走统一 Grid/Revision 边界。
- 入口最后一个波次才失效，保证合理逃生窗口。
- Collapsed 后未退出 Projection 进入 Dying，未耗尽 Opportunity 销毁，Runtime 在结算完成后销毁。

CollapseWavePlan 在生成时验证至少有一个从主阵眼 ApproachPoint 到入口的可行逃生窗口；不通过即时随机封路制造必死结果。

#### 守卫持续状态

- 死亡守卫不会重生。
- 受伤但脱战的守卫按古修道场具体配置缓慢恢复；首版只允许恢复到 50%，不完全重置。
- PatrolAnchor 被破坏时改用最近兼容锚点；无锚点时停留在当前位置附近。
- Site Exhausted 后剩余守卫仍存在，直至最后参与者离开；不瞬间删除。

### 步骤 7：完成战斗确定性与四条生死流程验收

#### 四条端到端流程

1. **成功返程**：观察守卫 -> 绕行或击败 -> 取得机缘 -> 活着返回。
2. **主动撤退**：战斗不利 -> 脱离 -> 无所得/部分所得返回 -> Site 继续 Open。
3. **修士死亡**：Projection 死亡 -> 认知收益丢失、Ingredient 落地 -> Source Actor 死亡 -> 后续修士可发现现场。
4. **遗迹崩塌**：分别运行“及时逃出”和“未及时逃出”两次 -> Site、Actor 与 Runtime 各自正确结算。

#### 一致性

- MainWorld golden fixtures 在抽取共享 resolver 前后完全一致。
- 相同 Seed、Snapshot、命令和 tick 的守卫巡游、感知、攻击 roll、伤害、死亡与掉落 signature 一致。
- Runtime 始终可见、始终 Culled 和反复聚焦三种情况下结果一致。
- LocalSpeed 1x/2x/4x 只改变真实耗时，不改变 tick 结果。
- 守卫不知道未感知参与者；Projection 不知道未发现守卫。

#### 边界故障

注入并验证：

- Projection 创建后战斗组件不完整：整次入场回滚。
- 伤害事件订阅者抛错：逻辑生命不回滚，错误隔离并记录；不得重复结算伤害。
- Source Actor 在 Projection 死亡结算前失效：清理 Binding 与 Runtime loot owner，不创建替代 Actor。
- death port 预检失败：死亡入口调用计数为 0，Ledger 回到 NotApplied，同一 Token 可重试。
- 死亡入口已令 Actor canonical dead/removed 后抛错：Ledger 记 Applied，Runtime 最终 Settled；同一 Token 再处理不调用死亡入口，调用总数恒为 1。
- 异常后 Actor 仍存活且无法证明无副作用：Ledger 记 Faulted，禁止自动重试并让阶段验收失败。
- Collapse 中 clearWorld：释放 DeathToken/Ledger 和全部会话状态，不发奖励或补偿。

#### 构建与游戏内验证

- `dotnet build Cultiway.csproj -c Debug` 无错误。
- 游戏内分别使用弱、同阶、强于守卫的修士运行四条流程。
- 连续 20 场战斗后没有悬空 projectile、Threat、Binding、DroppedLoot owner、DeathToken、DeathApplicationLedger 或 View 对象。
