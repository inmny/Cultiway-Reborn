# 第3阶段-规则模块与场景生成

## 具体说明

### 设计边界

- RuleSet 只组合稳定 Module ID 和参数，不把任意委托或脚本保存进实例。
- Template 决定允许的规则空间，实例只冻结创建时参数。
- 地图生成、逻辑和视觉三层共享稳定 terrain/entity ID，但互不持有运行时对象。
- 地形视觉以第一阶段提供的原版 terrain catalog 为基线；主题只保存差异 override，不复制整套 tile。
- 物品只使用第二阶段提供的 PortableItem typed snapshot/codec、stable ItemId 和 ItemLease，不定义新的 payload 分发协议。
- 主世界与 SubWorld 只允许通过唯一 `ICraftProcessKindRegistry` 和 `ICraftDomainService` 执行制造规则；世界层只做输入采集和结果提交。
- 本阶段加入非战斗环境损耗、交互和制造，不加入敌人、技能、战斗和死亡。
- 两个 Template 必须在同一 Runtime 上表现出明显不同的地图、时间和画面。
- SubWorld 始终显示在非模态浮窗中，主/子世界独立时钟；浮窗状态不能成为制造或规则输入。

### 步骤 1：建立规则、时钟与 catalog 驱动的视觉合同

#### RuleSet

`SubWorldRuleSetAsset`：

```text
Id
MovementModuleId
VisibilityModuleId
EnvironmentModuleIds[]
InteractionModuleIds[]
ObjectiveModuleIds[]
ExitModuleId
Parameters
```

`SubWorldRuleModuleAsset` 只声明 ID、配置 schema、依赖和执行优先级。实际无状态实现由 `SubWorldRuleModuleRegistry` 注册。

模块生命周期：

```text
OnRuntimeCreated
BeforeTick
HandleCommands
UpdateEntities
UpdateEnvironment
EvaluateObjectives
AfterTick
```

每个阶段的调用顺序在 RuleRuntime 创建时冻结。模块不能在运行中自行插入新的全局 system 顺序。

#### ClockProfile

完整字段：

```text
Id
FixedStep
DefaultLocalRate
BodyTimeRatio
RunsWhileParentPaused
BackgroundPolicy
AllowedLocalSpeedOptions[]
MaxTicksPerFrame
MaxCatchUpTime
LocalDayLength
```

ClockProfile 只决定时间如何推进；环境模块读取 LocalTime，但不能直接修改时钟。

#### VisualProfile

```text
Id
TerrainThemeOverrideId?
EntityVisualProfileId
BackgroundColor
FogColor
AmbientColor
LocalLightProfileId
CameraMinSize
CameraMaxSize
EffectBindings[]
```

VisualProfile 不保存 catalog selector；所有 Profile 都通过依赖注入使用第一阶段唯一的 `IWorldBoxTerrainVisualCatalog`。`TerrainThemeOverrideId` 可选，只保存按 `SourceLayer + AssetId` 索引的 sprite、material 参数或 overlay 差异；未覆盖的 terrain 直接使用 visual catalog 条目，禁止用 `TerrainSpriteSetId` 为每个主题复制整套 tile。

VisualProfile 不保存 Camera、Material 或 Sprite 实例。View 从 catalog 解析 terrain visual，再应用主题 override，并创建自己的材质实例，避免主世界昼夜修改共享材质。MapRecord 的 `VariantSeeds` 决定稳定变体，切换主题不重写 terrain ID。

### 步骤 2：实现确定性场景生成管线

`ISubWorldGenerator` 接收：

```text
Template
Seed
Width/Height
CreationParameters
```

输出完整 `SubWorldGeneratedScene`。生成阶段固定为：

1. `Layout`：房间、路径、区域和入口出口。
2. `Terrain`：地面、墙、深坑、水域和通行标记。
3. `Environment`：灵气场、毒雾、热区、照明和局部时间节点。
4. `Content`：门、禁制、容器、机关、真实工作台和目标对象。
5. `Validate`：路径、容量、目标可达性和 ID 引用。
6. `Commit`：一次写入 MapRecord 与 EntityRecords。

Generator 在 Commit 前只操作临时 scene，不逐步修改 Archive。验证失败不创建半个 Instance。

#### 区域

生成结果可以保存 `SubWorldZoneRecord[]`：

```text
ZoneId
Bounds/TileIds
SemanticIds[]
DiscoveryState
```

Zone 是小世界内部的房间或区域，不复用主世界 GeoRegion。消费系统可以把主世界语义作为创建参数输入 Generator。

#### 确定性

- 所有随机从实例 RandomState 获取。
- 不使用 UnityEngine.Random 全局状态。
- 对集合排序后再抽样。
- 地图生成后保存最终状态；后续破坏只修改 MapRecord。
- Debug 可用同 Template、Seed、参数重建并比较结构签名。

### 步骤 3：实现视野、迷雾与发现

首版按队伍共享视野，不为每个 Actor 保存一张完整迷雾图：

```text
SubWorldVisionRecord
  VisionGroupId
  SeenBits
  VisibleBits
  DiscoveredEntityIds[]
```

视野规则：

- Projection 提供 VisionRadius 和 VisionGroupId。
- `VisibilityModule` 只在单位跨格、阻挡变化或视野属性变化时重算。
- Seen 表示曾见过，Visible 表示当前可见。
- 未见 tile 不绘制；已见但不可见 tile 使用 VisualProfile FogColor。
- 机关和容器可以拥有独立 Concealment，只有进入视野并通过感知检查后加入 DiscoveredEntityIds。

多个互不共享情报的队伍拥有不同 VisionGroup。浮窗默认绑定当前观察队伍；消费系统可以提供“天道视角”作为只读视图模式，但不能因此把发现写给 Projection。

### 步骤 4：实现门、容器、机关与真实工作台

#### 交互对象

```text
SubWorldInteractable
  InteractionAssetId
  State
  Charges
  RequiredTags[]
```

首批交互：

| 交互 | 状态 | 命令结果 |
| --- | --- | --- |
| 门 | Closed/Open/Locked | 开启、关闭或等待解锁 |
| 禁制 | Sealed/Weakening/Broken | 持续投入破禁进度 |
| 容器 | Hidden/Closed/Opened/Empty | 发现、开启并暴露已保存的物品记录 |
| 压力机关 | Armed/Triggered/Disabled | 触发环境效果或解除 |
| 传送节点 | Inactive/Active | 将实体移动到配对节点 |
| 真实工作台 | Idle/Reserved/Running/Completed/Failed | 放入材料、开工、推进工序和拾取产物 |
| 出口 | Locked/Available | 请求退出或完成实例 |

所有交互通过 `SubWorldInteractionService.TryStart()` 创建短生命周期 InteractionState。单位离开、失去资格或对象状态变化时中止，不在 UI 中直接切换状态。

#### 容器物品

容器生成时直接创建第二阶段 PortableItem 的 typed snapshot，并在 Archive 中保存 `ContentRef`。运行位置只由下列记录表达：

```text
SubWorldItemRecord
  ExpeditionItemId
  StableItemId
  ContentRef
  Holder
  Ground
  State
```

- `ExpeditionItemId` 是本次实例内的唯一移动身份；`StableItemId` 直接保存第二阶段 `PortableItemIdentity.ItemId`，不是新生成的第二种稳定身份。它跨主世界 Entity、SubWorld Entity、保存读档和返回事务保持不变。
- `ContentRef` 指向 `SubWorldArchive` 的 typed snapshot store，并由第二阶段 PortableItem codec 解码；记录中不保存 `PayloadKind/Payload`。
- `Holder` 是带类型的位置，可指向 ContainerSlot、ProjectionInventory、Process 或 WorkbenchOutput；`Ground` 保存地面 tile。除终止态外两者必须恰有一个有效。
- 容器内容在场景 Commit 时已经获得 StableItemId 和 ContentRef。开箱只把 Holder 从隐藏容器槽切换为可见容器槽，不重新抽奖或复制 snapshot。
- 容器战利品与 SubWorld 制造产物都以 Archive 为初始权威，不创建 MainWorld Entity，也不预先取得 `ItemLease`；实际带出者开始返回提交时，才为对应 StableItemId 取得 Lease。MainWorld 来源的输入物品则沿用第二阶段入场时已取得的 Lease。

#### 真实工作台

工作台是地图中的可占用交互对象，不是打开 UI 后立即生成成品的按钮：

```text
SubWorldWorkbenchRecord
  WorkbenchId
  CraftCapabilities[]
    ProcessKindId
  InputSlots[]
  RecipeSlot?
  OutputSlots[]
  ActiveProcessId?
  State
```

单位必须到达工作台并占用主行动，才能放入材料、放入 recipe、开始或继续手工制造。`CraftCapabilities[]` 的每一项只保存稳定字符串 `ProcessKindId`，不保存 enum 数值或 handler 类型名。`RecipeSlot` 可保存当前 Kind 注册的 typed recipe ContentRef；运行时动态丹方的完整定义保存在当前世界槽位的 typed snapshot store 中，不能只保存全局 Elixir library ID。全局 library 可以按签名缓存或索引定义，但不是读档恢复的权威来源。

材料开工后从 ContainerSlot、ProjectionInventory 或 Ground 转为 `Holder = Process(ProcessId)`。成功产物以 Archive 为初始权威，先进入 `Holder = WorkbenchOutput(WorkbenchId, Slot)`，必须由单位执行拾取交互；目标完成、浮窗关闭或工序结束都不能把产物远程塞进背包。

#### 环境场

tile 可以保存有界环境值：

```text
Aura
Heat
Toxin
Instability
```

Environment Module 只处理脏区和活动实体所在区域，不逐 tick 扫描全部 `128x128` tile。首版效果为非致命资源消耗、移动成本和视野变化；致死效果在第四阶段接入统一死亡规则。

### 步骤 5：抽取共享制造领域与 typed snapshot

#### 唯一制造入口

从现有主世界行为中抽取唯一 `ICraftProcessKindRegistry` 和 `ICraftDomainService`。registry 是 Process Kind 注册与解析的唯一入口：

```text
ICraftProcessKindRegistry
  Register<TRecipe, TState>(
    ProcessKindId,
    ICraftRecipeCodec<TRecipe>,
    ICraftProcessStateCodec<TState>,
    ICraftProcessKindHandler<TRecipe, TState>)
  Resolve(ProcessKindId)

ICraftProcessKindHandler<TRecipe, TState>
  Start(TRecipe, CraftStartRequest, CraftContext, IDeterministicRandom)
  Advance(TRecipe, TState, CraftContext, IDeterministicRandom)
  Interrupt(TRecipe, TState, CraftContext, CraftInterruptReason,
            IDeterministicRandom)
```

每个 `ProcessKindId` 必须同时注册 typed recipe codec、typed state codec 和对应 handler。重复 ID 在注册时直接失败；未知 ID、recipe/state codec 类型或版本不匹配在启动、推进、中断或读档时直接失败，不提供通用 payload fallback。

`ICraftDomainService` 只接受可序列化值和确定性随机源，不读取 Actor、City、Friflo Entity、WorldTile 或 SubWorld Runtime；三个入口都先按 `ProcessKindId` 经 registry 路由到 typed handler：

```text
Start(CraftStartRequest, CraftContext, IDeterministicRandom) -> CraftStartResult
Advance(CraftProcessSnapshot, CraftContext, IDeterministicRandom) -> CraftAdvanceResult
Interrupt(CraftProcessSnapshot, CraftContext, CraftInterruptReason,
          IDeterministicRandom) -> CraftInterruptResult
```

- `CraftStartRequest` 保存 `ProcessKindId`、操作者能力快照、输入 `PortableItemIdentity.ItemId`/ContentRef、该 Kind 的 typed recipe 和请求的工序模式。
- `CraftContext` 保存本次制造真实使用的工作台能力、环境语义、时间、熟练度、规则修正和 `CraftResourcePoolSnapshot[] { ResourceId, Current, Maximum }`；MainWorld 与 SubWorld adapter 必须从各自世界构造同一语义。
- `IDeterministicRandom` 是唯一随机入口。工序保存 RandomState 或确定的 random cursor，读档后从同一点继续。
- `CraftStartResult` 返回可持久化 `CraftProcessSnapshot` 或共享 `CraftFailure`；Advance/Interrupt 结果返回更新后的 snapshot、typed 产物和有序领域 commands。任何资源消耗都必须表现为明确的 `DeductCraftResourceCommand { ResourceId, Amount }`，不能只在结果中隐含“已消耗”。

首批注册固定为：

| `ProcessKindId` | typed recipe | typed state | MainWorld 行为入口 | typed 产物 |
| --- | --- | --- | --- | --- |
| `alchemy` | `ElixirRecipeBlueprint` | `AlchemyCraftStateSnapshot` | `BehCraftElixir`；`FindNewElixir` 只负责推演并产出丹方 | `ElixirItemSnapshot` |
| `artifact_refining` | `ArtifactRefiningRecipeSnapshot` | `ArtifactRefiningStateSnapshot` | `BehCraftArtifact` | `ArtifactInstanceSnapshot` |
| `talisman_crafting` | `TalismanCraftRecipeSnapshot` | `TalismanCraftStateSnapshot` | `BehCraftTalisman` | `TalismanSnapshot` |
| `magic_scroll_crafting` | `MagicScrollCraftRecipeSnapshot` | `MagicScrollCraftStateSnapshot` | `BehCraftMagicScroll` | `MagicScrollSnapshot` |

`FindNewElixir` 是 `alchemy` 的配方推演入口，不是第五种 Process Kind。原版法杖打造和写书暂不纳入首批，也不预留假注册项。

第三阶段直接扩展第二阶段已经建立的 `CraftProcessSnapshot`，不另建工序 DTO。第二阶段字段保持原义：

```text
ProcessId
ProcessKindId
CrafterId
InputItemIds[]
OutputItemId
TypedRecipeSnapshot
TypedStateSnapshot
RecipeCodecVersion
StateCodecVersion
Progress
RandomState
```

第三阶段增加运行与调度所需字段：

```text
WorkbenchRef
State
StartRequest
ContextSnapshot
RecipeContentRef?
RequiredProgress
AdvancementMode
StartedAt/UpdatedAt
Result?
```

状态固定为 Prepared、Running、Succeeded、Failed、Interrupted。`AdvancementMode` 区分有人贡献行动的 Manual、必须固定 tick 推进的 Automatic 和明确支持解析推进的 AnalyticAutomatic，供第五阶段决定 Runtime Tier；世界 adapter 不能自行把 Manual 工序换算成 elapsed 进度。

失败和中断统一返回对应 Kind handler 的 `CraftFailure` 与有序 commands，由共享规则决定材料与制造资源的消耗、退回或废料 typed snapshot。现有 `CraftFailureService` 改为 MainWorld 提交 adapter，不再拥有另一套失败判定；SubWorld adapter 提交同一结果到 Process/WorkbenchOutput Holder。

#### 主世界与 SubWorld adapter

- MainWorld adapter 把现有特殊物品 Entity、Actor 熟练度、资源池、City/设备和生产事件转换为 `CraftStartRequest/CraftContext`，调用领域服务，再按原有 ECS 组件、计时、事件、装备和城市入库顺序提交 commands。
- `BehCraftElixir`、`BehCraftArtifact`、`BehCraftTalisman`、`BehCraftMagicScroll` 分别以 `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting` 调用同一 registry/domain；它们只保留 AI task 生命周期和 MainWorld 提交职责，不再直接计算资格、资源扣减、槽匹配、进度、效果、品质、产量或失败。
- SubWorld 工作台 adapter 从 Archive typed snapshot、Projection 资源池和工作台状态构造相同请求；只要 `CraftCapabilities[]` 包含对应 Kind ID，就通过同一 registry/domain 启动、推进或中断四类工序，并把结果提交为资源与 ItemRecord Holder commands。
- 相同 `ProcessKindId`、typed recipe/input、`CraftContext` 和 RNG 序列必须产生相同领域结果。AIGC 名称以及产物 60% 分配给城市、40% 留给个人的选择只在 MainWorld adapter 提交结果时执行，不进入领域输出，也不消耗领域 RNG。
- 禁止新增 SubWorld 专属丹方类型、炼丹器规则、炼器 planner 或 artifact composer；两个世界也不能各维护一份 recipe cache 作为权威数据。

#### 复用并重构现有制造能力

下列能力迁入共享领域或改为接受 typed snapshot/value object，并继续作为主世界和 SubWorld 的唯一实现：

- `IngredientSemanticService`：从 `IngredientSnapshot` 读取直接语义，不要求材料必须是 ECS Entity。
- `ElixirRecipeBuilder`：生成完整 `ElixirRecipeBlueprint`、稳定签名和槽位要求。
- 现有丹方槽匹配、`ElixirEffectComposer` 效果组合、品质与产量计算：改为纯数据输入和确定性随机输入。
- `ArtifactMaterialSemantics`：从 IngredientSnapshot 构建设计语义。
- `ArtifactIngredientPlanner`：基于候选 snapshot 和 CraftContext 选材。
- `ArtifactComposer`：输出 `ArtifactInstanceSnapshot` 或领域失败，不创建世界对象。
- 魔法卷轴 handler：保留 `BehCraftMagicScroll` 现有的魔法资格、对应资源、技能克隆路径、PowerLevel 和寿命计算，返回 `MagicScrollSnapshot` 与明确资源扣减 command。
- 符箓 handler：保留 `BehCraftTalisman` 现有的仙道资格、对应资源、共享技能路径、PowerLevel 与使用者力量换算输入，返回 `TalismanSnapshot` 与明确资源扣减 command。

MainWorld adapter 负责把这些结果 materialize 为现有 Entity；SubWorld 只把 typed snapshot 写入 Archive，不实现任何简化版 composer。

魔法卷轴和符箓不能共用一个抹平差异的 handler。两种 recipe/state codec 可以共同引用第二阶段的嵌套 `StoredSkillPayloadSnapshot { SkillBlueprint, Signature, Strength, PowerLevel }`，但顶层产物、资格、资源、技能克隆/共享、PowerLevel、寿命、城市分配以及学习/使用行为仍按各自 Kind 处理。领域核心负责可确定的资格、强度、寿命、产物与资源 commands；AIGC 名称、60% 城市/个人分配及 Entity 物化属于 MainWorld adapter。

#### 复用第二阶段首批 typed snapshot

第二阶段已经注册以下 PortableItem typed snapshot/codec；本阶段不新建 DTO，只把现有制造语义改为直接消费这些快照，并为 SubWorld Holder/ContentRef、工序输入和产物启用它们：

| 类型 | 权威内容 | 使用位置 |
| --- | --- | --- |
| `IngredientSnapshot` | Core.ItemId、数量/阶段、直接语义、品质及制造所需材料属性 | 容器、输入槽、Process Holder |
| `ElixirRecipeBlueprint` | 完整材料槽、语义要求、效果组合、品质/产量规则、稳定签名和版本 | 丹方物品与工作台 RecipeSlot |
| `ElixirItemSnapshot` | 丹方定义引用、实际效果、品质、数量和使用状态 | 工作台输出、容器和背包 |
| `ArtifactInstanceSnapshot` | 器形、材料语义、atoms、能力、品质、耐久/寿命和表现引用 | 工作台输出及第四阶段法宝使用 |
| `MagicScrollSnapshot` | Core 寿命与嵌套 `StoredSkillPayloadSnapshot`；保留魔法资格和学习/施放载体语义 | `magic_scroll_crafting` 输出、容器及第四阶段使用 |
| `TalismanSnapshot` | Core 与嵌套 `StoredSkillPayloadSnapshot`；保留仙道资格、使用者力量换算和一次性施放语义 | `talisman_crafting` 输出、容器及第四阶段使用 |

`ContentRef` 只引用 Archive typed snapshot store 中的具体记录。动态 `ElixirRecipeBlueprint` 以及 `MagicScrollSnapshot`、`TalismanSnapshot` 中的 `StoredSkillPayloadSnapshot.SkillBlueprint` 必须随世界槽位完整保存；全局 library/definition ID 只能作为可重建索引，不能替代完整定义，也不能把 `CompiledSkillDefinition` 副本写入载体。

#### 工序提交顺序

1. adapter 验证工作台 `CraftCapabilities[]` 包含请求的 `ProcessKindId`、输入槽和操作者行动占用，并构造实际资源池快照。
2. 在同一事务中创建 `CraftProcessSnapshot`，并把全部材料转为 Process Holder。
3. 每个推进点调用 `ICraftDomainService.Advance`，提交更新后的进度和 RandomState。
4. 按领域结果顺序提交 `DeductCraftResourceCommand` 和材料 commands；魔法卷轴、符箓不得只生成产物而不扣对应资源。
5. 成功时先写入 Kind handler 返回的 typed 产物，再创建 StableItemId/ExpeditionItemId，并放入 WorkbenchOutput Holder。
6. 失败或中断时调用同一 registry/domain 的 `Interrupt` 或失败结果，并提交其资源与材料 commands。
7. 单位另行执行拾取，把输出槽物品转为 ProjectionInventory；未拾取产物继续属于工作台。

### 步骤 6：实现可组合探索与制造目标

`SubWorldObjectiveRecord` 由稳定 Objective Asset ID 和状态组成：

```text
ObjectiveId
AssetId
State
Progress
RequiredObjectiveIds[]
TargetEntityIds[]
CompletedAt
```

首批目标：

- `ReachZone`
- `DiscoverEntity`
- `BreakSeal`
- `OpenContainer`
- `ActivateNodes`
- `CompleteCraftProcess`
- `CollectCraftOutput`
- `ExitWorld`

目标使用前置关系组成有向无环图。Template 注册时验证不存在循环，实例运行中不修改目标依赖结构。

Objective Service 只消费已经提交的领域事件，例如 `EntityEnteredZone`、`SealBroken`、`ContainerOpened`，不反向扫描全世界状态猜测是否完成。

### 步骤 7：实现规则专属时间与视觉

#### 时间

增加两种 ClockProfile：

| Profile | DefaultLocalRate | BodyTime | 主世界单独暂停时 | 浮窗隐藏时 |
| --- | --- | ---: | --- | --- |
| `SealedEstate` | `4x` | `1.0` | 继续 | 有参与者时继续 |
| `StillDream` | `20x` | `0.05` | 继续 | 有参与者时继续 |

两个 Profile 都与主世界时钟并行，实际 LocalTime 还乘以浮窗选择的 LocalSpeed。浮窗打开、折叠或关闭不参与时钟判定。同一 Instance 创建后不切换 ClockProfile；规则造成的临时时间区域通过局部状态改变实体行动速度，不修改全局 LocalTime。

#### 视觉

View 根据 VisualProfile：

- 从原版 terrain visual catalog 解析 tile，并叠加当前主题中实际存在的 override。
- 加载实体、工作台和交互对象的共享 presentation binding。
- 克隆局部材质并设置 LocalTime 参数。
- 使用实例 AmbientColor 和 FogColor。
- 按 EffectBindings 映射门、禁制、环境和目标反馈。
- 限制相机缩放与地图边界。

局部昼夜只改变小世界材质，不修改 `LibraryMaterials`、主世界全局 shader 或主相机背景。

## 验收标准

### 规则与生成

- 相同 Template、Seed 和参数生成相同结构签名。
- Generator 验证失败时 Archive 不增加 Instance。
- 两种 Template 的地图、目标、时间、迷雾和视觉明显不同。
- Rule Module 不保存运行时状态，实例状态均可序列化。
- 目标依赖存在循环时 Template 注册失败。
- VisualProfile 的未覆盖 terrain 均按 `SourceLayer + AssetId` 来自第一阶段 `IWorldBoxTerrainVisualCatalog`；切换主题不复制或改写整套 tile。

### 视野与交互

- Seen、Visible 和未见格在视图中明确区分。
- 两个 VisionGroup 不会自动共享发现结果。
- 门和禁制变化只重算受影响导航与视野区域。
- 容器和机关只结算一次，读档不重复生成内容。
- 容器内容创建时即拥有唯一 StableItemId、ExpeditionItemId 和 Archive ContentRef；记录中不存在 `PayloadKind/Payload`。
- 打开、折叠或关闭浮窗不会改变发现、交互和 Objective 逻辑结果。

### 制造与 typed snapshot

- `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting` 分别以同一 `CraftStartRequest`、`CraftContext` 和 RNG 序列经 MainWorld `BehCraft*` adapter 与 SubWorld workbench adapter 执行时，`CraftProcessSnapshot`、资源扣减、材料消耗、产物、品质、产量、`CraftFailure` 和领域 commands 一致。
- registry 对重复 `ProcessKindId` 注册、未知 ID、recipe/state codec 类型或版本不匹配直接失败；工作台不能用未注册 ID 开工，Archive 不生成通用 payload。
- `IngredientSnapshot`、`ElixirRecipeBlueprint`、`ElixirItemSnapshot`、`ArtifactInstanceSnapshot`、`MagicScrollSnapshot`、`TalismanSnapshot` 均能经第二阶段 codec 保存读档并保持稳定签名。
- 材料开工后只属于 Process Holder；成功产物只属于 WorkbenchOutput，未执行拾取时不会进入 Projection 背包或返回奖励。
- 失败和中断均走共享 `CraftFailure`，MainWorld 与 SubWorld 不各自判断材料退回、消耗或废料。
- 动态丹方只存在于世界槽位时仍能保存读档并完成炼制，不依赖进程内 Elixir library 缓存。
- `IngredientSemanticService`、`ElixirRecipeBuilder`、丹方槽匹配/效果组合/品质产量以及三项 Artifact 服务只有一份领域实现。
- 魔法卷轴与符箓制造都从 `CraftResourcePoolSnapshot[]` 读取现有对应资源并返回明确扣减 command；资源不足时不产出物品。
- 主世界既有炼丹、炼器、魔法卷轴和符箓的 AI task、耗时、资格、资源、技能克隆/共享、PowerLevel、寿命、生产事件、品质产量、学习/使用与失败行为在重构前后不变；AIGC 名称和 60% 城市/个人分配只由 MainWorld adapter 执行。

### 时间与视觉

- 两个 ClockProfile 的 DefaultLocalRate、LocalSpeed 和 BodyTime 结果符合配置，主世界维持自己的速度。
- 浮窗显示和隐藏时 SealedEstate、StillDream 都按参与者与显式局部暂停状态决定是否推进。
- 主世界与当前可见实例使用不同倍率运行时，两边计时、环境和目标互不覆盖。
- 制造进度只读取所属世界的 `ITimeSource`/CraftContext；主世界暂停、SubWorld LocalSpeed 和非模态浮窗开关不会串改另一世界工序。
- 局部昼夜不改变主世界材质和光照。
- 切换查看两个不同 VisualProfile 时对象池材质与 sprite 不串用。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
