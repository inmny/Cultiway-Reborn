# 第3阶段-规则模块与场景生成

本阶段把最小验证实例扩展为可配置平台，并把真实工作台接入现有制造领域。不同 Template 可以组合地图生成、时间、视野、环境、交互、目标和视觉主题，但地形表现、PortableItem、炼丹、炼器、魔法卷轴制造与符箓制造都复用前两阶段和主世界已有能力。

`SubWorldManager` 统一管理运行期间常驻的 SubWorld Runtime。地图、Zone、Vision、Item、Workbench、CraftProcess、Objective 都是 Runtime Map/ECS 会话状态；WorldView 与底栏只负责观察、导航和输入，不拥有实例状态。

## 具体说明

### 设计边界

- `SubWorldManager` 是实例创建、Runtime 注册、tick、交互命令、退出同步和销毁的唯一入口。一个活动实例对应一个常驻 Runtime；相机聚焦、WorldView 相交或裁剪都不改变 Runtime 生命周期。
- RuleSet 只组合稳定 Module ID 和参数，不把任意委托或脚本作为实例模块。
- Template 决定允许的规则空间，Runtime 在创建时冻结模块顺序和参数。
- Generator 逐格写入 Runtime Map 的原版 terrain 字符串 ID；Runtime Grid 直接解析并缓存原版对象，WorldView 消费同一引用，不建立第二种 terrain 表示。
- terrain 外观由 Template/Generator 选择的原版 Asset ID 决定。VisualProfile 不按 terrain ID 替换 Tile、Sprite 或材质；需要另一种地面或墙体时直接选择另一个已存在的原版 `TileTypeBase` Asset ID。
- PortableItem typed snapshot、`ContentRef` 与 Blueprint 只作为 Runtime 内存值对象使用。物品只在所属 Runtime Store 中物化一次，并由唯一 ItemId 标识。
- 退出实例时，`SubWorldManager` 按退出规则把需要带回的 Runtime Store 物品同步物化到 MainWorld，随后释放该 Runtime 中的物品实体和会话状态。
- 主世界与 SubWorld 只允许通过唯一 `ICraftProcessKindRegistry` 和 `ICraftDomainService` 执行制造规则；世界层只做输入采集和结果应用。
- 本阶段加入非战斗环境损耗、交互和制造，不加入敌人、技能、战斗和死亡。
- 两个 Template 必须在同一 Runtime 实现上表现出明显不同的地图、时间和画面。
- SubWorld 显示在主地图周边的世界空间槽位中并与主世界共用主相机，主/子世界独立时钟；相机聚焦和 WorldView 可见性不能成为制造或规则输入。

### 步骤 1：建立 Runtime、规则、时钟与非 terrain 视觉合同

#### SubWorldManager 与 Runtime

`SubWorldManager` 持有活动 Runtime 集合，并统一驱动其生命周期：

```text
Create(templateId, anchor, seed, parameters)
Get(instanceId)
Destroy(instanceId)
Update(unscaledDeltaTime)
IssueCommand(instanceId, command)
FocusMainWorld()
Focus(instanceId)
Clear()
```

每个 Runtime 包含：

```text
RuntimeId
TemplateId
RuleRuntime
Clock
RandomState
Map/Grid
ECS World
Runtime Item Store
Event Queue
```

Generator 完成验证和物化后，`SubWorldManager` 才把 Runtime 加入活动集合。Runtime 的地图、区域、视野、物品、工作台、工序和目标都由 Map/ECS 组件表达，模块不能把状态藏在 UI、静态字段或 Module Asset 中。

#### RuleSet

`SubWorldRuleSetAsset`：

```text
Id
MovementModuleId
VisibilityModuleId
EnvironmentModuleIds[]
InteractionModuleIds[]
ObjectiveModuleIds[]
ExitModuleId
Parameters
```

`SubWorldRuleModuleAsset` 只声明 ID、配置 schema、依赖和执行优先级。实际无状态实现由 `SubWorldRuleModuleRegistry` 注册。

模块生命周期：

```text
OnRuntimeCreated
BeforeTick
HandleCommands
UpdateEntities
UpdateEnvironment
EvaluateObjectives
AfterTick
```

每个阶段的调用顺序在 RuleRuntime 创建时冻结。模块不能在运行中自行插入新的全局 system 顺序。

#### ClockProfile

完整字段：

```text
Id
FixedStep
DefaultLocalRate
BodyTimeRatio
RunsWhileParentPaused
BackgroundPolicy
AllowedLocalSpeedOptions[]
MaxTicksPerFrame
MaxCatchUpTime
LocalDayLength
```

ClockProfile 只决定时间如何推进；环境模块读取 LocalTime，但不能直接修改时钟。

#### VisualProfile

```text
Id
EntityVisualProfileId
BackgroundColor
FogColor
AmbientColor
LocalLightProfileId
OverlayProfileId?
FocusZoom
EffectBindings[]
```

VisualProfile 只描述 terrain 定义之外的 FogColor、槽位背景、局部光照、底栏聚焦缩放、独立 overlay/VFX 和 EntityVisualProfile。它不包含 terrain selector，不按 Asset ID 绑定替换 Sprite/Tile/Material，也不注册 SubWorld 基础 terrain。

VisualProfile 不持有 Camera、Material、Tile 或 Sprite 实例。WorldView 始终从 Runtime Grid 的直接原版引用取得 `TileTypeBase.sprites.main`；私有 Renderer Material 只承载局部光照参数，不能替换原版 terrain Tile/Sprite。切换 VisualProfile 不重写 Runtime Map 中的 terrain ID，也不修改主相机全局缩放边界。

### 步骤 2：实现确定性场景生成管线

`ISubWorldGenerator` 接收：

```text
Template
Seed
Width/Height
CreationParameters
```

输出完整 `SubWorldGeneratedScene`。生成阶段固定为：

1. `Layout`：房间、路径、区域和入口出口。
2. `Terrain`：逐格 Main/Top 原版 Asset ID；入口出口继续属于 Layout 的地图外目标元数据。
3. `Environment`：灵气场、毒雾、热区、照明和局部时间节点。
4. `Content`：门、禁制、容器、机关、真实工作台和目标对象。
5. `Validate`：路径、容量、目标可达性和 ID 引用。
6. `Materialize`：一次构造 Runtime Map、ECS 实体、Runtime Store 内容和初始事件。

Generator 在 Materialize 前只操作临时 scene，不逐步修改活动 Runtime。验证失败时，`SubWorldManager` 不注册实例。

`Terrain` 阶段直接逐格写入 `SubWorldTile.MainAssetId/TopAssetId`，只选择已经存在的原版字符串 Asset ID；没有 Top 的格子写入空 `TopAssetId`。`Validate` 对每格通过 `AssetManager.tiles.get(MainAssetId)` 与非空时的 `AssetManager.top_tiles.get(TopAssetId)` 确认对象存在；缺失 ID 使生成失败，不提供默认地面。Materialize 后，生成结果成为 Runtime Map 的 tile 数据。

#### 区域

区域作为 Runtime ECS 会话状态：

```text
SubWorldZone
  ZoneId
  Bounds/TileIds
  SemanticIds[]
  DiscoveryState
```

Zone 是小世界内部的房间或区域，不复用主世界 GeoRegion。消费系统可以把主世界语义作为创建参数输入 Generator。

#### 确定性

- 所有随机从 Runtime RandomState 获取。
- 不使用 UnityEngine.Random 全局状态。
- 对集合排序后再抽样。
- 地图生成后的变化只修改对应 Runtime tile，并刷新该格 Grid 缓存与 dirty tile，不写原版 Asset。
- Debug 可用同 Template、Seed、参数重建临时 scene 并比较结构签名。

### 步骤 3：实现视野、迷雾与发现

首版按队伍共享视野，不为每个 Actor 建立一张完整迷雾图。每个 VisionGroup 对应一个 Runtime ECS 状态：

```text
SubWorldVisionState
  VisionGroupId
  SeenBits
  VisibleBits
  DiscoveredEntityIds[]
```

视野规则：

- Projection 提供 VisionRadius 和 VisionGroupId。
- `VisibilityModule` 只在单位跨格、阻挡变化或视野属性变化时重算。
- Seen 表示曾见过，Visible 表示当前可见。
- 未见 tile 不绘制；已见但不可见 tile 使用 VisualProfile FogColor。
- 机关和容器可以拥有独立 Concealment，只有进入视野并通过感知检查后加入 DiscoveredEntityIds。

多个互不共享情报的队伍拥有不同 VisionGroup。每个 WorldView 保留自己的观察队伍选择，底栏只编辑当前 `FocusedRuntime`；消费系统可以提供“天道视角”作为只读视图模式，但不能因此把发现写给 Projection。

### 步骤 4：实现门、容器、机关与真实工作台

#### 交互对象

```text
SubWorldInteractable
  InteractionAssetId
  State
  Charges
  RequiredTags[]
```

首批交互：

| 交互 | 状态 | 命令结果 |
| --- | --- | --- |
| 门 | Closed/Open/Locked | 开启、关闭或等待解锁 |
| 禁制 | Sealed/Weakening/Broken | 持续投入破禁进度 |
| 容器 | Hidden/Closed/Opened/Empty | 发现、开启并暴露 Runtime Store 槽物品 |
| 压力机关 | Armed/Triggered/Disabled | 触发环境效果或解除 |
| 传送节点 | Inactive/Active | 将实体移动到配对节点 |
| 真实工作台 | Idle/Reserved/Running/Completed/Failed | 放入材料、开工、推进工序和拾取产物 |
| 出口 | Locked/Available | 请求退出或完成实例 |

所有交互都通过 `SubWorldManager.IssueCommand(instanceId, StartInteractionCommand)` 创建短生命周期 InteractionState。单位离开、失去资格或对象状态变化时中止，不在 UI 中直接切换状态。

#### Runtime Store 与容器物品

容器生成时直接在 Runtime Store 创建 typed item value，并把唯一 ItemId 放入容器槽：

```text
SubWorldRuntimeItem
  ItemId
  ContentRef
  Holder
  State
```

- Runtime Store 是活动实例内物品的唯一物化位置；`ItemId` 是物品跨 Holder 移动时保持不变的唯一身份。
- `ContentRef` 是 Runtime Store 内指向 typed item value 的内存引用，不承担跨会话表示。
- `Holder` 是带类型的位置，可指向 ContainerSlot、ProjectionInventory、Process、WorkbenchOutput 或 Ground；活动物品始终只有一个 Holder。
- 容器内容在场景 Materialize 时已经获得 ItemId 和 ContentRef。开箱只把 Holder 从隐藏容器槽切换为可见容器槽，不重新生成或复制内容。
- MainWorld 来源物品进入实例后由 `SubWorldManager` 接管当前表示；Runtime 活动期间不能同时存在可操作的 MainWorld Entity 与 SubWorldRuntimeItem。
- SubWorld 生成物和制造产物直接进入同一个 Runtime Store，不预先创建 MainWorld Entity。
- 退出时，`SubWorldManager` 按返回队伍、Holder 和退出规则把带出物品同步为 MainWorld Entity；未带出的会话物品随 Runtime 释放。

#### 真实工作台

工作台是地图中的可占用交互对象，不是打开 UI 后立即生成成品的按钮。状态全部位于 Runtime ECS：

```text
SubWorldWorkbenchState
  WorkbenchId
  CraftCapabilities[]
    ProcessKindId
  InputSlots[]
  RecipeSlot?
  OutputSlots[]
  ActiveProcessId?
  State
```

单位必须到达工作台并占用主行动，才能放入材料、放入 recipe、开始或继续手工制造。`CraftCapabilities[]` 的每一项只使用稳定字符串 `ProcessKindId`，不使用 enum 数值或 handler 类型名。`RecipeSlot` 引用当前 Runtime Store 中的 typed recipe value；动态丹方的完整 `ElixirRecipeBlueprint` 直接存在于该 Runtime value 中。全局 library 可以按签名缓存或索引定义，但不能替代当前工序实际引用的 Blueprint。

材料开工后从 ContainerSlot、ProjectionInventory 或 Ground 转为 `Holder = Process(ProcessId)`。成功产物在 Runtime Store 中创建，并进入 `Holder = WorkbenchOutput(WorkbenchId, Slot)`；单位必须执行拾取交互，目标完成、相机离开实例或工序结束都不能把产物远程塞进背包。

#### 环境场

tile 可以持有有界环境值：

```text
Aura
Heat
Toxin
Instability
```

Environment Module 只处理脏区和活动实体所在区域，不逐 tick 扫描全部 `128x128` tile。首版效果为非致命资源消耗、移动成本和视野变化；致死效果在第四阶段接入统一死亡规则。

### 步骤 5：抽取共享制造领域与 typed runtime value

#### 唯一制造入口

从现有主世界行为中抽取唯一 `ICraftProcessKindRegistry` 和 `ICraftDomainService`。registry 是 Process Kind 注册与解析的唯一入口：

```text
ICraftProcessKindRegistry
  Register<TRecipe, TState>(
    ProcessKindId,
    ICraftProcessKindHandler<TRecipe, TState>)
  Resolve(ProcessKindId)

ICraftProcessKindHandler<TRecipe, TState>
  Start(TRecipe, CraftStartRequest, CraftContext, IDeterministicRandom)
  Advance(TRecipe, TState, CraftContext, IDeterministicRandom)
  Interrupt(TRecipe, TState, CraftContext, CraftInterruptReason,
            IDeterministicRandom)
```

每个 `ProcessKindId` 只注册一个 typed handler。重复 ID 在注册时直接失败；未知 ID 或 recipe/state 类型不匹配在启动、推进或中断时直接失败，不提供通用 payload fallback。

`ICraftDomainService` 只接受纯内存值对象和确定性随机源，不读取 Actor、City、Friflo Entity、WorldTile 或 SubWorld Runtime；三个入口都先按 `ProcessKindId` 经 registry 路由到 typed handler：

```text
Start(CraftStartRequest, CraftContext, IDeterministicRandom) -> CraftStartResult
Advance(CraftProcessSnapshot, CraftContext, IDeterministicRandom) -> CraftAdvanceResult
Interrupt(CraftProcessSnapshot, CraftContext, CraftInterruptReason,
          IDeterministicRandom) -> CraftInterruptResult
```

- `CraftStartRequest` 包含 `ProcessKindId`、操作者能力快照、输入 ItemId/ContentRef、该 Kind 的 typed recipe 和请求的工序模式。
- `CraftContext` 包含本次制造真实使用的工作台能力、环境语义、时间、熟练度、规则修正和 `CraftResourcePoolSnapshot[] { ResourceId, Current, Maximum }`；MainWorld 与 SubWorld adapter 必须从各自世界构造同一语义。
- `IDeterministicRandom` 是唯一随机入口。工序在 Runtime ECS 中持有 RandomState 或确定的 random cursor，每次推进从当前位置继续。
- `CraftStartResult` 返回 Runtime `CraftProcessSnapshot` 或共享 `CraftFailure`；Advance/Interrupt 结果返回更新后的 snapshot、typed 产物和有序领域 commands。任何资源消耗都必须表现为明确的 `DeductCraftResourceCommand { ResourceId, Amount }`，不能只在结果中隐含“已消耗”。

首批注册固定为：

| `ProcessKindId` | typed recipe | typed state | MainWorld 行为入口 | typed 产物 |
| --- | --- | --- | --- | --- |
| `alchemy` | `ElixirRecipeBlueprint` | `AlchemyCraftStateSnapshot` | `BehCraftElixir`；`FindNewElixir` 只负责推演并产出丹方 | `ElixirItemSnapshot` |
| `artifact_refining` | `ArtifactRefiningRecipeSnapshot` | `ArtifactRefiningStateSnapshot` | `BehCraftArtifact` | `ArtifactInstanceSnapshot` |
| `talisman_crafting` | `TalismanCraftRecipeSnapshot` | `TalismanCraftStateSnapshot` | `BehCraftTalisman` | `TalismanSnapshot` |
| `magic_scroll_crafting` | `MagicScrollCraftRecipeSnapshot` | `MagicScrollCraftStateSnapshot` | `BehCraftMagicScroll` | `MagicScrollSnapshot` |

`FindNewElixir` 是 `alchemy` 的配方推演入口，不是第五种 Process Kind。原版法杖打造和写书暂不纳入首批，也不预留假注册项。

`CraftProcessSnapshot` 是 ECS 工序组件中的 typed 内存值对象，不是独立状态源：

```text
ProcessId
ProcessKindId
CrafterId
InputItemIds[]
OutputItemId?
TypedRecipeSnapshot
TypedStateSnapshot
Progress
RandomState
WorkbenchRef
State
StartRequest
ContextSnapshot
RecipeContentRef?
RequiredProgress
AdvancementMode
StartedAt/UpdatedAt
Result?
```

状态固定为 Prepared、Running、Succeeded、Failed、Interrupted。`AdvancementMode` 区分有人贡献行动的 Manual、必须固定 tick 推进的 Automatic 和明确支持解析推进的 AnalyticAutomatic；世界 adapter 不能自行把 Manual 工序换算成 elapsed 进度。

失败和中断统一返回对应 Kind handler 的 `CraftFailure` 与有序 commands，由共享规则决定材料与制造资源的消耗、退回或废料 typed value。现有 `CraftFailureService` 改为 MainWorld 提交 adapter，不再拥有另一套失败判定；SubWorld adapter 把同一结果应用到 Process Holder、Runtime Store 和 WorkbenchOutput。

#### 主世界与 SubWorld adapter

- MainWorld adapter 把现有特殊物品 Entity、Actor 熟练度、资源池、City/设备和生产事件转换为 `CraftStartRequest/CraftContext`，调用领域服务，再按原有 ECS 组件、计时、事件、装备和城市入库顺序应用 commands。
- `BehCraftElixir`、`BehCraftArtifact`、`BehCraftTalisman`、`BehCraftMagicScroll` 分别以 `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting` 调用同一 registry/domain；它们只保留 AI task 生命周期和 MainWorld 结果应用职责，不再直接计算资格、资源扣减、槽匹配、进度、效果、品质、产量或失败。
- `SubWorldManager` 驱动工作台 adapter 从 Runtime Store、Projection 资源池和工作台 ECS 状态构造相同请求；只要 `CraftCapabilities[]` 包含对应 Kind ID，就通过同一 registry/domain 启动、推进或中断四类工序，并把结果应用为资源 command、工序状态与物品 Holder 变化。
- 相同 `ProcessKindId`、typed recipe/input、`CraftContext` 和 RNG 序列必须产生相同领域结果。AIGC 名称以及产物 60% 分配给城市、40% 留给个人的选择只在 MainWorld adapter 应用结果时执行，不进入领域输出，也不消耗领域 RNG。
- 禁止新增 SubWorld 专属丹方类型、炼丹器规则、炼器 planner 或 artifact composer；两个世界也不能各维护一份 recipe cache 作为权威数据。

#### 复用并重构现有制造能力

下列能力迁入共享领域或改为接受 typed snapshot/value object，并继续作为主世界和 SubWorld 的唯一实现：

- `IngredientSemanticService`：从 `IngredientSnapshot` 读取直接语义，不要求材料必须是 ECS Entity。
- `ElixirRecipeBuilder`：生成完整 `ElixirRecipeBlueprint`、稳定签名和槽位要求。
- 现有丹方槽匹配、`ElixirEffectComposer` 效果组合、品质与产量计算：改为纯数据输入和确定性随机输入。
- `ArtifactMaterialSemantics`：从 IngredientSnapshot 构建设计语义。
- `ArtifactIngredientPlanner`：基于候选 snapshot 和 CraftContext 选材。
- `ArtifactComposer`：输出 `ArtifactInstanceSnapshot` 或领域失败，不创建世界对象。
- 魔法卷轴 handler：保留 `BehCraftMagicScroll` 现有的魔法资格、对应资源、技能克隆路径、PowerLevel 和寿命计算，返回 `MagicScrollSnapshot` 与明确资源扣减 command。
- 符箓 handler：保留 `BehCraftTalisman` 现有的仙道资格、对应资源、共享技能路径、PowerLevel 与使用者力量换算输入，返回 `TalismanSnapshot` 与明确资源扣减 command。

MainWorld adapter 负责把这些结果物化为现有 Entity；SubWorld adapter 只在 Runtime Store 中创建 typed item value，不实现任何简化版 composer。

魔法卷轴和符箓不能共用一个抹平差异的 handler。两种 recipe/state 可以共同引用 `StoredSkillPayloadSnapshot { SkillBlueprint, Signature, Strength, PowerLevel }`，但顶层产物、资格、资源、技能克隆/共享、PowerLevel、寿命、城市分配以及学习/使用行为仍按各自 Kind 处理。领域核心负责可确定的资格、强度、寿命、产物与资源 commands；AIGC 名称、60% 城市/个人分配及 Entity 物化属于 MainWorld adapter。

#### Runtime typed item value

本阶段复用以下 PortableItem typed value，只把现有制造语义改为直接消费这些内存对象，并让 Runtime Store、Holder、工序输入和产物使用它们：

| 类型 | 权威内容 | Runtime 使用位置 |
| --- | --- | --- |
| `IngredientSnapshot` | Core.ItemId、数量/阶段、直接语义、品质及制造所需材料属性 | 容器、输入槽、Process Holder |
| `ElixirRecipeBlueprint` | 完整材料槽、语义要求、效果组合、品质/产量规则、稳定签名和版本 | 丹方物品与工作台 RecipeSlot |
| `ElixirItemSnapshot` | 丹方定义引用、实际效果、品质、数量和使用状态 | 工作台输出、容器和背包 |
| `ArtifactInstanceSnapshot` | 器形、材料语义、atoms、能力、品质、耐久/寿命和表现引用 | 工作台输出及第四阶段法宝使用 |
| `MagicScrollSnapshot` | Core 寿命与嵌套 `StoredSkillPayloadSnapshot`；保留魔法资格和学习/施放载体语义 | `magic_scroll_crafting` 输出、容器及第四阶段使用 |
| `TalismanSnapshot` | Core 与嵌套 `StoredSkillPayloadSnapshot`；保留仙道资格、使用者力量换算和一次性施放语义 | `talisman_crafting` 输出、容器及第四阶段使用 |

`ContentRef` 只引用当前 Runtime Store 中的具体 typed value。动态 `ElixirRecipeBlueprint` 以及 `MagicScrollSnapshot`、`TalismanSnapshot` 中的 `StoredSkillPayloadSnapshot.SkillBlueprint` 必须作为完整内存对象存在于物品或工序状态中；全局 library/definition ID 只能作为索引，不能替代完整定义，也不能把 `CompiledSkillDefinition` 副本写入载体。

#### 工序命令顺序

1. adapter 验证工作台 `CraftCapabilities[]` 包含请求的 `ProcessKindId`、输入槽和操作者行动占用，并构造实际资源池快照。
2. 在同一个 Runtime ECS command batch 中创建 `CraftProcessSnapshot`，并把全部材料转为 Process Holder。
3. 每个推进点调用 `ICraftDomainService.Advance`，更新 ECS 中的进度、typed state 和 RandomState。
4. 按领域结果顺序应用 `DeductCraftResourceCommand` 和材料 commands；魔法卷轴、符箓不得只生成产物而不扣对应资源。
5. 成功时在 Runtime Store 创建 Kind handler 返回的 typed 产物，分配唯一 ItemId，并放入 WorkbenchOutput Holder。
6. 失败或中断时调用同一 registry/domain 的 `Interrupt` 或失败结果，并应用其资源与材料 commands。
7. 单位另行执行拾取，把输出槽物品转为 ProjectionInventory；未拾取产物继续属于工作台。

### 步骤 6：实现可组合探索与制造目标

目标状态位于 Runtime ECS：

```text
SubWorldObjectiveState
  ObjectiveId
  AssetId
  State
  Progress
  RequiredObjectiveIds[]
  TargetEntityIds[]
  CompletedAt
```

首批目标：

- `ReachZone`
- `DiscoverEntity`
- `BreakSeal`
- `OpenContainer`
- `ActivateNodes`
- `CompleteCraftProcess`
- `CollectCraftOutput`
- `ExitWorld`

目标使用前置关系组成有向无环图。Template 注册时验证不存在循环，实例运行中不修改目标依赖结构。

`SubWorldManager` 在 RuleRuntime 的 `EvaluateObjectives` 阶段消费已经应用的领域事件，例如 `EntityEnteredZone`、`SealBroken`、`ContainerOpened`，不反向扫描全世界状态猜测是否完成。

### 步骤 7：实现规则专属时间与视觉

#### 时间

增加两种 ClockProfile：

| Profile | DefaultLocalRate | BodyTime | 主世界单独暂停时 | WorldView 被裁剪时 |
| --- | --- | ---: | --- | --- |
| `SealedEstate` | `4x` | `1.0` | 继续 | 有参与者时继续 |
| `StillDream` | `20x` | `0.05` | 继续 | 有参与者时继续 |

两个 Profile 都与主世界时钟并行，实际 LocalTime 还乘以底栏为 `FocusedRuntime` 选择的 LocalSpeed。相机聚焦、WorldView 相交或裁剪不参与 Runtime 生命周期判定。同一实例创建后不切换 ClockProfile；规则造成的临时时间区域通过局部状态改变实体行动速度，不修改全局 LocalTime。

#### 视觉

WorldView 根据 VisualProfile：

- 把 Grid 已解析的 Main/Top 原版对象的 `sprites.main` 分别直接放入私有 Main/Top Tilemap；没有 Top 时清空 Top Tilemap 对应格。
- 加载实体、工作台和交互对象的共享 presentation binding。
- 在私有 Renderer Material 上设置 LocalTime 与局部光照参数。
- 使用实例 AmbientColor 和 FogColor。
- 按 OverlayProfile 与 EffectBindings 映射独立的门、禁制、环境和目标 overlay/VFX。
- 为底栏聚焦提供目标缩放，不修改主相机全局缩放边界。

局部昼夜只改变小世界私有材质参数，不修改原版 Tile/Sprite Asset、`LibraryMaterials`、主世界全局 shader 或主相机背景。若场景需要不同的地面、墙体或水域，由 Template 的 Generator 参数选择另一个已经存在的原版 Asset ID，而不是由 VisualProfile 替换。

## 验收标准

### Runtime、规则与生成

- `SubWorldManager` 是活动实例的唯一所有者；相机聚焦和 WorldView 裁剪不会创建、复制或销毁 Runtime。
- Map、Zone、Vision、Item、Workbench、CraftProcess、Objective 都能在 Runtime Map/ECS 中定位，不存在 UI 或 Module Asset 私有状态源。
- 相同 Template、Seed 和参数生成相同结构签名。
- Generator 验证失败时，`SubWorldManager` 不注册 Runtime。
- 两种 Template 的地图、目标、时间、迷雾和视觉明显不同。
- Rule Module 无运行时字段，状态全部写入 Runtime Map/ECS。
- 目标依赖存在循环时 Template 注册失败。
- 两种 Generator 都逐格写入 Runtime Map 的原版 Asset ID；任一 ID 缺失时不创建 Runtime。
- VisualProfile 不包含 terrain selector 或按 ID 的 Tile/Sprite/Material 替换；不同地面与墙体只能通过 Template 选择不同的原版 Asset ID。

### 视野、交互与物品

- Seen、Visible 和未见格在视图中明确区分。
- 两个 VisionGroup 不会自动共享发现结果。
- 门和禁制变化只重算受影响导航与视野区域。
- 容器和机关在同一 Runtime 会话中只结算一次。
- 容器、Projection、地面、Process 和 WorkbenchOutput 中的同一物品共用唯一 ItemId，Runtime Store 中只有一份 typed value。
- Holder 变化只移动物品归属，不复制 typed value；未执行拾取时工作台产物不会进入 ProjectionInventory。
- 退出时，符合带出规则的 Runtime Store 物品由 `SubWorldManager` 同步物化到 MainWorld；未带出物品随 Runtime 释放。
- 相机聚焦、离开实例或 WorldView 裁剪不会改变发现、交互和 Objective 逻辑结果。

### 制造与 typed runtime value

- `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting` 分别以同一 `CraftStartRequest`、`CraftContext` 和 RNG 序列经 MainWorld `BehCraft*` adapter 与 SubWorld workbench adapter 执行时，`CraftProcessSnapshot`、资源扣减、材料消耗、产物、品质、产量、`CraftFailure` 和领域 commands 一致。
- registry 对重复 `ProcessKindId` 注册、未知 ID 或 recipe/state 类型不匹配直接失败；工作台不能用未注册 ID 开工，也不能生成通用 payload。
- `IngredientSnapshot`、`ElixirRecipeBlueprint`、`ElixirItemSnapshot`、`ArtifactInstanceSnapshot`、`MagicScrollSnapshot`、`TalismanSnapshot` 都作为 typed 内存值对象被 Runtime Store 和领域服务直接消费。
- 材料开工后只属于 Process Holder；成功产物只属于 WorkbenchOutput，未执行拾取时不会进入 Projection 背包或返回结果。
- 失败和中断均走共享 `CraftFailure`，MainWorld 与 SubWorld 不各自判断材料退回、消耗或废料。
- 动态丹方只存在于 Runtime Store 或工序状态时仍能完成炼制，不依赖 Elixir library 缓存。
- `IngredientSemanticService`、`ElixirRecipeBuilder`、丹方槽匹配/效果组合/品质产量以及三项 Artifact 服务只有一份领域实现。
- 魔法卷轴与符箓制造都从 `CraftResourcePoolSnapshot[]` 读取现有对应资源并返回明确扣减 command；资源不足时不产出物品。
- 主世界既有炼丹、炼器、魔法卷轴和符箓的 AI task、耗时、资格、资源、技能克隆/共享、PowerLevel、寿命、生产事件、品质产量、学习/使用与失败行为在重构前后不变；AIGC 名称和 60% 城市/个人分配只由 MainWorld adapter 执行。

### 时间与视觉

- 两个 ClockProfile 的 DefaultLocalRate、LocalSpeed 和 BodyTime 结果符合配置，主世界维持自己的速度。
- WorldView 相交和裁剪时 SealedEstate、StillDream 都按参与者与显式局部暂停状态决定是否推进。
- 主世界与任一小世界使用不同倍率运行时，各自计时、环境和目标互不覆盖。
- 制造进度只读取所属世界的 `ITimeSource`/CraftContext；主世界暂停、SubWorld LocalSpeed、相机聚焦和视图裁剪不会串改另一世界工序。
- 局部昼夜不改变主世界材质和光照。
- 切换查看两个不同 VisualProfile 时，私有材质、overlay/VFX 和 EntityVisualProfile 不串用；terrain Tile 仍是各自 Grid 解析的原版 `sprites.main`。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
