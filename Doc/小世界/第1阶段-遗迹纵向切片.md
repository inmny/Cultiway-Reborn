# 第1阶段-遗迹纵向切片

本阶段保留已经完成的地图、Runtime、时钟和 WorldView 底座，从当前真实断点继续实现第一条可玩的开放遗迹闭环。阶段结束时，一名真实修士会由 AI 前往一处残破古修道场，在连续地貌中根据残碑、灵气异常和道痕调查多个独立机缘，并根据风险与所得自行决定继续深入或返回。后续修士进入同一 Runtime，继承已经发生的一切并继续寻找剩余机缘。

首个遗迹不是房间和走廊组成的地牢，也没有唯一核心宝箱。它是一块有山势、遗构、残阵、药圃和道台的开放遗址；任一机缘都可以被独立发现、取得或错过。

## 具体说明

### 设计边界

- 当前代码事实是“步骤 1-5 已完成”。规划中的 Projection、机缘、Outcome 和战斗类型尚不存在。
- `SubWorldManager` 继续作为 Runtime 集合与生命周期唯一所有者；遗迹 Site 与内容放在 `Source/Content/SubWorlds/Ruins`。
- 正式遗迹由 AI 自主调查。现有右键 `MoveToTileCommand` 只保留为 Debug 验证工具。
- 一处 Site 只创建一个 Runtime。参与者离开不会重建地图、恢复残阵或补充已取走机缘。
- 首版使用一个手工开放布局、三个独立收益节点、一种非致命危险场和一种 Ingredient 实物奖励。
- 首版没有敌人和死亡。危险场最多把 Projection 生命降到 1，阶段 3 再统一加入致死与正式死亡结算。
- 主世界携带物不进入 Runtime，也不能在遗迹内使用。
- 不建立房间图、走廊生成、钥匙门、清图目标、通用目标 DAG、制造、BodyTime 或 Active/Warm。
- 地貌可通过自然窄道和坍塌形成空间引导，但不得把开放遗址退化成单线关卡。
- 全部状态只属于当前游戏会话；重新加载世界时直接清理，不恢复。

### 步骤 1：复用原版 terrain 并建立地图数据

该步骤已经完成，后续实现保持现有合同：

- `SubWorldMapData` 使用 row-major `SubWorldTile[]`、`EntryTileIndices[]` 和 `ExitTileIndices[]`。
- `SubWorldTile` 只保存原版 `MainAssetId/TopAssetId`。
- `SubWorldGrid` 直接解析并缓存 `TileType/TopTileType`。
- 有效 terrain 固定为 `Top ?? Main`；Navigation、格效果和渲染读取同一对象。
- ID 缺失时创建失败，不回退到默认地面。
- 不创建 `WorldTile`，不修改原版 Asset 或主世界地图数组。

新增地形改变时，必须由单一 Runtime 方法按顺序完成：校验 -> `Grid.SetTile` -> 刷新 Navigation -> 递增 Revision。调用方不能分别修改 Grid 和 Revision。

### 步骤 2：建立 Template、Runtime 与 Manager

该步骤已经完成：

- Generator、Template、ClockProfile 与 VisualProfile 四类 AssetLibrary 已注册。
- 每个 Runtime 独立持有 MapData、Grid、`EntityStore`、`SystemRoot`、Clock、队列与 Revision；Runtime 不持有通用随机数生成器。
- `SubWorldManager` 已提供 Create/Get/Destroy/Update/IssueCommand/Focus/Clear。
- 现有 `32x32 TestSubWorld` 继续作为 Debug 地图，不充当正式遗迹内容。

现有 `SubWorldGeneratedScene.InitialPawnTileIndex` 是测试遗留。通用生成结果改为 MapData 与命名 SpawnPoint；用途 Generator/Bootstrap 在 Runtime 构造后创建强类型实体。不得使用 `Dictionary<string, object>`、JSON payload 或字符串组件名替代类型合同。

### 步骤 3：实现独立固定时钟与命令边界

该步骤已经完成：

- 固定步长为 `0.1s`。
- 每个实例独立暂停并支持 1x/2x/4x。
- `FramePriorityGovernor` 控制每帧推进预算。
- 主世界暂停策略来自 ClockProfile；相机聚焦和 Renderer 可见性不改变 Clock。
- `MoveToTileCommand` 已验证 InstanceId、Revision、绑定 Store 与 generation 的 `Entity` handle 和目标格后进入 `MoveCommandQueue`。

步骤 5 起固定 tick 顺序为：边界命令、感知与线索、AI 决策、寻路、移动、危险场、调查交互、机缘/返回。状态结果直接写入组件和 Runtime 版本，不建立无消费者的本地事件队列。

### 步骤 4：实现周边 WorldView、相机与导航栏

该步骤已经完成：

- 小世界按稳定 SlotId 放在主地图周边，共用主相机。
- Runtime 局部坐标与槽位世界坐标分离。
- Terrain、Wall、Unit 与 Overview 渲染已经可用。
- 相机边界、聚焦、视野相交裁剪和 WORLD 分区导航入口已经接通。
- 清理世界时会销毁 Runtime、WorldView 和槽位。

正式遗迹只在 WorldView 中增加遗构、道痕、危险场、机缘和 Projection 的 Render binding；不新建 Camera、RenderTexture 或大型遗迹窗口。

### 步骤 5：补齐开放地形寻路与固定 tick 移动

该步骤已经完成。小世界没有复制或重写一套寻路器，而是扩展已有成熟异步寻路系统，使主世界和小世界共用一个 `PathFinder.Instance`、一组 `CultiwayPathFinder-*` 常驻 worker、`PathSession/PathStream` 和 `PortalAwarePathGenerator`。

#### 世界作用域合同

新增统一身份与请求合同：

- `PathWorldKey` 区分主世界生命周期和每个小世界 Runtime；`PathAgentKey` 在所属世界内标识实体。
- `PathHandle` 绑定 Agent 与单调递增 submission token。提交、替换、游标打开、终态清理和取消由同一所有权临界区保护，旧 handle 不能消费或取消后来替换的请求。
- 主世界 `Actor/WorldTile` API 只在主线程边界捕获纯数据 `PathRequest`；现有 Portal、分段 stream 和按模拟时间重试语义继续保留。
- `PathStep` 只保存 tile index、移动方式和规划 flags，不再隐式读取 `World.world.tiles_list`。主世界执行补丁在适配边界解析 `WorldTile`。
- 小世界请求携带 `SubWorldNavigationContext` 发布的只读导航快照和 `PathTraversalProfile`。worker 不读取 Unity 对象、Friflo Store 或可变 `SubWorldGrid`。
- Runtime terrain 变化统一经过 `SubWorldRuntime.SetTile`：修改 Grid、发布新的 copy-on-write 导航快照，并递增 Map/Navigation Revision。

#### 八向异步搜索

小世界搜索使用共享生成器的请求级规则：

- 标准地面单位使用八向邻接，`block == true` 是硬阻挡；斜向移动的两个侧邻格必须都可通行，禁止穿墙角。
- 小世界禁用 Portal 和主世界 Region Corridor，不允许跨世界路线，也不做自动传送或忽略阻挡。
- 单次最多展开 `Width * Height` 个节点；open set 按 `f`、`h`、tile index 稳定排序，启发式使用按导航快照最大 `walk_multiplier` 归一的 octile distance。
- terrain `walk_multiplier` 同时进入规划成本和实际移动速度。
- 移动实体不参与通行判定，允许多个单位停留或穿过同一格；terrain 是当前唯一的通行依据。执行每一步前仍再次验证相邻关系、terrain flags 和 Navigation Revision。
- 小世界失败不进入主世界的计时重试。Runtime 在后续 local tick 根据 `SubWorldMovement` 中保留的目标重算过期或被阻挡的路径。

异步 worker 的完成时机不是逻辑确定性输入。同一不可变导航快照、起终点和 traversal profile 必须产生相同 tile index 序列；结果在哪个 local tick 变为 ready 不作确定性承诺。暂停时不会消费结果或修改 Position。

#### 固定 tick 移动

Runtime 已注册 `SubWorldMovementSystem`，并使用：

```text
SubWorldMovement
  配置：MoveSpeedTilesPerSecond
  路径位置：CurrentTileIndex
  目标：TargetTileIndex
  路径：PathHandle / NextTileIndex / PlannedTileFlags
        NavigationRevision
```

`SubWorldMovementSystem` 直接查询 `Position + SubWorldMovement`，不存在额外 mover 列表或注册标记。二者是移动实体从创建到回收始终存在的终身组件，固定 tick 只修改组件字段，不增删组件或改变 archetype。当前阶段只在 Runtime 销毁时先 `CancelWorld` 再统一删除实体；后续单实体死亡或退出必须经过专用回收系统，按“取消外部路径资源 -> 清理业务状态 -> 最终删除实体”执行，不能从任意调用点直接 `DeleteEntity`。

移动组件不复制异步状态枚举：`TargetTileIndex < 0` 表示无意图；有目标但 handle 无效时提交或重算；handle 有效且没有 `NextTileIndex` 时轮询 `PathFinder`；存在下一步时推进位置。请求的 Waiting/Ready/Completed/Failed/Cancelled 状态只以实时 `PathPollKind` 为准。
每个完整 local tick：

1. 以 latest-wins 语义消费已验证的 `MoveToTileCommand`，取消旧 handle 并提交纯数据请求。
2. 只在固定 tick 中轮询和消费 ready stream；渲染帧、相机和 WorldView 不推进路径。
3. 按 `MoveSpeed * terrain.walk_multiplier * fixedDelta` 推进局部连续 Position；到达格中心后更新 `CurrentTileIndex`，不声明格子所有权。
4. 路径版本过期、terrain flags 改变或出现非法斜步时退回当前路径格，下一 local tick 重算。
5. 无路径时结束当前移动意图；抵达目标时完成当前意图。后续 AI 自己保留行动目标，并根据 `TargetTileIndex` 和 `CurrentTileIndex` 判断移动是否仍在进行以及最终结果，不通过临时事件转发。
6. Debug 路径序列不作为 ECS 组件或 Runtime 持久状态。

WorldView 直接读取固定 tick 提交后的 `Position`，不维护额外运动快照，也不回写逻辑状态；画面位置随固定 tick 离散更新。Runtime 销毁时先按 `PathWorldKey` 取消 queued/searching/ready 会话，再删除 ECS 和导航状态。

#### Debug 验收入口

`32x32 TestSubWorld` 使用中央纵墙和上下两个单格通道，覆盖八向绕路与禁止斜穿墙角。右键只提交目标格，不附加风险倍率或 Debug 路径数据；确定性序列在共享 PathFinder stream 层验证，不向实体附加 Debug trace 组件。

本步验收口径：主世界与多个小世界同时只出现同一组 PathFinder worker；Debug Pawn 能八向绕开 terrain 硬阻挡且不能切墙角；旧 token、旧 Revision 和销毁后结果均不能推进实体；暂停不移动，1x/2x/4x 只改变 local tick 吞吐；相同请求快照得到相同 tile index 序列。

### 步骤 6：建立残破古修道场和机缘节点模型

#### 正式模板

注册：

```text
Cultiway.SubWorld.Template.RuinedDaoGround
Cultiway.SubWorld.Generator.RuinedDaoGround
Cultiway.SubWorld.Visual.RuinedDaoGround
```

地图为 `48x48` 连续开放地貌。首版使用手工地貌与遗构锚点，Seed 只改变局部内容：

| 地貌/遗构 | 地图作用 | Seed 变化 |
| --- | --- | --- |
| 山脚裂隙与残阶 | 入口、撤离点、初始观察范围 | 初始道痕方向 |
| 倾塌外院遗构 | 视觉地标、遮挡和多个自然通路 | 选择 1 个坍塌 mask，但始终保留至少 2 条上行路线 |
| 荒废药圃 | 材料类机缘候选区 | 生长点、品质和显露度 |
| 断裂阵带 | 可穿越的持续危险区 | 强度、覆盖 tile 和阵眼位置 |
| 山腰废殿 | 残碑、尸骸或器物线索锚点 | 启用的调查点与线索类型 |
| 高处道台 | 悟道类机缘候选区 | 道痕相性与收益 |

所有区域属于同一连续地图，没有内部房间容器。自然高地、林地、废墙和残阵可以形成路线差异，但 Generator 验证入口到每个候选区至少存在一条不穿不可通行 tile 的路径。

#### 遗构、线索与机缘

Bootstrap 创建强类型实体：

```text
RuinLandmarkState
  LandmarkId / Kind / TileIndex
  Unobserved | Observed | Investigated

RuinClueSource
  ClueId / SourceLandmarkId
  TargetOpportunityId
  Bearing / DistanceBand / Confidence

RuinHazardField
  HazardId / TileIndices[] / Intensity
  Active | Stabilized

RuinOpportunityState
  OpportunityId / Kind / AnchorTileIndex
  Unrevealed | Clued | Exposed | ClaimedPendingSettlement | Exhausted
  ClaimParticipantId?

RuinSiteProgress
  TotalOpportunities / ExhaustedCount
```

首批三个独立机缘：

1. **残碑悟痕**：调查倾塌外院的一块残碑后显露；成功感悟产生灵气/悟道类 Outcome，并可能给出道台线索。
2. **荒圃遗株**：通过灵气异常或直接观察显露；采集后产生一个 Ingredient reward value。
3. **破损道台**：通过残碑或阵眼线索更容易定位；调查产生第二个悟道类 Outcome。

三个节点都不是全局“核心”。任一节点 Exhausted 不会自动改变其他节点或要求参与者立刻返回。

`RuinClueSource` 只给方向、距离档和可信度，不给精确 tile。AI 必须到目标范围内实际观察；玩家视图也不显示隐藏节点坐标。

#### Seed 规则

同一 Seed 必须确定：坍塌 mask、危险场强度、候选锚点选择、线索指向误差、收益数值和视觉变体。Generator 在生成调用内部使用局部的生成随机输入或稳定哈希，并把完整结果物化到场景；不把通用 RNG 安装到 Runtime。后续玩法需要随机时，由具体命令或业务组件显式携带 roll、seed 或自身状态。

本步验收：至少 10 个固定 Seed 都保留开放多路径，三个机缘彼此独立；同 Seed 的 MapData、遗构、线索和收益签名一致。

### 步骤 7：实现单 Actor Projection、感知与线索调查

#### Binding 与入场

新增 `SubWorldExpeditionService`。`RuinSiteService` 请求进入时，同一主线程调用：

1. 校验 Site、Runtime、Entry、Actor 存活且未被其他 Binding 占用。
2. 捕获最小 `RuinProjectionSnapshot`。
3. 登记 `SourceActorId -> InstanceId/ProjectionEntityId`。
4. 在 Runtime Store 创建 Projection 并放置到入口合法空格。
5. 启用主世界 Actor 的统一远征门禁和隐藏表现。
6. 调用返回前把参与者设置为 Exploring。

`RuinProjectionSnapshot` 只包含：

```text
SourceActorId
DisplayName / ActorAssetId / VisualVariant
MoveSpeed / PerceptionRange
CurrentHealth / MaxHealth
CurrentWakan / MaxWakan
ExplorationRiskPreference
DesiredGainThreshold
```

主世界 Actor 留在原 manager。Binding 期间，原版和 Cultiway 的 AI、移动、攻击、受伤、修炼、恢复与 Render 入口统一查询会话内索引。入场失败时删除 Projection、移除 Binding 并恢复表现；一个 Actor 同时只能绑定一个 Runtime。

#### 参与者知识

每个 Projection/队伍拥有自己的 `RuinKnowledgeState`：

```text
ObservedTiles
ObservedLandmarkIds
KnownHazardTiles
KnownOpportunityIds
Clues[]
FailedInvestigationAnchors[]
```

物理状态属于 Runtime，知识属于参与者。后续队伍进入时会看到已经稳定的残阵和已经耗尽的节点，但不会自动继承上一队未公开的精确地图记忆。

感知每 tick 只处理视野范围变化后的边缘格：

- terrain/遗构阻挡视线。
- 显著地标比普通格拥有更远观察距离。
- 灵气/道痕感知可以在视线外产生低精度 Clue，但不能直接 Expose 节点。
- 相机和玩家是否看到该区域不写入 KnownTiles。

#### 自主调查 AI

`RuinExplorerState` 保存 CurrentMode、Target、LastDecisionTick 和已持有 Outcomes。AI 决策：

1. 当前生命低于撤离阈值，或已取得价值达到 DesiredGainThreshold：Return。
2. 邻接可调查遗构/机缘：Investigate 或 Claim。
3. 对每个 Exposed 机缘计算 `预期收益 - 路程 - 已知危险 * 风险权重`，选择最高正值。
4. 没有 Exposed 机缘时选择最高可信 Clue，前往其方向与距离范围内的观察点。
5. 没有 Clue 时选择最近的显著未调查遗构或观察边界。
6. 连续调查无结果、所有候选效用非正或无安全返程时返回。

路径规划只接收 AI 选出的观察点，不接收隐藏 Opportunity tile。玩家点击 Projection 只能聚焦和查看 ReadModel。

本步验收：真实 Actor 入场后主世界本体不推进；不同风险偏好的两个测试 Snapshot 对相同 Seed 选择不同路线/返程时机；相机在外时决策签名不变。

### 步骤 8：实现风险取舍、部分收获与同步返回

#### 调查与危险

- Landmark 邻接调查持续若干 tick，完成后进入 Investigated，并按配置产生 Clue、Expose 机缘或稳定危险场。
- 首版断裂阵带每个停留 tick 造成固定生命损失；未知时不会进入寻路成本，首次接触后加入 KnownHazards。
- 调查阵眼可把整个 HazardField 改为 Stabilized，后续参与者继承。
- 危险伤害最低保留 1 点生命，不调用临时死亡。
- Opportunity 领取使用 `ClaimOpportunityCommand` 原子提交；成功后记录 ParticipantId 并进入 ClaimedPendingSettlement。
- 同一参与者可以持有多个 claim，也可以取得一个后主动返回。

#### 首批 Outcome

```text
RuinOutcomeValue
  OutcomeId
  OpportunityId
  SourceSiteId
  EstimatedValue

RuinInsightOutcome
  WakanDelta
  QiyunDelta

RuinIngredientOutcome
  RuinLootId
  IngredientShapeId
  CreatedTimeValue
  NameSeed
  PowerValue
```

`RuinInsightOutcome` 只在返回时应用主世界资源，不创建物品。`RuinIngredientOutcome` 在 Runtime 中是 typed 值，不是主世界 SpecialItem Entity；首版退出时调用现有 Ingredient/SpecialItem 构建入口在主世界 Store 物化。

首版不在 SubWorld Store 创建 SpecialItem，因此不需要提前重构 `SpecialItemUtils`。阶段 4 出现真实地面物品和多类型 loot 时再建立显式目标 Store factory。

#### 返回事务

AI 到达入口后先由 Runtime 发布 `RuinExitReadyEvent`，随后走 Prepare + 同步原子 Commit：

1. `SubWorldExpeditionService` 提交 `PrepareSettlementCommand(ParticipantId, Revision)`。
2. Runtime 在 tick 边界校验参与者、Outcome/claim owner 与 Revision，把 Projection 和 claims 改为 Settling，并发布 `SettlementPreparedEvent(Token, Snapshot)`。
3. 服务完成预检后，只把 `SourceActorId/HolderId`、typed Outcome、仅含标量/不可变 typed value 的 ActorOldValues、`MaterializerKey` 与纯数据参数写入 `SettlementStagingRegistry`。Record 禁止保存 Actor、Entity、Store、holder adapter、delegate、handler 或 Unity 对象，也不参与 holder、UI 或存档枚举。
4. 服务提交 `CommitSettlementCommand(Token, StagingId)`。Runtime 预校验 Token、owner、Revision 和所有待写状态后，在当前 tick 进入不可重入主线程提交段。
5. `ISubWorldSettlementCommitPort.TryPromote(StagingId)` 在该调用内创建/验证 Ingredient、绑定 holder、应用 Insight/生命/灵气并返回可逆 Receipt；Runtime 随后以无分配、无外部回调的代码把对应 Opportunity 改为 Exhausted、更新 ledger、销毁 Projection。
6. MainWorld promote 或 Runtime 最终提交任一步失败时，port 在退出提交段前按 Receipt 删除新物品、恢复 Actor 旧值，Runtime 同步回到 Prepared；服务随后提交 Rollback 或重试，外界看不到半成品。
7. 两边成功后 Runtime 发布 `SettlementCommittedEvent`；服务移除 Binding/StagingRecord，Site 摘要从事件派生，仍有机缘时 Open，全部耗尽时 Exhausted。

保存、入口删除、`clearWorld`、Mod 重载和普通事件派发不能插入步骤 5；只能在 Commit 前删除 StagingRecord 并 Rollback，或在完整 Commit 后观察正式结果。服务不能直接修改 Opportunity、Projection 或 Runtime ledger。Settling 期间 Projection 不移动、不受伤、不重复退出；无收获撤离使用同一协议但 Snapshot 不含 Outcome。

本步验收：第一个低 DesiredGainThreshold 的修士取得一个机缘后返回；第二个修士进入同一 Runtime，看到第一个节点 Exhausted、已稳定/触发的危险场，但仍能找到另外两个节点；三个节点全部结算前 Site 始终 Open。

### 步骤 9：实现最小 RuinPowerSiteProvider 并完成验收

#### 最小正式合同

本阶段直接实现可继续扩展的具体 `RuinPowerSiteProvider`，不做临时 Debug 接线，也不在只有一个 Provider 时先抽 `IRuinSiteProvider`。最小 `RuinSiteDescriptor` 是创建输入，只包含：

```text
SiteId / RuinContentId / Seed
MainWorldAnchor / EntranceBuildingId
```

创建成功后，`RuinSiteService` 自有的 `RuinSiteRecord` 才保存 `InstanceId / State / Revision`；Descriptor 不在创建后反向变成可写进度对象。`RuinSiteService.CreateSite(descriptor)`、`RequestAdmission(siteId, sourceActorId)`、`GetSiteSummary(siteId)` 和 `DestroySite(siteId, reason)` 是正式用途边界。阶段 5 在第二个 Provider 和组队需求实际出现后扩展 Descriptor/Admission，并从两个具体实现中提取 Provider 接口；不得重写阶段 1 的 Site/Runtime 所有权。

#### 神力入口

在 WORLD 神力分区注册非 Debug 的“残破古修道场”投放按钮：

1. 玩家点击主世界合法陆地格。
2. 创建 `Cultiway.Ruin.RuinedDaoGroundEntrance` Building。
3. `RuinSiteService` 分配当前会话 `RuinSiteId`，立即创建并绑定一个 Runtime。
4. Site 进入 Open，导航栏出现实例入口。
5. Provider 只支持 Discovered 和单 Actor Admission；本阶段只验收一个活动 Site，但所有 API 仍以 SiteId 定位，不写全局单例。主世界 AI 在附近 Actor 中按“可进入、未 Binding、路径可达、距离、稳定 Actor ID”选择候选并前往入口。
6. Actor 到达后通过正式 `RequestAdmission` 调用步骤 7 的入场边界。

开发自动创建 TestSubWorld 不进入正式流程。Debug 下保留测试地图、右键移动、固定 Snapshot 和故障注入。

#### 端到端验收

至少完成以下连续会话：

```text
投放古修道场
-> 第一名修士进入
-> 观察地貌/调查残碑
-> 沿线索或自行发现一个机缘
-> 因收益阈值主动返回
-> 主世界结算部分所得
-> 第二名修士进入同一 Runtime
-> 继承物理变化并取得剩余机缘
-> 全部节点耗尽后 Site 才进入 Exhausted
-> 销毁/清理
```

另外验证：

- 不存在必须按固定顺序经过的区域；至少两个机缘有两条以上可行接近路线。
- AI 的目标选择没有读取隐藏 Opportunity tile；日志可记录决策输入供 Debug 核对，但正式 UI 不显示评分数字。
- 主世界与小世界倍速互不覆盖；相机始终看着、始终离开和中途切换时结果一致。
- 入场失败、Staging 校验失败、Outcome 第 N 个物化失败、Runtime 最终提交失败和 Source Actor 失效都不会留下半个 Binding、StagingRecord、Receipt、待确认 Entity 或半份奖励。
- 删除入口时，内部参与者走 Aborted 清理；未进入 Actor 取消前往。
- 分别在 Prepare 前、Prepared 后和 Commit 返回后触发保存/`MapBox.clearWorld`；清理后 Manager、Site、Binding、StagingRecord、PromotionReceipt、待确认 Entity、WorldView、Slot、Clue 和 claim 数量均为零。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
