# 第4阶段-战斗物品与目标

本阶段让 SubWorld 复用现有 SkillLibV3、Core Combat 和 PortableItem 领域能力，形成完整远征风险：单位可以战斗、施展同一份技能定义、真实使用与损坏物品、死亡，并通过具体目标决定队伍与实例结果。`SubWorldManager` 管理当前游戏会话内常驻的 `SubWorldRuntime`；战斗、物品、目标、Winner 和死亡过程都直接属于 Runtime ECS。真实 Actor 始终留在 MainWorld，并由 `ExpeditionBinding` 隔离。退出或终局时，Manager 在同一主线程调用内同步卸载对应 SubWorld 物化，把 typed 值和结果应用到 MainWorld；任一步失败都立即恢复调用前状态。世界差异只存在于查询、碰撞、状态应用、时间和视觉 adapter，不建立平行技能或战斗系统。

## 具体说明

### 设计边界

- 全项目只有一份 `CompiledSkillDefinition`、一套技能 capability 声明和一个 `DamageResolver`；MainWorld 与 SubWorld 不各自维护技能语义或伤害公式。
- 删除规划中的 `SubWorldAbilityDescriptor`、`SubWorldAbilityCompiler`、`SubWorldSkillEffectAdapterRegistry`、独立 `SubWorldCombatService` 以及所有 `PayloadKind/Payload`。
- `SkillBlueprint` 只编译一次。MainWorld adapter 可把定义包装为现有 ECS `SkillContainer`，SubWorld adapter 直接执行同一不可变定义。
- 轨迹、几何、目标选择、relation/trigger/outcome、战术评分和伤害阶段是共享纯数据/计算；world query、碰撞、状态提交和 VFX 才由 adapter 实现。
- adapter 未提供定义声明的 capability 时，该技能明确不可执行，不生成近似技能；capability 来自共享 catalog，不按世界维护第二套 effect registry。
- `SubWorldManager` 是 Runtime 集合和 `ExpeditionBinding` 索引的唯一所有者；Runtime 从创建成功到退出或终局同步卸载成功始终常驻内存。
- 战斗组件、技能运行态、PortableItem Entity、Objective 进度、Winner 和死亡状态都存在所属 Runtime ECS 中，不在 Runtime 之外维护另一份实例结果状态。
- 真实 Actor 始终属于 MainWorld ActorManager。远征期间 `ExpeditionBinding` 与 `TagExpeditionSequestered` 阻止其渲染、AI、移动、战斗、资源和状态推进；Projection 不能反查并修改 Actor。
- SubWorld 战斗只操作 Projection/SubWorldEntity，不调用 `MapBox.checkAttackFor()`；MainWorld 仍保持现有 Actor、Building、ECS 和原版回调入口。
- 物品沿用第二、三阶段 PortableItem typed snapshot、Stable ItemId、transfer adapter 和 `SubWorldItemState`。入场后物品只在 Runtime Store 中物化并被真实使用、消耗、损坏、转交、掉落或拾取；两个世界不共享 ECS Entity，也不重新定义物品 payload。
- 魔法卷轴与符箓是两个独立顶层载体类型；二者只共享嵌套 `StoredSkillPayloadSnapshot`，载体资格和强度换算由共享 portable item handler 处理。
- 战斗 tick 只修改 Runtime ECS。退出单个参与者时只卸载其 Projection 与所属物品；实例终局时卸载整个 Runtime。两种情况都由 `SubWorldManager` 在同一主线程调用内把 typed 值、Objective 结果和 Winner 应用到 MainWorld。
- MainWorld/SubWorld 物品转移始终在同一主线程调用内完成，不保留跨帧中间状态。应用失败时立即撤销本次 MainWorld 修改，并从调用内 typed 值恢复 SubWorld 物化与 Binding。
- 多队伍是否敌对由 Runtime FactionPolicy 决定，不能从 Sect 不同推导自动敌对。
- 非模态浮窗不暂停战斗；主/子世界独立时钟分别通过各自 `ITimeSource` 提供时间。

### 步骤 1：建立共享战斗状态与阵营结构

#### 阵营

```text
SubWorldFactionState
  FactionId
  SourceKind
  SourceId
  Relations[]
```

关系为 Friendly、Neutral、Competitive、Hostile。Competitive 允许争夺目标和阻挡交互，但不允许伤害；Hostile 才进入攻击候选。

消费系统在创建队伍时把关系交给 Runtime。主世界 Kingdom 战争变化可以通过显式 `IssueCommand` 更新，但 Runtime 不每 tick 查询 `World.world`。

#### Projection 战斗状态

```text
ProjectionCombatState
ProjectionResources
ProjectionFaction
ProjectionSkillLoadout
ProjectionCooldowns
ProjectionActionState
ProjectionStatusSet
```

这些组件是共享 `CombatSnapshot` 在 SubWorld Runtime 中的直接表示，不是第二套战斗规则。所有数值来自入场 Baseline 或 Template 实体定义；战斗中不读取主世界 Actor.stats 缓存。`ProjectionSkillLoadout` 只持有 `CompiledSkillDefinition` 的稳定 ID/签名和个体等级、冷却、资源状态，不复制另一份能力描述。

#### 行动

行动状态：

```text
Idle -> Preparing -> Executing -> Recovering -> Idle
                         ↘ Interrupted
```

移动、攻击、技能、交互、制造和拾取共用一个主行动占用，避免同一 Projection 同 tick 同时炼制、攻击和开箱。行动准备、执行、恢复时间统一读取所属世界 `ITimeSource`；浮窗是否可见不是行动状态。

### 步骤 2：建立唯一 CompiledSkillDefinition 与运行端口

#### 共享编译产物

`CompiledSkillDefinition` 是 SkillBlueprint 的唯一运行定义：

```text
DefinitionId
BlueprintId/Revision/Signature
CastProfile
ResourceCosts[]
TrajectoryDefinition
GeometryDefinition
TargetDefinition
EffectDefinitions[]
DamageDefinitions[]
TacticalProfile
RequiredCapabilities[]
VisualCues[]
```

定义只包含稳定 ID、枚举和数值结构，不持有 Friflo Entity、`SkillContainer`、Actor、BaseSimObject、WorldTile、Unity Object 或世界委托。现有 `SkillBlueprintCompiler` 调整为：

```text
SkillBlueprint
  -> Validate
  -> CompileDefinition
  -> CompiledSkillDefinition
       -> MainWorldSkillContainerAdapter.Materialize() -> ECS SkillContainer
       -> SharedSkillExecutor.Execute()                 -> world ports
```

MainWorld 编辑器预览、运行时施法和 SubWorld 都从 `ISkillDefinitionRegistry` 解析同一 DefinitionId/Signature。MainWorld 的 `SkillContainer` 是定义的 ECS 包装和运行状态载体，不再是另一份技能语义；SubWorld 不 materialize 主世界 ECS Entity。

基础近战、远程武器攻击也注册为共享 CompiledSkillDefinition，由装备/基础战斗数据参数化，不在 SubWorld 内硬编码 BasicAttack 公式。

#### 共享端口

`ISkillExecutionPorts` 是执行器接收的聚合结构，只组合以下细分端口，不增加领域规则：

```text
ISkillExecutionPorts
  WorldQuery: ISkillWorldQuery
  CombatState: ICombatStatePort
  CombatCommit: ICombatCommitPort
  Runtime: ISkillRuntimePort
  Random: IRandomSource
  Time: ITimeSource
  Visual: IVisualSink
```

| 端口 | 共享执行器需要的能力 | MainWorld adapter | SubWorld adapter |
| --- | --- | --- | --- |
| `ISkillDefinitionRegistry` | 按稳定 ID/签名读取定义 | 现有 SkillLibV3 library 包装 | 同一 registry，只持有引用 |
| `ISkillWorldQuery` | relation、目标、范围、几何、射线、碰撞和 tile/building 查询 | Actor/Building/WorldTile 查询 | Grid、Projection、SubWorldEntity 查询 |
| `ICombatStatePort` | 读取 caster/target 的 `CombatSnapshot`、资源、状态和冷却 | ActorExtend/ECS snapshot | Projection 组件 snapshot |
| `ICombatCommitPort` | 原子应用 Damage/Status/Shield/Force/Death 等 commands | 现有事件、ECS 与 Actor API | Projection Store command buffer |
| `ISkillRuntimePort` | 施法序列、轨迹实例、命中记忆、周期效果和冷却运行态 | 现有 SkillLibV3 systems | SubWorld 固定 tick runtime |
| `IRandomSource` | 命中、目标抽样、反应等稳定随机序列 | MainWorld 随机 adapter | Runtime Random adapter |
| `ITimeSource` | 当前时间、fixed elapsed、冷却和持续时间 | 主世界时钟 | SubWorld 独立 LocalTime |
| `IVisualSink` | 消费共享 VisualCue，不产生玩法副作用 | SkillWorldVisualService adapter | 浮窗 RenderTexture/VFX adapter |

`SharedSkillExecutor` 只依赖以上端口。逻辑结果先应用，`IVisualSink` 后消费 VisualCue；VFX 缺失不能改变命中、状态或资源结果。

#### capability

轨迹、目标类型和效果在共享 capability catalog 中声明，首批使用 `TargetEntity`、`TargetTile`、`ResourceCost`、`InstantTrajectory`、`LinearProjectile`、`EntityCollision`、`TileCollision`、`Damage`、`Heal`、`ApplyStatus`、`Displacement`、`SpawnExecution` 和 `VisualCue`。编译器把实际需要的原子 capability 写入 `RequiredCapabilities`，adapter 只声明自己实现了哪些共享 capability；Melee、Ranged、Area、Chain 等是由这些能力组成的测试与展示类别，不进入另一套执行分支。

capability 缺失时 registry 返回明确的不可执行诊断，定义本身仍保持同一签名。禁止建立 `SubWorldSkillEffectAdapterRegistry` 或按 Effect 类型复制第二份执行器。

### 步骤 3：抽取 SkillLibV3 与 Core Combat 纯数据计算

#### SkillLibV3 共享核心

从现有 SkillLibV3 中抽取并保留一份世界无关表示与算法：

- `SkillTrajectoryDomain`、Trajectory/Motion/Impact profile 转为稳定轨迹参数和逐 tick 运动计算；生成对象与碰撞查询走 `ISkillRuntimePort/ISkillWorldQuery`。
- 射线、圆、扇形、链式跳转、接触体和落点等几何只计算 value type 和稳定 ObjectId/TileId，不枚举 Actor、Building 或 Projection 实例。
- TargetMode、`SkillEffectTargetRelation`、`SkillEffectTrigger`、`SkillEffectOutcomeFlags` 保留为共享结构；relation 判断所需阵营数据由 query port 提供。
- 现有 Effect descriptor/pipeline 去除 `BaseSimObject`、`WorldTile`、`ActorExtend`、ECS Entity 委托，改为输入 snapshot、输出 effect commands 和 outcome。
- `SkillContainerEvaluator`、施法成本、预期目标数和 modifier 贡献改为对 CompiledSkillDefinition 的纯计算，MainWorld UI 与 SubWorld AI 使用同一结果。

共享计算不引用 Unity 随机、主世界单例或 SubWorld Store。所有集合在抽样前按稳定 ID 排序，随机值只从 `IRandomSource` 获取。

#### Core Combat 共享核心

从 `Source/Core/Combat/Tactical` 抽取候选动作、威胁、距离、资源、效果收益、风险、保护与 Objective 倾向等纯数据评分。MainWorld adapter 提供 Actor/Building 候选，SubWorld adapter 只提供 VisionGroup 当前可见的 Projection/SubWorldEntity 候选；两边调用同一 candidate builder 和 scorer。

世界层保留的职责仅有：

- 枚举当前世界实际对象和 tile。
- 路径请求、碰撞 broad phase 与对象生命周期。
- 将共享 commands 应用到 Actor/ECS 或 Projection Store。
- 把共享 VisualCue 映射到所在世界坐标与 VFX。

不得在 `Source/Core/SubWorlds/Skills/` 或 `Source/Core/SubWorlds/Combat/` 下复制 trajectory、effect、resolver 或 tactical scorer。

### 步骤 4：抽取共享 DamageResolver 并保持主世界时序

#### 结构

```text
DamageResolver.Resolve(DamageRequest, CombatSnapshot)
  -> DamageResolution
       PhaseValues
       FinalDamage
       IneffectiveHit
       Commands[]
```

`DamageRequest` 持有 Source/Target stable ID、RawDamage、ElementComposition、AttackType、DamageOrigin、power override 与 IgnoreDamageReduction。`CombatSnapshot` 持有本次结算观察到的存活/无敌、攻防 power level、元素抗性、状态、护盾、生存/反应规则、阶段修正和由 `IRandomSource` 预取的稳定随机样本。

`DamageResolution` 不直接修改世界对象。它给出每阶段数值、最终伤害、无效命中结果，以及按顺序应用的记录、状态、护盾、生存、反应、击杀和 VisualCue commands。

#### 阶段顺序

Resolver 必须按当前 `ActorExtend.GetHit` 的顺序固化阶段，不能借重构调整主世界时序：

1. 自伤、存活与无敌门禁，并记录 attack attempt。
2. `action_before_be_attacked` 对伤害、元素、AttackType 和忽略减伤的前置修正。
3. 攻防 power level、跨级压制和 minimum damage 资格。
4. 元素组成抗性与通用减伤。
5. 第一次 minimum damage。
6. ineffective hit 概率、固定 RNG 抽样和无效命中 reaction。
7. 实际受伤前的 `action_on_be_attacked`。
8. 原版 `checkSpecialAttackLogic` 上限及第二次 minimum damage。
9. `ApplyFinalDamageActions`、护盾、生存与共享 reaction commands。
10. damage outcome/OnDamageResolved，再进入最终生命、受击、死亡与击杀应用。

MainWorldDamageAdapter 保留现有 hook 和原版 special logic 的阶段位置，在当前 `ActorExtend.GetHit` 入口构造 snapshot、应用 resolution commands，最后仍且只调用一次原版 `Actor.getHit` 尾部，使用现有 `pCheckDamageReduction: false`，不能提前进入、重复减伤或改变事件顺序。

SubWorldDamageAdapter 从 Projection 构造同一 CombatSnapshot，经 `ICombatCommitPort` 把同一领域 commands 应用到 Projection 状态，不调用 Actor API。两种 adapter 的 world-only commands 可以不同，但 DamageResolution、共享状态/反应/击杀 commands 在同输入与随机样本下必须一致。

### 步骤 5：用共享定义实现行动与战术决策

#### 感知与候选

SubWorld AI 只通过 `ISkillWorldQuery` 观察当前 VisionGroup 已见对象和本地事件：

- 最近敌对单位、可保护单位与建筑。
- 当前目标距离、共享几何结果和本地路径成本。
- 自身生命、资源、状态、冷却和主行动占用。
- 附近盟友、危险 tile、可用物品、工作台和 Objective。
- CompiledSkillDefinition 的共享 TacticalProfile 和 evaluation。

不读取迷雾后的敌人、主世界 Actor 或消费系统隐藏评分。MainWorld 与 SubWorld adapter 生成相同 `TacticalSnapshot` 后，候选过滤、评分、稳定 tie-break 和动作选择必须一致。

#### 决策与执行

每个 AI 决策周期：

1. 选择必须响应的威胁、盟友或 Objective。
2. 由共享 candidate builder 生成移动、基础攻击、技能、物品、交互和制造候选。
3. 由共享 scorer 按距离、资源、效果、风险与战术目标评分。
4. 按稳定 ObjectId/DefinitionId 打破同分，冻结一个 Action Command。
5. 在所属世界固定 tick 执行准备、轨迹、命中和恢复。

浮窗 Visible 与 Background 运行相同 executor、端口顺序和 AI 周期。View 只插值位置和播放已经产生的 VisualCue/CombatEvent；主世界同时按自己的时钟继续 AI 和战斗。

### 步骤 6：实现真实 PortableItem 使用、死亡与同步卸载

#### 使用、掉落与战斗损坏

本阶段不重新定义物品状态。所有物品继续使用第三阶段结构，并直接作为所属 Runtime Store 的 ECS 状态：

```text
SubWorldItemState
  ItemId
  SnapshotKind
  TypedSnapshot
  Location
  State
```

- MainWorld 来源物品已在第二阶段同步入场边界中转移为 Runtime Entity；`ItemId` 保持不变，主世界不同时持有对应 Entity。
- 使用、消耗、耐久损坏、战斗破坏、转交、掉落和拾取通过明确 typed handler 更新 `TypedSnapshot`、Location 与 State，不改写无类型 payload。
- 每个使用命令都在当前 Runtime tick 内检查真实持有关系、资格、行动占用和资源，并立即修改或销毁对应 Item Entity；战斗与 AI 后续观察到的就是修改后的物品状态。
- 地面物品不阻挡移动；拾取需要到达、主行动时间和容量检查。每个 ItemId 同一时刻只允许一个 Location。
- 容器、工作台输出和死亡掉落只移动现有 Runtime Entity；目标完成不自动拾取地面或输出槽物品。

法宝必须使用 `ArtifactInstanceSnapshot`。其器形、atoms、能力、品质、耐久和表现来自第三阶段共享 snapshot；主动能力解析为同一 CompiledSkillDefinition，不建立 SubWorld artifact combat model。

魔法卷轴必须使用 `MagicScrollSnapshot`，符箓必须使用 `TalismanSnapshot`。二者都把嵌套的 `StoredSkillPayloadSnapshot { SkillBlueprint, Signature, Strength, PowerLevel }` 交给共享 `PortableSkillCarrierHandler`：

1. handler 按顶层 typed snapshot 执行对应 carrier 资格检查，不让技能执行器猜载体类型。
2. handler 按 `SkillBlueprint/Signature` 从 `ISkillDefinitionRegistry` 解析唯一 `CompiledSkillDefinition`；快照不持有 `SkillContainer` Entity 或 compiled definition 副本。
3. handler 按载体规则换算本次执行强度。魔法卷轴保留其存储强度、PowerLevel 与现有魔法资格；符箓保留仙道资格，并以实际使用者力量执行现有换算。
4. 魔法卷轴继续支持现有学习/施放分支并受快照寿命约束；学习时由所在世界 skill adapter 从同一 definition 建立角色运行态，施放时进入 `SharedSkillExecutor`。
5. 符箓只执行一次性施放，逻辑结果应用后消费对应 Runtime 物品；不把符箓解释成可学习卷轴。

载体 handler 返回更新后的 typed snapshot、技能授予或施放 command、物品消费 command；不增加统一 `UseCount`。卷轴学习/施放与符箓施放共享 `CompiledSkillDefinition` 和执行器，但资格、强度换算、寿命及消费语义不会进入技能定义本身。

#### 会话内状态与退出局部值

战斗、物品使用、Objective 进度、Winner 和死亡结果在运行期间只写入 Runtime ECS。退出或终局调用开始后，`SubWorldManager` 直接从被冻结的组件读取以下调用内局部值，不把它们登记为另一份 Runtime 状态：

```text
ActorReturnValues
  ResourceValues[]
  PermanentStatValues[]
  TraitChanges[]
  SkillChanges[]
  QiyunValue
  DeathOutcome?
PortableItemTransferValue[]
ObjectiveResultValue[]
WinnerResultValue?
```

`PortableItemTransferValue` 包含 Stable ItemId、来源、最终 typed snapshot、最终 MainWorld Holder 和 Disposition，不持有 Runtime Entity。卸载时明确区分三类：

- `Existing`：从 MainWorld 带入且仍存活，按最终 snapshot 在 MainWorld Store 物化同一 ItemId。
- `New`：SubWorld 战利品或制造产物，按同一 transfer adapter 在 MainWorld Store 物化其 ItemId。
- `ConsumedOrDestroyed`：已消费或销毁，不在 MainWorld Store 创建 Entity。

所有新战利品和四类制造产物都先在 Runtime Store 中建立 ItemId、typed snapshot、Entity 与 Location，经过真实拾取和持有关系后才能进入 `PortableItemTransferValue`；不能从奖励表或工序结果直接创建 MainWorld Entity。

#### 同步卸载、应用与回滚

`SubWorldManager` 在退出 tick 或终局 tick 结束后执行一个不可插入其他模拟的主线程调用。单人退出的处理范围是该 Participant、Projection 及其所属物品；实例终局的处理范围是整个 Runtime：

1. 冻结处理范围内的 Projection、item、Objective 与 Winner 组件，不再接受相关 command；从 Runtime ECS 读取最终 typed 值和结果，同时保存本次调用会改动的 MainWorld Actor 值、物品关系和结果值。
2. 解析 Source Actor、MainWorld 目标 Store、最终 Holder、全部 transfer adapter 和结果消费入口；检查阶段不修改任一 Store。
3. 卸载处理范围内的 SubWorld 物化：Capture 物品最终 typed snapshot 后销毁 Existing 与 New 对应的 Item Entity，移除其 Location，并移除本次退出的 Projection 运行组件。终局时同时卸载剩余 Objective、Winner 和实例 Entity。
4. 对 Existing 与 New 调用原 `IPortableItemTransferAdapter.Materialize(targetStore, snapshot, factory)`，创建同一 ItemId 的 MainWorld Entity 并绑定最终 Holder；ConsumedOrDestroyed 不物化。
5. 对存活 Actor 应用资源、伤势、trait、技能与 Qiyun typed 值，并把已完成的 Objective 结果与 Winner 应用到 MainWorld 消费系统；需要带出但无 Actor Holder 的物品按入口容器或明确丢弃规则处理。
6. 对死亡 Projection 应用 `DeathOutcome`。正式死亡始终是玩法结果应用的最后一步。
7. 全部应用成功后才删除 Participant，移除 `ExpeditionBinding` 与隔离 Tag，重新启用存活 Actor 的主世界渲染和 AI；终局时再由 Manager 从常驻集合移除并销毁 Runtime。

步骤 3 至 7 在同一次调用内完成，期间 MainWorld 与 SubWorld 都不推进 tick。任一步失败时，Manager 立即删除本次创建的 MainWorld Item Entity，恢复 Actor、物品关系和结果值，再用步骤 1 捕获的 typed 值重新物化已卸载的 SubWorld Entity 与组件；Runtime 回到冻结前状态，`ExpeditionBinding` 保持有效，本次调用返回失败。只有成功调用才发布退出或终局结果。方法结束后每个 Stable ItemId 只属于一个 Store。

#### 死亡

Projection 死亡先进入 Terminal，不立即调用主世界 Actor：

- 共享 DamageResolver 产生 survival、reaction、death 和 kill commands；SubWorld adapter 先应用 Projection 状态与物品掉落，再由 Objective 系统读取该 tick 的最终存活和物品状态。
- `DeathOutcome` 作为 Projection 的 Runtime 终态组件，持有死亡原因、DefinitionId、来源 Participant/Entity stable ID、地点和最终 CombatSnapshot 摘要。
- 同步卸载时先处理 portable item 和其他 MainWorld 结果，再进入本次调用的 `ExpeditionReturnContext` 解除死亡门禁。
- 设置主 Actor 致死状态并调用正式 `checkDeath()`；Context 标记 LootAlreadyResolved，避免 `newKillAction` 再复制一次物品。
- 无对应主世界攻击者时仍走正式死亡回调，但攻击者为空；日志使用 SubWorld 的来源快照。

### 步骤 7：实现多队伍目标与 Runtime Winner

扩展 Objective Asset：

- `DefeatEntityGroup`
- `ProtectEntity`
- `CollectItem`
- `HoldZone`
- `CompleteInteractionRace`
- `SelectUniqueWinner`
- `EscapeBeforeCollapse`

每个 Asset 在实例创建时物化为 Runtime ECS 状态：

```text
ObjectiveRuntimeState
  ObjectiveId
  ObjectiveAssetId
  Status
  Progress
  Sequence
  Result?
```

Objective system 只读取当前 Runtime 的 Entity、事件和固定 tick 状态，并把进度与完成结果写回组件。视图与消费系统读取这些组件，不持有另一份目标状态。

#### 队伍

Participant 通过 FactionId 和 VisionGroupId 组成队伍。不同队伍可以从不同 Entry 进入同一 Runtime。

#### 竞争

Competitive 队伍可以：

- 分别探索迷雾。
- 争夺一次性容器和机关。
- 对同一禁制贡献进度。
- 抢先占据目标区域。
- 参加唯一结果评估。

不能互相伤害，除非 Faction Relation 明确为 Hostile。

#### Runtime Winner

`SelectUniqueWinnerObjective` 在所属 Runtime tick 内冻结合格 Projection 及其小世界内可观察成绩：

- 到达和发现。
- 机关、战斗和保护贡献。
- 消费系统提供的稳定相性分。
- 当前存活与退出状态。

Winner 直接写入所属 Runtime 的唯一组件：

```text
WinnerRuntimeState
  ObjectiveId
  Status
  WinnerParticipantId?
  SelectedTick
  SourceSequence
```

Objective 只选择一个 ParticipantId，先写入 `WinnerRuntimeState`，再生成 Runtime 内的 `UniqueWinnerSelected` Event。具体奖励含义由消费系统解释，并只在退出或终局同步调用成功时应用到 MainWorld。同 tick 多个候选按事件 Sequence 和稳定 ParticipantId 裁定，不依赖浮窗状态。

每个固定 tick 的顺序固定为：战斗与技能 commands、伤害和生存反应、死亡终态与物品掉落、普通 Objective 评估、Winner 评估、Runtime 事件派发。目标与 Winner 因而读取死亡和掉落后的最终状态；该顺序在 Visible 与 Background 下完全相同。

### 步骤 8：固化主世界并完成跨世界差分验收

先为当前主世界行为建立 golden fixtures，再移动任何 SkillLibV3/Core Combat 逻辑。固定输入 snapshot、目标顺序、时间和 RNG，覆盖：

```text
melee
ranged
area
chain
building
status
shield
survival
reaction
kill
```

每类 fixture 记录 Definition signature、候选目标、轨迹/几何结果、DamageResolution 各阶段值、共享 commands、MainWorld hook/事件顺序和最终 Actor/Building 状态。重构后的 MainWorld adapter 必须逐项与 golden 结果一致，尤其不能改变 `ActorExtend.GetHit` 到原版 `Actor.getHit` 尾部的顺序。

然后使用同一 CompiledSkillDefinition、CombatSnapshot、TacticalSnapshot 和固定 RNG，分别运行 MainWorld fake ports 与 SubWorld ports，差分共享领域结果；只忽略明确列出的 world-only object handle 和 VisualCue 坐标。

最后增加战斗验证 Template：两支队伍从不同入口进入，争夺一个由守卫保护的核心容器，并允许配置 Competitive 或 Hostile 关系。两个同 Seed Runtime 分别持续 Visible 与持续 Background 运行相同 TickIndex，比较定义、RandomState、Projection、状态、物品、死亡和 Objective 签名。

## 验收标准

### 共享技能与主世界回归

- 一个 SkillBlueprint revision 只产生一个 CompiledSkillDefinition signature；MainWorld `SkillContainer` 与 SubWorld loadout 都引用该定义。
- 代码与运行对象中不存在 `SubWorldAbilityDescriptor`、`SubWorldAbilityCompiler`、`SubWorldSkillEffectAdapterRegistry`、独立 `SubWorldCombatService` 或 `PayloadKind/Payload`。
- capability 由共享定义声明；adapter 能力不足时给出明确不可执行结果，不产生近似 effect，也不查询世界专属效果 registry。
- 主世界 melee、ranged、area、chain、building、status、shield、survival、reaction、kill golden fixtures 在重构前后逐项一致。
- MainWorld `action_before_be_attacked`、power suppression、resistance、minimum、ineffective、`action_on_be_attacked`、vanilla special、final actions、reaction/kill 和原版 tail 顺序不变。
- 每次 MainWorld 命中只进入一次原版 `Actor.getHit` 尾部，且不会重复执行原版或共享减伤。

### 跨世界战斗

- 同一 CompiledSkillDefinition、DamageRequest、CombatSnapshot、TacticalSnapshot 和 RNG 序列经两种 adapter 后，共享目标、几何、DamageResolution、effect outcome、战术评分与 commands 一致。
- Competitive 队伍不能互伤，Hostile 队伍能够按 Runtime 关系战斗；relation 由同一共享计算处理。
- SubWorld AI 只使用 VisionGroup 已见目标和已声明 capability 的定义。
- Visible 与 Background 执行相同 TickIndex 时，RandomState、Projection、技能运行态、伤害、status、shield、reaction、kill 和 Objective 结果一致。
- 移动、攻击、技能、制造、交互和拾取不会在同一实体上并发执行。
- MainWorld 与 SubWorld 使用独立 `ITimeSource`；非模态浮窗打开、折叠或切换不会串改冷却、持续时间或战斗结果。

### PortableItem 与同步返回

- MainWorld 来源物品入场后，源 Entity 已解除 holder/装备/工序关系并回收；同一 Stable ItemId 不会同时出现在两个 Store。
- 容器内容在 Runtime 创建时只生成一次。
- 使用、消耗、战斗损坏、转交、掉落、死亡分配和带出均通过 typed handler 与 transfer adapter 正确同步。
- `PortableItemChanges` 对 Existing、New、ConsumedOrDestroyed 分别执行物化返回、物化返回和不物化销毁；所有 SubWorld 战利品与制造产物使用同一 New 流程。
- 法宝全程使用 `ArtifactInstanceSnapshot`，魔法卷轴全程使用 `MagicScrollSnapshot`，符箓全程使用 `TalismanSnapshot`，三者不转换为无类型数据。
- 魔法卷轴学习/施放与符箓施放都按 `SkillBlueprint/Signature` 解析同一 `CompiledSkillDefinition`；共享 portable item handler 负责 carrier 资格和强度换算，`SharedSkillExecutor` 不包含载体分支。
- 魔法卷轴的资格、学习/施放和寿命语义保持不变；符箓的仙道资格、使用者力量换算和一次性施放语义保持不变，不存在臆造的 `UseCount`。
- 镇府法宝或唯一物品不会被两个返回者同时取得。
- 未实际拾取的 Ground 或 WorkbenchOutput 物品不会自动进入返回背包。
- 返回调用结束时，转出的 ItemId 在 MainWorld Store 中各有一个 Entity，在 SubWorld Store 中均不存在；ConsumedOrDestroyed 在两边都不存在。

### 死亡、目标与生命周期

- Projection 死亡后先结算小世界战利品，再触发主世界正式死亡。
- survival、reaction、death、kill commands 在固定 RNG 下结果稳定。
- `newKillAction` 不重复夺取已由小世界分配的物品。
- 唯一目标同一 Runtime 只产生一个 Winner。
- 两队同时提交最后一步时仍由单一 Objective Service 原子裁定。
- Runtime 被 Manager 销毁后，战斗 Entity、技能运行态、物品、目标状态和参与者 Binding 全部释放。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
