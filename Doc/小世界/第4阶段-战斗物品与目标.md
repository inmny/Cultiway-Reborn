# 第4阶段-战斗物品与目标

本阶段让 SubWorld 复用现有 SkillLibV3、Core Combat 和 PortableItem 领域能力，形成完整远征风险：单位可以战斗、施展同一份技能定义、使用与损坏物品、死亡，并通过具体目标决定队伍与实例结果。世界差异只存在于查询、碰撞、状态提交、时间和视觉 adapter，不建立平行技能或战斗系统。

## 具体说明

### 设计边界

- 全项目只有一份 `CompiledSkillDefinition`、一套技能 capability 声明和一个 `DamageResolver`；MainWorld 与 SubWorld 不各自维护技能语义或伤害公式。
- 删除规划中的 `SubWorldAbilityDescriptor`、`SubWorldAbilityCompiler`、`SubWorldSkillEffectAdapterRegistry`、独立 `SubWorldCombatService` 以及所有 `PayloadKind/Payload`。
- `SkillBlueprint` 只共享编译一次。MainWorld adapter 可把定义包装为现有 ECS `SkillContainer`，SubWorld adapter 直接执行同一不可变定义。
- 轨迹、几何、目标选择、relation/trigger/outcome、战术评分和伤害阶段是共享纯数据/计算；world query、碰撞、状态提交和 VFX 才由 adapter 实现。
- adapter 未提供定义声明的 capability 时，该技能明确不可执行，不生成近似技能；capability 来自共享 catalog，不按世界维护第二套 effect registry。
- SubWorld 战斗只操作 Projection/SubWorldEntity，不调用 `MapBox.checkAttackFor()`；MainWorld 仍保持现有 Actor、Building、ECS 和原版回调入口。
- 物品沿用第二、三阶段 PortableItem typed snapshot/codec、StableItemId、ItemLease、`SubWorldItemRecord` 和 ContentRef，不共享 ECS Entity，也不重新定义物品 payload。
- 魔法卷轴与符箓是两个独立顶层载体 codec；二者只共享嵌套 `StoredSkillPayloadSnapshot`，载体资格和强度换算统一由共享 portable item handler 处理。
- 物品、伤势和死亡在统一 Outcome Commit 中结算，不能在战斗 tick 直接修改主世界 Actor。
- 多队伍是否敌对由 Instance FactionPolicy 决定，不能从 Sect 不同推导自动敌对。
- 非模态浮窗不暂停战斗；主/子世界独立时钟分别通过各自 `ITimeSource` 提供时间。

### 步骤 1：建立共享战斗状态与阵营合同

#### 阵营

```text
SubWorldFactionRecord
  FactionId
  SourceKind
  SourceId
  Relations[]
```

关系为 Friendly、Neutral、Competitive、Hostile。Competitive 允许争夺目标和阻挡交互，但不允许伤害；Hostile 才进入攻击候选。

消费系统在创建队伍时冻结关系。主世界 Kingdom 战争变化可以通过显式外部命令更新，但 Runtime 不每 tick查询 `World.world`。

#### Projection 战斗状态

```text
ProjectionCombatState
ProjectionResources
ProjectionFaction
ProjectionSkillLoadout
ProjectionCooldowns
ProjectionActionState
ProjectionStatusSet
```

这些组件是共享 `CombatSnapshot` 在 SubWorld 的持久化投影，不是第二套战斗规则。所有数值来自入场 Baseline 或 Template 实体定义；战斗中不读取主世界 Actor.stats 缓存。`ProjectionSkillLoadout` 只保存 `CompiledSkillDefinition` 的稳定 ID/签名和个体等级、冷却、资源状态，不保存另一份能力描述。

#### 行动

行动状态：

```text
Idle -> Preparing -> Executing -> Recovering -> Idle
                         ↘ Interrupted
```

移动、攻击、技能、交互、制造和拾取共用一个主行动占用，避免同一 Projection 同 tick 同时炼制、攻击和开箱。行动准备、执行、恢复时间统一读取所属世界 `ITimeSource`；浮窗是否可见不是行动状态。

### 步骤 2：建立唯一 CompiledSkillDefinition 与运行端口

#### 共享编译产物

`CompiledSkillDefinition` 是 SkillBlueprint 的唯一运行定义：

```text
DefinitionId
BlueprintId/Revision/Signature
CastProfile
ResourceCosts[]
TrajectoryDefinition
GeometryDefinition
TargetDefinition
EffectDefinitions[]
DamageDefinitions[]
TacticalProfile
RequiredCapabilities[]
VisualCues[]
```

定义只包含稳定 ID、枚举和数值结构，不持有 Friflo Entity、`SkillContainer`、Actor、BaseSimObject、WorldTile、Unity Object 或世界委托。现有 `SkillBlueprintCompiler` 调整为：

```text
SkillBlueprint
  -> Validate
  -> CompileDefinition
  -> CompiledSkillDefinition
       -> MainWorldSkillContainerAdapter.Materialize() -> ECS SkillContainer
       -> SharedSkillExecutor.Execute()                 -> world ports
```

MainWorld 编辑器预览、运行时施法和 SubWorld 都从 `ISkillDefinitionRegistry` 解析同一 DefinitionId/Signature。MainWorld 的 `SkillContainer` 是定义的 ECS 包装和运行状态载体，不再是另一份权威技能语义；SubWorld 不 materialize 主世界 ECS Entity。

基础近战、远程武器攻击也注册为共享 CompiledSkillDefinition，由装备/基础战斗数据参数化，不在 SubWorld 内硬编码 BasicAttack 公式。

#### 共享端口

`ISkillExecutionPorts` 是执行器接收的聚合合同，只组合以下细分端口，不增加领域规则：

```text
ISkillExecutionPorts
  WorldQuery: ISkillWorldQuery
  CombatState: ICombatStatePort
  CombatCommit: ICombatCommitPort
  Runtime: ISkillRuntimePort
  Random: IRandomSource
  Time: ITimeSource
  Visual: IVisualSink
```

| 端口 | 共享执行器需要的能力 | MainWorld adapter | SubWorld adapter |
| --- | --- | --- | --- |
| `ISkillDefinitionRegistry` | 按稳定 ID/签名读取定义 | 现有 SkillLibV3 library 包装 | 同一 registry，只保存引用 |
| `ISkillWorldQuery` | relation、目标、范围、几何、射线、碰撞和 tile/building 查询 | Actor/Building/WorldTile 查询 | Grid、Projection、SubWorldEntity 查询 |
| `ICombatStatePort` | 读取 caster/target 的 `CombatSnapshot`、资源、状态和冷却 | ActorExtend/ECS snapshot | Projection 组件 snapshot |
| `ICombatCommitPort` | 原子提交 Damage/Status/Shield/Force/Death 等 commands | 现有事件、ECS 与 Actor API | Projection Store command buffer |
| `ISkillRuntimePort` | 施法序列、轨迹实例、命中记忆、周期效果和冷却运行态 | 现有 SkillLibV3 systems | SubWorld 固定 tick runtime |
| `IRandomSource` | 命中、目标抽样、反应等稳定随机序列 | MainWorld 随机 adapter | Instance RandomState adapter |
| `ITimeSource` | 当前时间、fixed elapsed、冷却和持续时间 | 主世界时钟 | SubWorld 独立 LocalTime |
| `IVisualSink` | 消费共享 VisualCue，不产生玩法副作用 | SkillWorldVisualService adapter | 浮窗 RenderTexture/VFX adapter |

`SharedSkillExecutor` 只依赖以上端口。逻辑结果先提交，`IVisualSink` 后消费 VisualCue；VFX 缺失不能改变命中、状态或资源结果。

#### capability

轨迹、目标类型和效果在共享 capability catalog 中声明，首批使用 `TargetEntity`、`TargetTile`、`ResourceCost`、`InstantTrajectory`、`LinearProjectile`、`EntityCollision`、`TileCollision`、`Damage`、`Heal`、`ApplyStatus`、`Displacement`、`SpawnExecution` 和 `VisualCue`。编译器把实际需要的原子 capability 写入 `RequiredCapabilities`，adapter 只声明自己实现了哪些共享 capability；Melee、Ranged、Area、Chain 等是由这些能力组成的测试与展示类别，不进入另一套执行分支。

capability 缺失时 registry 返回明确的不可执行诊断，定义本身仍保持同一签名。禁止建立 `SubWorldSkillEffectAdapterRegistry` 或按 Effect 类型复制第二份执行器。

### 步骤 3：抽取 SkillLibV3 与 Core Combat 纯数据计算

#### SkillLibV3 共享核心

从现有 SkillLibV3 中抽取并保留一份世界无关表示与算法：

- `SkillTrajectoryDomain`、Trajectory/Motion/Impact profile 转为稳定轨迹参数和逐 tick 运动计算；生成对象与碰撞查询走 `ISkillRuntimePort/ISkillWorldQuery`。
- 射线、圆、扇形、链式跳转、接触体和落点等几何只计算 value type 和稳定 ObjectId/TileId，不枚举 Actor、Building 或 Projection 实例。
- TargetMode、`SkillEffectTargetRelation`、`SkillEffectTrigger`、`SkillEffectOutcomeFlags` 保留为共享合同；relation 判断所需阵营数据由 query port 提供。
- 现有 Effect descriptor/pipeline 去除 `BaseSimObject`、`WorldTile`、`ActorExtend`、ECS Entity 委托，改为输入 snapshot、输出 effect commands 和 outcome。
- `SkillContainerEvaluator`、施法成本、预期目标数和 modifier 贡献改为对 CompiledSkillDefinition 的纯计算，MainWorld UI 与 SubWorld AI 使用同一结果。

共享计算不引用 Unity 随机、主世界单例或 SubWorld Store。所有集合在抽样前按稳定 ID 排序，随机值只从 `IRandomSource` 获取。

#### Core Combat 共享核心

从 `Source/Core/Combat/Tactical` 抽取候选动作、威胁、距离、资源、效果收益、风险、保护与 Objective 倾向等纯数据评分。MainWorld adapter 提供 Actor/Building 候选，SubWorld adapter 只提供 VisionGroup 当前可见的 Projection/SubWorldEntity 候选；两边调用同一 candidate builder 和 scorer。

世界层保留的职责仅有：

- 枚举当前世界实际对象和 tile。
- 路径请求、碰撞 broad phase 与对象生命周期。
- 将共享 commands 提交到 Actor/ECS 或 Projection Store。
- 把共享 VisualCue 映射到所在世界坐标与 VFX。

不得在 `Source/Core/SubWorlds/Skills/` 或 `Source/Core/SubWorlds/Combat/` 下复制 trajectory、effect、resolver 或 tactical scorer。

### 步骤 4：抽取共享 DamageResolver 并保持主世界时序

#### 合同

```text
DamageResolver.Resolve(DamageRequest, CombatSnapshot)
  -> DamageResolution
       PhaseValues
       FinalDamage
       IneffectiveHit
       Commands[]
```

`DamageRequest` 保存 Source/Target stable ID、RawDamage、ElementComposition、AttackType、DamageOrigin、power override 与 IgnoreDamageReduction。`CombatSnapshot` 保存本次结算观察到的存活/无敌、攻防 power level、元素抗性、状态、护盾、生存/反应规则、阶段修正和由 `IRandomSource` 预取的稳定随机样本。

`DamageResolution` 不直接修改世界对象。它给出每阶段数值、最终伤害、无效命中结果，以及按顺序提交的记录、状态、护盾、生存、反应、击杀和 VisualCue commands。

#### 阶段顺序

Resolver 必须按当前 `ActorExtend.GetHit` 的顺序固化阶段，不能借重构调整主世界时序：

1. 自伤、存活与无敌门禁，并记录 attack attempt。
2. `action_before_be_attacked` 对伤害、元素、AttackType 和忽略减伤的前置修正。
3. 攻防 power level、跨级压制和 minimum damage 资格。
4. 元素组成抗性与通用减伤。
5. 第一次 minimum damage。
6. ineffective hit 概率、固定 RNG 抽样和无效命中 reaction。
7. 实际受伤前的 `action_on_be_attacked`。
8. 原版 `checkSpecialAttackLogic` 上限及第二次 minimum damage。
9. `ApplyFinalDamageActions`、护盾、生存与共享 reaction commands。
10. damage outcome/OnDamageResolved，再进入最终生命、受击、死亡与击杀提交。

MainWorldDamageAdapter 保留现有 hook 和原版 special logic 的阶段位置，在当前 `ActorExtend.GetHit` 入口构造 snapshot、提交 resolution commands，最后仍且只调用一次原版 `Actor.getHit` 尾部，使用现有 `pCheckDamageReduction: false`，不能提前进入、重复减伤或改变事件顺序。

SubWorldDamageAdapter 从 Projection 构造同一 CombatSnapshot，经 `ICombatCommitPort` 把同一领域 commands 提交到 Projection 状态，不调用 Actor API。两种 adapter 的 world-only commands 可以不同，但 DamageResolution、共享状态/反应/击杀 commands 在同输入与随机样本下必须一致。

### 步骤 5：用共享定义实现行动与战术决策

#### 感知与候选

SubWorld AI 只通过 `ISkillWorldQuery` 观察当前 VisionGroup 已见对象和本地事件：

- 最近敌对单位、可保护单位与建筑。
- 当前目标距离、共享几何结果和本地路径成本。
- 自身生命、资源、状态、冷却和主行动占用。
- 附近盟友、危险 tile、可用物品、工作台和 Objective。
- CompiledSkillDefinition 的共享 TacticalProfile 和 evaluation。

不读取迷雾后的敌人、主世界 Actor 或消费系统隐藏评分。MainWorld 与 SubWorld adapter 生成相同 `TacticalSnapshot` 后，候选过滤、评分、稳定 tie-break 和动作选择必须一致。

#### 决策与执行

每个 AI 决策周期：

1. 选择必须响应的威胁、盟友或 Objective。
2. 由共享 candidate builder 生成移动、基础攻击、技能、物品、交互和制造候选。
3. 由共享 scorer 按距离、资源、效果、风险与战术目标评分。
4. 按稳定 ObjectId/DefinitionId 打破同分，冻结一个 Action Command。
5. 在所属世界固定 tick 执行准备、轨迹、命中和恢复。

浮窗 Visible 与 Background 运行相同 executor、端口顺序和 AI 周期。View 只插值位置和播放已经提交的 VisualCue/CombatEvent；主世界同时按自己的时钟继续 AI 和战斗。

### 步骤 6：扩展 PortableItem、死亡与返回事务

#### 使用、掉落与战斗损坏

本阶段不重新定义 ItemRecord。所有物品继续使用第三阶段：

```text
SubWorldItemRecord { ExpeditionItemId, StableItemId, ContentRef, Holder, Ground, State }
```

- MainWorld 来源物品按第二阶段先 Capture 并持久化 Archive snapshot、record 与 ItemLease，再在同一提交边界解除源关系并回收源 Entity；`StableItemId` 就是 `PortableItemIdentity.ItemId`，Projection 只持有该 ItemId 对应的 Archive 记录和 ContentRef。
- 使用、消耗、耐久损坏、战斗破坏、转交、掉落和拾取通过 PortableItem typed codec 生成 snapshot revision 与 holder command，不改写无类型 payload。
- 地面物品不阻挡移动；拾取需要到达、主行动时间和容量检查。每个 ExpeditionItemId 同一时刻只允许一个 Holder 或 Ground。
- 容器、工作台输出和死亡掉落只移动现有记录；目标完成不自动拾取地面或输出槽物品。

法宝必须使用 `ContentRef<ArtifactInstanceSnapshot>`。其器形、atoms、能力、品质、耐久和表现来自第三阶段共享 snapshot；主动能力解析为同一 CompiledSkillDefinition，不建立 SubWorld artifact combat model。

魔法卷轴必须使用 `ContentRef<MagicScrollSnapshot>`，符箓必须使用 `ContentRef<TalismanSnapshot>`。二者都把嵌套的 `StoredSkillPayloadSnapshot { SkillBlueprint, Signature, Strength, PowerLevel }` 交给共享 `PortableSkillCarrierHandler`：

1. handler 按顶层 typed snapshot 执行对应 carrier 资格检查，不让技能执行器猜载体类型。
2. handler 按 `SkillBlueprint/Signature` 从 `ISkillDefinitionRegistry` 解析唯一 `CompiledSkillDefinition`；快照不保存 `SkillContainer` Entity 或 compiled definition 副本。
3. handler 按载体规则换算本次执行强度。魔法卷轴保留其存储强度、PowerLevel 与现有魔法资格；符箓保留仙道资格，并以实际使用者力量执行现有换算。
4. 魔法卷轴继续支持现有学习/施放分支并受快照寿命约束；学习时由 MainWorld skill adapter 从同一 definition 建立角色运行态，施放时进入 `SharedSkillExecutor`。
5. 符箓只执行一次性施放，提交施放结果后消费该 `TalismanSnapshot` 对应物品；不把符箓解释成可学习卷轴。

载体 codec 和 handler 返回 typed snapshot revision、技能授予或施放 command、物品消费 command；不增加统一 `UseCount`。卷轴学习/施放与符箓施放共享 `CompiledSkillDefinition` 和执行器，但资格、强度换算、寿命及消费语义不会进入技能定义本身。

#### OutcomeDelta

扩展 OutcomeDelta：

```text
PermanentStatDeltas[]
TraitAdditions[]
TraitRemovals[]
SkillChanges[]
PortableItemChanges[]
QiyunDelta
DeathOutcome?
```

`PortableItemChanges` 保存 StableItemId、来源、最终 typed snapshot/ContentRef、最终 Holder、Disposition 和目标 MainWorld holder，不保存 Runtime Entity。返回明确区分三类：

- `Existing`：MainWorld 来源且仍存活，沿用入场 `ItemLease`，按最终 snapshot 在 MainWorld 物化同一 ItemId。
- `New`：SubWorld 战利品或制造产物，以 Archive 为初始权威；开始返回提交时才取得 `ItemLease`，随后走与 Existing 相同的卸载、Materialize、绑定和幂等提交流程。
- `ConsumedOrDestroyed`：已消费或销毁，不在 MainWorld Materialize；MainWorld 来源物品在销毁结果提交后释放原 Lease，未进入跨世界返回的新物品不创建第二种提交状态。

所有新战利品和四类制造产物都先建立 StableItemId、typed snapshot、`SubWorldItemRecord` 与 Holder，再按 `New` 流程返回；不能从奖励表或工序结果直接创建 MainWorld Entity。

#### 提交顺序

1. 冻结全部退出或终局 Projection 及其待提交 combat/item commands，Capture 每件物品的最终 typed snapshot、Holder、Ground、损坏和消耗状态，并写入 `PendingOutcome` 的 `PortableItemChanges`。
2. 为需要带出的 `New` 物品取得本次 `CommitId` 的 `ItemLease`；Existing 沿用入场 Lease，ConsumedOrDestroyed 不新增物化工作。
3. `SubWorldOutcomeCommitService` 先销毁或卸载本次变化涉及的 SubWorld Runtime item materialization；Archive 与 `PendingOutcome` 继续权威持有 snapshot、record 和最终 holder。
4. Existing 与 New 按 `ItemId + CommitId` 查询已提交的 MainWorld ownership；未物化时在同一主线程 item commit 边界调用原 `IPortableItemCodec.Materialize(targetStore, snapshot, factory)` 创建同一 ItemId、绑定目标 holder，并持久化带本次 CommitId 的 ownership，已存在本次提交结果时不重复创建。ConsumedOrDestroyed 不 Materialize。
5. 对存活 Actor 提交资源、伤势、trait、技能和 portable ownership 结果；需要带出但无 Actor holder 的物品按 Outcome 中已冻结的入口容器或丢弃规则处理。
6. 对死亡 Projection 提交 DeathOutcome。
7. 持久化完成的 `CommitId` 并确认存活物品的 MainWorld ownership 都带同一 CommitId 后，才删除相应 Archive item record 和不再可达的 snapshot 引用，并释放已完成或确定销毁物品的 `ItemLease`。
8. 最后释放 Actor 的 `ExpeditionLease`。失败重试始终使用 Archive、`PendingOutcome` 和 `ItemLease`，并以 `ItemId + CommitId` 跳过已经物化、绑定的结果。

#### 死亡

Projection 死亡先进入 Terminal，不立即调用主世界 Actor：

- 共享 DamageResolver 产生 survival、reaction、death 和 kill commands；SubWorld adapter 先提交 Projection 状态与物品掉落。
- DeathOutcome 保存死亡原因、DefinitionId、来源 Participant/Entity stable ID、地点和最终 CombatSnapshot 摘要。
- 返回提交时进入 `ExpeditionCommitContext`，先应用已结算的 PortableItem changes，再解除死亡门禁。
- 设置主 Actor 致死状态并调用正式 `checkDeath()`；Context 标记 LootAlreadyResolved，避免 `newKillAction` 再复制一次物品。
- 无对应主世界攻击者时仍走正式死亡回调，但攻击者为空；日志使用 SubWorld 保存的来源快照。

### 步骤 7：实现多队伍目标与唯一结果

扩展 Objective Asset：

- `DefeatEntityGroup`
- `ProtectEntity`
- `CollectItem`
- `HoldZone`
- `CompleteInteractionRace`
- `SelectUniqueWinner`
- `EscapeBeforeCollapse`

#### 队伍

Participant 通过 FactionId 和 VisionGroupId 组成队伍。不同队伍可以从不同 Entry 进入同一 Instance。

#### 竞争

Competitive 队伍可以：

- 分别探索迷雾。
- 争夺一次性容器和机关。
- 对同一禁制贡献进度。
- 抢先占据目标区域。
- 参加唯一结果评估。

不能互相伤害，除非 Faction Relation 明确为 Hostile。

#### 唯一结果

`SelectUniqueWinnerObjective` 冻结合格 Projection 及其小世界内可观察成绩：

- 到达和发现。
- 机关、战斗和保护贡献。
- 规则消费系统提供的稳定相性分。
- 当前存活与退出状态。

Objective 只提交一个 ParticipantId，并生成 `UniqueWinnerSelected` Event。具体奖励含义由消费系统解释。

### 步骤 8：固化主世界并完成跨世界差分验收

先为当前主世界行为建立 golden fixtures，再移动任何 SkillLibV3/Core Combat 逻辑。固定输入 snapshot、目标顺序、时间和 RNG，覆盖：

```text
melee
ranged
area
chain
building
status
shield
survival
reaction
kill
```

每类 fixture 同时记录 Definition signature、候选目标、轨迹/几何结果、DamageResolution 各阶段值、共享 commands、MainWorld hook/事件顺序和最终 Actor/Building 状态。重构后的 MainWorld adapter 必须逐项与 golden 结果一致，尤其不能改变 `ActorExtend.GetHit` 到原版 `Actor.getHit` 尾部的顺序。

然后使用同一 CompiledSkillDefinition、CombatSnapshot、TacticalSnapshot 和固定 RNG，分别运行 MainWorld fake ports 与 SubWorld ports，差分共享领域结果；只忽略明确列出的 world-only object handle 和 VisualCue 坐标。

最后增加战斗验证 Template：两支队伍从不同入口进入，争夺一个由守卫保护的核心容器，并允许配置 Competitive 或 Hostile 关系。该实例分别持续 Visible 与持续 Background 运行相同 TickIndex，比较定义、RandomState、Projection、状态、物品、死亡和 Objective 签名。

## 验收标准

### 共享技能与主世界回归

- 一个 SkillBlueprint revision 只产生一个 CompiledSkillDefinition signature；MainWorld `SkillContainer` 与 SubWorld loadout 都引用该定义。
- 代码和存档中不存在 `SubWorldAbilityDescriptor`、`SubWorldAbilityCompiler`、`SubWorldSkillEffectAdapterRegistry`、独立 `SubWorldCombatService` 或 `PayloadKind/Payload`。
- capability 由共享定义声明；adapter 能力不足时给出明确不可执行结果，不产生近似 effect，也不查询世界专属效果 registry。
- 主世界 melee、ranged、area、chain、building、status、shield、survival、reaction、kill golden fixtures 在重构前后逐项一致。
- MainWorld `action_before_be_attacked`、power suppression、resistance、minimum、ineffective、`action_on_be_attacked`、vanilla special、final actions、reaction/kill 和原版 tail 顺序不变。
- 每次 MainWorld 命中只进入一次原版 `Actor.getHit` 尾部，且不会重复执行原版或共享减伤。

### 跨世界战斗

- 同一 CompiledSkillDefinition、DamageRequest、CombatSnapshot、TacticalSnapshot 和 RNG 序列经两种 adapter 后，共享目标、几何、DamageResolution、effect outcome、战术评分与 commands 一致。
- Competitive 队伍不能互伤，Hostile 队伍能够按冻结关系战斗；relation 由同一共享计算处理。
- SubWorld AI 只使用 VisionGroup 已见目标和已声明 capability 的定义。
- Visible 与 Background 执行相同 TickIndex 时，RandomState、Projection、技能运行态、伤害、status、shield、reaction、kill 和 Objective 结果一致。
- 移动、攻击、技能、制造、交互和拾取不会在同一实体上并发执行。
- MainWorld 与 SubWorld 使用独立 `ITimeSource`；非模态浮窗打开、折叠或切换不会串改冷却、持续时间或战斗结果。

### PortableItem

- MainWorld 来源物品进入 Archive 后，源 Entity 已解除 holder/装备/工序关系并回收；同一 StableItemId 在 MainWorld 与 SubWorld 不能同时存在有效 Entity。
- 容器内容只生成一次，读档不重复。
- 使用、消耗、战斗损坏、转交、掉落、死亡分配和带出均通过 typed codec 正确同步。
- `PortableItemChanges` 对 Existing、New、ConsumedOrDestroyed 分别执行物化返回、物化返回和不物化销毁；所有 SubWorld 战利品与制造产物使用同一 New 流程。
- 法宝全程使用 `ArtifactInstanceSnapshot`，魔法卷轴全程使用 `MagicScrollSnapshot`，符箓全程使用 `TalismanSnapshot`，三者不转换为无类型数据。
- 魔法卷轴学习/施放与符箓施放都按 `SkillBlueprint/Signature` 解析同一 `CompiledSkillDefinition`；共享 portable item handler 负责 carrier 资格和强度换算，`SharedSkillExecutor` 不包含载体分支。
- 魔法卷轴的资格、学习/施放和寿命语义保持不变；符箓的仙道资格、使用者力量换算和一次性施放语义保持不变，存档和运行时都不存在臆造的 `UseCount`。
- 镇府法宝或唯一物品不会被两个返回者同时取得。
- 未实际拾取的 Ground 或 WorkbenchOutput 物品不会自动进入返回背包。
- 返回重试按 `ItemId + CommitId` 识别已物化 MainWorld 结果；MainWorld ownership 与 CommitId 持久化前不删除 Archive item record/snapshot 引用，也不释放 ItemLease。

### 死亡与目标

- Projection 死亡后先结算小世界战利品，再触发主世界正式死亡。
- survival、reaction、death、kill commands 在固定 RNG 下保存读档前后一致。
- `newKillAction` 不重复夺取已由小世界分配的物品。
- 唯一目标同一 Instance 只产生一个 Winner。
- 两队同时提交最后一步时仍由单一 Objective Service 原子裁定。
- 保存读档后不会重新杀死 Actor、重复发物品或选择第二个 Winner。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
