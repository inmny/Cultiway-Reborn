# 第2阶段-远征投影与返回

本阶段让真实主世界 Actor 和首批 SpecialItem 进入小世界。`SubWorldManager` 持有当前会话内常驻的 `SubWorldRuntime` 与运行时 `ExpeditionBinding`；typed snapshot、Blueprint 和稳定 `ItemId` 仅作为当前会话内跨 `EntityStore` 转移的值对象。入场和返回都在同一主线程调用内按 `Capture -> 移除源物化 -> Materialize 目标` 同步完成，调用结束时物品只属于一个 Store。

## 具体说明

### 设计边界

- 真实 Actor 始终属于主世界 ActorManager，不移动到自定义 Grid。
- 主世界本体在入口地块保持有效对象，但远征期间不渲染、不参与模拟和战斗。
- `SubWorldManager` 是本阶段唯一协调入口，持有 Runtime 集合、命令分派和 Binding 索引。`SubWorldRuntime` 创建后常驻，直到实例显式销毁或当前世界会话结束；浮窗关闭、折叠和切换只解除 View 绑定。
- `ExpeditionBinding` 只隔离参与远征的 Actor；主世界时钟、其他 Actor、战争和生态在浮窗打开期间继续运行。
- Projection 只复制小世界需要的结构化能力，不持有 `ActorBinder`。
- 本阶段同步生命、法力、体力、灵气、气运、营养和 BodyTime；永久伤势与死亡留到第四阶段。
- 本阶段建立 portable item identity、typed snapshot、物品 transfer adapter、`ISpecialItemFactory` 和 `CraftProcessSnapshot`，但物品只读，不实现使用、消耗、转交、掉落、装备或制造。
- typed snapshot、Blueprint 和稳定 `ItemId` 的语义不跨当前会话；它们不定义外部格式，当前会话结束时随 Runtime 一起释放。
- MainWorld/SubWorld 转移在一个主线程调用内固定执行 `Capture -> 移除源物化 -> Materialize 目标`。边界开始前完成全部资格和类型校验；源被移除后任一步失败，都立即销毁已创建的目标物化，并用本次调用局部持有的 typed snapshot Materialize 回源 Store，恢复原 holder、装备、工序、Actor 与 Binding 状态后再返回失败。
- 同步调用不排队等待后续帧，也不保留待处理结果、提交标识或重试状态。
- 首批只支持 `IngredientSnapshot`、`ElixirRecipeBlueprint`、`ElixirItemSnapshot`、`ArtifactInstanceSnapshot`、`MagicScrollSnapshot` 和 `TalismanSnapshot` 六种顶层 typed snapshot；没有注册 transfer adapter 的物品不能加入远征物品集合，不生成通用 payload。
- 共享 portable item 类型放在 `Source/Core/Items/Portable`，禁止新增平行的 `SubWorldItem` payload、SubWorld 丹方或 SubWorld 法宝定义。
- 一个 Actor 同时只能拥有一个有效 `ExpeditionBinding`。
- 同一稳定 `ItemId` 在边界调用结束时只能对应一个有效 Entity。

### 步骤 1：建立参与者、Baseline 与 ExpeditionBinding

#### ParticipantRuntimeState

每个参与者的可变状态直接属于目标 `SubWorldRuntime`：

```text
ParticipantId
SourceActorId
EntryId
State
ProjectionEntityId
Baseline
EnteredParentTime
BodyElapsed
```

状态：

```text
Inside -> Exiting -> Returned
   ↘ Lost
```

Participant 只在同步入场成功后加入 Runtime。`Exiting` 只存在于本次同步返回调用；返回失败时在方法返回前恢复为 `Inside`。`Returned` 只用于完成当前退出 tick 的事件派发，随后从 Runtime 移除参与者状态。`Lost` 表示 Actor 在当前会话中被外部删除，由消费系统立即处理实例内 Projection。

#### Baseline

`ActorProjectionBaseline` 冻结入场时允许比较和投影的值：

- Actor ID、姓名快照和 ActorAsset ID。
- 生命、法力、体力、营养和修炼资源当前值与上限。
- 仙道境界、元素灵根、神识和战斗属性快照。
- Qiyun 当前值与有效上限。
- 主世界入场时间、年龄和 status 剩余时间。
- 已装备槽位对应的稳定 `ItemId`。
- 本次远征携带的 typed `IPortableItemSnapshot[]` 与 `CraftProcessSnapshot[]` 深拷贝。
- Actor 自身技能使用 `SkillBlueprint` 与签名；第四阶段从同一蓝图编译 `CompiledSkillDefinition`。

Baseline 只用于创建 Projection 和计算退出结果，不在返回时覆盖整个 ActorData。它与 Participant 一起存在于 Runtime，Participant 移除时一并释放。

#### ExpeditionBinding

`SubWorldManager` 持有当前会话的 `SourceActorId -> ExpeditionBinding` 索引：

```text
SourceActorId
InstanceId
ParticipantId
ProjectionEntityId
EntryParentTime
FrozenAge
State
```

`TagExpeditionSequestered` 作为 Cultiway Query 过滤标记；`ExpeditionBinding` 索引是原版并行 Patch 查询 Actor 是否被占用的来源。该索引只描述正在运行的远征，不承担会话外身份。

本步验证：创建 Participant 后，Baseline、ProjectionEntityId 与 Binding 全部指向同一 `ParticipantId` 和 InstanceId；Manager 拒绝把已有 Binding 的 Actor 加入另一 Runtime。

### 步骤 2：建立 Portable Item 与制造进程内存值

#### 稳定物品身份

所有进入 portable 边界的 SpecialItem 增加 `PortableItemIdentity.ItemId`。`ItemId` 在物品当前会话内首次参与跨 Store 转移时生成，之后在源 Entity、typed snapshot、SubWorld Entity 和返回后的目标 Entity 之间保持不变；其身份语义不延伸到下一次会话。禁止使用 Friflo `Entity.Id`、数组下标或对象 hash 代替。

公共基础快照：

```text
SpecialItemCoreSnapshot
  ItemId
  ShapeAssetId
  Name
  ItemLevel
  ItemIconData
  ItemCreation
  AliveTimerValue?
  AliveTimeLimitValue?
```

typed snapshot 只表达物品固有定义和当前实例状态。holder、背包/装备位置与制造关系由所属 `EntityStore` 的组件表达，不放入 Core。

#### typed snapshot 与物品 transfer adapter

```text
IPortableItemSnapshot
  ItemId
  SnapshotKind
  Core

IPortableItemTransferAdapter<TSnapshot>
  Capture(Entity source) -> TSnapshot
  Materialize(EntityStore targetStore, TSnapshot snapshot,
              ISpecialItemFactory factory) -> Entity

ISpecialItemFactory
  Create(EntityStore targetStore, SpecialItemCoreSnapshot core) -> Entity
```

`PortableItemTransferRegistry` 按明确的 `SnapshotKind + TSnapshot` 注册 transfer adapter。adapter 只在当前会话内完成 Entity 与 typed 内存值之间的 Capture/Materialize，不复制任意 ECS 组件包，也不处理未知类型。`ISpecialItemFactory` 的 `EntityStore` 是必传参数，内部不得固定访问 `ModClass.I.ActorExtendManager.World`。

首批六种 portable item typed snapshot 与共享嵌套定义：

| 类型 | 必须深拷贝的固有内容 | 不包含 |
| --- | --- | --- |
| `IngredientSnapshot` | Core、`ItemShape`、`ItemLevel`、`ItemCreation`、`ElementRoot`、`XianBase`、`Jindan` 及 `IngredientSemanticService` 消费的固有语义字段 | 持有者 Entity、`CraftOccupyingRelation` |
| `ElixirRecipeBlueprint` | Recipe/Asset ID、规范 Signature、`ElixirRecipeContext`、`ElixirIngredientRequirement[]`、CompositionSeed 与确定性效果定义 | `ElixirLibrary` 运行对象和 delegate |
| `ElixirItemSnapshot` | Core、`ElixirRecipeBlueprint` 深拷贝、药力值、效果类型与实例效果状态 | 对全局动态 `ElixirAsset` 的唯一引用 |
| `ArtifactInstanceSnapshot` | Core、`ArtifactBlueprint` 深拷贝、`ArtifactAbilityRuntime`、储藏、器灵及 extension 实例状态 | 持有者、装备槽位、显化 Entity |
| `MagicScrollSnapshot` | Core、`StoredSkillPayloadSnapshot`；Core 保留现有魔法卷轴 `AliveTimer/AliveTimeLimit` 数据 | `SkillContainer` Entity、`CompiledSkillDefinition` 副本与万法阁目录引用 |
| `TalismanSnapshot` | Core、`StoredSkillPayloadSnapshot` | `SkillContainer` Entity、`CompiledSkillDefinition` 副本与万法阁目录引用 |

```text
StoredSkillPayloadSnapshot
  SkillBlueprint
  Signature
  Strength
  PowerLevel
```

`StoredSkillPayloadSnapshot` 只能作为两个载体 snapshot 的嵌套值对象，不注册成可独立携带的顶层物品。魔法卷轴 transfer adapter 保留现有魔法资格、学习/施放和寿命语义；符箓 transfer adapter 保留仙道资格、使用者力量换算和一次性施放语义。二者都按 `SkillBlueprint/Signature` 解析唯一 `CompiledSkillDefinition`，不持有运行 definition，也不增加 `UseCount` 一类不存在的字段。

`ElixirRecipeBlueprint` 是共享制造定义，不是第二套 SubWorld 丹方。现有 `ElixirRecipeBuilder` 和 `IngredientSemanticService` 在第三阶段抽出纯快照核心后，MainWorld Entity 与 SubWorld portable item 都产生这个相同值对象。

#### CraftProcessSnapshot

```text
CraftProcessSnapshot
  ProcessId
  ProcessKindId
  CrafterId
  InputItemIds[]
  OutputItemId
  TypedRecipeSnapshot
  TypedStateSnapshot
  Progress
  RandomState
```

`CraftProcessSnapshot` 是当前会话内跨 MainWorld/SubWorld Store 的 typed 内存值，不是外部格式。`ProcessKindId` 是当前会话中用于选择 handler 的字符串，首批允许 `alchemy`、`artifact_refining`、`talisman_crafting` 和 `magic_scroll_crafting`；recipe/state 只能由该 ID 在唯一 `ICraftProcessKindRegistry` 中绑定的 handler 解释。炼制中的产物和全部输入材料分别拥有 `ItemId`，通过数组建立关系，不持有 `CraftOccupyingRelation` Entity 引用。第二阶段只 Capture、Materialize 和再次 Capture，进度与随机状态都不推进；第三阶段在同一类型上实现共享制造。

万法阁、百宝阁只提供全局创作目录。`MagicScrollSnapshot`、`TalismanSnapshot`、`ArtifactInstanceSnapshot` 和 `CraftProcessSnapshot` 跨 Store 时深拷贝其 `SkillBlueprint`/`ArtifactBlueprint`；当前会话中编辑或删除目录条目不会反向改变已进入 Runtime 的值。

本步验证：六种顶层值均完成 `MainWorld Entity -> Capture -> SubWorld Materialize -> Capture -> MainWorld Materialize -> Capture` 的 typed 结构等价往返，`ItemId` 全程不变。两个技能载体中的 `StoredSkillPayloadSnapshot` 结构一致但 transfer adapter 和载体语义彼此独立，工厂创建的 Entity 确实属于传入 Store，快照中没有 Entity、compiled definition 或目录对象引用。验收比较 typed 结构，不比较 ECS Entity 身份。

### 步骤 3：实现 Actor 隔离与同步入场转移

#### 入场前置

Actor 必须：

- 存活且已经落地。
- 不在船、磁铁、外力位移或变形过程中。
- 位于消费系统指定的入口范围。
- 没有其他 `ExpeditionBinding`。
- 已经完成或安全移交当前协调活动。
- 本次携带的每件物品都有稳定 `ItemId` 和已注册的 typed transfer adapter。
- 炼制中物品若随行，其 `CraftProcessSnapshot` 的产物与全部输入 ItemId 都包含在同一转移集合。

`SubWorldManager.IssueCommand(instanceId, AddParticipantsCommand)` 在主线程处理。进入顺序固定为：

1. 解析 Actor、入口、目标 Runtime、全部物品和 transfer adapter，构造 Baseline 与目标组件数据。
2. 确认所有 ItemId 唯一、目标格可用、Runtime 容量充足；校验阶段不改变任何 Store。
3. 对全部物品和制造进程执行 Capture，把 typed snapshot、holder、装备槽位、工序位置以及 Actor 原工作状态保留在本次调用的局部上下文中。
4. 解除每件物品在 MainWorld 的 holder、装备与工序关系，回收全部源 Entity，完成源物化移除。
5. 在目标 Runtime `EntityStore` 创建 Projection，逐件 Materialize 相同 ItemId 的物品并绑定 ProjectionInventory 或工序位置。
6. 把 Projection 放到 Entry，创建 Participant 与 `ExpeditionBinding`，停止 Actor 原工作，清理目标、路径和短时动作，写入视图事件后结束边界调用。

整个调用在一个主线程模拟边界内执行，不允许 tick、AI 或另一个转移命令插入。步骤 4 之前失败不改变任何运行状态；步骤 4 之后失败时，Manager 立即销毁目标 Store 中已创建的 Projection 和物品，用步骤 3 的值 Materialize 回 MainWorld Store，恢复全部关系和 Actor 原状态，并移除本次调用创建的 Participant 与 Binding。方法返回失败时不存在半完成转移或可供稍后重放的状态。

#### 原版更新门禁

Binding 期间：

- `Actor.updateParallelChecks()` 跳过普通更新和行为。
- `Actor.updateNutritionDecay()` 不推进营养。
- `Actor.updateAge()/getAge()` 使用入场年龄。
- `canAttackTarget` 在攻击者或目标被 Binding 时返回 false。
- `Actor.getHit()` 拒绝主世界伤害。
- 已排队 GetHit Event 在处理时再次过滤。
- `checkDeath()` 和 `die()` 只允许第四阶段的同步返回死亡上下文绕过。

#### Cultiway 系统门禁

以下系统的 Query 排除 `TagExpeditionSequestered`：

- 生命、魔力、灵气和气运回复。
- 定时修炼、骑士获取和境界效果。
- 法宝装备、显化、载具和持续活动。
- 师徒寻访和其他会改变任务的候选系统。
- Cultiway status 时间推进；portable item 的 `AliveTimer` 只存在于目标 Runtime 的 typed snapshot，本阶段不推进。

`DisposeActorExtendSystem` 不排除该 Tag；真实 Actor 被世界清理或外部删除时仍要销毁 Projection 并移除 Binding。

#### 表现

主世界单位渲染过滤 Binding Actor，入口 Building 显示远征人数与状态。不能只写 `is_visible=false`，因为原版每帧会更新可见性。

本步验证：远征期间尝试移动、攻击或修改 Actor 资源均被门禁；参与转移的物品已不在 MainWorld Store，目标 Runtime 中存在相同 ItemId 的 Entity；未参与远征的 Actor 和物品继续正常运行。

### 步骤 4：实现 Projection 与 portable item 运行实体

`ExpeditionProjectionFactory` 从 Baseline 创建纯数据组件：

```text
ProjectionIdentity
Position
ProjectionFaction
ProjectionVitals
ProjectionStats
ProjectionElementRoot
ProjectionResources
ProjectionVisual
ProjectionController
ProjectionInventory
```

`Position` 复用 `Cultiway.Core.Components.Position`，数值解释为所属 Runtime 的局部连续坐标；tile index 由该 Runtime 的 Grid 换算。

- `SourceActorId` 只作为同步返回身份，不用于访问主世界 Actor 热路径。
- ProjectionVisual 解析 ActorAsset 的 sprite ID 快照，但使用小世界自己的 SpriteRenderer。
- 主世界 avatar、render_data、batch 和材质实例不进入小世界。
- 小世界视图可以显示姓名和头像，但所有详情来自 Projection ReadModel。

`ProjectionInventory` 持有有序 `ItemId[]`。每件 portable item 已通过 transfer adapter 物化到当前 `SubWorldRuntime.EntityStore`，由 ItemId、typed snapshot 组件和明确 Holder 组件表达。Runtime 始终常驻，浮窗关闭、折叠或切换不会销毁这些 Entity。

- 不加入使用、装备、转移、掉落、消耗或制造 system。
- 不推进 `AliveTimer` 或 `CraftProcessSnapshot.Progress`。
- `MagicScrollSnapshot` 与 `TalismanSnapshot` 只携带嵌套 `StoredSkillPayloadSnapshot`，不编译、学习或执行技能。
- `ArtifactInstanceSnapshot` 只呈现固有定义与实例状态，不创建显化物或装备关系。

本阶段角色由简单自主移动或玩家右键命令控制。消费系统以后可以选择完全 AI、玩家可指挥或只读观察。

本步验证：Projection 与每个物品 Entity 都属于实例 Store，不引用主世界 `Actor`、`ActorBinder`、SpecialItem Entity 或 SkillContainer Entity；关闭浮窗只解除 View 绑定，Runtime、Projection 和物品 Entity 均保持原对象。

### 步骤 5：实现入口、退出和 BodyTime

#### 入口

每个 Template 定义一个或多个 Entry ID。参与者创建 Projection 时放置在对应 Entry tile；位置被占用时使用入口附近合法空格，不允许两个实体共享阻挡格。

#### 退出

退出条件由 Template 决定，首版支持：

- Projection 到达 Exit tile 后主动返回。
- 玩家或消费系统在允许撤离时请求退出。
- Runtime 完成后强制结算全部参与者。

退出请求作为 `RequestExitCommand` 进入所属 Runtime，在 tick 边界完成资格检查。随后由 Manager 在同一主线程边界把 Participant 临时置为 Exiting 并执行步骤 6；Projection 在调用期间不接受移动命令。返回失败时，Participant 在方法返回前恢复为 Inside，Projection 继续运行。

#### BodyTime

Projection 每 tick 按 ClockProfile 累积：

```text
BodyElapsed += LocalElapsed * BodyTimeRatio
```

主世界 Binding 期间年龄冻结。解除 Binding 时按以下目标调整 `created_time`：

```text
最终年龄增量 = BodyElapsed
created_time += ParentElapsed - BodyElapsed
```

单位换算使用原版一年 60 世界秒，不把小世界本地秒直接当年龄年数。

原版 status 的 `_end_time` 在返回时增加 ParentElapsed，使其保持入场剩余时长；小世界产生的新状态由 OutcomeDelta 单独添加。

`AliveTimer` 的入场值随 typed snapshot 进入目标 Store，第二阶段不按 ParentTime、LocalTime 或 BodyTime 推算，也不推进。物品时间属于后续明确 capability，不从 Actor BodyTime 推导。

本步验证：BodyTimeRatio 为 0、1 和大于 1 时只改变 Actor 返回年龄；同一轮测试中的 portable item `AliveTimer` 和 CraftProcess progress 始终等于入场快照。

### 步骤 6：实现 OutcomeDelta 与同步返回

Actor 临时结果值：

```text
OutcomeDelta
  HealthValue
  ManaValue
  StaminaValue
  NutritionValue
  WakanValue
  QiyunValue
  BodyElapsed
```

物品临时返回值：

```text
PortableItemTransferValue
  ItemId
  SnapshotKind
  Snapshot
  FinalHolder
```

第二阶段没有任何会修改物品的命令，因此每个物品的最终 typed snapshot 必须与同 ItemId 的 Baseline 结构等价，`CraftProcessSnapshot` 的 Progress 与 RandomState 也必须相同。返回验证 typed 结构和稳定 `ItemId`，不要求 ECS Entity 身份相同。

`SubWorldManager` 在主线程模拟边界执行返回：

1. 在退出 tick 结束后冻结 Projection 与 portable item Entity，不再接受该 Participant 的命令。
2. 从 Projection 构造 `OutcomeDelta`，由各 transfer adapter Capture `PortableItemTransferValue[]` 与 `CraftProcessSnapshot[]`，并把 SubWorld holder、工序位置和 Actor 返回前字段保留在本次调用的局部上下文中。
3. 解析仍存活的 Source Actor，确认目标 MainWorld Store、Holder 和全部 transfer adapter 可用；此时尚未改变任一 Store。
4. 移除 SubWorld 中对应物品的 ProjectionInventory、工序和 Holder 关系并销毁源 Entity，完成源物化移除。
5. 在 MainWorld 目标 Store 逐件 Materialize 相同 ItemId 的 Entity，并绑定最终 Holder 与装备/工序位置。
6. 通过原版资源 setter 和现有资源 Service 写入 Actor 当前值，按返回时真实上限 clamp，调整年龄与 status 时间，标记 Actor/Cultiway stats dirty。
7. 删除 Projection 和 Participant 状态，移除 `TagExpeditionSequestered` 与 `ExpeditionBinding`，重新启用主世界 Actor 渲染和普通 AI。

步骤 4 至 7 属于同一次主线程调用，期间不执行主世界或 SubWorld tick。步骤 4 之后失败时，Manager 立即销毁 MainWorld 中本次已创建的物品，按步骤 2 的 typed snapshot Materialize 回 SubWorld Store，恢复 ProjectionInventory、Holder、工序与 Actor 返回前字段，把 Participant 恢复为 Inside 并重新接受命令。调用结束后没有跨 Store 中间状态，也没有稍后重放的结果。第四阶段加入永久伤势、技能、物品消耗和死亡时沿用相同边界，死亡仍放在物品和普通 Actor 字段之后。

写入采用 Projection 最终值而不是“入场差值加到当前主世界值”，因为 Binding 保证主世界本体的这些资源没有并发变化。

本步验证：六种顶层 portable snapshot 与内嵌的 `StoredSkillPayloadSnapshot` 经过“Capture -> SubWorld Materialize -> Capture -> MainWorld Materialize -> Capture”后，ItemId 不变且 typed 结构等价；方法返回后 MainWorld Store 中各 ItemId 恰好一个，SubWorld Store 中对应 Entity 为零，Actor Binding 已移除。

### 步骤 7：完成隔离、返回与回滚验收

测试 Template 增加一块非致命资源消耗区域，使 Projection 在内部损失生命、法力或灵气后返回，验证 Delta。测试角色携带 Ingredient、Elixir、Artifact、MagicScroll、Talisman 各一件，并携带一份 `ElixirRecipeBlueprint`，覆盖六种顶层 typed snapshot 和内嵌 `StoredSkillPayloadSnapshot`，再附带一份冻结的 `CraftProcessSnapshot`；只执行查看和退出，不提供任何物品使用或制造命令。

另用测试 transfer adapter 分别在入场和返回的第二件物品 Materialize 时失败。入场失败后 MainWorld 恢复全部源物品、关系与 Actor 原状态，Runtime 中没有 Participant、Binding、Projection 或目标物品；返回失败后 SubWorld 恢复全部源物品与关系，Actor 字段不变，Participant 回到 Inside，MainWorld 没有本次目标物品。

本步验证：完成“同步入场 -> Actor 隔离 -> 资源消耗 -> 物品只读查看 -> 同步退出”的单条流程；Actor 资源按 Projection 最终值返回，所有物品和制造进程保持 typed 结构等价且 ItemId 不变，两个世界时钟仍独立运行。两个失败用例都在调用返回前完成回滚且没有重试状态。再销毁 Runtime，确认 Manager 中没有参与者、Binding 或 SubWorld Item 残留。

## 验收标准

### 隔离

- Actor 入场后仍存在于主世界 manager，但不渲染、不移动、不攻击、不受伤。
- 营养、年龄、原版 status 和 Cultiway status 在主世界侧不推进。
- 主世界回复、修炼、法宝和师徒系统不修改 Binding Actor。
- MainWorld 来源物品在同一主线程边界内先 Capture，再解除源关系并回收源 Entity，最后在目标 Runtime Materialize 相同 ItemId。
- 入场中途失败时，目标 Store 的本次物化全部删除，MainWorld 源物品、关系与 Actor 原状态在调用返回前恢复，Manager 不留下 Participant 或 Binding。
- 浮窗打开并运行 Projection 时，未被 Binding 的主世界 Actor 继续执行普通 AI 和战斗。
- 一个 Actor 无法同时进入两个实例。
- 世界清理能够回收被 Binding 的 ActorExtend、Projection 和 Manager 索引条目。

### Projection 与返回

- Projection 的坐标、资源和视觉不引用 Actor、WorldTile 或 ActorBinder。
- portable item Entity 属于 SubWorld Runtime 的显式 `EntityStore`，不引用主世界 SpecialItem Entity、SkillContainer Entity 或目录对象。
- 内部资源消耗返回后准确写入主世界 Actor。
- 返回时按当前真实上限 clamp，不覆盖 trait、装备或无关 ActorData。
- BodyTimeRatio 为 0、1 和大于 1 时，年龄结果符合 ClockProfile。
- 进入和返回都在一次 Manager 主线程调用中完成，任一边界调用结束时同一 ItemId 只存在于一个 Store。
- 返回中途失败时，MainWorld 本次物化全部删除，SubWorld 源物品、关系与 Actor 字段在调用返回前恢复，Participant 回到 Inside。
- 两个方向的失败都不留下待执行工作或重试状态。
- 返回结束后 Projection、Participant、Tag 和 Binding 全部移除，Actor 在下一主世界 tick 正常参与模拟。

### Portable Item

- `ItemId` 在主世界 Entity、typed snapshot、SubWorld Entity 和返回后的 Entity 中一致，且不等同于任何 ECS Entity ID。
- `IngredientSnapshot` 完整持有 `IngredientSemanticService` 所需固有输入，重新构建的语义档案一致。
- `ElixirItemSnapshot` 内嵌 `ElixirRecipeBlueprint`，不依赖当前动态 ElixirLibrary 才能表达定义。
- `ArtifactInstanceSnapshot` 同时持有 `ArtifactBlueprint` 固有定义和能力、储藏、器灵等实例状态。
- `MagicScrollSnapshot` 持有 `StoredSkillPayloadSnapshot` 与寿命数据，`TalismanSnapshot` 持有独立载体值；二者都不持有 SkillContainer Entity 或 CompiledSkillDefinition 副本。
- 六种顶层 transfer adapter 完成 `Capture -> SubWorld Materialize -> Capture -> MainWorld Materialize -> Capture` 后 typed 内容结构等价，`ItemId` 不变。
- `ISpecialItemFactory` 创建的 Entity 总是属于调用方传入的 Store，不访问固定全局 Store。
- `CraftProcessSnapshot` 的 `ProcessKindId`、typed recipe/state、InputItemIds、OutputItemId、Progress 和 RandomState 在本阶段不变化。
- SubWorld UI 和命令队列没有使用、制造、装备、转移、掉落或消耗入口。
- 当前会话中修改万法阁、百宝阁目录条目不会改变已经跨 Store 深拷贝的 Blueprint。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
