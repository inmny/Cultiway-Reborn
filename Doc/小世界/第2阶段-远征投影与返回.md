# 第2阶段-远征投影与返回

本阶段让真实主世界 Actor 和首批 SpecialItem 安全进入小世界。主世界本体由 `ExpeditionLease` 隔离；MainWorld 来源物品在 Archive 提交边界转移所有权，小世界从 typed portable snapshot 创建 Projection，退出时按稳定 `ItemId` 重新物化并提交资源增量。

## 具体说明

### 设计边界

- 真实 Actor 始终属于主世界 ActorManager，不移动到自定义 Grid。
- 主世界本体在入口地块保持有效对象，但远征期间不渲染、不参与模拟和战斗。
- Lease 只隔离参与远征的 Actor；主世界时钟、其他 Actor、战争和生态在浮窗打开期间继续运行。
- Projection 只复制小世界需要的结构化能力，不持有 `ActorBinder`。
- 本阶段同步生命、法力、体力、灵气、气运、营养和 BodyTime；永久伤势与死亡留到第四阶段。
- 本阶段完整建立 portable item identity、typed snapshot/codec、`ISpecialItemFactory`、Archive item record、`ItemLease` 和 `CraftProcessSnapshot`，但物品投影只读，不实现使用、消耗、转交、掉落、装备或制造。
- MainWorld 来源物品在 Archive 记录与 Lease 持久化后，于同一主线程提交边界解除 holder、装备和工序关系并回收源 Entity；Archive 随即成为唯一权威。失败发生在边界前时不移除源，边界后只从 Archive 与 Lease 恢复。
- 首批只支持 `IngredientSnapshot`、`ElixirRecipeBlueprint`、`ElixirItemSnapshot`、`ArtifactInstanceSnapshot`、`MagicScrollSnapshot` 和 `TalismanSnapshot` 六种顶层 typed snapshot；没有注册 codec 的物品不能加入远征物品集合，不生成通用 payload。
- 共享 portable item 合同放在 `Source/Core/Items/Portable`，禁止新增平行的 `SubWorldItem` payload、SubWorld 丹方或 SubWorld 法宝定义。
- 一个 Actor 同时只能拥有一个有效 SubWorld Lease。
- 一个稳定 `ItemId` 同时只能拥有一个有效 `ItemLease`。

### 步骤 1：建立参与者、Baseline 与 ExpeditionLease 合同

#### ParticipantRecord

保存于 `SubWorldInstanceRecord`：

```text
ParticipantId
SourceActorId
EntryId
State
ProjectionRecord
Baseline
PortableItemSnapshots[]
CraftProcessSnapshots[]
ItemLeaseIds[]
EnteredParentTime
BodyElapsed
PendingOutcome
CommitId
```

状态：

```text
Preparing -> Inside -> Exiting -> Committing -> Returned
                          ↘ Lost
```

#### Baseline

`ActorProjectionBaseline` 冻结入场时允许比较的值：

- Actor ID、姓名快照和 ActorAsset ID。
- 生命、法力、体力、营养和修炼资源当前值与上限。
- 仙道境界、元素灵根、神识和战斗属性快照。
- Qiyun 当前值与有效上限。
- 主世界入场时间、年龄和 status 剩余时间。
- 已装备槽位对应的稳定 `ItemId`。
- 本次远征携带的 typed `PortableItemSnapshots[]` 与 `CraftProcessSnapshots[]` 深拷贝。
- Actor 自身技能只保存 `SkillBlueprint` 签名，第四阶段从同一蓝图编译 `CompiledSkillDefinition`；`MagicScrollSnapshot` 与 `TalismanSnapshot` 已在第二阶段通过共享嵌套 payload 保存完整 `SkillBlueprint`。

Baseline 只用于生成 Projection 和计算 Delta，不在返回时覆盖整个 ActorData。

#### Lease

`ExpeditionLeaseRegistry` 使用 `actor.data.id` 建立主线程可写、并行只读快照：

```text
ActorId
InstanceId
ParticipantId
EntryParentTime
FrozenAge
State
```

Friflo `TagExpeditionSequestered` 只作为 Cultiway Query 过滤镜像，Registry 才是原版并行 Patch 的查询来源。

本步验证：创建 Participant 后，Baseline、PortableItemSnapshots、CraftProcessSnapshots 与 Lease 引用全部归属于同一 `ParticipantId`；不读取任何投影 Entity 才能恢复这些数据。

### 步骤 2：建立 Portable Item、codec 与制造快照合同

#### 稳定物品身份

所有进入 portable 边界的 SpecialItem 增加 `PortableItemIdentity.ItemId`。`ItemId` 在物品首次进入某个世界槽位时生成，之后跨主世界 Entity、SubWorld Entity、保存读档和返回事务保持不变；禁止使用 Friflo `Entity.Id`、数组下标或对象 hash 代替。

公共基础快照：

```text
SpecialItemCoreSnapshot
  ItemId
  ShapeAssetId
  Name
  ItemLevel
  ItemIconData
  ItemCreation
  AliveTimerValue?
  AliveTimeLimitValue?
```

物品固有定义只在 typed snapshot 中保存；当前 holder、背包/装备位置与工序关系由 `SubWorldItemRecord` 或已提交的 MainWorld ownership 保存，`ItemLease` 只保存跨世界转移和提交幂等状态，不保存一个长期冻结的源 Entity。

#### typed snapshot 与 codec

```text
IPortableItemSnapshot
  ItemId
  SnapshotKind
  Core

IPortableItemCodec<TSnapshot>
  Capture(Entity source) -> TSnapshot
  Materialize(EntityStore targetStore, TSnapshot snapshot,
              ISpecialItemFactory factory) -> Entity

ISpecialItemFactory
  Create(EntityStore targetStore, SpecialItemCoreSnapshot core) -> Entity
```

`PortableItemCodecRegistry` 按明确的 `SnapshotKind + TSnapshot` 注册 codec。序列化器登记首批具体 DTO，不保存无类型 JSON、任意 ECS 组件包或未知类型 fallback。`ISpecialItemFactory` 的 `EntityStore` 是必传参数，内部不得固定访问 `ModClass.I.ActorExtendManager.World`。

首批六种 portable item typed snapshot 与共享嵌套定义：

| 类型 | 必须深拷贝的固有内容 | 不包含 |
| --- | --- | --- |
| `IngredientSnapshot` | Core、`ItemShape`、`ItemLevel`、`ItemCreation`、`ElementRoot`、`XianBase`、`Jindan` 及 `IngredientSemanticService` 消费的固有语义字段 | 持有者 Entity、`CraftOccupyingRelation` |
| `ElixirRecipeBlueprint` | Recipe/Asset ID、规范 Signature、`ElixirRecipeContext`、`ElixirIngredientRequirement[]`、CompositionSeed 与确定性效果定义 | `ElixirLibrary` 运行对象和 delegate |
| `ElixirItemSnapshot` | Core、`ElixirRecipeBlueprint` 深拷贝、药力值、效果类型与实例效果状态 | 对全局动态 `ElixirAsset` 的唯一引用 |
| `ArtifactInstanceSnapshot` | Core、`ArtifactBlueprint` 深拷贝、`ArtifactAbilityRuntime`、储藏、器灵及 extension 实例状态 | 持有者、装备槽位、显化 Entity |
| `MagicScrollSnapshot` | Core、`StoredSkillPayloadSnapshot`；Core 必须保留现有魔法卷轴 `AliveTimer/AliveTimeLimit` 寿命数据 | `SkillContainer` Entity、`CompiledSkillDefinition` 副本与万法阁目录引用 |
| `TalismanSnapshot` | Core、`StoredSkillPayloadSnapshot` | `SkillContainer` Entity、`CompiledSkillDefinition` 副本与万法阁目录引用 |

```text
StoredSkillPayloadSnapshot
  SkillBlueprint
  Signature
  Strength
  PowerLevel
```

`StoredSkillPayloadSnapshot` 只能作为两个载体 snapshot 的嵌套值对象，不注册成可独立携带的顶层物品。魔法卷轴 codec 保留现有魔法资格、学习/施放和寿命语义；符箓 codec 保留仙道资格、使用者力量换算和一次性施放语义。二者都按 `SkillBlueprint/Signature` 解析唯一 `CompiledSkillDefinition`，不保存运行时 definition，也不增加 `UseCount` 一类不存在的字段。

`ElixirRecipeBlueprint` 是共享制造定义，不是第二套 SubWorld 丹方。现有 `ElixirRecipeBuilder` 和 `IngredientSemanticService` 在第三阶段抽出纯快照核心后，MainWorld Entity 与 SubWorld portable item 都产生这个相同定义。

#### CraftProcessSnapshot

```text
CraftProcessSnapshot
  ProcessId
  ProcessKindId
  CrafterId
  InputItemIds[]
  OutputItemId
  TypedRecipeSnapshot
  TypedStateSnapshot
  RecipeCodecVersion
  StateCodecVersion
  Progress
  RandomState
```

`ProcessKindId` 是稳定字符串。首批归档允许 `alchemy`、`artifact_refining`、`talisman_crafting` 和 `magic_scroll_crafting`；recipe/state 只能由该 ID 在唯一 `ICraftProcessKindRegistry` 中绑定的 typed codec 编解码。重复或未知 ID、codec 类型不匹配都直接失败，不保存通用 payload。炼制中的产物和全部输入材料分别拥有 `ItemId`，通过数组建立关系，不保存 `CraftOccupyingRelation` Entity 引用。第二阶段只捕获、物化和再次捕获该快照，进度与随机状态都不推进；第三阶段在同一合同上实现共享制造。

万法阁、百宝阁只提供全局创作目录。`MagicScrollSnapshot`、`TalismanSnapshot`、`ArtifactInstanceSnapshot` 和 `CraftProcessSnapshot` 进入主世界槽位或 SubWorldArchive 时必须深拷贝 `SkillBlueprint`/`ArtifactBlueprint`；保存后编辑或删除目录条目不能改变世界内快照。

本步验证：六种顶层 DTO 均完成 `MainWorld Entity -> Capture -> Archive snapshot -> SubWorld Materialize -> Capture -> MainWorld Materialize -> Capture` 的 typed 结构等价往返，`ItemId` 全程不变；`ElixirRecipeBlueprint` 单独完成 encode/decode 深拷贝等价。两个技能载体中的 `StoredSkillPayloadSnapshot` 结构一致但 codec 和载体语义彼此独立，工厂创建的 Entity 确实属于传入 Store，快照中没有 Entity、compiled definition 或目录对象引用。验收比较 typed 结构，不比较 ECS Entity 身份。

### 步骤 3：实现 Actor 隔离与 ItemLease 所有权转移

#### 入场前置

Actor 必须：

- 存活且已经落地。
- 不在船、磁铁、外力位移或变形过程中。
- 位于消费系统指定的入口范围。
- 没有其他 SubWorld Lease。
- 已经完成或安全移交当前协调活动。
- 本次携带的每件物品都有稳定 `ItemId` 和已注册的 typed codec。
- 炼制中物品若随行，其 `CraftProcessSnapshot` 的产物与全部输入 ItemId 都包含在同一 Lease 集合。

入场顺序固定为：创建持久化 ParticipantRecord，捕获 Actor/Item/Craft baseline；对每件 MainWorld 来源物品调用对应 codec `Capture()`，写入并持久化 Archive snapshot、`SubWorldItemRecord` 和 `ItemLease`；随后在同一主线程提交边界移除 holder、装备和 craft occupying 关系并回收源 Entity；边界完成后再取得 `ExpeditionLease`、停止原工作并创建 Projection。不能先 `cancelAllBeh()` 再尝试创建记录，也不能在 Archive/Lease 持久化前移除源物品。边界后的重试不查找源 Entity，只依赖 Archive 和 Lease。

#### 原版更新门禁

Lease 期间：

- `Actor.updateParallelChecks()` 直接跳过普通更新和行为。
- `Actor.updateNutritionDecay()` 不推进营养。
- `Actor.updateAge()/getAge()` 使用入场年龄。
- `canAttackTarget` 在攻击者或目标被 Lease 时返回 false。
- `Actor.getHit()` 拒绝主世界伤害。
- 已排队 GetHit Event 在处理时再次过滤。
- `checkDeath()` 和 `die()` 仅允许 Outcome Commit Context 绕过。

#### Cultiway 系统门禁

以下系统的 Query 排除 `TagExpeditionSequestered`：

- 生命、魔力、灵气和气运恢复。
- 定时修炼、骑士获取和境界效果。
- 法宝装备、显化、载具和持续活动。
- 师徒寻访和其他会改变任务的候选系统。
- Cultiway status 时间推进；portable item 的 `AliveTimer` 只以快照值存在，本阶段不推进。

`DisposeActorExtendSystem` 不排除该 Tag；真实 Actor 被世界清理或外部删除时仍要回收 Projection 和 Lease。

#### ItemLease

`ItemLeaseRegistry` 以稳定 `ItemId` 为键，并提供主线程可写、并行只读快照：

```text
ItemId
SourceActorId
InstanceId
ParticipantId
OriginKind
State
CommitId?
```

`ItemLease` 是跨世界所有权转移与幂等状态，不是冻结 MainWorld Entity 的机制。MainWorld 来源物品在 Archive 入口提交时取得 Lease，并一直保持到返回或确定销毁；SubWorld 新生成或制造且要离开实例的物品在返回提交开始时取得 Lease。Archive 记录 holder、装备槽位和工序位置；Lease 只按 `ItemId` 防止两个世界同时提交同一物品。

提交边界前的 Capture/Archive/Lease 任一步失败，源物品仍由 MainWorld 正常持有；边界完成后源 Entity 已回收，任何恢复、保存或读档都不依赖它。稳定 `ItemId` 同时只能有一个有效 Lease，且 MainWorld 与 SubWorld 不能同时存在同一 `ItemId` 的有效 Entity。

未进入 Archive 的普通物品继续由 MainWorld 正常转移、装备和推进 `AliveTimer`。返回或确定销毁的提交成功后，先持久化 MainWorld ownership 与 `CommitId`，再删除 Archive item record/snapshot 引用并释放对应 `ItemLease`；`ExpeditionLease` 仍与真实 MainWorld Actor 绑定，按 Actor 返回事务最后释放。

#### 表现

主世界单位渲染过滤 Lease Actor，入口 Building 显示远征人数与状态。不能只写 `is_visible=false`，因为原版每帧会更新可见性。

本步验证：远征期间尝试移动、攻击或修改 Actor 资源均被门禁；归档物品不再有 MainWorld Entity，Archive holder 与 Lease 状态保持唯一，而未参与远征的 Actor 和物品继续正常运行。

### 步骤 4：实现 Projection 与 portable item 投影

`ExpeditionProjectionFactory` 从 Baseline 创建纯数据组件：

```text
ProjectionIdentity
SubWorldPosition
ProjectionFaction
ProjectionVitals
ProjectionStats
ProjectionElementRoot
ProjectionResources
ProjectionVisual
ProjectionController
ProjectionInventory
```

- `SourceActorId` 只作为返回身份，不用于访问主世界 Actor 热路径。
- ProjectionVisual 解析 ActorAsset 的 sprite ID 快照，但使用小世界自己的 SpriteRenderer。
- 主世界 avatar、render_data、batch 和材质实例不进入小世界。
- 小世界视图可以显示姓名和头像，但所有详情来自 Projection ReadModel。

`ProjectionInventory` 只保存有序 `ItemId[]`。每个 `SubWorldItemRecord` 从 Archive snapshot store 取出 typed snapshot，通过对应 codec 和 `ISpecialItemFactory` 物化到当前 `SubWorldRuntime.EntityStore`，得到本世界的只读 Runtime Entity 并保持相同 `ItemId`。Archive 可以在 Dormant 状态没有这类 Entity；MainWorld 不同时物化同一 `ItemId`。

- 不加入使用、装备、转移、掉落、消耗或制造 system。
- 不推进 `AliveTimer` 或 `CraftProcessSnapshot.Progress`。
- `MagicScrollSnapshot` 与 `TalismanSnapshot` 只携带嵌套 `StoredSkillPayloadSnapshot`，不编译、学习或执行技能。
- `ArtifactInstanceSnapshot` 只恢复固有定义与实例状态，不创建显化物或装备关系。

本阶段角色由简单自主移动或玩家右键命令控制。消费系统以后可以选择完全 AI、玩家可指挥或只读观察。

本步验证：Projection 与每个物品投影都属于实例 Store，不引用主世界 `Actor`、`ActorBinder`、SpecialItem Entity 或 SkillContainer Entity；关闭浮窗只销毁 View，不销毁 Archive 权威数据，Runtime 卸载时可从 snapshot/record 重新物化。

### 步骤 5：实现入口、退出和 BodyTime

#### 入口

每个 Template 定义一个或多个 Entry ID。参与者创建 Projection 时放置在对应 Entry tile；位置被占用时使用入口附近合法空格，不允许两个实体共享阻挡格。

#### 退出

退出条件由 Template 决定，首版支持：

- Projection 到达 Exit tile 后主动返回。
- 玩家或消费系统在允许撤离时请求退出。
- Instance 完成后强制结算全部参与者。

退出请求在 tick 边界冻结 Projection，状态进入 Exiting，之后不再接受移动命令。

#### BodyTime

Projection 每 tick 按 ClockProfile 累积：

```text
BodyElapsed += LocalElapsed * BodyTimeRatio
```

主世界 Lease 期间年龄被冻结。释放时按以下目标调整 `created_time`：

```text
最终年龄增量 = BodyElapsed
created_time += ParentElapsed - BodyElapsed
```

单位换算使用原版一年 60 世界秒，不把小世界本地秒直接当年龄年数。

原版 status 的 `_end_time` 在释放时增加 ParentElapsed，使其保持入场剩余时长；小世界产生的新状态由 OutcomeDelta 单独添加。

`AliveTimer` 的入场值随 typed snapshot 保存，第二阶段不按 ParentTime、LocalTime 或 BodyTime 推算，也不推进；它不是 Lease 期间冻结源 Entity 的 gate。物品时间属于后续明确 capability，不从 Actor BodyTime 推导。

本步验证：BodyTimeRatio 为 0、1 和大于 1 时只改变 Actor 返回年龄；同一轮测试中的 portable item `AliveTimer` 和 CraftProcess progress 始终等于入场快照。

### 步骤 6：实现 OutcomeDelta 与物品物化返回

Actor 资源 Delta：

```text
OutcomeDelta
  CommitId
  HealthValue
  ManaValue
  StaminaValue
  NutritionValue
  WakanValue
  QiyunValue
BodyElapsed
```

物品返回集合：

```text
PortableItemReturnRecord
  ItemId
  SnapshotKind
  ReturnedSnapshot
  FinalHolder
  Disposition
  BaselineSignature

PortableItemReturnSet[]
CraftProcessSnapshots[]
```

第二阶段没有任何会修改物品的命令，因此每个存活物品的 `ReturnedSnapshot` 必须与同 ItemId 的 Baseline typed snapshot 结构等价，`CraftProcessSnapshot` 的 Progress 与 RandomState 也必须相同。返回验证的是 typed 结构和稳定 `ItemId`，不是 ECS Entity 身份。所有物品都由 Archive 权威到返回提交结束；返回时先卸载 SubWorld Runtime materialization，再由同一 typed codec 在 MainWorld 目标 Store 物化。

`SubWorldOutcomeCommitService` 在主线程模拟边界执行：

1. 在 tick 边界冻结 Projection 与 portable item 投影。
2. 用各 typed codec 从 SubWorld Runtime 或 Archive snapshot 生成 `PortableItemReturnSet` 与 `CraftProcessSnapshots`，并把最终 holder 冻结进 `PendingOutcome` 的 `OutcomeDelta`。
3. 验证 Participant 仍为 Exiting、`CommitId` 未完成，且所有 ItemId、SnapshotKind、固有字段和制造进程与 Baseline 相同。
4. 对即将带回的 Archive-origin 新物品取得本次 `CommitId` 的 `ItemLease`；已有 MainWorld 来源物品沿用入场 Lease。
5. 先销毁或卸载 SubWorld portable item Runtime materialization；Archive snapshot、`SubWorldItemRecord` 和 `PendingOutcome` 在此期间仍是唯一权威。
6. 对每个存活物品，按 `ItemId + CommitId` 查询 MainWorld ownership。没有已物化结果时，在同一主线程 item commit 边界调用原 `IPortableItemCodec.Materialize(targetStore, snapshot, factory)` 创建同一 `ItemId` Entity、绑定 `FinalHolder`，并持久化带本次 CommitId 的 ownership；已有结果只复用记录，不重复创建。第二阶段没有消耗项，后续阶段的 `ConsumedOrDestroyed` 不执行 Materialize。
7. 解析仍存活的 Source Actor，并通过原版资源 setter 和现有资源 Service 写入 Actor 当前值。
8. 所有资源值按返回时真实上限 clamp，调整年龄与冻结 status 时间，标记 Actor/Cultiway stats dirty。
9. 全部字段提交成功并持久化完成的 `CommitId`，确认每个存活物品的 MainWorld ownership 已带同一 CommitId 后，删除对应 Archive item record 和不再可达的 snapshot 引用；再释放完成或确定销毁物品的 `ItemLease`，删除 SubWorld Projection，并把 Participant 标为 Returned。
10. 最后释放 `ExpeditionLease`，恢复主世界 Actor 的渲染和普通 AI。

写入采用 Projection 最终值而不是“入场差值加到当前主世界值”，因为 Lease 保证主世界本体的这些资源没有并发变化。

提交失败时保持 Committing、ExpeditionLease、Archive、`PendingOutcome` 和全部相关 ItemLease；即使 SubWorld Runtime 已卸载，也只从 Archive snapshot 恢复，不能回到已回收的源 Entity。没有 generic codec、按位置猜物品或用目录当前定义重建物品的处理路径。

本步验证：六种顶层 portable snapshot 与内嵌的 `StoredSkillPayloadSnapshot` 经过“Capture -> SubWorld Materialize -> Capture -> MainWorld Materialize -> Capture”后，ItemId 不变且 typed 结构等价；重试按 ItemId+CommitId 不重复物化、绑定、提交资源或释放 Lease。

### 步骤 7：实现参与者、物品与 Lease 读档恢复

保存前：

- ParticipantRecord、ProjectionRecord、PortableItemSnapshots、CraftProcessSnapshots、BodyElapsed、PendingOutcome 和 CommitId 全部写入 Archive。
- ExpeditionLeaseRegistry 与 ItemLeaseRegistry 不直接序列化；`ExpeditionLease` 由 Inside/Exiting/Committing Participant 推导，ItemLease 由 Archive item record、PendingOutcome item changes 和提交状态推导。
- ActorData 不重复保存整份 Projection。
- 世界槽位保存 Skill/Artifact/Elixir 定义的深拷贝，不只保存万法阁、百宝阁或动态 ElixirLibrary 的目录 ID。

读档顺序：

1. 恢复 SubWorldArchive。
2. 原版完成 Actor 加载。
3. `finishMakingWorld` 后解析 SourceActorId。
4. 在任何 Actor 或制造 system 推进前重建 `ExpeditionLease`；从 Archive item record 与 `PendingOutcome` 恢复 ItemLease，不按 ItemId 查找旧 MainWorld source Entity。
5. 活跃实例通过 Archive 内 typed snapshot 和明确的 Runtime `EntityStore` 重建 Projection 与 portable item Entity；Dormant 只保留 Archive。
6. 恢复主世界 Actor 的渲染门禁和只读 ProjectionInventory。
7. Committing 状态按 `ItemId + CommitId` 查询已持久化的 MainWorld ownership，已物化项只确认结果，未完成项继续从 Archive Materialize。

找不到 Source Actor 时 Participant 进入 Lost，由消费系统处理队伍结果；不能生成同名替代 Actor。

本步验证：在 Inside、Exiting、Committing 三种状态读档时，Actor 与 Item Lease 都先于首帧模拟恢复；修改全局万法阁/百宝阁目录后再读档，世界槽位中的 SkillBlueprint 与 ArtifactBlueprint 内容不变。

### 步骤 8：完成隔离与返回验收

测试 Template 增加一块非致命资源消耗区域，使 Projection 在内部损失生命、法力或灵气后返回，验证 Delta。测试角色携带 Ingredient、Elixir、Artifact、MagicScroll、Talisman 各一件，并携带一份 `ElixirRecipeBlueprint`，覆盖六种顶层 typed snapshot 和内嵌 `StoredSkillPayloadSnapshot`，再附带一份冻结的 `CraftProcessSnapshot`；只执行查看、保存和退出，不提供任何物品使用或制造命令。

本步验证：完成“Archive 入场提交 -> Actor 隔离 -> 资源消耗 -> 物品只读查看 -> 保存读档 -> 退出物化提交”的单条流程；Actor 资源按 Delta 返回，所有物品和制造进程保持 typed 结构等价且 ItemId 不变，两个世界时钟仍独立运行。

## 验收标准

### 隔离

- Actor 入场后仍存在于主世界 manager 和保存数据中，但不渲染、不移动、不攻击、不受伤。
- 营养、年龄、原版 status 和 Cultiway status 在主世界侧不推进。
- 主世界恢复、修炼、法宝和师徒系统不修改 Lease Actor。
- MainWorld 来源物品先 Capture 并持久化 Archive snapshot/record/Lease，再在同一提交边界解除源关系并回收源 Entity；边界前失败不移除源，边界后恢复不依赖源 Entity。
- Archive/Runtime 物品只由稳定 ItemId、typed snapshot、SubWorldItemRecord 和 ItemLease 表示；Dormant 可以没有 Runtime Entity，两个世界不能同时物化同一 ItemId。
- 返回先卸载 SubWorld materialization，再按 `ItemId + CommitId` 幂等调用 typed codec Materialize 存活物品；消耗或销毁物品不 Materialize。MainWorld ownership 与 CommitId 持久化后才删除 Archive 引用并释放 ItemLease；Actor Lease 最后释放。
- 浮窗打开并运行 Projection 时，未被 Lease 的主世界 Actor 继续执行普通 AI 和战斗。
- 一个 Actor 无法同时进入两个实例。
- 世界清理仍能回收被 Lease 的 ActorExtend、Projection 和 Registry 条目。

### Projection 与返回

- Projection 的坐标、资源和视觉不引用 Actor、WorldTile 或 ActorBinder。
- portable item Entity 属于 SubWorld Runtime 的显式 `EntityStore`，不引用主世界 SpecialItem Entity、SkillContainer Entity 或目录对象。
- 内部资源消耗返回后准确写入主世界 Actor。
- 返回时按当前真实上限 clamp，不覆盖 trait、装备或无关 ActorData。
- BodyTimeRatio 为 0、1 和大于 1 时，年龄结果符合 ClockProfile。
- Commit 失败时 Actor 不提前恢复，Archive、PendingOutcome 和 Lease 保留；重复 `ItemId + CommitId` 不重复物化、绑定或写结果。

### Portable Item

- `ItemId` 在主世界 Entity、snapshot、SubWorld Entity、保存读档和返回记录中一致，且不等同于任何 ECS Entity ID。
- `IngredientSnapshot` 完整保存 `IngredientSemanticService` 所需固有输入，重新构建的语义档案一致。
- `ElixirItemSnapshot` 内嵌 `ElixirRecipeBlueprint`，不依赖当前动态 ElixirLibrary 才能恢复定义。
- `ArtifactInstanceSnapshot` 同时保存 `ArtifactBlueprint` 固有定义和能力、储藏、器灵等实例状态。
- `MagicScrollSnapshot` 保存 `StoredSkillPayloadSnapshot` 与寿命数据，`TalismanSnapshot` 保存独立载体快照；二者都不保存 SkillContainer Entity 或 CompiledSkillDefinition 副本。
- 六种顶层 codec 完成 `Capture -> SubWorld Materialize -> Capture -> MainWorld Materialize -> Capture` 后 typed 内容结构等价，`ItemId` 不变，`ElixirRecipeBlueprint` codec 深拷贝往返等价。
- `ISpecialItemFactory` 创建的 Entity 总是属于调用方传入的 Store，不访问固定全局 Store。
- `CraftProcessSnapshot` 的 `ProcessKindId`、typed recipe/state、InputItemIds、OutputItemId、Progress 和 RandomState 在本阶段不变化；未知 Kind ID 不能恢复为模糊工序。
- SubWorld UI 和命令队列没有使用、制造、装备、转移、掉落或消耗入口。
- 修改或删除万法阁、百宝阁目录条目不会改变已保存到世界槽位的深拷贝定义。

### 存档

- 在 Inside、Exiting 和 Committing 状态保存读档后，Actor、Archive typed item snapshot 和 CraftProcessSnapshot 均能恢复。
- 读档重建 `ExpeditionLease`、Archive item record 与相关 ItemLease 前，Actor 和制造 system 不执行一帧；`AliveTimer` 只按 snapshot 恢复且本阶段不推进。
- Source Actor 缺失时 Projection 不错误绑定同 ID 之外的对象。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
