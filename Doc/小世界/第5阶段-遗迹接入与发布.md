# 第5阶段-遗迹接入与发布

本阶段扩展已经完成的最小神力 Provider，把阶段 4 已验证的 Party Admission 接入主世界组队 AI，并加入 Hidden 发现、可选内容 Provider、正式 UI、日志、异常清理和多 Site 调度，以真实负载确定发布容量。阶段完成后，玩家不需要 Debug 工具即可在一个当前会话中看到多处不同遗迹被发现、接续探索、争夺、耗尽或崩塌。

本阶段不继续堆叠第三种遗迹、完整技能、更多物品或制造。发布稳定性优先于内容数量；宗门驻地和完整独立世界在此阶段验收完成后另立规划。

## 具体说明

### 设计边界

- `SubWorldManager` 只认识 Runtime 及通用 Actor/Building/Tile 生命周期，不认识遗迹能力、Site Provider、主世界 Building/Actor 或内容来源。
- Site Provider 只负责创建/销毁主世界入口、选择 Archetype 和解释用途事件；`RuinSiteService` 唯一创建/维护 Site MetaObject。Provider 不直接修改 Runtime Actor、Building、Tile 环境、claims 或 relations。
- 阶段 1 已正式实现玩家神力投放的 `RuinPowerSiteProvider`；本阶段只扩展其能力。`OpportunityLegacySiteProvider` 是可选内容接入，不是小世界发布门槛；自然世界生成以后再由对应消费者接入。
- 主世界 Actor 由 AI 自主发现、评估、前往和探索；正式 UI 不提供逐格移动、攻击、调查或领取按钮。
- 多 Site 容量根据 1/2/4/8 个真实 Runtime 的 Profile 结果确定，不预写固定上限。
- 不实现 Active/Warm 解析式后台演化。空遗迹只按明确 ClockPolicy 暂停或继续，不切换成另一套模拟。
- 所有状态只属于当前会话；世界保存/加载不恢复 Runtime、Site、Binding 或 RuinLootId。
- 发布验收要求阶段 2 的古修道场和阶段 4 的远古战场通过既有内容合同，不以增加第三种半成品 Archetype 代替质量工作。

### 步骤 1：扩展既有 RuinPowerSiteProvider 与用途边界

#### Site CreateRequest

阶段 1 已建立 `RuinSiteCreateRequest`、`RuinSiteService`、`CreateSite`、单 Actor `RequestAdmission` 和 `RuinPowerSiteProvider`。本阶段在不改变其所有权的前提下，为 Hidden 发现、组队和公开风险信息扩展 CreateRequest；第二 Provider 若实际接入，由 SiteService 另持 Provider key 映射，不把接口对象塞入输入：

```text
RuinContentId
Seed
MainWorldAnchor
EntranceBuildingId
DiscoveryProfileId
AdmissionProfileId
ThreatTier
ExpectedOpportunityTier
```

`RuinSiteId` 仍由 `RuinSiteService.CreateSite(request)` 在调用内分配；`EntranceBuildingId` 必须来自 Provider 已成功创建的主世界入口。两者和 Site MetaObject 中的 `InstanceId` 都只在当前会话有效。CreateRequest 不保存 InstanceId、Runtime Actor/Building Entity、WorldTile 或 UI 引用，也不承载可写进度；`RuinSiteRecord` 只保存 SiteId、Runtime binding、生命周期和 Public Knowledge，探索摘要由 ReadModel 派生。

`ThreatTier/ExpectedOpportunityTier` 是主世界 AI 在发现后能掌握的粗略公开信息；不暴露隐藏守卫、精确收益或具体 GenerationPlan。

#### 可选 Provider 合同

```text
IRuinSiteProvider
  CreateEntrance(context) -> EntranceHandle
  CreateRequest(context, entranceHandle) -> RuinSiteCreateRequest
  OnSiteDiscovered(siteId, discovererId)
  OnSiteExhausted(siteId, readModel)
  OnSiteCollapsed(siteId, readModel)
  RemoveEntrance(siteId)
```

Provider 负责解释遗迹对自身玩法的意义，`RuinSiteService` 负责共享 Runtime 的一致行为。只有[机缘道统](../机缘道统-摘要.md)完成开放遗迹重写并确实接入第二个 Provider 时，才从两个具体实现已重复的入口/事件行为提取最小 `IRuinSiteProvider`；否则跳过此接口，继续使用阶段 1 的具体 `RuinPowerSiteProvider`。发布不得为制造第二个消费者而创建空实现或通用内容工厂。

既有与可选 Provider：

| Provider | 创建方式 | 完成后结果 |
| --- | --- | --- |
| `RuinPowerSiteProvider` | 玩家在合法主世界格投放 | 更新 Building 状态并保留到销毁/会话结束 |
| `OpportunityLegacySiteProvider`（可选） | 机缘道统按自身规则投放古修遗迹入口 | 把发现、伤亡、战利品和耗尽转成机缘道统事件；不作为小世界发布门槛 |

Core 不引用这两个类型。Provider 创建流程：

1. 校验 Provider context 并创建主世界 Entrance，取得 `EntranceBuildingId`。
2. 以 EntranceHandle 构造不可变 `RuinSiteCreateRequest`。
3. 调用 `RuinSiteService.CreateSite(request)`；Service 分配 SiteId、创建 Site MetaObject，并调用 Manager Create/绑定 Runtime。
4. 全部成功后发布 SiteCreated；失败则 Service 删除未发布 MetaObject/Runtime，Provider 删除 Entrance。

不得留下入口已存在但 Runtime 创建失败的半状态，也不得在失败时创建“空白默认遗迹”。

#### 对外命令

用途外部只能调用：

```text
CreateSite(request)
DiscoverSite(siteId, actorId)
RequestAdmission(siteId, partyAdmissionRequest)
RequestCollapse(siteId, reason)
DestroySite(siteId, reason)
GetSiteReadModel(siteId, disclosureContext)
```

主世界 AI、入口和导航只请求 `Public` context；选中某一参与者/队伍的 WorldView 信息页请求对应 `Participant(ParticipantId)`，切换观察对象时必须重建 ReadModel；`Debug` 只允许开发诊断。Collapsed Site 已无 Runtime，只能从 MetaObject 的不可变最终快照返回 Public ReadModel，Participant/Debug 查询失败。调查 Building、战斗 Actor、拾取地面 loot Building 和返回继续走 Runtime/Expedition command；Provider 不能直接把 Opportunity 槽设为 Exhausted，也不能写 Tile 危险覆盖或参与者 Knowledge。

### 步骤 2：扩展 Hidden 发现、寻访、组队与入场 AI

#### 发现

阶段 1 的神力 Provider 默认直接创建为 Discovered，阶段 4 已把 Runtime 边界扩展为原子 `PartyAdmissionRequest`。本阶段新增 Hidden 发现、多 Site 寻访与主世界 AI 组队，并把形成的请求接到既有 Admission；可选第二 Provider 也只能复用这条边界。Hidden 遗迹只有 Actor 的主世界感知行为可以发现：

- 候选 Actor 必须存活、未 Binding、可以到达入口附近。
- 感知距离与现有修为/感知属性适配，具体字段实现前核对当前代码。
- 每个 Site 按低频间隔扫描附近候选，不每帧遍历全部 Actor。
- 首个发现者触发 `SiteDiscoveredEvent`，把 Site MetaObject 的公开知识从 Hidden 改为 Discovered；物理生命周期保持 Open，入口和导航按钮才向玩家公开。
- 玩家相机看到 Hidden Building 不等于玩法发现；Hidden 外观使用自然遗构而非“不可见碰撞体”。

神力 Provider 可以直接创建为 Discovered，便于玩家测试和主动投放。

#### 寻访效用

主世界 AI 只使用公开摘要：

```text
Interest = ExpectedOpportunityTier
         + ActorCuriosity/Affinity
         - ThreatTier * RiskAversion
         - MainWorldTravelCost
         - CurrentObligations
```

- 不读取内部机缘数量、精确品质、守卫位置或已隐藏战利品。
- Site 已部分探索时，公开 ReadModel 可以降低预期收益，但不告诉 AI 剩余宿主 Building 坐标。
- Actor 有紧急战斗、死亡、被控制或已有 Expedition Binding 时不能加入。
- 目标 Site 的 ReadModel 已为 Exhausted，或物理生命周期进入 Collapsing/Collapsed 时取消寻访。

#### 组队

阶段 4 已支持两队，主世界侧建立最小组队：

- 发起者按现有关系在附近选择 0-2 名可加入成员。
- 候选成员在前往途中不占用 Runtime 名额；到达入口后先逐个执行纯校验，非法随行者在创建 PartyAdmissionRequest 前过滤，发起者非法则整次取消。
- 过滤后的 Party 在真正入场边界创建；每个保留成员都必须通过 Binding reservation。
- 同一 Site 可以有第二支队伍前往，不建立全局独占 reservation。
- Admission 达到当前 Profile 得出的上限时返回 Busy；AI 等待一个低频周期或选择其他 Site，不无限每 tick 重试。

#### 抵达与入场

- 主世界移动仍使用原版 Actor 行为和 Building 交互。
- 所有成员进入入口交互范围后，PartyAdmissionRequest 在同一主线程批量验证。
- 对过滤后的成员创建 Binding reservation，再逐个创建 Projection Actor；全部成功才激活 Party，任一创建/放置失败则回滚本批所有 Projection/Binding，不在失败时临时缩减已提交的 Party。
- 入场后主世界 Actor 从会话内门禁隐藏；Building 显示内部人数。

### 步骤 3：完成入口、导航、观察状态与 WorldLog

#### 主世界入口表现

Entrance 至少表达：

| 披露/生命周期/ReadModel | 世界表现 | Tooltip 摘要 |
| --- | --- | --- |
| PublicKnowledge Hidden | 普通残破遗构，无显眼发光标记 | 不显示遗迹玩法信息 |
| Open + Unexplored | 可辨识入口和 Archetype 图标 | 类型、公开危险档、内部人数 |
| Open + Partial | 遗构有被扰动痕迹 | 已公开 Building/机缘槽数、公开耗尽数、内部人数 |
| Open + Exhausted ReadModel | 灵气/道痕沉寂 | 已无可用机缘；停止 Admission |
| Collapsing | 明确不稳定反馈 | 剩余本地倒计时、内部人数 |
| Collapsed | 坍塌遗构 | 不可进入、崩塌原因摘要 |

数字只显示 Site Public Knowledge 允许的 Building 和能力信息；未公开的 Opportunity 槽不计入“已知总数”，物理总数只在 ReadModel 规则允许时公开。入口外观只消费 ReadModel，不能保存或回写另一份进度。

#### WORLD 导航

复用现有 `SubWorldNavigationSection`：

- 主世界按钮保持原语义。
- 每个 Discovered 且 Runtime 存活的 Site 一个图标按钮，按 Site 创建序稳定排列。
- 图标包含 Archetype、物理生命周期和 ReadModel 角标；Tooltip 显示名称、公开探索摘要和参与者。
- 点击只调用 Focus；不创建、重置、传送 Actor 或领取收益。
- 局部暂停、1x/2x/4x 和聚焦参与者继续只绑定当前 FocusedRuntime。
- 参与者选择只用于观察信息页，不出现玩家移动/攻击/调查命令。

按钮使用原版 `PowerButton` 交互语义和 Tooltip；不新建横向文字胶囊或大型遗迹列表窗口。

#### WorldView 观察

玩家能看到：

- 全部基础 Tile 地貌和按 Public context 可见的显著 Building。
- Site Public Knowledge 允许显示的 Landmark、HazardController/Tile 覆盖、Guardian Actor 和 Opportunity 槽状态。
- 选中某个参与者/队伍后，再叠加且只叠加该 `Participant` context 的 KnownObjects、EvidenceObservation、KnownHazardCoverage，以及对应 Actor 的生命、战斗、调查、持有物和返程状态；不能把多队私有 Knowledge 求并集。
- 已公开的 Tile 改变、死亡现场、地面 loot Building 与崩塌波次。

玩家不能看到：对当前 disclosure context 未定位的 Building、隐藏能力 payload/秘密 EvidenceRelation、守卫隐藏仇恨数值、AI Utility、完整 path 或 RNG。Debug Overlay 单独受开发配置控制。

#### WorldLog

至少注册：

- 遗迹被发现。
- 某队进入/返回。
- 取得 Ingredient/MagicScroll/Insight。
- 修士撤退、死亡。
- 两队因机缘发生冲突。
- Site ReadModel 首次派生为 Exhausted。
- 遗迹开始崩塌/已经崩塌。

同一批拾取不逐件刷屏；按一次调查/返回事件聚合。日志中的 Actor、Site 和物品名称使用现有格式化器，不手拼颜色富文本。

### 步骤 4：实现多 Site 调度并用实测确定容量

#### 逻辑策略

不建立 Active/Warm 两套模拟。每个 Runtime 仍执行相同 fixed-tick Systems，但通过 Core 定义的用途无关 `SubWorldWorkSignal` 提供空闲 fast path：

```text
TickDemand: Idle | NeedsTicks
PriorityClass: Normal | Urgent
```

遗迹用途层从自身真实状态派生该信号，Core 不读取 Participant、Hazard、Collapsing、Settling 等遗迹类型。ClockPolicy 优先级固定为：

1. 未结算 transaction、生命周期倒计时或其他必须完成的边界工作始终 `NeedsTicks/Urgent`，即使当前没有参与者。
2. 有参与者 Actor 时为 `NeedsTicks`；遗迹用途层可以把紧急返回等映射为 Urgent，但不把原因暴露给 Core。
3. 没有参与者、没有 mandatory work 且 ClockPolicy 为 `PauseWhenEmpty` 时为 `Idle/Normal`；守卫 Actor 和移动 HazardController/Tile 覆盖一起冻结。首批两个 Archetype 使用此策略。
4. 只有明确配置 `ContinueWhenEmpty` 时，空 Runtime 的普通 Actor/Hazard 模拟才为 `NeedsTicks/Normal`。

Idle 只跳过 gameplay tick，不改变 LocalTime、Actor/Building/Tile 状态或显式业务 seed/roll。新队进入后从原状态继续；它不是解析式演化，也没有不同公式。

#### 调度顺序

`SubWorldManager.Update` 每帧：

1. 只读取各 Runtime 的通用 `SubWorldWorkSignal`，收集 TickDemand=NeedsTicks 的实例。
2. 按 PriorityClass、累计欠债、InstanceId 排稳定顺序；Manager 不知道 Urgent 的遗迹原因。
3. 在 `FramePriorityGovernor` 预算内逐个执行完整 fixed tick。
4. 未获得时间片者保留 accumulator；不合并或跳过 tick。
5. View prepare/render 继续独立按相机相交执行。

Urgent 只影响获得时间片顺序，不改变单 Runtime 内系统顺序；任何用途都可发布同一通用信号，不向 Core 增加 `SubWorldKind` 分支。

#### 真实性能 Profile

用 Release 构建或游戏实际配置分别运行：

| 组合 | Runtime 内容 |
| --- | --- |
| 1 | 1 个 Party MetaObject、1-3 个 Projection Actor、12 个内容 Building、5 个 Opportunity 槽、8 个守卫 Actor、2 个 HazardController |
| 2 | 每个 Site 1 队，中等战斗/调查并存 |
| 4 | 两个古修道场、两个战场，至少一处两队争夺 |
| 8 | 最坏压力样本，只用于测量是否可支持 |

采集：

- 每个 gameplay System 平均/P95/P99 时间。
- 每帧 Runtime tick 数、欠债 tick、结算延迟。
- Navigation、Perception、Combat、RenderPrepare 的 GC 与分配。
- Actor/Building Entity 数、各遗迹 capability 数、Tile 环境修改量、MetaObject 数、Path、Knowledge、Threat、`OpportunityClaimKey`、地面 loot Building、carried relations、RuinLoot、VFX pool 数量。

发布硬上限选择规则：在目标硬件上 P99 小世界总 CPU 不超过经项目确认的帧预算、无持续 tick 欠债、稳态 0 B GC 的最大 Site/参与者组合。把测得数字和最终常量写回本文件，不在测量前承诺 8 个实例或 1 ms。

达到上限时新 Site 创建返回 `CapacityReached`，Provider 删除刚创建入口并记录一次日志；不静默销毁旧 Site，也不创建无 View/无逻辑的残缺实例。

### 步骤 5：实现异常边界、会话清理与故障注入

#### 会话边界

全部小世界状态不进入存档：

- Binding 通过内存索引阻止 Actor 推进，不写需要恢复的永久隐藏字段。
- 世界保存时 Source Actor 在存档数据中仍是入场前主世界状态；未返回收益尚未物化，重新加载相当于回到入场前。
- `SettlementStagingRegistry` 只保存 `SourceActorId/HolderId`、typed values、仅含标量/不可变 typed value 的 ActorOldValues、`MaterializerKey` 和纯数据参数；禁止 Actor、Entity、Store、adapter、delegate、handler 或 Unity 引用，commit port 只在提交段内按 ID/Key 解析它们。
- Commit 的 MainWorld promote 与 Runtime 最终状态更新处于同一不可重入主线程调用；保存、入口删除、`clearWorld` 和 Mod 重载只能在调用前中止 staging，或在调用完整返回后继续。
- 已成功返回并物化的物品、生命变化和正式结果属于主世界状态，继续走现有存档；会话清理不得把它们当 staging 删除。
- 加载/切换世界时 `MapBox.clearWorld` 先让 Expedition 服务清除 StagingRecord/回滚 Prepared Token，再释放 Site 内存引用，最后清 Manager/WorldView/Slot。
- 新世界中若 Provider Building 因原版存档仍存在但没有当前会话 Site，Provider 在加载扫描中直接删除/失效该孤立入口；不从 Building 反建旧 Runtime。

#### 活动 Source Actor 失效

非 clearWorld 场景中，如果仍存活的 Projection 对应 Source Actor 在 Prepare 前或 Prepared 状态下变成 canonical removed/dead：

1. 阻止新的 Prepare；已有 StagingRecord 删除并把统一 Settlement Rollback 到可清理状态。
2. 非物理 Outcomes 消失，其 `Participant` claims 从 Reserved 回到 Available。
3. 每份 carried loot 保持 `Loot(RuinLootId)` claim owner，在 Projection 当前 Tile 原子创建地面 Building 并把 carrier 转为 Ground；任一物化失败都阻断该 Projection 清理并进入显式 Faulted 诊断，不能静默删除 loot。
4. 删除 Projection Actor/Binding，把 Party Member 标记 Aborted；Party 最后一名活动成员结束时按阶段 4 规则退休。
5. 不创建替代主世界 Actor，不应用生命/Insight，不调用死亡入口。

若失效来源是 `clearWorld`/切换会话，则不在即将销毁的 Runtime 中物化地面 loot，直接走整会话清理且不发奖励。不可重入 Commit 调用期间禁止 Source Actor 删除；调用返回后只能观察完整成功或完整回滚。

#### 入口消失

Entrance 被摧毁或 Provider 主动撤销：

1. Site MetaObject 的生命周期进入 `Collapsing`，记录 `CollapseReason=EntranceDestroyed/ProviderRemoved` 并停止新 Admission；`Aborted` 只用于单次 Expedition 结果，不增加 Site 状态。
2. 内部存活 Projection Actor 以当前 Entry Tile 强制开始 Return；主世界出现位置使用原入口 Anchor。
3. Prepared 但尚未 Commit 的 transaction 删除 StagingRecord 并 Rollback；不可重入 Commit 段不能被入口删除插入，调用返回后只会看到完整成功或完整失败。
4. 倒计时结束仍未返回者按阶段 3 死亡结算。
5. 参与者、claim、loot 和未结算 token 清零后，Service 捕获不可变最终公开快照并销毁 Runtime，再把 Site 生命周期提交为 Collapsed、发布最终 ReadModel/事件。Collapsed MetaObject 不再持有 InstanceId/Runtime 引用。
6. Provider 策略若保留坍塌入口，则保留只含最终快照的 Site MetaObject；若入口已经消失或要求彻底移除，再调用 DestroySite 删除 MetaObject 和导航按钮。

不得直接 Destroy Runtime 丢弃内部 Actor。

#### 故障注入点

Debug 必须可精确注入：

- Generator/Validator 失败。
- WorldView 创建失败。
- Party 第 N 个 Projection 创建失败。
- Move/Investigation event handler 失败。
- SettlementStagingRecord 创建/校验失败。
- MainWorld commit port 在 Ingredient/MagicScroll 第 N 个物化时失败。
- MainWorld promote 成功后、Runtime 无分配最终提交前注入失败，验证 Receipt 回滚。
- Source Actor 在 Prepare 前或 Prepared 后失效：非物理 claim 释放、carried loot 原子落地、Member Aborted；Commit 不开始且无悬空 Binding/owner。
- death port 预检失败（入口未调用）后同一 Token 重试。
- 死亡入口已令 Actor canonical dead/removed 后抛错；断言 Ledger 为 Applied、Runtime 最终 Settled、同一 Token 再处理时死亡入口总调用数仍为 1。
- 死亡异常后 canonical state 未生效且副作用不可证明时进入 Faulted；禁止自动重试并阻断发布。
- 入口在战斗、Prepared settlement、DeadPendingSettlement 或完整 Commit 后被删除。
- 保存/clearWorld/Mod 重载分别发生在 Prepare 前、Prepared 后和 Commit 调用返回后；不能注入到不可重入提交段内部。

每个故障都验证以下计数：Site MetaObject、Runtime、Binding、Projection/Guardian Actor、内容/地面 loot Building、Tile 环境索引、Party MetaObject、Knowledge、Path、Threat、`OpportunityClaimKey` claim、carried relation、RuinLoot、settlement ledger、DeathToken、DeathApplicationLedger、StagingRecord、PromotionReceipt、待确认主世界 Entity、WorldView、Slot、Renderer/VFX pool。每条结算失败路径结束后 StagingRecord、PromotionReceipt 和待确认主世界 Entity 必须为零；Applied/可重试死亡流程最终完成后 DeathToken/Ledger 条目必须移除，Faulted 条目保留诊断并阻断发布直到 clearWorld；完整清理后全部计数为零。

#### 清理顺序

正常 Destroy：

```text
StopAdmission
-> wait for any non-reentrant commit call to return
-> abort StagingRecord / rollback Prepared Token
-> resolve or release non-Applying DeathToken / DeathApplicationLedger
-> settle/abort participant Actors
-> release Opportunity claims/carried relations and destroy ground loot Buildings
-> detach Provider/Entrance
-> dispose Runtime Actor/Building systems, Tile environment/indexes, store and queues
-> destroy WorldView/render pools
-> return Slot
-> remove Site/Party MetaObjects and Manager indexes
```

`clearWorld` 不发奖励、不触发死亡日志、不调用已经销毁的主世界对象；它先清空 staging registry、DeathToken/Ledger 并验证没有 Applying、PromotionReceipt 或待确认 Entity，再按反向所有权顺序释放当前会话资源。

### 步骤 6：按既有内容合同执行 Archetype 发布审计

阶段 2 已建立并验证 `RuinContentAcceptance`，阶段 4 已分别实现古修道场与远古战场的具体配置。这里不再创建新的内容合同，也不把未验证的通用 Archetype 注册器作为发布前置；本步骤只审计两种内容是否满足已存在的合同，并确认共同字段抽取没有抹平机械差异。

#### 审计范围

- 古修道场和远古战场各抽取至少 20 个固定 Seed，提交全图俯视诊断图、Building/能力分布、Entry 到每个 `OpportunityClaimKey` 的独立可达性和路线差异报告。
- 两类生成 schema 都不得提供跨槽 prerequisite 字段；每个机缘槽不依赖清空守卫、区域解锁或另一个机缘槽。
- 逐项复核 Entry、部分收益返程、派生 Exhausted ReadModel、Collapsed 生命周期、Building/Tile 物理状态接续和参与者 Knowledge 隔离。
- 逐项复核 EvidenceSource 传播、HazardController/Tile 覆盖移动或稳定方式、守卫 Actor 活动、非战斗机缘应对和开放路线，不能只比较名称、贴图或数值。
- 逐项复核每个物理遗构只对应一个 Building；Landmark、EvidenceSource、HazardController、Opportunity 没有独立 Entity/ID，地面 loot 是 Building，Site/Party 是 MetaObject。
- 只有两类具体配置都通过后，才允许把已证明重复的字段提取为 `RuinArchetypeAsset`；提取后的资产不能拥有任何一类内容专属规则，也不能引入通用规则解释器。

#### 发布阻断条件

以下任一情况存在时，内容不进入正式 Library：

- 生成器重新出现房间图、走廊树、钥匙门、唯一核心奖励或串联“战斗区 -> 奖励区”。
- 某一机缘槽只能在另一个槽完成、守卫清空或区域解锁后访问。
- 全图诊断无法显示 Tile 地貌、Building/能力和机缘槽的空间关系，或 AI 需要读取隐藏 Building/秘密 EvidenceRelation 才能完成调查。
- 第二种遗迹只是古修道场的调色、贴图、数值倍率或 Opportunity 槽权重变化。
- 内容 Provider、UI 或日志绕过 Runtime command 边界修改 Building 能力、Tile 环境、Knowledge、claim 或 relation。

### 步骤 7：完成发布回归与真实游戏验收

#### 无 Debug 完整体验

新建普通主世界后，玩家只使用正式功能完成：

1. 投放或等待 Provider 创建 Site。
2. 修士发现、评估并组队前往。
3. 导航按钮聚焦开放遗址。
4. 观察不同队伍调查、战斗、争夺、部分返程或死亡。
5. 查看主世界实际物品、Actor 生命和 WorldLog。
6. 后续队伍接续探索，直至 Site ReadModel 为 Exhausted 或生命周期为 Collapsed。

全程不需要右键移动、生成 Pawn、显示隐藏目标或手动触发结算。

#### 50 次生命周期回归

至少完成 50 个 Site 周期，覆盖：

- 古修道场/远古战场各不少于 20 次。
- 成功、无所得撤退、部分所得、多队分取、Hostile 争夺、死亡、崩塌。
- 1/2/最终容量上限 Site 并存。
- LocalSpeed、主世界暂停、相机持续切换。
- 入口被删除、Provider 清理、返回主菜单、加载另一世界、Mod 重载。

每轮后对所有计数与关键引用做断言。结束时工作集合回到基线，无增长趋势。

#### 行为回归

- 主世界普通战斗仍通过全部 golden fixtures。
- 主世界 Ingredient/MagicScroll 创建、显示、使用和销毁行为不变。
- 原版相机、Power 输入、Actor AI、世界保存与 clearWorld 在没有 Site 时无额外行为变化。
- 相同 Seed/输入只在回放相同 path publication trace 时比较 View 可见性、倍速和多 Site 调度下的逐 tick/最终结果；真实异步 worker 运行仅断言每个不可变请求的路径 Tile 序列与事务不变量，不要求不同 publication trace 得到相同竞争、战斗或结算结果。
- Hidden Site、未定位 Building、隐藏 Opportunity payload/Guardian Actor 不通过 UI、日志或 AI 目标泄露。

#### 资源与构建

- `dotnet build Cultiway.csproj -c Debug` 无错误。
- 游戏内检查所有 Archetype 在近景、远景、主世界与多 WorldView 同屏下的遮挡、sorting、比例和文本。
- 本阶段涉及的新增资源逐项记录路径；缺失资源不使用临时纯色方块进入发布。
- 本地化至少覆盖项目当前支持语言中的键完整性，缺失键在构建/启动诊断中报错。
