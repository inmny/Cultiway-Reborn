# 第5阶段-遗迹接入与发布

本阶段扩展已经完成的最小神力 Provider 与单人 Admission，接入 Hidden 发现、可选内容 Provider、组队、正式 UI、日志、异常清理和多 Site 调度，并用真实负载确定发布容量。阶段完成后，玩家不需要 Debug 工具即可在一个当前会话中看到多处不同遗迹被发现、接续探索、争夺、耗尽或崩塌。

本阶段不继续堆叠第三种遗迹、完整技能、更多物品或制造。发布稳定性优先于内容数量；宗门驻地和完整独立世界在此阶段验收完成后另立规划。

## 具体说明

### 设计边界

- `SubWorldManager` 仍不认识遗迹、Building、Actor 或内容来源。
- Site Provider 只负责创建/销毁主世界入口和选择 Archetype，不直接修改 Runtime Entity。
- 阶段 1 已正式实现玩家神力投放的 `RuinPowerSiteProvider`；本阶段只扩展其能力。`OpportunityLegacySiteProvider` 是可选内容接入，不是小世界发布门槛；自然世界生成以后再由对应消费者接入。
- 主世界 Actor 由 AI 自主发现、评估、前往和探索；正式 UI 不提供逐格移动、攻击、调查或领取按钮。
- 多 Site 容量根据 1/2/4/8 个真实 Runtime 的 Profile 结果确定，不预写固定上限。
- 不实现 Active/Warm 解析式后台演化。空遗迹只按明确 ClockPolicy 暂停或继续，不切换成另一套模拟。
- 所有状态只属于当前会话；世界保存/加载不恢复 Runtime、Site、Binding 或 RuinLootId。
- 发布验收要求阶段 2 的古修道场和阶段 4 的远古战场通过既有内容合同，不以增加第三种半成品 Archetype 代替质量工作。

### 步骤 1：扩展既有 RuinPowerSiteProvider 与用途边界

#### Site Descriptor

阶段 1 已建立 `RuinSiteDescriptor`、`RuinSiteService`、`CreateSite`、单 Actor `RequestAdmission` 和 `RuinPowerSiteProvider`。本阶段在不改变其所有权的前提下，为 Hidden 发现、组队和公开风险信息扩展 Descriptor；第二 Provider 若实际接入，由 SiteService 另持 Provider 映射，不把接口对象塞入 Descriptor：

```text
SiteId
RuinContentId
Seed
MainWorldAnchor
EntranceBuildingId
DiscoveryProfileId
AdmissionProfileId
ThreatTier
ExpectedOpportunityTier
```

`SiteId`、`EntranceBuildingId` 和 SiteService Record 中的 `InstanceId` 都只在当前会话有效。Descriptor 不保存 InstanceId、Runtime Entity、Actor、WorldTile 或 UI 引用，也不承载可写进度。

`ThreatTier/ExpectedOpportunityTier` 是主世界 AI 在发现后能掌握的粗略公开信息；不暴露隐藏守卫、精确收益或具体 GenerationPlan。

#### 可选 Provider 合同

```text
IRuinSiteProvider
  CreateDescriptor(context) -> RuinSiteDescriptor
  CreateEntrance(descriptor) -> EntranceHandle
  OnSiteDiscovered(siteId, discovererId)
  OnSiteExhausted(siteId, summary)
  OnSiteCollapsed(siteId, summary)
  RemoveEntrance(siteId)
```

Provider 负责解释遗迹对自身玩法的意义，`RuinSiteService` 负责共享 Runtime 的一致行为。只有[机缘道统](../机缘道统-摘要.md)完成开放遗迹重写并确实接入第二个 Provider 时，才从两个具体实现已重复的入口/事件行为提取最小 `IRuinSiteProvider`；否则跳过此接口，继续使用阶段 1 的具体 `RuinPowerSiteProvider`。发布不得为制造第二个消费者而创建空实现或通用内容工厂。

既有与可选 Provider：

| Provider | 创建方式 | 完成后结果 |
| --- | --- | --- |
| `RuinPowerSiteProvider` | 玩家在合法主世界格投放 | 更新 Building 状态并保留到销毁/会话结束 |
| `OpportunityLegacySiteProvider`（可选） | 机缘道统按自身规则投放古修遗迹入口 | 把发现、伤亡、战利品和耗尽转成机缘道统事件；不作为小世界发布门槛 |

Core 不引用这两个类型。Provider 创建流程：

1. 构造 Descriptor。
2. 创建主世界 Entrance。
3. 调用 `RuinSiteService.CreateSite`。
4. Site Service 调用 Manager Create 并绑定 Runtime。
5. 全部成功后发布 SiteCreated；失败则删除 Entrance 并释放 Descriptor。

不得留下入口已存在但 Runtime 创建失败的半状态，也不得在失败时创建“空白默认遗迹”。

#### 对外命令

用途外部只能调用：

```text
CreateSite(descriptor)
DiscoverSite(siteId, actorId)
RequestAdmission(siteId, partyRequest)
RequestCollapse(siteId, reason)
DestroySite(siteId, reason)
GetSiteSummary(siteId)
```

调查、战斗、拾取和返回继续走 Runtime/Expedition command；Provider 不能直接设 Opportunity Exhausted。

### 步骤 2：扩展 Hidden 发现、寻访、组队与入场 AI

#### 发现

阶段 1 的神力 Provider 默认直接创建为 Discovered；本阶段新增 Hidden 发现，并把同一 Admission 合同扩展到多 Site 与组队。可选的第二 Provider 若存在也只能复用这条边界。Hidden 遗迹只有 Actor 的主世界感知行为可以发现：

- 候选 Actor 必须存活、未 Binding、可以到达入口附近。
- 感知距离与现有修为/感知属性适配，具体字段实现前核对当前代码。
- 每个 Site 按低频间隔扫描附近候选，不每帧遍历全部 Actor。
- 首个发现者触发 `SiteDiscoveredEvent`，Site 进入 Discovered/Open，入口和导航按钮才向玩家公开。
- 玩家相机看到 Hidden Building 不等于玩法发现；Hidden 外观使用自然遗构而非“不可见碰撞体”。

神力 Provider 可以直接创建为 Discovered，便于玩家测试和主动投放。

#### 寻访效用

主世界 AI 只使用公开摘要：

```text
Interest = ExpectedOpportunityTier
         + ActorCuriosity/Affinity
         - ThreatTier * RiskAversion
         - MainWorldTravelCost
         - CurrentObligations
```

- 不读取内部机缘数量、精确品质、守卫位置或已隐藏战利品。
- Site 已部分探索时，公开摘要可以降低预期收益，但不告诉 AI 剩余节点坐标。
- Actor 有紧急战斗、死亡、被控制或已有 Expedition Binding 时不能加入。
- 目标 Site 在 Actor 抵达前 Exhausted/Collapsed 时取消寻访。

#### 组队

阶段 4 已支持两队，主世界侧建立最小组队：

- 发起者按现有关系在附近选择 0-2 名可加入成员。
- 成员各自通过 Binding 校验；任一成员失败只移除该成员，不取消合法发起者。
- Party 在真正入场边界创建，不在前往途中占用 Runtime 名额。
- 同一 Site 可以有第二支队伍前往，不建立全局独占 reservation。
- Admission 达到当前 Profile 得出的上限时返回 Busy；AI 等待一个低频周期或选择其他 Site，不无限每 tick 重试。

#### 抵达与入场

- 主世界移动仍使用原版 Actor 行为和 Building 交互。
- 所有成员进入入口交互范围后，PartyRequest 在同一主线程批量验证。
- 逐个创建 Projection，全部成功才激活 Party；失败成员回滚，成功成员不留孤立 Binding。
- 入场后主世界 Actor 从会话内门禁隐藏；Building 显示内部人数。

### 步骤 3：完成入口、导航、观察状态与 WorldLog

#### 主世界入口表现

Entrance 至少表达：

| 状态 | 世界表现 | Tooltip 摘要 |
| --- | --- | --- |
| Hidden | 普通残破遗构，无显眼发光标记 | 不显示遗迹玩法信息 |
| Open/未探索 | 可辨识入口和 Archetype 图标 | 类型、公开危险档、内部人数 |
| Open/部分探索 | 遗构有被扰动痕迹 | 已公开地标数、已耗尽/总机缘数、内部人数 |
| Exhausted | 灵气/道痕沉寂 | 已无可用机缘 |
| Collapsing | 明确不稳定反馈 | 剩余本地倒计时、内部人数 |
| Collapsed | 坍塌遗构 | 不可进入、崩塌原因摘要 |

数字只显示玩家已经公开知道的信息；Hidden Opportunity 不计入“已知总数”，内部真实 Total 只在 Site Exhausted 后可公开。

#### WORLD 导航

复用现有 `SubWorldNavigationSection`：

- 主世界按钮保持原语义。
- 每个 Discovered 且 Runtime 存活的 Site 一个图标按钮，按 Site 创建序稳定排列。
- 图标包含 Archetype 与状态角标；Tooltip 显示名称、Open/Exhausted/Collapsed、公开进度和参与者。
- 点击只调用 Focus；不创建、重置、传送 Actor 或领取收益。
- 局部暂停、1x/2x/4x 和聚焦参与者继续只绑定当前 FocusedRuntime。
- 参与者选择只用于观察信息页，不出现玩家移动/攻击/调查命令。

按钮使用原版 `PowerButton` 交互语义和 Tooltip；不新建横向文字胶囊或大型遗迹列表窗口。

#### WorldView 观察

玩家能看到：

- 全部基础地貌和显著遗构。
- 已由任一队伍公开发现的 Landmark、Hazard、Guardian 和 Opportunity 状态。
- 当前队伍位置、生命、战斗、调查、持有物和返程状态。
- 已发生的地形改变、死亡现场、地面 loot 与崩塌波次。

玩家不能看到：未发现机缘坐标、守卫隐藏仇恨数值、AI Utility、完整 path 或 RNG。Debug Overlay 单独受开发配置控制。

#### WorldLog

至少注册：

- 遗迹被发现。
- 某队进入/返回。
- 取得 Ingredient/MagicScroll/Insight。
- 修士撤退、死亡。
- 两队因机缘发生冲突。
- Site 全部机缘耗尽。
- 遗迹开始崩塌/已经崩塌。

同一批拾取不逐件刷屏；按一次调查/返回事件聚合。日志中的 Actor、Site 和物品名称使用现有格式化器，不手拼颜色富文本。

### 步骤 4：实现多 Site 调度并用实测确定容量

#### 逻辑策略

不建立 Active/Warm 两套模拟。每个 Runtime 仍执行相同 fixed-tick Systems，但允许一个明确的空闲 fast path：

`RuinRuntimeActivityState` 从真实状态派生：

- 有参与者、崩塌倒计时、未结算 transaction 或移动 Hazard：NeedsTicks。
- 无参与者且 Archetype ClockPolicy 为 PauseWhenEmpty：IdleNoTick。
- 无参与者但明确配置 ContinueWhenEmpty：NeedsTicks；首批两个 Archetype 都使用 PauseWhenEmpty。

IdleNoTick 只跳过 gameplay tick，不改变 LocalTime、守卫位置、Hazard 或 RNG。新队进入后从原状态继续。它不是解析式演化，也没有不同公式。

#### 调度顺序

`SubWorldManager.Update` 每帧：

1. 收集 NeedsTicks Runtime。
2. 按累计欠债、是否有 Collapsing/Settling、InstanceId 排稳定顺序。
3. 在 `FramePriorityGovernor` 预算内逐个执行完整 fixed tick。
4. 未获得时间片者保留 accumulator；不合并或跳过 tick。
5. View prepare/render 继续独立按相机相交执行。

结算与崩塌优先只影响获得时间片顺序，不改变单 Runtime 内系统顺序。

#### 真实性能 Profile

用 Release 构建或游戏实际配置分别运行：

| 组合 | Runtime 内容 |
| --- | --- |
| 1 | 1 队、5 机缘、8 守卫、2 Hazard |
| 2 | 每个 1 队，中等战斗/调查并存 |
| 4 | 两个古修道场、两个战场，至少一处两队争夺 |
| 8 | 最坏压力样本，只用于测量是否可支持 |

采集：

- 每个 gameplay System 平均/P95/P99 时间。
- 每帧 Runtime tick 数、欠债 tick、结算延迟。
- Navigation、Perception、Combat、RenderPrepare 的 GC 与分配。
- Entity、Path、Knowledge、Threat、Loot、VFX pool 数量。

发布硬上限选择规则：在目标硬件上 P99 小世界总 CPU 不超过经项目确认的帧预算、无持续 tick 欠债、稳态 0 B GC 的最大 Site/参与者组合。把测得数字和最终常量写回本文件，不在测量前承诺 8 个实例或 1 ms。

达到上限时新 Site 创建返回 `CapacityReached`，Provider 删除刚创建入口并记录一次日志；不静默销毁旧 Site，也不创建无 View/无逻辑的残缺实例。

### 步骤 5：实现异常边界、会话清理与故障注入

#### 会话边界

全部小世界状态不进入存档：

- Binding 通过内存索引阻止 Actor 推进，不写需要恢复的永久隐藏字段。
- 世界保存时 Source Actor 在存档数据中仍是入场前主世界状态；未返回收益尚未物化，重新加载相当于回到入场前。
- `SettlementStagingRegistry` 只保存 `SourceActorId/HolderId`、typed values、仅含标量/不可变 typed value 的 ActorOldValues、`MaterializerKey` 和纯数据参数；禁止 Actor、Entity、Store、adapter、delegate、handler 或 Unity 引用，commit port 只在提交段内按 ID/Key 解析它们。
- Commit 的 MainWorld promote 与 Runtime 最终状态更新处于同一不可重入主线程调用；保存、入口删除、`clearWorld` 和 Mod 重载只能在调用前中止 staging，或在调用完整返回后继续。
- 已成功返回并物化的物品、生命变化和正式结果属于主世界状态，继续走现有存档；会话清理不得把它们当 staging 删除。
- 加载/切换世界时 `MapBox.clearWorld` 先让 Expedition 服务清除 StagingRecord/回滚 Prepared Token，再释放 Site 内存引用，最后清 Manager/WorldView/Slot。
- 新世界中若 Provider Building 因原版存档仍存在但没有当前会话 Site，Provider 在加载扫描中直接删除/失效该孤立入口；不从 Building 反建旧 Runtime。

#### 入口消失

Entrance 被摧毁或 Provider 主动撤销：

1. Site 进入 Collapsing/Aborting，停止新 Admission。
2. 内部存活 Projection 以当前 Entry tile 强制开始 Return；主世界出现位置使用原入口 Anchor。
3. Prepared 但尚未 Commit 的 transaction 删除 StagingRecord 并 Rollback；不可重入 Commit 段不能被入口删除插入，调用返回后只会看到完整成功或完整失败。
4. 倒计时结束仍未返回者按阶段 3 死亡结算。
5. 参与者清零后销毁 Runtime、Site 和导航按钮。

不得直接 Destroy Runtime 丢弃内部 Actor。

#### 故障注入点

Debug 必须可精确注入：

- Generator/Validator 失败。
- WorldView 创建失败。
- Party 第 N 个 Projection 创建失败。
- Move/Investigation event handler 失败。
- SettlementStagingRecord 创建/校验失败。
- MainWorld commit port 在 Ingredient/MagicScroll 第 N 个物化时失败。
- MainWorld promote 成功后、Runtime 无分配最终提交前注入失败，验证 Receipt 回滚。
- Source Actor 在 Prepare 后或 Commit 前失效。
- death port 预检失败（入口未调用）后同一 Token 重试。
- 死亡入口已令 Actor canonical dead/removed 后抛错；断言 Ledger 为 Applied、Runtime 最终 Settled、同一 Token 再处理时死亡入口总调用数仍为 1。
- 死亡异常后 canonical state 未生效且副作用不可证明时进入 Faulted；禁止自动重试并阻断发布。
- 入口在战斗、Prepared settlement、DeadPendingSettlement 或完整 Commit 后被删除。
- 保存/clearWorld/Mod 重载分别发生在 Prepare 前、Prepared 后和 Commit 调用返回后；不能注入到不可重入提交段内部。

每个故障都验证以下计数：Site、Runtime、Binding、Projection、Party、Knowledge、Path、Threat、Opportunity claim、RuinLoot、settlement ledger、DeathToken、DeathApplicationLedger、StagingRecord、PromotionReceipt、待确认主世界 Entity、WorldView、Slot、Renderer/VFX pool。每条结算失败路径结束后 StagingRecord、PromotionReceipt 和待确认主世界 Entity 必须为零；Applied/可重试死亡流程最终完成后 DeathToken/Ledger 条目必须移除，Faulted 条目保留诊断并阻断发布直到 clearWorld；完整清理后全部计数为零。

#### 清理顺序

正常 Destroy：

```text
StopAdmission
-> wait for any non-reentrant commit call to return
-> abort StagingRecord / rollback Prepared Token
-> resolve or release non-Applying DeathToken / DeathApplicationLedger
-> settle/abort participants
-> release loot claims
-> detach Provider/Entrance
-> dispose Runtime systems/store/queues
-> destroy WorldView/render pools
-> return Slot
-> remove Site/Manager indexes
```

`clearWorld` 不发奖励、不触发死亡日志、不调用已经销毁的主世界对象；它先清空 staging registry、DeathToken/Ledger 并验证没有 Applying、PromotionReceipt 或待确认 Entity，再按反向所有权顺序释放当前会话资源。

### 步骤 6：按既有内容合同执行 Archetype 发布审计

阶段 2 已建立并验证 `RuinContentAcceptance`，阶段 4 已分别实现古修道场与远古战场的具体配置。这里不再创建新的内容合同，也不把未验证的通用 Archetype 注册器作为发布前置；本步骤只审计两种内容是否满足已存在的合同，并确认共同字段抽取没有抹平机械差异。

#### 审计范围

- 古修道场和远古战场各抽取至少 20 个固定 Seed，提交全图俯视诊断图、Opportunity 前置关系图和路线差异报告。
- 两类前置关系图必须为空；每个机缘不依赖清空守卫、区域解锁或另一个机缘。
- 逐项复核 Entry、部分收益返程、Exhausted、Collapsed、物理状态接续和参与者 Knowledge 隔离。
- 逐项复核线索传播、危险移动/稳定方式、守卫活动、非战斗机缘应对和开放路线，不能只比较名称、贴图或数值。
- 只有两类具体配置都通过后，才允许把已证明重复的字段提取为 `RuinArchetypeAsset`；提取后的资产不能拥有任何一类内容专属规则。

#### 发布阻断条件

以下任一情况存在时，内容不进入正式 Library：

- 生成器重新出现房间图、走廊树、钥匙门、唯一核心奖励或串联“战斗区 -> 奖励区”。
- 某一机缘只能在另一个机缘完成、守卫清空或区域解锁后访问。
- 全图诊断无法显示地貌/遗构/机缘的空间关系，或 AI 需要读取隐藏坐标才能完成调查。
- 第二种遗迹只是古修道场的调色、贴图、数值倍率或 Opportunity 权重变化。
- 内容 Provider、UI 或日志绕过 Runtime command 边界修改状态。

### 步骤 7：完成发布回归与真实游戏验收

#### 无 Debug 完整体验

新建普通主世界后，玩家只使用正式功能完成：

1. 投放或等待 Provider 创建 Site。
2. 修士发现、评估并组队前往。
3. 导航按钮聚焦开放遗址。
4. 观察不同队伍调查、战斗、争夺、部分返程或死亡。
5. 查看主世界实际物品、Actor 生命和 WorldLog。
6. 后续队伍接续探索，直至 Site Exhausted 或 Collapsed。

全程不需要右键移动、生成 Pawn、显示隐藏目标或手动触发结算。

#### 50 次生命周期回归

至少完成 50 个 Site 周期，覆盖：

- 古修道场/远古战场各不少于 20 次。
- 成功、无所得撤退、部分所得、多队分取、Hostile 争夺、死亡、崩塌。
- 1/2/最终容量上限 Site 并存。
- LocalSpeed、主世界暂停、相机持续切换。
- 入口被删除、Provider 清理、返回主菜单、加载另一世界、Mod 重载。

每轮后对所有计数与关键引用做断言。结束时工作集合回到基线，无增长趋势。

#### 行为回归

- 主世界普通战斗仍通过全部 golden fixtures。
- 主世界 Ingredient/MagicScroll 创建、显示、使用和销毁行为不变。
- 原版相机、Power 输入、Actor AI、世界保存与 clearWorld 在没有 Site 时无额外行为变化。
- 相同 Seed/输入在 View 可见性、倍速和多 Site 调度顺序变化下保持 tick 结果一致。
- Hidden Site/Opportunity/Guardian 不通过 UI、日志或 AI 目标泄露。

#### 资源与构建

- `dotnet build Cultiway.csproj -c Debug` 无错误。
- 游戏内检查所有 Archetype 在近景、远景、主世界与多 WorldView 同屏下的遮挡、sorting、比例和文本。
- 本阶段涉及的新增资源逐项记录路径；缺失资源不使用临时纯色方块进入发布。
- 本地化至少覆盖项目当前支持语言中的键完整性，缺失键在构建/启动诊断中报错。
