## 具体说明

### 设计边界

- Visible 与 ActiveBackground 执行相同固定逻辑 tick、CompiledSkillDefinition、DamageResolver、唯一 `ICraftProcessKindRegistry`/`ICraftDomainService` 和 PortableItem commands，不因渲染状态改变结果。
- Warm 和 Dormant 只在 RuleSet 与全部活动工序明确支持解析推进时使用，不能把即时战斗或有人手工炼制压成低频近似。
- 任意 Manual `CraftProcessSnapshot` 都阻止 Warm/Dormant；只有声明 AnalyticAutomatic 且共享制造领域实现解析推进的自动工序可以随实例降级。
- 一个实例最多存在一个 Runtime；View 可以解绑和切换，不复制 Runtime。
- 后台预算服从项目全局 FramePriorityGovernor，不抢占主世界硬预算。
- 浮窗不是模态窗口，不暂停主世界；主世界全局速度和各实例 LocalSpeed 分别维护。
- Archive 长期保留仍可达的 typed snapshot、完整动态 blueprint 和 CraftProcess；完成实例的数据保留策略由 Template 与消费系统共同决定，不无限保存所有逐 tick 事件。
- Runtime item Entity 只物化 Archive snapshot/record；Dormant 销毁这些 Entity 后仍由 Archive 权威持有。归档的 MainWorld 来源 ItemId 不在 MainWorld 同时保留有效 Entity。

### 步骤 1：建立含 CraftProcess 门禁的 Runtime Tier

#### Visible

- 当前绑定 `SubWorldFloatingPanel`，与主世界地图同时显示。
- 逻辑使用固定 tick。
- Camera 手动渲染最高 30 FPS。
- 接受玩家允许的局部移动、技能、物品、工作台和拾取命令。

#### ActiveBackground

- 有参与者、战斗、技能运行态、物品提交、倒计时、即时 Objective 或不能解析推进的 CraftProcess。
- 仍执行与 Visible 完全相同的固定 tick。
- tick 可以跨帧分批执行，但顺序、随机状态和结果不变。
- 不创建或更新 View 对象。

#### Warm

- 没有战斗、技能运行态、移动命令、待提交物品变化和即时交互。
- 只有 Rule Module 声明支持低频推进的环境或目标。
- 不存在 Manual 或 fixed-tick-only CraftProcess；活动自动工序全部声明 AnalyticAutomatic，并由同一 `ICraftDomainService` 支持解析推进。
- Runtime 保留，但调度频率降低；模块按真实 LocalElapsed 结算。
- 任意即时事件或参与者命令会返回 ActiveBackground。

#### Dormant

- 无参与者，或全部参与者处于模板允许的长期停滞状态。
- 没有必须逐 tick 处理的投射物、战斗、技能、物品 command、机关、短时 Objective 或制造工序。
- 未完成 CraftProcess 必须全部是支持 Dormant catch-up 的 AnalyticAutomatic；否则即使无人查看也保持 ActiveBackground。
- Runtime 投影回 DTO 后销毁。
- 保存 `SuspendedAtParentTime`、typed snapshot store、完整 CraftProcessSnapshot 和模块声明的解析式状态。
- portable item 只保留 Archive snapshot、`SubWorldItemRecord` 和必要的 `ItemLease`；休眠不要求任何冻结的 MainWorld 影子 Entity。

Template 的 LifecyclePolicy 决定实例是否允许 Warm/Dormant。没有解析式实现的 Rule Module 或 CraftProcess 都会阻止降级。

#### 制造门禁矩阵

| 工序 | Visible | ActiveBackground | Warm | Dormant |
| --- | --- | --- | --- | --- |
| Manual，有人手工炼制 | 允许 | 允许，执行相同固定 tick | 禁止 | 禁止 |
| Automatic，仅支持固定 tick | 允许 | 允许 | 禁止 | 禁止 |
| AnalyticAutomatic，共享领域明确支持 elapsed 解析 | 允许 | 允许 | 允许 | Template 允许时可用 |

工序是否可解析由 `CraftProcessSnapshot.AdvancementMode` 和其 `ProcessKindId` 注册的 typed handler capability 共同决定，不能由 Scheduler 按名称、工作台类型或当前是否可见猜测。

### 步骤 2：实现技能、制造与物品感知的全局调度器

`SubWorldScheduler` 维护实例 Tier 队列和可诊断的领域就绪队列：

```text
VisibleQueue
ActiveBackgroundQueue
WarmQueue
ReadySkillQueue
ReadyCraftProcessQueue
ReadyItemQueue
PendingLoadQueue
PendingCommitQueue
```

`ReadySkillQueue`、`ReadyCraftProcessQueue` 和 `ReadyItemQueue` 不绕过实例 tick；它们标识实例内部到期工作，Scheduler 仍在所属实例的固定阶段执行。队列键固定为 `(DueTick, InstanceId, Sequence)`，同一初始状态下不会因帧预算或容器遍历顺序改变先后。

优先级：

1. Pending Outcome Commit。
2. Visible 当前浮窗所需 tick。
3. 即将发生死亡、崩塌或期限到期的 ActiveBackground。
4. 到期的 skill execution、CraftProcess 和 item command，按所属实例 tick 与稳定 Sequence 执行。
5. 其他 ActiveBackground 轮转。
6. Warm 的环境与 AnalyticAutomatic craft slice。
7. Pending Load/Unload。

预算：

- 平均每渲染帧 `1 ms`。
- 本地硬停止 `2 ms`。
- 单 cooperative slice `0.15..0.25 ms` 或最多 64 条记录。
- 全局待处理路径请求达到 64 时延迟新请求。
- 所有实例共享一个 ParallelJobRunner 和现有 SimulationWorkerPool，不创建实例线程。

Scheduler 不修改 `World.world._is_paused` 或主世界速度。Visible 和 ActiveBackground 都以 `Time.unscaledDeltaTime × DefaultLocalRate × LocalSpeed` 累积自己的 tick；用户单独暂停主世界时，各实例是否继续由 `RunsWhileParentPaused` 决定。MainWorld skill/craft time 与每个 SubWorld `ITimeSource` 独立，调度预算只延迟 wall-frame 完成时间，不改变 LocalTime、DueTick 或领域结果。

### 步骤 3：实现确定性后台推进与自动工序解析

#### 后台固定 tick

ActiveBackground 保存 `PendingLocalTime`。Scheduler 每次取出实例时执行若干完整 tick 并更新 TickIndex。跨帧分批不会跳过中间技能、伤害、物品、制造或 Objective 事件。

同一初始存档分别在持续 Visible 和持续 Background 下运行相同 tick 数，应产生相同结构签名、RandomState、CompiledSkill runtime、CraftProcessSnapshot、typed item revision 和结果。渲染准备、VisualCue 播放和浮窗输入设备读取不进入逻辑签名。

#### CraftProcess 调度

- Manual 工序每次进度都来自操作者成功提交的主行动 contribution；操作者离开、失能或切换行动时按第三阶段共享 `CraftFailure`/中断规则处理，不能按离线 elapsed 自动补进度。
- fixed-tick Automatic 工序由 `ReadyCraftProcessQueue` 在所属实例完整 tick 内调用 `ICraftDomainService.Advance`，保存新的 progress 与 RandomState；它仍阻止 Warm/Dormant。
- AnalyticAutomatic 必须由同一 registry 中该 `ProcessKindId` 的 typed handler 明确声明支持，并由 `ICraftDomainService` 提供基于当前 CraftProcessSnapshot、CraftContext、LocalElapsed 和确定性 random cursor 的解析推进结果。
- 解析推进必须产生与领域合同定义的逐 tick 推进相同的材料消耗、品质、产量、失败、完成时间区间和输出 ContentRef；Scheduler 不实现配方、概率或产量公式。
- 工序成功仍把产物放入 WorkbenchOutput Holder。后台完成、Warm 解析或 Dormant catch-up 都不能代替单位拾取。

#### Warm

Warm Module 接收明确 elapsed，只能修改自己拥有的低频状态，例如：

- 缓慢灵气变化。
- 非战斗机关倒计时。
- 无参与者植物生长。
- 已完成后的崩塌倒计时。
- 明确支持解析推进的 AnalyticAutomatic CraftProcess。

单位移动、战斗、技能、拾取、物品使用、即时交互和 Manual/fixed-tick Automatic 制造不允许 Warm 近似。

#### Dormant Catch-up

实例唤醒时：

1. 计算 ParentElapsed。
2. 按 `BackgroundPolicy.DormantLocalPerParentTime` 转换可追赶 LocalElapsed；该比例只用于无 Runtime 的解析式休眠，不驱动活跃实例时钟。
3. 每个允许休眠的 Module 和 AnalyticAutomatic CraftProcess 返回解析式 Delta。
4. 按模块优先级、ProcessId 和 command Sequence 的固定顺序提交环境、craft、item 与 Objective Delta。
5. 超过 `MaxCatchUpTime` 的部分按 Template 规则截断或分批，不在一帧补算数万 tick。
6. 重建 Runtime 并从完整 tick 边界继续。

解析式结算必须与“无实体即时交互”的假设匹配；存在参与者战斗、手工炼制、待命中技能或待提交物品变化时绝不能休眠后凭平均数决定结果。唤醒后从保存的 TickIndex、RandomState 和每个 CraftProcess random cursor 继续。

### 步骤 4：实现浮窗实例切换和视图资源复用

`SubWorldViewCoordinator` 同时只把一个 Visible 实例绑定到 `SubWorldFloatingPanel`：

1. 冻结当前 View ReadModel。
2. 归还实体和特效对象池对象。
3. 清理 Tilemap 内容但保留 Tilemap GameObject。
4. 加载目标 VisualProfile、地图和视觉快照。
5. 更新 Camera 边界与局部时间控件。
6. 恢复目标实例允许的输入，浮窗外区域继续由主世界处理。

切换浮窗绑定不改变 Runtime Tier 之外的逻辑数据，也不重建 skill/craft/item queues。原 Visible 若仍有参与者，转为 ActiveBackground；目标实例按需从 DTO 加载。切换、折叠和关闭浮窗都不修改主世界暂停与倍速，主/子世界独立时钟继续按各自策略推进。

#### 实例入口

消费系统可以提供：

- 主世界入口 Building Tooltip 的“查看内部”命令。
- 参与者人物页的“查看远征”命令。
- 小世界浮窗工具栏中的当前可访问实例菜单。

实例菜单使用 `UiOptionMenu`，支持搜索；不增加一排逐个循环实例的文字按钮。

### 步骤 5：实现 typed snapshot、工序与长期归档

#### Archive 根与长期保存集合

SubWorldArchive 在任意 Tier 都必须保留：

- typed snapshot store 中被 `SubWorldItemRecord.ContentRef`、CraftProcess 输入/recipe/result、`PendingOutcome.PortableItemChanges` 或消费系统历史引用的记录。
- `IngredientSnapshot`、`ElixirRecipeBlueprint`、`ElixirItemSnapshot`、`ArtifactInstanceSnapshot`、`MagicScrollSnapshot`、`TalismanSnapshot` 六种顶层记录及其 codec type/version；两个技能载体还保存嵌套 `StoredSkillPayloadSnapshot`。
- 每个未终止 `CraftProcessSnapshot` 的 `ProcessKindId`、typed recipe/state codec type/version、StartRequest、ContextSnapshot、Progress、AdvancementMode、RandomState/random cursor 和 Result。
- `CraftContext` 中参与当前工序的 `CraftResourcePoolSnapshot[] { ResourceId, Current, Maximum }` 以及尚未提交的明确资源扣减 commands。
- 动态丹方、魔法卷轴与符箓中的完整 blueprint/signature；全局 library/registry ID 仍只作为可重建索引，不保存 `CompiledSkillDefinition` 副本。
- StableItemId、ExpeditionItemId、Holder/Ground/State，以及 MainWorld 来源或开始返回提交的 New 物品所持有的 `ItemLease`。

Archive 可达性根只包括 `SubWorldItemRecord`、未终止 `CraftProcessSnapshot`、`PendingOutcome` 中的 item changes 和消费系统明确保留的历史引用。`ItemLease` 是这些记录的跨世界转移/幂等状态，不另建第二种 item commit 对象；所有待提交物品状态都放在 `PendingOutcome.PortableItemChanges`。

Warm/Dormant 只销毁 Runtime cache，不删以上权威数据。读档先注册并冻结唯一 `ICraftProcessKindRegistry`，再恢复 snapshot store 和 CraftProcess，按 `ProcessKindId` 选择 typed recipe/state codec，最后重建 ItemRecord 引用、领域 ready queues 和 Runtime；不能先调度一个 tick 后再补工序或物品。重复注册、未知 Kind ID 或 codec 版本/类型不匹配直接使归档恢复失败，不创建通用 payload。

#### 归档与压缩

Template 指定：

- `DestroyAfterCompletion`：全部 Outcome 提交、MainWorld ownership 持久化并释放相关 ItemLease 后删除详细实例，只保留消费系统历史所引用的 typed snapshot。
- `KeepReadOnly`：保留最终地图、实体、物品、工序终态和目标摘要，可重新查看但不 tick。
- `PersistentWorld`：继续作为可再次进入的 SubWorld，保留可继续使用的物品与完整 blueprint。

归档压缩：

- Terrain/Flags 使用数组或 RLE。
- 删除已消费事件、已提交 Outcome、路径、AI cache、临时技能运行态和 VisualCue。
- `CraftProcessSnapshot`、其输入/recipe/result ContentRef 以及所有可达 typed snapshot 不参与普通事件清理。
- 只有在对应 `CommitId` 与 MainWorld ownership 已持久化、Archive item record 已删除或物品已确定销毁、相关 ItemLease 已释放，且没有 Process、`PendingOutcome.PortableItemChanges` 或历史引用后，snapshot 才能按 StableItemId 可达性回收。
- Archive JSON 超过 2 MiB 时记录诊断，并按 terrain、entity、typed snapshot、craft process、event 分类列出最大实例。

### 步骤 6：实现完成、崩塌与清理

#### 完成

Objective 完成后 Instance 进入 Completing：

- 停止生成新敌人与新目标。
- 允许 Template 定义的领取和撤离窗口。
- 已运行的 CraftProcess 按 Template 明确选择继续至领取窗口结束、共享 CraftFailure 中断或随 PersistentWorld 保留，不能静默丢弃材料。
- 处理所有 Participant Outcome。
- 所有 Commit 完成后进入 Completed。

#### 崩塌

Collapsed 是终止状态：

- 不再允许新参与者。
- 按 ExitPolicy 决定强制撤离、死亡或封闭。
- 通过共享 CraftFailure 终止不允许继续的 Manual/Automatic 工序，提交已有物品、工序产物和伤势结果。
- 消费系统获得 CollapseReason。

#### 世界清理

`MapBox.clearWorld()`：

1. 停止 Scheduler 接受任务。
2. 取消 worker 结果提交。
3. 销毁全部 Runtime Root/Store。
4. 清空 instance、skill、craft、item queues。
5. 清空 Actor Lease、ItemLease Registry 和视图对象。
6. Release/Destroy RenderTexture 与 Camera。
7. 清空 Archive、typed snapshot store 与 CraftProcess 引用。

不在下一个世界首次 tick 延迟清理。

### 步骤 7：增加 skill、craft、item queues 诊断

仅 Debug 展示：

- 实例总数与各 Tier 数量。
- 每实例 TickIndex、PendingLocalTime 和 Runtime Revision。
- 逻辑、路径、投影和渲染准备 P50/P95。
- 命令、事件、路径、skill、craft、item queues 深度、最早 DueTick 与最长等待 LocalTime。
- 每实例 CompiledSkill execution 数量、到期/延迟/提交 commands 数量。
- CraftProcess 的 Manual、Automatic、AnalyticAutomatic、Running、Succeeded、Failed 数量和最老 ProcessId。
- CraftProcess 按 `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting` 的数量、typed recipe/state codec 版本、资源 command 数量，以及未知 Kind/codec 诊断。
- typed snapshot 按 codec 类型的记录数、字节数、可达/可回收数，分别列出 `MagicScrollSnapshot`、`TalismanSnapshot`，以及 active ItemLease、`PendingOutcome.PortableItemChanges` 的 Existing/New/ConsumedOrDestroyed 数量。
- Entity、SpriteRenderer、Effect 数量。
- DTO、typed snapshot、CraftProcess 和序列化 JSON 大小。
- 最近一次 Tier 变化原因，以及阻止 Warm/Dormant 的 skill/craft/item blocker。

正式玩家 UI 只显示实例局部时间、运行状态和目标，不显示内部毫秒预算。

### 步骤 8：完成多实例长期差分验收

测试组合：

- 1 个 Visible 战斗与手工制造实例，同时保持主世界运行，并覆盖魔法卷轴和符箓载体使用。
- 3 个 ActiveBackground 远征，分别覆盖 skill、四种 `ProcessKindId` 的 fixed-tick Automatic craft 和 item/death commit。
- 4 个 Warm 环境实例，其中 2 个运行已由对应 typed handler 声明支持的 AnalyticAutomatic craft。
- 20 个 Dormant 或 Completed 记录。

运行至少 100 个主世界年，并反复切换视图、保存读档和清理世界。另把同一固定存档分为持续 Visible、持续 ActiveBackground 两路运行相同 TickIndex，差分 Projection、技能、CraftProcess、typed item、RandomState、Objective 和 Outcome；AnalyticAutomatic 另与其领域逐 tick 基准比较。

## 验收标准

### 一致性

- 同一实例运行相同 TickIndex，Visible 与 ActiveBackground 的 Projection、CompiledSkill runtime、DamageResolution、CraftProcessSnapshot、typed item revision、RandomState、Objective 和 Outcome 一致。
- skill、craft、item ready queues 只决定何时获得 CPU slice，不绕过实例 tick 或改变 `(DueTick, InstanceId, Sequence)` 顺序。
- Warm 只运行声明支持低频推进的模块和 AnalyticAutomatic CraftProcess。
- 有人手工炼制时实例不能进入 Warm 或 Dormant；fixed-tick Automatic 同样阻止降级。
- AnalyticAutomatic 在 Warm/Dormant 推进后的领域结果与相同输入、LocalElapsed、RNG 的逐 tick 基准一致，产物仍留在 WorkbenchOutput。
- `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting` 在 Visible/Background/Warm 允许的层级都经同一 registry/domain；Scheduler 不按 Kind 名称实现任何制造或资源公式。
- 有战斗、投射物、技能运行态、移动、待提交物品或即时交互时不能进入 Dormant。
- Dormant 追赶不跨过 Template 的 MaxCatchUpTime。
- 切换查看不会重置 RandomState、AI、路径、技能、CraftProcess、item queues 或 Objective。

### 性能与生命周期

- `1+3+4+20` 测试组合下平均小世界 CPU 不超过 1 ms/渲染帧，单帧硬停止 2 ms。
- 浮窗隐藏或折叠时小世界渲染开销为零，但活跃实例 LocalTime 不因此停止。
- 同时只有一个 ViewHost 绑定 Visible 实例。
- 浮窗打开期间主世界持续运行并可操作；主世界和 Visible 实例设置不同倍率时互不覆盖。
- 主世界 craft/skill 时钟与每个 SubWorld `ITimeSource` 独立，暂停或调整任一方不会改变另一方的 DueTick、冷却或工序进度。
- Completed/Collapsed 实例按策略正确销毁或转只读。
- 清理主世界后 Runtime、Store、SystemRoot、skill/craft/item queues、Actor Lease、ItemLease、Camera、RT 和池对象计数归零。

### 存档

- 多 Tier 混合状态保存读档后恢复正确。
- Pending Outcome Commit 优先恢复且不重复提交。
- Archive 压缩不改变 tile、实体、目标、StableItemId、六种 typed snapshot、ContentRef、`ProcessKindId` 或 typed recipe/state。
- Manual、Automatic、AnalyticAutomatic 工序在 Running/Succeeded/Failed 各状态保存读档后保持 Progress、RandomState、材料 Holder、结果和 ready queue 顺序。
- 四种首批 `ProcessKindId` 的 Running/Succeeded/Failed 归档都能由已注册 typed recipe/state codec 恢复；重复/未知 ID 和 codec 类型/版本不匹配明确失败。
- 动态 `ElixirRecipeBlueprint`、`MagicScrollSnapshot` 与 `TalismanSnapshot` 不依赖全局 library/definition 缓存即可恢复；两种载体的 `StoredSkillPayloadSnapshot`、魔法卷轴寿命、符箓一次性语义以及 `ArtifactInstanceSnapshot` 的能力、品质和耐久不丢失。
- 诊断能分别报告六种顶层 snapshot、四种 Process Kind、资源扣减 commands 和对应 codec 版本。
- 未提交的 `PendingOutcome.PortableItemChanges`、仍有效的 ItemLease 或仍被 ItemRecord/CraftProcess 引用的 typed snapshot 不会被归档回收；诊断与回收使用同一组 Archive 根。
- 长期运行中 JSON 大小增长能由 terrain、entity、typed snapshot、craft process、event 和 Revision 数量解释。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
