# 第5阶段-多实例与后台演化

本阶段完成多个 SubWorld 在当前游戏会话中长期并存、后台推进、非模态浮窗切换和性能治理。`SubWorldManager` 始终持有每个实例的完整 `SubWorldRuntime`，调度器统一处理实例 tick、技能、`CraftProcessSnapshot` 与 PortableItem queues；调度层级只改变更新频率和渲染状态，所有 Runtime 在 `Destroy` 或 `Clear` 前均保持完整，也不改变逻辑结果。

## 具体说明

### 设计边界

- Visible 与 ActiveBackground 执行相同固定逻辑 tick、CompiledSkillDefinition、DamageResolver、唯一 `ICraftProcessKindRegistry`/`ICraftDomainService` 和 PortableItem commands，不因渲染状态改变结果。
- Warm 只在 RuleSet 与全部活动工序明确支持 elapsed 推进时使用，不能把即时战斗或有人手工炼制压成低频近似。
- 任意 Manual `CraftProcessSnapshot` 都阻止 Warm；仅支持固定 tick 的 Automatic 工序也保持 ActiveBackground；只有声明 AnalyticAutomatic 且共享制造领域实现 elapsed 推进的自动工序可以进入 Warm。
- 一个 InstanceId 恰好对应一个 Runtime；Runtime 从 Manager `Create` 成功到 `Destroy` 或 `Clear` 始终常驻内存。
- View 可以解绑和切换，不复制 Runtime，不销毁 Store、Entity、MapData、Clock 或 Random。
- 后台预算服从项目全局 FramePriorityGovernor，不抢占主世界硬预算。
- 浮窗不是模态窗口，不暂停主世界；主世界全局速度和各实例 LocalSpeed 分别维护。
- typed snapshot、完整 Blueprint、CraftProcess 和 Stable ItemId 都由所属 Runtime 的组件和值对象直接持有，不存在独立实例状态层。
- MainWorld/SubWorld 返回在 Manager 主线程边界同步完成，不进入等待队列，不跨帧拆分。
- 切换世界、返回主菜单或 Mod 重载时调用 `SubWorldManager.Clear()`，清空全部 Runtime、队列、Binding 和视图资源。

### 步骤 1：建立含 CraftProcess 门禁的 Runtime Tier

#### Visible

- 当前绑定 `SubWorldFloatingPanel`，与主世界地图同时显示。
- 逻辑使用固定 tick。
- Camera 手动渲染最高 30 FPS。
- 接受玩家允许的局部移动、技能、物品、工作台和拾取命令。
- Runtime、Store 与 Entity 由 Manager 持有，ViewHost 只读取视觉快照。

#### ActiveBackground

- 有参与者、战斗、技能运行态、物品命令、倒计时、即时 Objective 或不能解析推进的 CraftProcess。
- 仍执行与 Visible 完全相同的固定 tick。
- tick 可以跨帧分批执行，但顺序、随机状态和结果不变。
- 不创建或更新 View 对象。
- 退出命令在所属完整 tick 后立即交给 Manager 执行同步跨 Store 转移。

#### Warm

- 没有战斗、技能运行态、移动命令、物品使用、即时交互或待退出参与者。
- 只有 Rule Module 声明支持低频推进的环境或目标。
- 不存在 Manual 或 fixed-tick-only CraftProcess；活动自动工序全部声明 AnalyticAutomatic，并由同一 `ICraftDomainService` 支持 elapsed 推进。
- Runtime、MapData、EntityStore、全部 Entity、Clock、Random、RuleState、typed item 和 CraftProcess 继续常驻。
- Manager 累积 LocalElapsed，到模块约定的更新点后执行一个低频 slice。
- 任意即时事件或参与者命令会在处理前转为 ActiveBackground。

Template 的 LifecyclePolicy 决定实例是否允许 Warm。没有 elapsed 实现的 Rule Module 或 CraftProcess 会阻止降级；浮窗是否可见只决定 Visible 与非 Visible，不足以让实例进入 Warm。

#### 制造门禁矩阵

| 工序 | Visible | ActiveBackground | Warm |
| --- | --- | --- | --- |
| Manual，有人手工炼制 | 允许 | 允许，执行相同固定 tick | 禁止 |
| Automatic，仅支持固定 tick | 允许 | 允许 | 禁止 |
| AnalyticAutomatic，共享领域明确支持 elapsed 解析 | 允许 | 允许 | 允许 |

工序是否可解析由 `CraftProcessSnapshot.AdvancementMode` 和其 `ProcessKindId` 注册的 typed handler capability 共同决定，不能由 Scheduler 按名称、工作台类型或当前是否可见猜测。

#### Tier 转换

Tier 是 Runtime 的调度标签，不是生命周期状态：

```text
Visible <-> ActiveBackground <-> Warm
```

- 浮窗绑定使目标 Runtime 进入 Visible；原目标按自身即时状态转为 ActiveBackground 或 Warm。
- Warm 收到任何命令时，Manager 先切到 ActiveBackground，再把命令放入正常 tick 队列。
- ActiveBackground 满足全部低频条件后，在完整 tick 边界进入 Warm。
- Tier 切换不重建 system、不替换 EntityStore、不重置 accumulator，也不改变 TickIndex 或 RandomState。

### 步骤 2：实现技能、制造与物品感知的 Manager 调度器

`SubWorldManager.Update(unscaledDeltaTime)` 是唯一全局入口。Manager 内部的 `SubWorldScheduler` 维护 Tier 队列和可诊断的领域就绪队列：

```text
VisibleQueue
ActiveBackgroundQueue
WarmQueue
ReadySkillQueue
ReadyCraftProcessQueue
ReadyItemQueue
```

`ReadySkillQueue`、`ReadyCraftProcessQueue` 和 `ReadyItemQueue` 不绕过实例 tick；它们只标识 Runtime 内部到期工作，Scheduler 仍在所属实例的固定阶段执行。队列键固定为 `(DueTick, InstanceId, Sequence)`，同一初始状态下不会因帧预算或容器遍历顺序改变先后。

优先级：

1. Visible 当前浮窗达到的完整 tick。
2. 即将发生死亡、崩塌或期限到期的 ActiveBackground Runtime。
3. 到期的 skill execution、CraftProcess 和 item command，按所属 Runtime tick 与稳定 Sequence 执行。
4. 其他 ActiveBackground Runtime 轮转。
5. Warm 的环境与 AnalyticAutomatic craft slice。

退出参与者不进入独立等待队列。所属 Runtime 完成当前 tick 后，Manager 立刻调用第二、四阶段定义的同步返回逻辑，再继续调度下一个 Runtime。

预算：

- 平均每渲染帧 `1 ms`。
- 本地硬停止 `2 ms`。
- 单 cooperative slice `0.15..0.25 ms` 或最多 64 条记录。
- 全局待处理路径请求达到 64 时延迟新请求。
- 所有实例共享一个 ParallelJobRunner 和现有 SimulationWorkerPool，不创建实例线程。

Scheduler 不修改 `World.world._is_paused` 或主世界速度。Visible 和 ActiveBackground 都以 `Time.unscaledDeltaTime × DefaultLocalRate × LocalSpeed` 累积自己的 tick；用户单独暂停主世界时，各实例是否继续由 `RunsWhileParentPaused` 决定。MainWorld skill/craft time 与每个 SubWorld `ITimeSource` 独立，调度预算只延迟 wall-frame 完成时间，不改变 LocalTime、DueTick 或领域结果。

### 步骤 3：实现确定性后台推进与自动工序解析

#### ActiveBackground 固定 tick

ActiveBackground Runtime 的 `SubWorldClock` 持有 `PendingLocalTime`。Scheduler 每次取出实例时执行若干完整 tick 并更新 TickIndex。跨帧分批不会跳过中间技能、伤害、物品、制造或 Objective 事件。

两个同 Template、Seed 和创建参数的 Runtime 分别持续 Visible 和持续 ActiveBackground，运行相同 TickIndex 后应产生相同结构签名、RandomState、CompiledSkill runtime、CraftProcessSnapshot、typed item state 和结果。渲染准备、VisualCue 播放和浮窗输入设备读取不进入逻辑签名。

#### CraftProcess 调度

- Manual 工序每次进度都来自操作者成功提交的主行动 contribution；操作者离开、失能或切换行动时按第三阶段共享 `CraftFailure`/中断规则处理，不能按 elapsed 自动补进度。
- fixed-tick Automatic 工序由 `ReadyCraftProcessQueue` 在所属 Runtime 完整 tick 内调用 `ICraftDomainService.Advance`，应用新的 progress 与 RandomState；它阻止 Runtime 进入 Warm。
- AnalyticAutomatic 必须由同一 registry 中该 `ProcessKindId` 的 typed handler明确声明支持，并由 `ICraftDomainService` 提供基于当前 CraftProcessSnapshot、CraftContext、LocalElapsed 和确定性 random cursor 的解析结果。
- 解析推进必须产生与领域结构定义的逐 tick 推进相同的材料消耗、品质、产量、失败、完成时间区间和 typed 产物；Scheduler 不实现配方、概率或产量公式。
- 工序成功仍把产物物化到所属 Runtime Store，并放入 WorkbenchOutput Location。后台或 Warm 完成都不能代替单位拾取。

#### Warm elapsed

Warm Module 接收明确 `LocalElapsed`，只能修改自己拥有的低频状态，例如：

- 缓慢灵气变化。
- 非战斗机关倒计时。
- 无参与者植物生长。
- 已完成后的崩塌倒计时。
- 明确支持解析推进的 AnalyticAutomatic CraftProcess。

Manager 每帧仍更新 Warm Runtime 的 Clock accumulator，但只在达到 `WarmStep` 时调用模块。一个 slice 按模块优先级、ProcessId 和 command Sequence 的固定顺序应用环境、craft、item 与 Objective commands。超出单帧预算的完整 slice 留在该 Runtime accumulator 中，后续帧继续；Runtime 和 Entity 不发生重建。

单位移动、战斗、技能、拾取、物品使用、即时交互和 Manual/fixed-tick Automatic 制造不允许 Warm 近似。

#### Tier 一致性

- Visible 与 ActiveBackground 的确定性基准是相同 TickIndex。
- ActiveBackground 与 Warm 的确定性基准只覆盖明确声明 elapsed 等价的模块和 AnalyticAutomatic handler。
- Warm 转回 ActiveBackground 时从现有 Clock、RandomState、Entity 和 CraftProcess 原地继续，不生成替代 Entity。
- 是否查看浮窗、ViewHost 是否绑定以及 Camera 是否 Render 都不能进入 Random 或领域命令顺序。

### 步骤 4：实现浮窗实例切换和视图资源复用

`SubWorldViewCoordinator` 同时只把一个 Visible Runtime 绑定到 `SubWorldFloatingPanel`：

1. 冻结当前 View ReadModel。
2. 归还实体和特效对象池对象。
3. 清理 Tilemap 内容但保留 Tilemap GameObject。
4. 从 `SubWorldManager.Get(instanceId)` 取得目标 Runtime，应用目标 VisualProfile 与当前视觉快照。
5. ViewHost 从目标 Runtime 的 Main/Top 直接引用重建私有 Tilemap；没有 Top 的格子保持为空。
6. 更新 Camera 边界与局部时间控件。
7. 开放目标实例允许的输入，浮窗外区域继续由主世界处理。

切换浮窗绑定不改变 Runtime 的逻辑数据，也不重建 skill/craft/item queues。原 Visible 按自身即时状态转为 ActiveBackground 或 Warm；目标 Runtime 已经常驻 Manager 集合，只增加 View 绑定。切换、折叠和关闭浮窗都不修改主世界暂停与倍速，主/子世界独立时钟继续按各自策略推进。

#### 实例入口

消费系统可以提供：

- 主世界入口 Building Tooltip 的“查看内部”命令。
- 参与者人物页的“查看远征”命令。
- 小世界浮窗工具栏中的当前可访问实例菜单。

实例菜单使用 `UiOptionMenu`，支持搜索；不增加一排逐个循环实例的文字按钮。菜单项显示 Runtime 名称、Tier、局部时间、参与人数和目标状态，不显示内部对象地址。

### 步骤 5：实现常驻内存预算与 Runtime 容量治理

#### Runtime 常驻内容

从 `Create` 到 `Destroy`，每个 Runtime 始终持有：

- InstanceId、TemplateId、Seed、State 与 Revision。
- `SubWorldMapData`、Grid 直接 terrain 引用、NavigationGrid 与地图脏区。
- EntityStore、SystemRoot、全部 Projection、交互物、物品、工作台和战斗 Entity。
- Clock、Random、RuleRuntime、VisionState、ObjectiveState、命令与事件队列。
- 六种 typed item snapshot、完整动态 Blueprint、Stable ItemId 与 `CraftProcessSnapshot`。
- CompiledSkillDefinition 引用、技能执行状态、冷却和持续效果。

Warm 只减少调度频率，不释放以上任何内容。关闭或切换浮窗只归还 ViewHost 的视觉对象；逻辑 Entity 和 Runtime 容器不受影响。

#### 首版容量

首版默认同时允许：

```text
1 Visible
3 ActiveBackground
4 Warm
8 Runtime total
```

Visible 是对总数中一个 Runtime 的视图标记，不额外创建实例。达到 8 个 Runtime 后，新的 `Create` 返回明确容量不足结果；消费系统必须先对已完成或不再需要的实例调用 `Destroy`。不得通过临时移除 Runtime 绕过容量限制。

单 Runtime 预算：

- 地图上限 `128x128`，tile 使用紧凑数组，不创建 tile Entity。
- gameplay Entity 建议上限 512，默认可见实体上限 256。
- 命令与事件队列各自硬上限 1024；每 tick 各消费最多 32。
- 路径结果只持有 tile index，最多保留当前请求和实体活动路径。
- typed item、CraftProcess、技能轨迹和状态按 Runtime 分组统计数量与估算字节。
- 完整逐 tick 事件不形成历史列表；WorldLog 与消费系统只接收明确需要的外部事件。

#### 生命周期策略

Template 可以选择：

- `DestroyAfterCompletion`：全部参与者完成同步返回后由 Manager 立即调用 `Destroy`。
- `KeepReadOnlyUntilSessionEnd`：Completed Runtime 停止 tick，在当前会话中保留地图、实体终态和目标摘要供查看。
- `ReusableUntilSessionEnd`：Runtime 完成一轮目标后按规则进入 Ready，可接受后续参与者并继续使用同一地图与实体状态。

三种策略都只作用于当前会话。消费系统可以随时对无参与者的 Runtime 调用 `Destroy`；销毁会释放完整 Runtime，不留下另一个实例描述对象。

### 步骤 6：实现完成、崩塌与清理

#### 完成

Objective 完成后 Runtime 进入 Completing：

- 停止生成新敌人与新目标。
- 允许 Template 定义的领取和撤离窗口。
- 已运行的 CraftProcess 按 Template 明确选择继续至领取窗口结束、通过共享 `CraftFailure` 中断或在 Reusable Runtime 中继续，不能静默丢弃材料。
- 通过第四阶段同步返回边界处理全部 Participant Outcome。
- 全部参与者离开后进入 Completed，并执行 Template 生命周期策略。

#### 崩塌

Collapsed 是终止状态：

- 不再允许新参与者。
- 按 ExitPolicy 决定强制撤离、死亡或封闭。
- 通过共享 CraftFailure 终止不允许继续的 Manual/Automatic 工序，结算已有物品、工序产物和伤势结果。
- 对仍有 Source Actor 的 Participant 执行同一主线程同步返回；死亡结果仍最后应用。
- 消费系统获得 CollapseReason。
- 参与者处理完毕后由 Manager 调用 `Destroy`，或按只读策略保留 Runtime。

#### 世界与 Mod 清理

切换世界、返回主菜单或 Mod 重载时统一调用 `SubWorldManager.Clear()`：

1. 停止 `SubWorldManager.Update` 接收新帧与命令。
2. 取消尚未应用的 worker 结果，阻止其回写 Runtime。
3. Mod 重载且主世界 Actor Store 仍有效时，先对现有 Participant 执行普通同步返回；世界本身即将销毁时直接释放 Binding。
4. 对全部实例执行与 `Destroy` 相同的销毁逻辑，销毁 Runtime Root、Store、Entity、Clock 和 RuleRuntime。
5. 清空 visible、background、warm、skill、craft、item 和 path queues。
6. 清空 `ExpeditionBinding`、视图 ReadModel 与对象池。
7. Release/Destroy RenderTexture、Camera、Tilemap 和私有 Material。
8. 清空 Manager Runtime 集合和会话序列。

`Clear` 在生命周期事件内同步结束，不延迟到下一个世界首次 tick。Mod 重载前的同步返回只处理当下仍有效的 MainWorld Store；它使用普通退出逻辑，不构造第二套路径。

### 步骤 7：增加 skill、craft、item queues 诊断

仅 Debug 展示：

- Runtime 总数与各 Tier 数量。
- 每 Runtime 的 TickIndex、PendingLocalTime、Revision、Entity 数和估算内存。
- 逻辑、路径、投影和渲染准备 P50/P95。
- 命令、事件、路径、skill、craft、item queues 深度、最早 DueTick 与最长等待 LocalTime。
- 每 Runtime CompiledSkill execution 数量、到期/延迟/已应用 commands 数量。
- CraftProcess 的 Manual、Automatic、AnalyticAutomatic、Running、Succeeded、Failed 数量和最老 ProcessId。
- CraftProcess 按 `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting` 的数量、资源 command 数量和 handler 类型诊断。
- typed snapshot 按具体类型的 Entity 数与估算字节，分别列出 `MagicScrollSnapshot`、`TalismanSnapshot` 和 `ArtifactInstanceSnapshot`。
- MainWorld/SubWorld 当前 ItemId 数量、重复 ItemId 诊断和同步转移次数。
- Entity、SpriteRenderer、Effect、Tilemap dirty cell 数量。
- 最近一次 Tier 变化原因，以及阻止 Warm 的 skill/craft/item blocker。
- Manager 容量上限、当前占用和最近一次 Create/Destroy 原因。

正式玩家 UI 只显示实例局部时间、运行状态和目标，不显示内部毫秒预算、类型名或对象计数。

### 步骤 8：完成多实例长期差分验收

测试组合：

- 1 个 Visible 战斗与手工制造 Runtime，同时保持主世界运行，并覆盖魔法卷轴和符箓载体使用。
- 3 个 ActiveBackground 远征，分别覆盖 skill、四种 `ProcessKindId` 的 fixed-tick Automatic craft 和 item/death 同步返回。
- 4 个 Warm 环境 Runtime，其中 2 个运行已由对应 typed handler 声明支持的 AnalyticAutomatic craft。

在同一游戏会话中运行至少 100 个主世界年，反复切换视图、提交命令、完成实例、调用 `Destroy` 并创建替代实例。另把两个同 Template、Seed 和参数的 Runtime 分为持续 Visible、持续 ActiveBackground 两路运行相同 TickIndex，差分 Projection、技能、CraftProcess、typed item、RandomState、Objective 和 Outcome；AnalyticAutomatic 另与其领域逐 tick 基准比较。

最后分别触发切换世界、返回主菜单和 Mod 重载清理。每次清理结束后 Manager 集合、Runtime Store、Binding、全部队列、Camera、RenderTexture 和对象池计数都必须归零。

## 验收标准

### 一致性

- 同一初始状态运行相同 TickIndex，Visible 与 ActiveBackground 的 Projection、CompiledSkill runtime、DamageResolution、CraftProcessSnapshot、typed item state、RandomState、Objective 和 Outcome 一致。
- skill、craft、item ready queues 只决定何时获得 CPU slice，不绕过 Runtime tick 或改变 `(DueTick, InstanceId, Sequence)` 顺序。
- Warm 只运行声明支持低频推进的模块和 AnalyticAutomatic CraftProcess。
- 有人手工炼制时 Runtime 不能进入 Warm；fixed-tick Automatic 同样阻止降级。
- AnalyticAutomatic 在 Warm 推进后的领域结果与相同输入、LocalElapsed、RNG 的逐 tick 基准一致，产物仍留在 WorkbenchOutput。
- 四种 `ProcessKindId` 在 Visible/ActiveBackground/Warm 允许的层级都经同一 registry/domain；Scheduler 不按 Kind 名称实现任何制造或资源公式。
- 有战斗、投射物、技能运行态、移动、待处理物品或即时交互时不能进入 Warm。
- 切换查看不会重置 RandomState、AI、路径、技能、CraftProcess、item queues 或 Objective。
- Tier 切换前后 Runtime、EntityStore、EntityId、MapData 和 Grid 对象保持同一实例。

### 性能与生命周期

- `1+3+4` 测试组合下平均小世界 CPU 不超过 1 ms/渲染帧，单帧硬停止 2 ms。
- 八个 Runtime 全部同时存在于 Manager 集合；Warm Runtime 仍持有完整 Store、Entity 和 typed snapshot。
- 达到容量上限后第九次 Create 明确失败，不隐式销毁或移除已有 Runtime。
- 浮窗隐藏或折叠时小世界渲染开销为零，但活跃 Runtime LocalTime 不因此停止。
- 同时只有一个 ViewHost 绑定 Visible Runtime。
- 浮窗打开期间主世界持续运行并可操作；主世界和 Visible Runtime 设置不同倍率时互不覆盖。
- 主世界 craft/skill 时钟与每个 SubWorld `ITimeSource` 独立，暂停或调整任一方不会改变另一方的 DueTick、冷却或工序进度。
- Completed/Collapsed Runtime 按 Template 策略正确销毁、保持只读或进入当前会话可复用状态。
- 返回参与者时，Manager 在一个主线程边界完成所有 Actor 与 Item 跨 Store 更新，调度器不会在中间状态推进其他 Runtime。
- 切换世界、返回主菜单或 Mod 重载后 Runtime、Store、SystemRoot、skill/craft/item queues、Binding、Camera、RT 和池对象计数归零。

### 内存与诊断

- 每个 Runtime 的地图、Entity、typed item、CraftProcess、技能运行态和队列内存都能按实例查看。
- 六种顶层 typed snapshot 与四种 Process Kind 分别统计，不合并为无类型 payload。
- Dynamic `ElixirRecipeBlueprint`、`MagicScrollSnapshot`、`TalismanSnapshot` 和 `ArtifactInstanceSnapshot` 在 Runtime 生命周期内保持完整 typed 内容。
- 未拾取的 Ground 或 WorkbenchOutput 物品始终属于原 Runtime，不被调度层自动转移。
- 诊断能定位阻止 Warm 的具体技能、工序、物品命令或交互。
- 长会话中的内存增长能由 Runtime 数量、terrain、Entity、typed snapshot、craft process、技能状态和队列数量解释。
- Manager 对一个 Runtime 调用 `Destroy` 后，该实例对应的全部内存统计归零，其他 Runtime 指标不变。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
