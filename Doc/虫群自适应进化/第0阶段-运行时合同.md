## 具体说明

### 步骤 1：世界清理边界

`MapBox.clearWorld()` 是唯一世界销毁边界。原版方法负责清理 WorldBox Actor、Building、地图模块和原版管理器；Cultiway 的两个长期 `EntityStore` 不会被原版识别，因此必须由 Mod 在同一边界显式清理。

现有 `Dispose -> TagRecycle -> RecycleDefaultEntitySystem` 只用于普通模拟期回收，不能承担世界清理：Actor 和 Book 的 `Dispose` 只向全局 `CommandBuffer` 写入标记，City 和 GeoRegion 也只是立即添加标记，真正删除要等后续 ECS 逻辑周期。世界切换期间调度器会停止，且 `StructuralChangeSystem` 和回收系统位于 GeneralLogic 后段；若等待新世界首个逻辑周期，旧实体和旧命令可能先被前面的系统观察或执行。Sect 库存根、世界根实体和通用 Event 队列也没有统一自动回收路径。

不新增 `WorldGeneration` 或 `WorldOwned`。世界级 ECS 状态按明确的组件和所属模块清理：

- Core 同步删除 `ActorBinder`、`CityBinder`、`BookBinder`、`GeoRegionBinder`、`SectInventoryBinder`、`WorldRecord` 和 Core 创建的世界期临时 Entity，而不是只清空 Manager 字典或添加 `TagRecycle`。
- InsectModule 同步删除 Hive、Trial、BiomassDeposit，并移除虫族个体组件和全部虫族关系。
- 各内容模块清空自己的 Repository、运行时索引、自有请求队列和延迟任务。
- LinkRelation 只表达引用，不负责删除目标；只有明确登记的 ChildEntities 才能按树形所有权级联清理。
- ApplicationScope 静态定义、Asset Library、`TagPrefab` Entity 和定义期 SourceGranted 技能容器不属于世界清理范围。
- 新增世界级 Entity 类型时，必须同时指定其 `clearWorld` 清理负责人；禁止把“下一次逻辑 Tick 会回收”作为清理实现。

清理顺序：

1. Prefix 停止模拟调度器和异步生产者，并拒绝新的 Event 与模块自有请求。
2. 清空各模块自有队列、结构请求以及全局 `ModClass.CommandBuffer`，使清理前尚未提交的旧世界操作失效。
3. 原版执行 `MapBox.clearWorld()`；原版对象 `Dispose` 期间仍可能向全局 `CommandBuffer` 写入旧世界回收标记。
4. Postfix 再次清空全局 `ModClass.CommandBuffer`，随后调用各模块的世界状态清理入口，同步删除其实体并清空索引。
5. Core 同步删除剩余的通用世界 ECS Entity，重置 `WorldRecord` 等世界根对象，并清空 Actor、Book、City Manager 字典。
6. 在 `clearWorld` 返回后、任何新世界逻辑 Tick 之前，检查所有世界实体、关系、队列和结构请求计数均为零。

如果未来某个任务确实跨线程执行且不能在 Prefix 同步停止，可以捕获原版已有的 `MapBox.current_world_seed_id` 并在回调时比较；这只是异步任务的局部校验，不建立新的世界代次模型。

当前实现由 `PatchMapBox` 编排：Prefix 暂停并清空 `EventSystemHub`、全局结构命令和地图像素 worker，关闭旧世界窗口并清空窗口历史；Postfix 清理动态 Asset、模块清理回调、Manager 索引、池化视觉资源和两个长期 `EntityStore`。Store sweep 保留 `StoreRoot`、`TagPrefab`、`SourceGrantedSkill` 与 `SourceGrantedSkillRoot`，并在仍有其他 Entity 时立即抛出诊断异常。新世界完成后先恢复 EventHub，再发布 `WorldGeneratedEvent` 并恢复地图 worker。

Actor、Entity、Cultibook 和 GeoRegion 的后台结果均携带并比较 `MapBox.current_world_seed_id`；世界切换时还会解除未提交 Cultibook 克隆技能的占用标记。连续三次创建和清理世界的游戏内验收仍归入步骤 7。

### 步骤 2：接入现有模块生命周期

不建立独立的 Feature 注册器。`InsectModule` 只实现 `ICanInit`，由现有 `Content.Manager` 扫描和初始化，作为虫族服务、Provider 与系统的组合入口。

定义和系统继续使用现有机制：

- Actor、Building、Kingdom、Job、Task 和 Coordination 资产继续放在现有 `ExtendLibrary` partial 类中，通过 `OnInit`、`PostInit`、`GlobalPostInit` 和统一语义链接流程完成注册。
- 虫族 ECS 系统组织为一个 `InsectSystemGroup`，由 `InsectModule.Init()` 挂到现有 `ModClass.I.GeneralLogicSystems` 的明确位置。
- 持有世界状态的 System 实现 `IWorldStateClearable`，由 `WorldSystemLifecycle` 统一发现和清理。
- 没有 System 所有者的少量索引才使用 `PatchMapBox.RegisterActionOnClearWorld`；不为清理再保存 System 静态实例。
- 阶段 0 不增加通用 `OnWorldCreated` 多播入口。当前不实现持久化，也没有需要在新世界恢复的虫族状态；出现真实需求后再接入现有世界生成事件或对应 System。

依赖方向作为虫族新代码的局部规则，不宣称由框架强制保证：

```text
Insect Presentation -> Insect ReadModels + UI Foundation
Insect Domain       -> Combat / Ability / Status / Semantics / Runtime
WorldBox Adapter    -> Insect Domain + WorldBox
Runtime/Core        -X-> Insect Domain
UI Foundation       -X-> Insect Domain
```

运行时通用能力不得放进虫族目录形成平行框架。虫族目录中的 `ActiveAbilities`、`Combat` 和 `Coordination` 只保存领域 Provider 与适配器，调度和生命周期继续由现有服务负责。

建议目录：

```text

  Inputs/
  Events/
  ReadModels/
  Services/
  Systems/
  ActiveAbilities/

```

现有资产入口继续使用：


### 步骤 3：领域输入与只读边界

不建立独立的 Ingress、Command、Event 或 Query 总线。虫族按具体用例复用现有事件系统、领域服务和 ECS 结构命令。

#### 输入与事件

- 可能跨线程、发生在 ECS Query 期间或需要延迟结构修改的 WorldBox 输入，通过 `EventSystemHub` 发布 typed Event；事件只保存稳定对象 ID、位置、数值和已结算事实。
- 必须同步修改返回值或立即参与 WorldBox 生命周期的 Harmony Patch，可以直接调用 `InsectWorldboxAdapter`，不强制绕过事件队列。
- 虫族领域 Event 表示已经发生的事实。Handler 可以调用现有服务或提出虫族后续请求，但不建立第二套 Event 分发器。
- `EventSystemHub` 的暂停、拒绝发布和统一清队列能力已由步骤 1 完成，本步骤只增加实际玩法需要的事件类型。

首批事件类型随对应玩法实现，不在阶段 0 预建空类型。预计会覆盖巢核创建、巢核受击、巢核销毁、虫族 Actor 创建、伤害结算、死亡和协调活动完成等事实。

#### 领域请求与 ECS 结构命令

领域请求与 `ModClass.CommandBuffer` 含义不同：前者描述虫族状态变更意图，后者只负责 ECS Entity、组件和关系的结构修改。

- 只有首个真实事务需要排队时，才在 `InsectSystemGroup` 内增加局部领域请求队列，不建设全局 Command 注册框架。
- 入队只能返回 `Accepted` 或明确的拒绝原因；最终执行结果由完成事件、结果记录或后续查询表达。
- 服务修改现有组件；创建、删除 Entity、组件和关系时使用当前 QuerySystem 的 CommandBuffer 或现有全局 `ModClass.CommandBuffer`。

#### 只读访问

不建立 Query Bus。虫族服务提供普通同步查询方法，返回复制后的 DTO、数组和标量。UI 和调试工具不能取得可写 Entity、组件数组或 Repository 内部集合。

`HiveOverview`、`HivePressureProfile`、`HiveGenomeView`、`ActiveTrialView`、`InsectPhenotypeView` 和 `BroodQueueView` 等 ReadModel 随首个消费者增加，不在阶段 0 预建未使用接口。

### 步骤 4：接入现有系统执行顺序

不建立新的全局八阶段调度器。虫族系统挂到现有 `GeneralLogicSystems`，继续复用已有 Event、Skill、结构提交和回收阶段。

`InsectSystemGroup` 只规定虫族内部的确定顺序：

```text
InputConsumption
DomainUpdate
DomainRequestExecution
StateTick
Maintenance
```

只在出现对应职责时增加系统，不为保持阶段表而创建空 System。技能通过现有 `IActiveAbilityProvider` 和 SkillV3 队列调度；战斗通过现有 Combat Provider 与 `CombatWorldService`；协调活动和集体工程分别接入现有 Provider、Planner、Executor 和 Service。

ECS 结构修改遵循现有提交机制：

- ECS Query 内不得直接创建、删除组件或关系。
- 结构请求写入当前 QuerySystem 的 CommandBuffer，或在需要跨系统汇总时写入 `ModClass.CommandBuffer`。
- 只保证单个队列或单个 `SystemGroup` 内的稳定顺序，不承诺所有结构修改存在一个全局 `StructuralCommit` 总序。
- 后续系统必须观察提交后的结构时，将前后职责拆进相邻子组，利用现有 SystemGroup 边界完成 Playback。

### 步骤 5：ECS 数据模型

#### Hive 实体

| 组件 | 核心字段 | 唯一写入者 |
| --- | --- | --- |
| `HiveTag` | 标记 | HiveLifecycleService |
| `HiveCoreBinder` | BuildingId | HiveLifecycleService |
| `HiveIdentity` | Serial、ParentSerial、GenomeGeneration、Seed、FoundedAt、State | HiveLifecycleService |
| `HiveBiomass` | Stored、Reserved、Capacity | HiveBiomassService |
| `HivePopulationState` | Total、Larvae、ByCaste、月均活跃人口 | HiveMembershipService |
| `HivePressureAccumulator` | Severity[]、Evidence[]、WorldMonth | HivePressureService |
| `HivePressureState` | Pressure[]、Evidence[]、HistoricalPeak[] | HivePressureService |
| `HiveSampleBank` | 有界语义样本数组 | HiveSampleService |
| `HiveGenome` | 职虫模板、巢器官、Doctrine、Memory | HiveEvolutionService |
| `HiveBroodQueue` | 固定容量环形队列 | HiveBroodService |
| `HiveTacticalPolicy` | 守巢、巡逻、捕猎和撤退参数 | HiveTacticalPolicyService |
| `HiveEvolutionSchedule` | 下次评估、序号、最后固化时间 | HiveEvolutionService |

#### Actor 虫族状态

| 组件 | 核心字段 |
| --- | --- |
| `InsectIndividual` | CasteId、MorphId、出生基因世代、BornAt、LifeStage |
| `InsectPhenotype` | Signature、固定五槽 ModuleIds、Version |
| `InsectFitnessState` | 伤害、击杀、职责、资源和失败指标 |
| `InsectObservationBudget` | 月份和个体压力贡献上限 |
| `InsectSomaticStress` | 主压力、严重度、濒死幸存、最后事件 |
| `InsectSomaticAdaptation` | AdaptationId、Potency |
| `InsectMetamorphosis` | 目标职虫、形态、完成时间和表现型签名 |

#### Trial 与临时实体

| 实体 | 组件 |
| --- | --- |
| Trial | `AdaptationTrial`、`TrialCohortMetrics`、`TrialDecision` |
| Deposit | `BiomassDeposit`：剩余量、过期时间、来源对象 ID |
| 携带者 | `BiomassCarrier`：携带量、来源 Deposit |
| 建巢母虫 | `FounderGenomePayload`：深拷贝快照和预留生物质 |
| 孤虫 | `OrphanedInsect`：原母巢序号和孤立时间 |

数组在实体创建时按固定上限分配；服务不得把共享临时数组写入组件。

#### 关系

```csharp
public struct HiveMembershipRelation : ILinkRelation
{
    public Entity Hive;
    public HiveMemberRole Role;
    public int GroupIndex;
    public Entity GetRelationKey() => Hive;
}

public struct HiveActiveTrialRelation : ILinkRelation
{
    public Entity Trial;
    public Entity GetRelationKey() => Trial;
}

public struct TrialCohortRelation : ILinkRelation
{
    public Entity Trial;
    public TrialGroup Group;
    public Entity GetRelationKey() => Trial;
}
```

- 一个 Actor 最多属于一座 Hive 和一个 Trial。
- 一座 Hive 最多指向一个活动 Trial。
- PopulationState 是增量缓存，Incoming Membership Links 是归属权威。
- AbilityGrant 和 StatusRelation 继续复用通用关系，不建立虫族平行所有权。

### 步骤 6：WorldBox 适配边界

`InsectWorldboxAdapter` 是唯一 WorldBox 转换入口，负责 Building/Actor 生命周期、伤害事实、位置和资产解析，以及虫族领域操作需要的 WorldBox 生成行为。

- `ActorBinder` 继续由 ActorExtendManager 管理。
- `HiveCoreBinder` 只保存 Building ID 和可丢弃缓存。
- `HiveRepository` 只保存 `BuildingId -> Hive Entity` 可重建索引。
- 延迟任务保存稳定 ID，不保存裸 Actor、Building 或 Entity 引用；真正跨线程的任务额外捕获 `MapBox.current_world_seed_id`。
- Binder 失效时向虫族系统组提交生命周期请求，不直接修补领域状态。

固定 ActorAsset 承担 `flying`、水陆强制属性、基础动画、体型碰撞和基础攻击骨架。ECS 承担属性贡献、伤害适应、Ability、Status、AI、生物质和遗传状态。

### 步骤 7：诊断与验收

诊断至少输出：

```text
ActorBinderEntityCount
CityBinderEntityCount
BookBinderEntityCount
GeoRegionBinderEntityCount
HiveCount
TrialCount
DepositCount
MembershipRelationCount
TrialRelationCount
HiveRepositoryCount
PendingInsectInputCount
PendingInsectDomainRequestCount
PendingInsectEventCount
```

不变量：

1. 每个活动 Hive 能解析有效巢核 Building。
2. 每座 Hive 最多一个活动 Trial。
3. 每个 Trial 恰好被一座 Hive 指向。
4. 已结束 Trial 不再拥有 Cohort IncomingLinks。
5. 已回收 Hive 不再被 Actor、Trial 或 Founder Payload 引用。

验收流程：连续创建并清理世界至少三次，每次都在 `clearWorld` 返回后且新世界逻辑尚未运行时检查所有上述计数归零；清理前排队的请求和全局结构命令不会在新世界执行，ApplicationScope 定义、Prefab 和 SourceGranted 技能容器保持有效。

### 存档范围

当前版本明确不实现持久化：

- 不写 `ActorData`、`BuildingData`、`ModSaveManager`、JSON、SQLite 或自定义文件。
- 不为已保存的虫族 Actor/Building 增加无状态重建规则。
- 不设计版本号、迁移或兼容层。

未来持久化必须另写世界级快照设计，不改变当前 ECS 权威图。
