# 现状与冲突分析

分析日期：2026-11-17。本文区分源码已确认的行为和仍需实机验证的事项。

## 1. 当前开发链路

1. Cultiway 仓库位于游戏的 `Mods/Cultiway` 中。
2. 游戏启动后，由 NML 编译模组源码并加载。`dotnet build` 是开发检查，游戏不加载它的输出。
3. DebugToolbox 启动本机调试服务，并把连接信息写入系统临时目录。
4. 客户端读取默认会话文件，再向游戏发送脚本。
5. 验证脚本创建人物、操作世界、保存资料、截图，部分脚本还会建立轮询请求的临时对象。

这条链路隐含了「一个默认安装位置、一个当前游戏、一个控制者」。worktree 只改变第一步的代码目录，后面几步不会自动跟着改变。

当前实际环境是 Linux 原生游戏，使用 Doorstop/BepInEx 加载模组。仓库技能和部分说明仍以 Windows 为例，因此后续应明确分开共用流程和系统专用启动部分。

`git worktree list` 当前只有主目录，分支为 `master`。工作区已有其他功能的未提交修改。迁移时不能把这些修改当成干净基线，也不能通过整体暂存、清理或重置来处理它们。

另外，环境中列出的 `/home/inmny/Games/Steam/worldbox/Mods/Cultiway` 和当前 Steam 路径，经 `realpath` 与目录编号核对，是同一个目录。不同拼写不能当成隔离；环境编号应基于规范化后的真实路径。

## 2. DebugToolbox：端口已经分开，会话发现没有分开

依据：[服务端](../../../DebugToolbox/Runtime/Transport/ScriptRpcServer.cs)、[客户端](../../../DebugToolbox/Client/RpcClient.client)、[命令入口](../../../DebugToolbox/Client/Program.client)。

### 已确认的行为

- 服务端使用 `new TcpListener(IPAddress.Loopback, 0)`。端口由系统分配，同时监听的服务通常不会抢同一个端口。
- 服务端统一写 `Path.GetTempPath()/DebugToolbox/session.json`，内容包含进程号、端口、令牌和开始时间。
- 客户端只从该固定位置读取端口和令牌，没有显式指定会话文件的参数，也没有利用其中的进程号验证归属。
- `hello` 返回协议、能力列表和游戏帧，没有返回进程号、所属环境、实际游戏目录或存档目录。
- 服务端退出时，只要默认会话文件存在就删除，不检查文件是否仍属于自己。
- 文件使用直接写入，客户端恰好读取时，存在读到尚未写完内容的窗口。
- MCP 客户端在处理工具调用时重新构造连接。因此共享默认文件变化后，同一个工具会话的后续操作也可能转向另一游戏。

### 两个游戏同时运行时会怎样

```text
甲启动 → 默认会话文件指向甲
乙启动 → 同一路径被覆盖，指向乙
甲任务再次执行命令 → 可能连到乙，且令牌也是乙的，校验仍可通过
甲退出 → 可能删掉乙写入的会话文件
```

这是连接目标选择错误。改成固定端口无法解决默认文件覆盖和退出误删。

### 现成的最小隔离办法

当前游戏端和客户端都通过 `Path.GetTempPath()` 找目录。让两个进程继承同一份、且属于该环境的临时目录，能够在不修改 DebugToolbox 协议的情况下分开默认文件。

Linux 基线脚本已使用 `TMPDIR` 做这件事；Windows 对应临时目录变量的效果要在实际 Mono 与客户端运行时下核对。后续显式会话参数仍有价值：让调用方直接表达目标，避免仅靠环境继承。

## 3. 连对游戏仍不等于可以共同控制游戏

依据：[主线程调度](../../../DebugToolbox/Runtime/MainThreadDispatcher.cs)、[脚本执行](../../../DebugToolbox/Runtime/Scripting/ScriptExecutor.cs)。

服务端可以接受多个客户端；脚本开始会进入主线程队列，但没有把整条脚本作为不可交错的操作锁住。脚本甲执行到 `await Game.NextFrame()` 后，脚本乙仍可能开始，切换世界、恢复速度或者删除甲依赖的人物。

游戏的暂停状态、当前世界、窗口、静态字段、人物集合都是该进程内共用的。给脚本加不同的请求编号并不能分开这些对象。首版应规定一个游戏环境只由一个任务控制，第二个修改世界的调用明确拒绝或等待。

取消也有边界：超时令牌不能保证停止所有用户代码；关闭客户端连接也不意味着游戏中的操作已结束。无响应时应标记该次验证结果不确定，恢复或重启所属实例，避免立刻重发同一条会修改世界的命令。

## 4. 日志有多处，不能只管 Player.log

| 来源 | 当前写入位置或规则 | 隔离要求 |
|---|---|---|
| Unity 游戏日志 | 默认用户日志位置；已有脚本用 `-logFile` 指定文件 | 每次启动指定独立文件，控制台输出也独立保存 |
| 原版资源加载 | `AssetModLoader.load()` 清空并写 `Application.streamingAssetsPath/mod_loading_logs.log` | 游戏数据目录可写部分独立 |
| BepInEx | 存在安装目录下的日志及配置 | 副本中保留私有写入位置 |
| CultiLog | 模组目录 `Logs/cultiway-日期.cultilog` | 模组运行目录独立，或以后显式配置日志目录 |
| 旧 PersistentLogger | 示例调用写相对路径 `JindanStats.log`，保存时整文件回写 | 游戏当前工作目录独立 |
| 验证脚本 | 模组目录内固定的 `artifacts/...` | 按环境与本次运行分开 |
| 崩溃和其他插件输出 | 可能落在游戏目录、工作目录或用户目录 | 运行环境至少覆盖这些目录；额外插件按实际写入补充 |

代码依据：[CultiLog 初始化](../../Source/Core/Logging/CultiLog.cs)、[文件写入器](../../Source/Core/Logging/CultiLogFileSink.cs)、[旧日志工具](../../Source/Utils/PersistentLogger.cs)、[金丹日志调用](../../Source/Content/Cultisyses.Xian.Yuanying.cs)、[原版加载日志](../../.GameSource/Assets/Scripts/Assembly-CSharp/AssetModLoader.cs)。

CultiLog 的锁是进程内的，同一天的两个游戏若指向同一模组目录，仍会打开同名文件。可能出现打开失败、内容争用或清空当天日志；具体表现取决于文件打开方式和系统。旧日志工具读取原内容后缓存在内存，保存时再整体覆盖，更容易出现后保存者覆盖先保存者内容。

不同 worktree 如果确实被各自的游戏加载，模组目录日志可以自然分开；但两个游戏都链接回同一个开发目录，或者同一 worktree 同时运行两个游戏，仍会共用它。

## 5. 加载器编译缓存是另一处关键冲突

本机 NML 源码的当前版本与游戏安装记录不同。本分析进一步使用安装目录 `NML/commit` 记录的提交 `10c557714f75cf0e99ea750fe30a60a3c9659ca3` 核对以下行为，避免直接拿新版源码代表当前安装。该记录是源码追溯依据，不是对现有 DLL 构建过程的认证。

依据：[该版本路径定义](https://github.com/WorldBoxOpenMods/ModLoader/blob/10c557714f75cf0e99ea750fe30a60a3c9659ca3/constants/Paths.cs)、[编译加载](https://github.com/WorldBoxOpenMods/ModLoader/blob/10c557714f75cf0e99ea750fe30a60a3c9659ca3/services/ModCompileLoadService.cs)、[编译记录](https://github.com/WorldBoxOpenMods/ModLoader/blob/10c557714f75cf0e99ea750fe30a60a3c9659ca3/utils/ModInfoUtils.cs)。

已确认：

- `Mods` 从游戏目录确定，不是从命令行的当前工作目录确定。仅在某个 worktree 里执行同一个游戏程序，不会自动让游戏加载该 worktree。
- 编译结果按模组编号落到 `worldbox_Data/StreamingAssets/mods/NML/CompiledMods/<编号>.dll`，Cultiway 对应 `CULTIWAY.dll`。
- 编译记录、启用记录和其他加载器记录也位于该 NML 目录。模组用户配置则在用户数据目录下，属于另一类路径。
- 源码实际是从模组目录递归搜索 `.cs`，结合忽略规则排除目录，并非仅依赖项目文件的编译清单。
- 是否重新编译包含文件时间戳比较。换到较旧分支、保留旧时间戳的复制，不能只假定会正确使旧缓存失效。
- 加载器有回写模组 `mod.json` 的能力；现有 Cultiway 版本记录代码也已专门排除部分运行信息。

由此推导：即使两个游戏各自找到了正确的模组目录，只要共享 NML 编译目录，仍可能覆盖同名 DLL 或编译记录。一个实例已把 DLL 载入内存，不代表另一个实例不会读取后来覆盖的磁盘文件。

不建议为不同 worktree 修改 `GUID`。编号还关系到配置、存档和资源身份；隔离运行目录就能保留相同的正式编号。

也不建议把多个 worktree 直接放进玩家游戏的 `Mods` 下：可能被同时扫描，出现相同编号或读到不希望加载的副本。

## 6. 存档、设置和模组全局资料必须一起分开

依据：[原版 SaveManager](../../.GameSource/Assets/Scripts/Assembly-CSharp/SaveManager.cs)、[原版 PlayerConfig](../../.GameSource/Assets/Scripts/Assembly-CSharp/PlayerConfig.cs)、[模组初始化](../../Source/ModClass.cs)、[全局资料写入](../../Source/Core/Persistence/GlobalFileSaveStorage.cs)、[名称资料](../../Source/Core/AIGCLib/BaseNameGenerator.cs)。

原版存档、自动存档与 `worldboxData` 都来自 `Application.persistentDataPath`。Cultiway 的独立存档库、恢复报告、可修改译文和多种名称资料也以这个目录为基础。多个分支共用它，可能互相改变设置、覆盖资料，或者让旧分支读到新分支写出的格式。

原子写入和备份机制用于保护一次保存，不能自动协调两个游戏对同一份资料的修改。

Linux 下 Unity 使用 `XDG_CONFIG_HOME` 作为用户资料路径依据，现有基线脚本已经采用该方法，并在游戏中核对最终路径。[Unity 官方说明](https://docs.unity3d.com/2021.3/Documentation/ScriptReference/Application-persistentDataPath.html)也指出，Windows 使用系统的 LocalLow 目录；因此只改 `TEMP`、`TMP` 或当前目录，不足以保证 Windows 存档隔离。

保存重启用例应复用同一环境的用户资料，但必须创建新游戏进程和新调试会话。需要比较进程开始身份，不能只断开再连，也不能每次重启都删除整个配置目录。

## 7. 现有脚本已做到哪里，还缺什么

| 入口 | 已有能力 | 仍存在的限制 |
|---|---|---|
| [common.py](../../Scripts/SpellDemos/common.py) | 共用调用、内容版本记录、演示结果 | 从固定旁边找客户端、向上找游戏；握手成功即复用当前默认游戏；启动只分开配置目录，没有同步分开临时目录 |
| [baseline_scenarios.py](../../Scripts/SpellDemos/baseline_scenarios.py) | 同时分开配置和临时目录；记录进程；核对进程、配置和实际存档位置；检查源码晚于启动 | 依赖 Linux `/proc`；缺少同环境的并发启动占用；仍继承固定位置的客户端和游戏默认值 |
| [benchmark_baselines.py](../../Scripts/SpellDemos/benchmark_baselines.py) | 准备私有 NML 与 BepInEx 目录；显式模组集合；顺序性能测量 | 整个模组仍链接回开发目录；游戏文件使用硬链接；主要按「不存在才创建」，缺少模板换版本后的更新规则 |
| [runtime.script](../../Scripts/SpellDemos/runtime.script) | 一次安装后处理多次演示请求，减少临时程序集 | 输入输出根目录由游戏内的模组路径确定，不能假定与外部脚本的开发目录相同 |
| [WorldSaveTests](../../Scripts/WorldSaveTests/README.md) | 可独立运行的纯资料转换检查及游戏内重启用例 | 纯资料项目仍从主构建输出找 Newtonsoft.Json；其他机器首次运行需要明确的准备顺序 |

因此，现成代码适合提取共用入口；不适合直接宣布已经支持任意 worktree 下的并行开发。

另一个已有优点是多数共用包装会检查脚本结果中的 `Success`。原始 DebugToolbox 命令成功输出一份 `Success=false` 的结果时，命令本身仍可能以 0 退出；新入口必须继续检查实际结果，不能只看命令退出码。

## 8. 构建和依赖位置也会阻碍 worktree

依据：[项目文件](../../Cultiway.csproj)、[存档检查项目](../../Scripts/WorldSaveTests/WorldSaveTests.csproj)、[忽略规则](../../.gitignore)。

- `GameManagedPath` 默认写成从项目向上两级找游戏；多个引用路径也直接写了同样的相对位置。
- 所以仅用参数覆盖 `GameManagedPath`，不能修好所有引用。需要让引用统一从明确的游戏或依赖根目录派生。
- DebugToolbox 也是独立仓库，不是 Cultiway worktree 的自动组成部分。不能依靠「刚好在旁边」或某人的未提交客户端构建。
- `.GameSource`、`artifacts`、本机生成资料不会随新 worktree 自动复制。游戏源码约 906 MB，可选地共享只读参考，不应把它变成构建必需品。
- 当前 `.gitignore` 中的 `.*` 会忽略 `.github/workflows/...`。接入自动检查时需要添加明确的跟踪例外。
- 当前没有被 Git 跟踪的 `.github` 工作流；不能据此断言远端完全没有其他检查或保护规则，本轮未检查这些远端设置。

本机目录占用粗测：`Source` 约 20 MB，`Content` 约 65 MB，`GameResources` 约 48 MB，`Locales` 约 584 KB，`Assemblies` 约 3.8 MB。游戏数据约 803 MB。这些是当前目录占用，包含可能被忽略的资料，不能当成新 worktree 大小或每次复制成本。

## 9. 验证记录还不能完整代表「实际运行了这份提交」

`version_stamp()` 已经记录提交和文件内容，比只写分支名可靠，但还有以下缺口：

- 读取的是调用脚本时的开发目录。游戏可能仍在运行改动之前载入的程序集。
- 现有私有游戏链接到活跃开发目录。代码载入后再改资源，可能形成「旧代码加新资源」的混合状态。
- 当前范围没有包括 `Locales`、随包依赖程序集和默认配置，也没有完整描述外部模组、游戏和 NML 版本。
- 某些清单和结果路径按固定名字复用，同一环境中的两个调用仍可能互相覆盖。
- 只认修改时间晚于游戏启动，会漏掉内容改变但保留了旧时间戳的情况。

改进方向是启动前准备实际运行快照，并记录该快照的完整输入清单；连接后核对所属进程、模组目录和已加载程序集身份。哈希用于关联测试输入，不能代替游戏内行为验证。

## 10. 文件隔离后的剩余共享资源

鼠标、键盘、剪贴板和前台窗口仍然属于桌面。当前 PowerShell 点击、按键和全屏截图工具没有按游戏进程锁定目标。AI 虚拟桌面能减少打扰用户，但同一桌面上的多个任务仍可能互相抢焦点。

游戏内截图可明确来自目标实例，但不能代替真实点击与输入的检查。首版应让桌面操作依次执行；确有需要后再考虑每任务独立显示环境。

多个游戏还会争用处理器、显卡、内存和磁盘。逻辑用例可以在容量允许时并行；性能采样应保留当前顺序测量的原则。现有性能入口发现其他游戏正在运行便拒绝，这个限制应保留在性能入口，不能推广为所有开发工作都禁止多游戏。

## 11. 尚未验证的边界

本轮没有运行游戏，以下内容应进入实施阶段的实际验收：

1. 当前游戏构建和 Steam 集成在两个私有安装目录下的并行启动行为。
2. Mono 和命令行客户端在目标系统下是否都遵守指定临时目录。
3. Windows 用户资料隔离的可靠做法；不能把 Linux 环境变量方案直接照搬。
4. 副本加载了哪些创意工坊或额外插件，以及这些插件是否还有外部写入位置。
5. 隔离配置下 Steam 云同步和成就等外部状态的实际影响。不能仅凭本地路径隔离宣称它们也已隔离。
6. 模板升级、后台窗口帧率和显卡容量对日常并行数量的限制。

这些是待验证事项，不是已经复现的缺陷。当前没有必要为它们先建立复杂的隔离平台。
