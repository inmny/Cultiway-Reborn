# 目标方案与迁移步骤

状态：供讨论的建议，所有新命令、配置字段和协议字段均尚未实现。

## 1. 先确定开发单位

建议以「一个可独立合并的任务」为单位：一个功能分支、一个 worktree、一个 PR，按需创建一个独占游戏环境。同一任务需要原版与 Worldfall 对比时，可有两个具名环境，但分别有自己的进程和资料。

多人各自在自己的电脑克隆仓库，再按需要使用 worktree；不共享一个可写 checkout，也不把另一位开发者电脑上的环境编号当成本地连接目标。同机多个自动开发任务使用相同规则。

初期不引入长期 `develop` 分支，也不要求每次小修改都开新游戏。可以复用同一输入快照对应的实例；一旦正式代码或资源输入改变，就明确准备新快照并重启，或者在专门的热重载会话中标记重载状态。热重载会话的结果不直接充当干净启动验收。

Git 的工作目录、暂存区和 HEAD 可分开，但对象库、分支引用及默认仓库配置有共享部分，详见 [Git 官方文档](https://git-scm.com/docs/git-worktree)。同一分支不能默认同时检出到两个工作目录；不使用强制参数绕过这个约束。`git worktree lock` 防止目录被清理，不是游戏控制锁。

## 2. 三类位置，各自承担一种职责

```text
本机开发目录/
  Cultiway/                         主仓库或稳定集成目录
  worktrees/
    task-a/                        甲的代码、暂存区和构建输出
    task-b/                        乙的代码、暂存区和构建输出
  dependencies/
    指定版本的游戏来源/              环境准备来源，不在这里执行测试
    指定版本的调试工具/
  runtime/
    环境编号/
      environment.json             所属 worktree、模板版本和路径
      game/                        私有游戏布局、NML 缓存与模组快照
      profile/                     原版及模组的测试配置和存档
      runs/
        本次启动编号/
          temp/                    本次启动的临时文件和 DebugToolbox 会话
          player.log               本次 Unity 日志
          console.log              本次启动输出
          runtime.json             进程身份、输入快照编号和实际连接状态
          cases/                   各条验证命令的输入、结果、截图和录像
```

这是职责示意，不要求所有开发者使用相同的绝对路径。运行目录位于开发仓库和玩家 `Mods` 扫描范围之外；worktree 可以放在任意位置。

环境编号保持稳定，以便保存和重启；每次启动编号必须更新，以便区分进程、日志和调试令牌；每次验证调用再使用独立结果目录，避免覆盖上次结果。

## 3. 游戏副本与模组快照

### 默认采用启动前快照

准备启动时，将当前任务要运行的代码和资源复制到私有 `game/Mods/Cultiway`。复制范围采用明确清单，可从现有 [发布打包清单](../../pack.ps1)提取：`Source`、`Content`、`GameResources`、`Locales`、`Assemblies`、模组声明和必要配置等。

开发检查程序、旧日志、整个 `.git`、`.GameSource`、`bin`、`obj` 和历史录像不放进模组运行目录。加载器的源码搜索规则和必要忽略规则必须保留，避免把检查程序编进游戏。

DebugToolbox 也使用明确版本的运行快照，客户端单独构建并绑定同一套版本。额外模组按具名环境的清单加入，不继承玩家安装目录中的所有启用项。

快照准备期间，该 worktree 的控制者停止写入输入文件；准备完成后再记录清单并启动。否则边复制边改动仍会形成混合版本。新快照就绪前不修改正在运行的环境。

### 为什么首版不直接链接整个 worktree

整个目录链接会让日志、模组声明回写、固定的演示请求路径重新落回开发目录，也会让运行中读入的资源跟随开发修改。

完整快照更容易解释「这个游戏跑的是哪份内容」。以后如果复制成本成为实际问题，再只对已经确认不写入的部分优化；无需一开始支持多种同步方式。

### 共享文件的规则

首版可以普通复制。文件系统支持写时复制时，可以减少空间占用，同时让两份文件的后续写入独立。不要用整个目录硬链接作为默认方案；硬链接只是另一个名字，并不提供修改隔离。

NML 编译输出、编译与启用记录、BepInEx 配置和日志、原版加载日志、模组声明及测试资料必须私有。模板版本改变后重新准备环境，不能继续采用「文件存在就永久复用」。玩家通过 Steam 更新游戏，也不应在测试过程中改变正在使用的模板。

首次准备一个模组快照时，不沿用来源安装的 `CULTIWAY.dll` 和编译记录。换输入快照后，明确使该模组的缓存失效，避免把较旧分支的时间戳当成已经编译过。相同快照重启时可以复用自己的缓存。

## 4. 连接、控制和退出规则

### 第一版先利用已有能力

Linux 游戏及客户端共同使用该次启动的 `TMPDIR`；游戏再设置该环境的 `XDG_CONFIG_HOME`，用 `-logFile` 写本次日志，并把当前工作目录设到私有游戏目录。启动方式保留本机必需的 Doorstop/BepInEx 设置。

启动窗口遵循本机 `ai-gui` 约定。它解决窗口归属，不承担日志、存档或输入隔离。

启动与连接流程应从「默认游戏」改成「明确环境」：

1. 取得该环境的启动占用，避免两个命令同时创建进程；若已经启动，只连接该环境。
2. 读取本次启动记录和本次会话文件，等待对应进程就绪。
3. 核对进程号、开始身份、实际用户资料目录、实际加载的模组目录和版本，再允许修改世界。
4. 由一个任务持续拥有修改世界的权利，覆盖所有跨帧操作；第二个控制者明确等待或失败。
5. `stop` 只向已验证属于该环境的游戏请求退出；必要时只终止已核实身份的所属进程。进程号会复用，不能仅凭旧文件里的数字判断。

环境不存在、身份不匹配或连接超时就报告该环境的状态和日志位置，不能悄悄改连另一游戏。客户端超时后也不能自动重试一条可能已经执行过的世界修改。

同一可信任务内的共用调用可以继承一次核对后的运行上下文；进程重启、连接重建或控制权交接时重新核对。无需在每个内部函数重复检查相同信息。

### 第二版明确 DebugToolbox 会话

建议在 DebugToolbox 独立仓库增加：

- 客户端支持显式会话文件选项；可另提供明确命名的环境变量。具体名称在实现时统一。
- 显式目标优先；显式文件失效时直接失败，不退回全局默认文件。
- 游戏端支持指定会话输出路径，用完整写入后替换的方式发布文件。
- 握手返回进程身份、启动编号、实际游戏与用户资料目录。模组加载清单按需要提供，保持 DebugToolbox 通用，不引用 Cultiway 类型。
- 退出只清理属于自己的会话文件；临时符号、默认截图与追踪资料也属于该环境。
- 长连接或 MCP 固定所属启动身份；重启后必须明确重新绑定，不能仅因某个文件变化就自动切换。

继续保留系统动态端口。固定端口分配表、每人手工记端口、每次重新扫描所有端口都没有必要。

单游戏旧流程可以保留作兼容入口；新的并行开发入口始终使用显式目标。

## 5. 本机配置与共用开发入口

建议 Cultiway 仓库保存工具本身和配置样例，本机实际路径放在不跟踪的配置中。必要内容只有游戏来源、DebugToolbox 来源或客户端路径、运行目录位置，以及可选的兼容模组位置。

游戏路径不再由 `PROJECT.parents[1]` 猜测；客户端不再假设位于 `PROJECT.parent/DebugToolbox`。项目引用统一从同一个依赖根路径派生，`bin/obj` 继续留在各自 worktree。

可考虑下面这组职责明确的命令。它们是建议接口，不是当前已存在的工具：

| 操作 | 目的 |
|---|---|
| `doctor` | 不启动游戏，检查路径、依赖、工具版本和目录归属 |
| `build` | 在当前 worktree 完成开发编译 |
| `start` | 准备或复用明确环境，启动对应输入快照 |
| `status` | 显示所属 worktree、运行版本、进程和日志位置 |
| `run` | 在指定环境执行脚本，保存本次结果并检查实际成功标志 |
| `stop` | 退出指定环境的游戏，保留测试资料和结果 |
| `clean` | 在进程已经退出后清理指定环境；保留或导出需要的存档与证据 |

首版是一组共用本地函数和薄命令入口即可。不建设后台常驻服务、分布式锁或数据库。

现有技能、`Prompts/DEBUG.md` 和验证说明最终统一引用这一入口，避免文档一套、基线脚本一套、临时命令又一套。

## 6. 验证脚本如何迁移

共用入口向脚本传入运行上下文：环境、启动编号、输入目录和输出目录。游戏内脚本也读取同一份上下文，不能继续假定 `GetDeclaration().FolderPath` 与外部脚本的开发目录相同。

保留现成场景、存档样本和临时演示工具。先迁移常用入口、一个正常场景、一个保存重启场景和一个画面场景；其他脚本在下次使用时迁移。不要先重写整个 `SpellDemos`。

日常验证按改动覆盖正常使用、一个相关失败情况和结束恢复。涉及保存、伤害、控制归还、换世界时，保留对应认真验证；外观以实际画面为准。公共流程通过后，不按身体和装备重复整套场景。

每份结果至少记录：所属 PR 或任务、提交及未提交状态、实际输入快照编号、游戏和工具版本、额外模组、场景与存档来源、运行身份和输出位置。会话令牌只留在本机连接文件，不放进 PR 或共享日志。

输入快照清单覆盖真正影响运行的代码、资源、本地化、默认配置、依赖程序集和外部模组。准备环境时计算一次内容身份即可，不在每次读状态时扫描整个资源目录。

本地允许验证未提交修改；PR 的正式验收应来自已提交内容。更新提交后，只重测被改动影响的场景；不能把旧结果改个提交号继续使用。依赖基线变了，也重新判断受影响范围。

## 7. PR 如何成为日常协作边界

### 推荐流程

1. 从明确的主线提交创建 `codex/<任务名>` 分支和 worktree。每个任务写清范围、玩法变化、必要验证和交付物。
2. 在该 worktree 开发。共享接口或存档格式需要其他任务配合时，先用小 PR 固定接口，再开展依赖任务，避免多个任务同时改公共入口。
3. 开发编译后，在所属环境执行所需验证。代码检查和资源检查可以并行；真实桌面输入和性能采样分别占用共享设备。
4. 提交中文 Conventional Commit 信息，开草稿 PR，说明玩家看到的变化、验证方式、结果、资源新增及是否需要手动迁移。
5. 评审依据最终差异和对应结果。主线变化涉及同一机制时，在最新主线组成的结果上做相关验证，不机械重跑所有场景。
6. 合并后关闭所属游戏，保留需要的测试资料和结果，再移除或归档 worktree。清理代码目录不能顺手终止其他任务的游戏。

一个可独立合并的功能一个 PR。必须修改 DebugToolbox 时，工具改动在其自身仓库提交 PR；Cultiway PR 说明依赖的工具版本。测试工具、玩法改动和批量格式调整不混成一个难评审的提交。

### 自动检查按依赖能力分层

| 检查 | 合适的执行位置 | 起步范围 |
|---|---|---|
| 文本、资源清单和可脱离游戏的资料转换 | 普通自动检查环境 | 逐项选择已有且能独立运行的检查 |
| Cultiway 完整开发编译 | 有合法本机游戏依赖的环境 | 固定游戏和加载器版本，统一引用根路径 |
| 游戏内逻辑和保存重启 | 准备了独立游戏环境的本机 | 输出结构化结果，明确对应提交 |
| 画面和性能 | 有图形环境及可控资源的本机 | 画面附截图或录像；性能独占采样 |

不把商业游戏 DLL 或整份游戏放进公开仓库来方便自动编译；同样不假定普通托管检查环境已经装好 WorldBox。接入本机执行器时，外部贡献代码由维护者明确选择后再运行，不能让陌生 PR 自动控制维护者的游戏和本机。

起步只固定 `master` 和少量必要检查。远端分支保护、评审人数和是否压缩合并属于仓库治理选择，后续落实时再按实际账户能力配置。

## 9. 平台范围与待讨论选择

建议先在当前 Linux 原生环境完成闭环，再扩展 Windows。

Windows 下临时目录、日志文件和私有安装目录可以分别处理，但它们不自动改变 LocalLow 存档和注册表中的偏好。可靠候选包括独立系统用户或完整隔离环境；若采用早期加载补丁重定向，则必须覆盖原版与模组保存入口和初始化顺序。选择前需要一次专门实测，不应凭一个环境变量承诺完成隔离。

多人各自在独立电脑上开发，也可以先获得「不互相影响的代码与 PR 流程」，然后再按各自系统完善同机多实例能力。

建议后续讨论集中在三项：

| 选择 | 建议起点 | 影响 |
|---|---|---|
| 首期平台 | 当前 Linux；Windows 单独验收 | 控制第一轮范围，同时保留多人跨机器使用方式 |
| 日常游戏并行 | 支持多个独立逻辑实例；桌面操作和性能采样依次执行 | 既分开任务，也保留可信的画面与测量结果 |
| 开发输入 | 默认启动前快照；热重载作为单独会话 | PR 结果有明确来源，复制优化以后再按实际成本做 |

当前工作区和 DebugToolbox 都存在既有未提交修改。真正开工时，先确定它们的任务归属和需要进入基线的部分；不要自动把所有本地变化带到基础设施 PR 中。本轮分析文档可作为后续讨论和实施拆分的依据。
