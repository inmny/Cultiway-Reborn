# 技能与一键环境流程

讨论日期：2026-11-17。本文保留实施前的讨论设计；第一版已落地，实际命令和范围见 [第1阶段记录](第1阶段-技能与隔离环境.md)。下文未落地的可选部分仍为建议。

## 1. 已确认的选择

用户已确认：

1. skill 管理完整开发流程，覆盖创建或接入 worktree、环境准备、开发验证、提交 PR 和收尾。
2. PR 交付后回收游戏副本，保留分支、worktree 和验证证据；PR 合并后再回收 worktree。

下面细节是围绕上述选择提出的建议，尚未逐项确定。

## 2. skill 与脚本如何分工

| 部分 | 负责什么 |
|---|---|
| skill | 理解任务范围；创建或接入正确的 worktree；选择必要验证；组织提交和 PR；判断何时正式交付并调用收尾 |
| setup 入口 | 识别本机依赖；准备独立游戏环境与构建引用；登记归属；输出后续操作所需的环境信息 |
| 启动和运行入口 | 准备实际代码快照；启动所属游戏；让客户端始终连接该环境；收集结果 |
| 收尾入口 | 保存交付证据；关闭所属游戏；删除可重建的运行文件；更新状态 |
| 已合并任务回收入口 | 核对 PR 状态及本地未交付修改后，移除或归档所属 worktree |

物理上不必拆成五套工具。建议是一个版本化脚本提供几个子命令，skill 调用同一实现；人手动开发也能执行它。

skill 放入仓库的 `.agents/skills/`，让其他开发者和新 worktree 取得同一份流程。脚本也随仓库跟踪。首版可把脚本放在该技能的 `scripts/` 中，避免在技能和 `Scripts/` 下维护重复实现。

skill 只保留本项目必要约定和入口说明，架构、编码规则及详细调试说明继续引用现有文件，不把所有资料复制进技能。

## 3. setup 的边界

skill 先创建或选择 worktree，再把明确路径交给 setup。若桌面应用或开发者已经建立 worktree，就直接接入，不再创建第二套目录。

建议 setup 一次完成：

1. 确认操作的是目标 worktree，识别是否已有属于它的环境。
2. 从本机配置读取游戏来源和 DebugToolbox，验证实际路径及所需版本。
3. 准备该环境的游戏目录、用户资料目录、构建引用和日志位置。
4. 登记环境编号、所属 worktree、依赖版本和本工具创建的资源。
5. 输出一份机器可读结果，让 skill 后续直接使用环境编号和路径。

重复 setup 应接回原环境；配置或依赖改变时说明需要更新什么，避免每次重新复制完整游戏。原版对比或 Worldfall 兼容验证可作为具名配置，按任务需要选择。

默认 setup 只准备环境，游戏在实际验证时启动。文档修改或纯资料转换检查无需占用游戏进程。启动时再准备当前代码快照，避免 setup 之后开发的内容没有进入游戏。

后续启动和调试命令读取登记信息，并自行向子进程传递隔离变量。不能要求每个终端手工执行相同的 `export`，也不能假定 setup 子进程能改变调用它的父终端环境。

## 4. 建议的完整流程

```text
接到任务
  → 创建或接入 worktree
  → setup 准备环境
  → 开发；按需启动并验证
  → 提交、推送并正式交付 PR
  → finish 保存证据，回收游戏环境
  → PR 等待评审
      ├── 需要返工：原 worktree 再次 setup，恢复开发
      └── 已合并：核对本地状态后，回收 worktree
```

可以提前创建草稿 PR，但「创建了 PR」本身不代表结束。只有 skill 完成当前交付范围，并进入正式交付状态，才触发 finish。

推送或 PR 创建失败时，不能记为已交付。验证失败后应保留定位资料；是否继续运行游戏由当前排查需要决定。用户暂停任务时也不删除代码或测试存档。

## 5. 两次回收分别清什么

| 时机 | 回收 | 保留 |
|---|---|---|
| 正式交付 PR 后 | 所属游戏进程、私有游戏副本、编译缓存、临时会话、可重建的测试资料 | 功能分支、worktree、PR 信息、验证结果、必要日志与截图，以及重现问题需要的输入 |
| PR 已合并后 | 经核对可回收的 worktree，以及对应残留运行资料 | PR 和提交历史、约定保留的验证证据、共享游戏来源与工具 |

证据必须先归档到不会随游戏副本或 worktree 删除的位置，再开始删除。若测试存档仍是唯一可复现输入，应将它一并归档，而不是只留下结果或内容哈希。

保存重启验证属于同一次开发过程，期间保留该环境的用户资料；不能在每次退出游戏时就清掉存档。

清理只处理登记为本工具创建且归属于该任务的资源。玩家安装、共享依赖、主工作目录和其他任务的进程都不属于清理范围。清理命令重复执行应能正常返回，而不是因为部分文件已不存在就卡住。

合并后回收还要核对本地是否有新增修改或尚未交付的提交。遇到这些情况保留并报告；不能仅凭分支名、时间长短或 PR 已关闭删除。压缩合并时应以 PR 的实际合并状态为依据，不能只用本地分支是否是主线祖先来判断。

桌面应用管理的 worktree 使用相应归档能力；开发者自行创建的 worktree 使用 Git 的移除流程。环境脚本不直接删除应用管理目录。

## 6. 自动清理靠什么触发

### 正常完成：由 skill 明确调用

建议把 finish 作为交付流程的一步：证据已保存、提交已推送、PR 已成功交付，随后自动执行环境收尾，再向用户报告结果。用户不需要额外手动清理。

不要以 setup 进程退出作为开发结束，因为它只负责准备环境；也不要用任意一轮对话回复结束来判断整项任务完成。

### 异常中断：保留状态，下次恢复或回收

只靠技能说明，无法保证主机断电或程序被强制结束时还能执行收尾。建议将资源归属和流程状态持续写入登记文件，在下一次 setup 或专门的回收命令中识别残留。

识别残留时，除了进程是否存在，还要判断任务是否仍处于开发或待恢复状态。其他任务仍在使用的环境，不能因为没有近期日志就回收。

首版不需要为此常驻一个后台服务。若以后确实需要更及时的异常收尾，再接入宿主生命周期钩子。

### PR 合并：由后续入口核对

PR 的远端合并可能发生在本地聊天停止以后。skill 在继续该任务、显式回收，或下次 setup 的轻量检查中核对已登记 PR，再回收满足条件的 worktree。

这实现的是「确认合并后回收」。若要求远端合并发生后立即无人值守回收，则还需要事件通知或周期执行；它不属于一份 skill 和一次 setup 自然拥有的行为，是否加入应另行讨论。

## 7. 与 Codex 自带能力的关系

当前官方说明提供了本地 worktree 的 setup 配置，可以在创建新 worktree 时调用准备脚本。适合把它作为调用同一 setup 的可选入口；手动建 worktree 的开发者仍可直接执行脚本。[本地环境说明](https://learn.chatgpt.com/docs/environments/local-environment)

官方也提供生命周期钩子，但 `Stop` 属于一轮交互停止，`SessionEnd` 属于主会话结束，都不能直接代表 PR 交付或远端合并。当前 `SessionEnd` 还有较短执行时限，不适合承担完整的游戏退出、证据归档和大目录清理。若接入，可用于简短的状态记录或恢复提示；具体客户端效果在实施时核对。[生命周期钩子说明](https://learn.chatgpt.com/docs/hooks)

项目技能可随仓库分发，官方列出了 `.agents/skills` 的发现范围。[技能说明](https://developers.openai.com/codex/skills)

## 8. 首版建议交付范围

- [ ] 一个覆盖完整开发流程的仓库技能。
- [ ] 一个脚本提供 setup、启动、执行、状态、交付收尾和已合并任务回收入口。
- [ ] 当前 Linux 环境下两个任务互不串线，正常收尾只关闭和删除所属环境。
- [ ] 同一 worktree 重复 setup、PR 返工重建、保存重启和中断恢复可用。
- [ ] 证明证据已经独立保存，再删除运行目录；确认 PR 合并及本地状态后再回收 worktree。

Windows、多平台统一分发、即时监听远端合并和常驻回收服务留待实际需要时讨论。首版没有修改客户端生命周期设置。
