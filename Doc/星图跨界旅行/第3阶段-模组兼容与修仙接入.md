## 具体说明

### 两层兼容检查

第一层检查目标世界能否在当前环境打开。第二层检查人物能否在该环境落地。两层都通过才导入人物。

| 检查对象 | 检查内容 | 失败处理 |
| --- | --- | --- |
| 整张世界 | 游戏存档版本、必要模组、种族、建筑、群系及世界附加数据 | 停留在旅途中，提示切换环境或修复目标 |
| 人物身体 | 身体资源、外观、亚种与必须的身体组件 | 无可用身体时阻止出发或抵达 |
| 人物能力 | 功法、技能、修为、血脉等的导出、恢复与依赖关系 | 按模组声明生效、封存或阻止 |
| 物品 | 装备定义、法宝本体、物品内嵌能力及引用 | 整体封存或阻止，不生成缺一半的数据 |
| 世界规则 | 目标世界允许的能力、当地限制、抵达条件 | 只改变可用范围，保留可恢复的原始资料 |

原版 `MapMetaData.modsActive` 可提供线索，但它不能代替完整的版本和必要依赖检查。新世界版本额外记录实际启用的模组标识、版本及与玩法有关的配置摘要。模组主动声明哪些内容是加载本世界必须具备的条件。

兼容状态至少区分“已验证支持”“可封存”“未经验证”“不支持”，不能因为模组名称相同就显示完全兼容。

### 接入约定

旅行核心提供一份小型接入约定，各模组按自己的数据结构实现。第一版使用直接注册的提供方列表。

| 提供方需要说明的事情 | 用途 |
| --- | --- |
| 模组标识、资料段标识、当前支持版本 | 找到正确的恢复方，避免不同模组使用相同字段名 |
| 能否导出当前人物 | 阻止出窍、夺舍等尚未支持的中间状态 |
| 需要随人物带走哪些对象 | 收集个人物品、技能及必要定义，避免带走整张世界 |
| 目标环境需要什么 | 给出必须存在的资源、版本和配置条件 |
| 哪些内容可以封存 | 判断缺少提供方时人物是否仍能正常存在 |
| 怎样导出与恢复 | 在目标环境重建数据、重新连接本地人物和物品 |
| 怎样处理离境关系 | 清理本模组拥有的宗门、师徒或其他本地引用 |
| 保存和加载时怎样恢复旅客资料 | 保证抵达后再次重启仍完整，不能只在抵达瞬间有效 |

最小导入流程为“先分配所有本地编号 → 创建人物与物品 → 恢复各资料段 → 重新建立相互关系 → 刷新属性 → 保存并提交”。提供方先检查依赖，再实际创建数据；失败的部分不能留下可活动的半个人物。

资料段内记录其依赖的其他资料段和对象。多个提供方修改同一项身份或身体时，必须有明确的联合支持规则；未验证的冲突组合显示不支持。

模组可以声明自己没有需要携带的人物资料。未接入的第三方模组只保证已明确支持的原版字段，界面显示“额外资料未经验证”；发现人物有必要但无法导出的资料时阻止旅行。正式发布的完整兼容只覆盖实际接入并通过测试的组合。

### 不同模组组合之间的旅行

所有世界记录预期使用的玩法组合。首版仅在组合相同、或被明确验证为可共存的环境之间直接切换。

需要切换组合时：

1. 在源环境检查目标声明，完成导出并提交出发。
2. 人物以文件资料保存在旅途中，界面显示目标组合与差异。
3. 玩家切换到目标组合并重启游戏，旅行核心仍启用。
4. 旅行核心发现未完成旅程，检查当前实际环境。
5. 加载目标世界，等待目标模组准备完成后继续抵达。
6. 目标环境仍不满足要求时保留人物包，提供处理说明和返航路径。

运行中按世界禁用玩法，只能在该玩法主动支持全部系统暂停、资源和事件隔离时开放。例如，修仙模组已经加载，它对所有世界安装的补丁不会因为给某颗星球写了“原版”标签就自动停止。

同一进程里同时加载两套模组，也不能据此认定它们没有冲突。首版对不同组合采用重启续行，对已经验证的同组合旅行采用直接切换。

返航也检查源世界需要的环境。当前组合无法打开源世界时，人物继续停留在旅途中，切回源环境后返航。

### 封存规则

封存指资料完整保留在旅客的附加保存中，暂时不参与当地世界的属性、施法、掉落和交易。

| 情况 | 规则 |
| --- | --- |
| 目标缺少修仙玩法，但人物身体受支持 | 修仙能力封存，原版部分正常活动 |
| 目标缺少人物的自定义种族 | 默认阻止；另行提供明确身体转换规则后才可开放 |
| 缺少某件法宝的本体或内嵌能力 | 作为一个整体封存，避免残缺法宝活动 |
| 目标支持另一种能力体系 | 可按当地玩法获得能力，分别记录各提供方资料 |
| 两种体系同时存在 | 由共同规则决定是否同时生效，默认不自动叠加和换算 |
| 目标模组版本较新且资料无法读取 | 保留资料段并停止恢复，不覆盖原数据 |
| 人物已经正常死亡 | 已完成旅程的封存资料只作历史，不提供复活入口 |

每次受管保存都更新旅客的当前原版资料、活动能力和封存资料。封存部分只恢复其拥有的数据，不能用出发时的整个人物覆盖当前状态。因此人物在外界增加的年龄、获得的装备或遭受的伤势会保留。

物品使用稳定的旅行物品编号。封存恢复时，把“封存物品”转换为一个活动实例并更新保存；再次封存时记录该活动实例的最新状态。活动物品与封存记录互斥，重复回乡不会再生成一件。

封存期间的能力是否计入寿命、是否保留特殊生存条件，由提供方明确说明。无法脱离某能力存活的人物不能直接将该能力封存。例如元神形态不能默认当作普通原版人物落地。

### 修仙接入

#### 当前前置

本地 `mod.json` 仍标注“存档无效”；切换世界还会清除运行期实体。修仙接入必须先验证参与旅行的人物资料能够保存、读档和重启恢复，并确认当前实际可用的世界存档范围。

如果整张修仙世界的本地修炼、物品和关系尚不能恢复，应先将其列为独立前置工作。旅行人物的附加保存可以保护旅客，不能据此承诺其他所有居民和整张世界都已完成持久化。未通过前，正式兼容列表中将修仙标为待支持。

#### 需要收集的资料

| 修仙资料 | 携带范围与恢复方式 |
| --- | --- |
| 修炼体系、境界和已获得的稳定成长 | 导出明确的个人数据，目标按新人物重新绑定 |
| 灵根、血脉、仙基、金丹等个人构成 | 导出个人组成及所依赖的定义；存在互相引用时一起恢复 |
| 元婴与元神 | 先支持稳定、完整的人物状态；出逃、夺舍、附体、出窍等中间状态暂时阻止 |
| 功法、掌握度和已学技能 | 携带个人进度、必要技能定义及自己的修改；运行中的施法和投射物重新结束处理 |
| 灵力和个人资源 | 携带当前资源，目标按活动能力计算上限；封存时保持资料而不提供当地效果 |
| 个人物品、已绑定法宝 | 携带真正属于此人的物品及内嵌能力，重建物品归属和绑定关系 |
| 宗门、师徒和故乡关系 | 保存来源世界引用，离境处理活动位置；目标重建可用关系，不复制整个宗门 |
| 缓存和显示状态 | 抵达后重新计算，绑定到目标人物的新本地编号 |

模组内部实体、物品和技能构成需要按“人物拥有的对象及其必要依赖”导出。共享技能定义可以按稳定资源标识引用；存在个人修改的定义要保存对应修改内容。先创建目标对象，再用新编号连接，不能直接照搬原运行期实体编号。

`ActorBinder` 使用当前世界的人物编号，因此导入时创建新的 `ActorExtend` 绑定。离境前完成导出；世界清理后，由目标环境重新创建所需实体并刷新属性和技能缓存。

#### 代码落点与依赖方向

| 位置 | 职责 |
| --- | --- |
| 独立旅行模组 | 世界目录、人物包约定、旅行流程、原版资料支持和星图界面 |
| 本仓库 `Source/Content/WorldTravel/` | 修仙资料导出、恢复、世界要求和离境关系处理 |
| 本仓库 `Source/Content/Manager.cs` | 在旅行核心存在时注册修仙提供方，并声明准备完成时机 |
| 本仓库玩法所属目录 | 为自己的数据提供明确读写方法，继续拥有自身规则 |
| 本仓库 `Source/Content/UI/` | 人物页入口、修仙封存说明等接入界面 |
| 本仓库 `Locales/` | 对应中文和其他语言文本 |

依赖由修仙可选地指向旅行核心，旅行核心可以单独使用。可选依赖名称以加载器实际识别的声明为准，参考官方依赖规则；不要凭本仓库 `GUID` 字段推测外部依赖字符串。

本轮只是设计，不创建独立模组目录、不修改 `mod.json`、注册入口或现有保存代码。

### 验收场景与发布条件

| 场景 | 通过条件 |
| --- | --- |
| 原版玩法 A → 原版玩法 B | 保持第1、2阶段结果 |
| 支持修仙的世界 A → 支持修仙的世界 B | 修炼、功法、法宝及个人资源正确，重启后仍可用 |
| 修仙环境 → 仅装旅行核心的环境 | 先提交出发，重启续行；可封存资料完整且不产生修仙效果 |
| 原版玩法中发展后返回修仙环境 | 恢复封存能力，保留当前年龄、原版成长与新获得物品 |
| 进入另一套已接入玩法后返回 | 两套个人资料分别保存，按声明启用，不自动重复叠加 |
| 身体、关键种族或必要物品依赖缺失 | 给出具体原因，保留人物包，不创建残缺人物 |
| 目标组合有冲突、版本不受支持 | 提示未经验证或不支持，不能显示完全兼容 |
| 各环境下抵达后保存、退出、重开 | 人物和封存资料恢复，不只在切换瞬间可用 |
| 连续往返多次，并在外界使用或获得物品 | 不重复恢复旧物品，不用旧资料覆盖当前人物 |

“兼容不同模组配置”的首个正式版本，以原版玩法和至少一套已经完成接入与往返测试的玩法组合为发布门槛。完整修仙接入是否包含在首次发布，由上述存档前置能否通过决定。
