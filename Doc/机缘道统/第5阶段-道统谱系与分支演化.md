# 第5阶段-道统谱系与分支演化

本阶段让功法传承形成可追溯历史。普通传授延续同一修订，真实改良产生子修订；残篇可以被补全，失传道统也可以重新出世。经由遗府取得的传承保留入口与小世界实例来源，使谱系能够追溯到实际探索地点和核心目标。

## 具体说明

### 设计边界

- `Lineage` 表示共同祖源，`Revision` 表示一套确定的功法内容，`TransmissionGeneration` 表示人物间传了多少代。
- 同一修订从师父传给弟子不会克隆功法资产或创建新 Revision。
- 名称变化但内容签名不变时不创建新修订。
- 功法属性、语义、元素要求、修炼方式或法术池发生实质变化时才创建子修订。
- “正宗”不是世界级真理；Sect 可以把某个修订奉为本宗正传，其他宗门可以有不同认定。
- 不建立复杂可编辑谱系图，不允许玩家手工改父子关系或指定正宗。

### 步骤 1：完善道统、修订与人物代数模型

#### 根道统

`LegacyWorldDocument` 增加 `DoctrineLineageRecord`：

```text
LineageId
RootRevisionId
CanonicalName
FounderSnapshot
CreatedAt
OriginKind
```

根道统只保存共同身份和祖师，不重复保存功法内容。

#### 修订

扩展 `DoctrineRevisionRecord`：

```text
RevisionId
LineageId
ParentRevisionId
ContentSignature
CreatedBySnapshot
CreatedAt
Integrity
SemanticDrift
CultibookBlueprint
```

`ContentSignature` 只包含影响修炼和法术的规范字段，不包含：

- 功法显示名与描述。
- 创建者姓名和 Actor ID。
- 创建年份、来源遗府和宗门认定。
- 掌握度和当前持有人。

因此同一内容被抄写、改名或重新装订时仍是同一 Revision。

#### 人物持有

扩展 `ActorLegacyHolding`：

```text
RevisionId
Mastery
TransmissionGeneration
TeacherActorId
AcquisitionKind
SourceSiteId
SourceSubWorldId
SourceBookId
AcquiredAt
IsMainCultibook
```

人物代数独立于修订深度：

- 自创根功法者为第 0 代。
- 从人物、书籍、宗门讲法或遗府继承时，在来源代数基础上加 1。
- 同一人物改良功法后仍保留自己的传承代数，但持有新的 Revision。
- 不知道直接传授者的残篇继承，以遗府祖师代数加 1，并把来源标记为 Site 与已提交 `OutcomeDelta` 中的机缘来源字段。

### 步骤 2：接入功法生成与改良事件

#### 自创功法

接入 `CultibookGeneratedEventSystem`。当角色成功接受一部尚未登记的自创功法时：

1. 使用 `CultibookBlueprintCodec` 完整导出。
2. 创建新的 Lineage 与根 Revision。
3. 角色持有记录写入第 0 代、`AcquisitionKind=Created`。
4. 将运行时功法 Asset ID 统一绑定为 RevisionId。
5. 写入世界目录和自创历史。

生成草稿失败、没有被角色接受或无法通过 Blueprint 验证时不创建空道统。

#### 改良功法

接入 `CultibookImprovedEventSystem` 的接受结果：

1. 找到角色原功法对应的 Parent Revision。
2. 导出改良后的完整 Blueprint。
3. 计算 ContentSignature。
4. 与 Parent 签名相同则只更新显示名或描述，不创建子修订。
5. 签名不同则创建同一 Lineage 下的新 Revision。
6. 将角色持有记录切换到新 Revision，旧 Revision 仍保留在世界目录和其他持有人身上。

如果原功法尚未进入世界目录，先以原功法创建根 Revision，再把改良结果作为子 Revision。不能把改良版错误登记为没有父级的全新道统。

#### 不可变蓝图

已经注册进世界目录的 `CultibookBlueprint` 不允许原地修改。任何内容变化必须生成新 Revision；运行时 `CultibookAsset` 只是该不可变修订的物化结果。

### 步骤 3：让师徒、书籍和藏经阁保留修订

#### 师徒传授

扩展现有 `TeachCultibook()`：

- 通过运行时功法 Asset ID 解析 RevisionId。
- 接收者继续 `Master(asset, mastery)`，同时写入 ActorLegacyHolding。
- `TeacherActorId` 指向真实师父。
- `TransmissionGeneration = teacher.Generation + 1`。
- 重复传授同一 Revision 只增加掌握度，不增加代数。

普通讲法和师徒传授不创建 Blueprint 深拷贝，也不增加 Revision 引用之外的动态资产。

#### 功法书

写书时在 `BookData.custom_data_string` 保存：

```text
Cultiway.Legacy.RevisionId
Cultiway.Legacy.WriterGeneration
Cultiway.Legacy.WrittenAt
```

读书时优先按 RevisionId 从世界目录解析功法。书中保存的旧显示名只用于历史，不覆盖当前 Revision 蓝图。

书籍本身继续使用原版 `Book` 与现有 `BookExtend`。不创建第二套“传承卷轴”对象。

#### 宗门藏经阁

`SectScriptureCollection` 收录带 RevisionId 的功法书后，建立 Sect 对该修订的真实知识来源。宗门讲法从藏经记录解析同一 Revision，并把讲法者或书籍作为接收者的来源记录。

Sect 可以保存：

```text
LineageId -> CanonicalRevisionId
```

这表示“本宗奉此修订为正传”，只影响宗门展示、讲法优先级和命名，不修改全局谱系关系。

### 步骤 4：实现支脉判定与残篇补全

#### 内容差异

新 Revision 相对 Parent 计算：

- 元素需求方向变化。
- 语义余弦相似度。
- 修炼方式是否改变。
- 属性集合与数值变化。
- 法术池新增、移除和替换比例。
- 完整度变化。

由这些事实推导展示类型：

| 类型 | 条件 |
| --- | --- |
| 根本 | 没有 Parent 的完整 Revision |
| 续修 | 内容保持同一方向，完整度不下降，差异未达到分支阈值 |
| 支脉 | 语义方向、修炼方式或法术池发生明显分化 |
| 残篇 | `Integrity < 1.0` |
| 复原 | Parent 为残篇且新 Revision 的完整度显著提高 |

类型由当前记录计算，不保存可与事实冲突的手工枚举。

#### 同父分支

同一个 Parent 出现两个及以上内容不同的子 Revision 时，谱系自然形成分叉。系统不选择唯一正确答案；Sect 可以分别认领其中一支为正传。

#### 残篇补全

角色满足以下条件时可进入 `Cultiway.RestoreDoctrineFragment` 工作：

- 掌握一个残篇 Revision 达到指定熟练度。
- 同时掌握同 Lineage 的另一残篇、父修订线索或足够多兼容法术。
- 神识、智力和当前境界达到残篇修复要求。

修复调用现有功法改良规则，以残篇为 Parent 生成新 Revision：

- `Integrity` 只能根据实际补回的属性和法术池提高。
- 两份来源残篇都记录为 `SourceRevisionIds`，但主 Parent 仍为当前修炼残篇。
- 完整度达到 `1.0` 时显示为复原版本，不自动等同于历史上已经失传的完整 Parent。
- 内容签名恰好与旧完整 Revision 相同时，复用旧 RevisionId 并记录“复得”，不创建重复版本。

### 步骤 5：实现活跃、沉寂、失传与复出

`LegacyLineageStatusService` 从当前世界真实引用推导每个 Revision 的状态：

| 状态 | 仍存在的来源 |
| --- | --- |
| `Active` | 至少一名存活角色正在掌握 |
| `Archived` | 没有存活持有人，但存在功法书或 Sect 藏经记录 |
| `Dormant` | 只存在于未完成核心目标的小世界遗府或宗门遗址 |
| `Lost` | 世界目录保留蓝图，但没有角色、书籍、Sect 或活跃地点引用 |

运行时 Holder Index 从 ActorLegacyHoldings、BookData、SectScriptureCollection、LegacySiteRecord 的修订引用和 SubWorldArchive 的未完成核心目标重建。入口只证明地点来源仍存在；道统是否仍可取得以实例目标和 SubWorldArchive 内的物品状态为准，物品 snapshot、ItemId 和 ItemLease 不写入 SiteRecord。状态本身可以缓存，但不能成为替代真实引用的权威字段。

#### 失传

Revision 首次从非 Lost 进入 Lost 时记录一次内部历史。只有根道统或曾经形成重要分支的修订写公开 WorldLog，普通短命改良版不刷屏。

失传不会删除 Blueprint。道统生成频率本身受角色自创和改良行为限制，因此首版不实现按年龄清理历史修订。

#### 复出

以下行为可以让 Lost Revision 重新出现：

- 玩家投放古修遗府时，优先从当前世界 Lost 修订中选择内容。
- 覆灭宗门遗址的小世界藏经阁中仍保存了对应书籍快照。
- 残篇修复的 ContentSignature 与旧 Revision 完全相同。

复出复用原 RevisionId，增加新的来源历史，不克隆成同内容新版本。

### 步骤 6：增加人物与道统只读页面

实施前继续遵守 `Prompts/UI.md`，复用当前 CreatureInfoPages、Foundation、Controls 和原版窗口行为。

#### 人物道统页

在人物信息中增加“道统”页，展示：

- 当前主修修订及所属根道统。
- 传承代数、直接师承或来源遗府实例。
- 掌握度、完整度和功法类型。
- 当前人物亲自创建的改良修订。
- 跳转到来源人物、书籍、Sect 或遗府入口；来源小世界仍可查看时可以打开其归档历史并定位核心房间。

页面只展示持有记录，不扫描全部世界谱系。

#### 道统谱系窗口

新增代码构建宽窗口，采用：

- 顶部搜索与 `现世 / 沉寂 / 失传` Segmented Tabs。
- 左侧可滚动根道统目录。
- 右侧单层详情区展示祖师、当前状态和按父级缩进的修订列表。
- 选中 Revision 后展示内容差异、历代重要事件和当前来源。
- 遗府来源事件显示 Site 名、SubWorldId、核心目标结果和取得者，不展示已经失效的运行时 Entity ID。

不实现可拖拽节点图、自由缩放画布或卡片嵌套。谱系父子关系用稳定缩进、连接符和状态图标表达。

#### 功法与书籍 Tooltip

现有功法、技能来源和书籍 Tooltip 增加：

- 根道统名。
- 修订类型和完整度。
- 创建者或改良者。
- 当前人物传承代数。
- Sect 正传认定仅在查看对应 Sect 内容时显示。

### 步骤 7：补齐历史、资源与验收

#### 世界历史

公开日志只记录：

- 世界中出现新的根道统。
- 某位重要修士开创明显支脉。
- 重要道统彻底失传。
- 失传道统重新出世。
- Sect 正式把某个修订奉为正传。

普通师徒传授只写入持有记录，不逐次生成 WorldLog。

#### 历史容量

世界目录保存完整 Revision 蓝图和关键事件。人物普通传授历史由当前 Actor Holding、书籍和重要事件共同还原，不保存每次讲法的听众列表。

## 验收标准

### 谱系

- 自创功法产生一个根 Lineage 和一个根 Revision。
- 改名或描述变化不产生新 Revision。
- 属性、语义、元素、修炼方式或法术池实质变化产生 Parent 正确的子 Revision。
- 同一 Parent 可以形成多个内容不同的支脉。
- 相同 ContentSignature 在同一 Lineage 中复用已有 RevisionId。
- Blueprint 注册后不可原地修改。

### 传承

- 师徒传授同一 Revision 只增加接收者代数和掌握度。
- 重复传授不会重复增加代数。
- 功法书保存读档后仍指向同一 Revision。
- 宗门讲法不会为每个听众创建功法副本。
- Sect 可以各自认定正传，但不会改变其他 Sect 和全局谱系。

### 失传与复出

- Actor、书籍、Sect、遗府入口和小世界核心目标变化能够正确更新状态。
- 没有任何世界来源时 Revision 标记为 Lost，但 Blueprint 仍保留。
- 古修遗府重新投放 Lost Revision 时复用原 RevisionId。
- 已耗尽入口不再让 Revision 保持 Dormant；仍含未完成核心目标的归档会保持 Dormant。
- 残篇补全为相同内容时复用旧完整修订，否则形成新的复原支脉。

### UI 与游戏验证

- 人物页正确展示多个持有修订、主修、代数和来源。
- 谱系窗口可处理空列表、单一根道统、多级分支和大量失传修订。
- 中文、英文和长功法名不遮挡状态与跳转按钮。
- 保存读档后窗口内容、父子关系和当前状态一致。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
