# 第1阶段-古修遗府闭环

本阶段建立第一个可保存、可读档、可由 AI 独立完成的古修遗府闭环。遗府由玩家神力投放，修士抵达主世界入口后投影进入真实 SubWorld，后续阶段再接入自然死亡来源。本阶段依赖[SubWorld 第 1 至第 4 阶段](../小世界-摘要.md)已经完成：直接消费第 1 阶段的原版 terrain catalog、第 2 阶段的 portable item 合同和第 4 阶段的 compiled skill/shared combat；第 3 阶段共享制造到机缘道统第 3 阶段才启用。

## 具体说明

### 设计边界

本阶段只实现一种来源和一种探索规模：

- 玩家在合法地块投放一座完整古修遗府。
- 遗府从当前已经注册且可完整导出的功法中构造古修道统。
- 附近修士可以独立发现入口、前往、投影进入实例并完成探索。
- 同时只允许一名预约探索者，不实现消息传播、多人试炼或宗门集结。
- 实例固定包含入口、封禁、外围室、核心室和出口；角色必须在内部移动并与目标交互。
- 核心奖励至少包含完整功法和一项代表法术；镇府法宝只在已注册 `IPortableItemCodec<ArtifactInstanceSnapshot>` 能完整导出时，以 typed `ContentRef<ArtifactInstanceSnapshot>` 和稳定 `ItemId` 物化为内部唯一物品。
- 外围遗藏可以包含已注册 codec 的 `ContentRef<MagicScrollSnapshot>` 与 `ContentRef<TalismanSnapshot>`；两种载体分别保存真实 typed snapshot，不用通用技能载体替代。
- 入口、实例归档、道统目录和继承人的掌握状态必须经过保存与读档恢复。

阶段结束时，玩家已经可以投放一个真实改变角色成长的机缘，而不是只看到建筑和日志。

### 步骤 1：建立可持久化功法蓝图

新增 `CultibookBlueprint` 及唯一 codec。蓝图只保存稳定值与稳定 Asset ID，不保存运行时 `Entity`：

```text
CultibookBlueprint
  SchemaVersion
  BlueprintId
  SourceAssetId
  Name
  Description
  Level
  Stats[]
  Semantics[]
  ElementRequirement
  ElementAffinityThreshold
  MinLevel
  MaxLevel
  CultivateMethodId
  SkillPool[]
  ConflictConditions[]
  SynergyConditions[]
```

`Stats` 保存按 Stat Asset ID 排序的数值，`Semantics` 直接保存 `SemanticContribution`。`SemanticQueryExpression` 已经只包含 `all/any/none` 三组字符串 ID，可以深拷贝进入蓝图。

每个 `SkillPoolBlueprintEntry` 保存：

```text
SkillBlueprint
BaseChance
MasteryThreshold
LevelRequirement
```

#### 导出规则

1. 读取 `CultibookAsset` 的全部稳定字段。
2. 对每个法术池 Entity 调用现有 `SkillBlueprintExporter`。
3. 使用 `SkillBlueprintValidator` 验证本体、轨迹、资源与词条 Asset ID。
4. 任意法术池条目无法导出时，整部功法导出失败；不能静默丢掉法术改变道统内容。
5. 规范化数组顺序并深拷贝，计算只基于内容的结构签名。
6. `SourceAssetId` 只记录来源，不作为未来重建的唯一依据。

#### 重建规则

1. 先验证修炼方式、属性、语义和全部技能蓝图。
2. 使用共享 Skill compiler 按结构签名把每个 `SkillBlueprint` 解析为唯一 `CompiledSkillDefinition`；相同蓝图不能为 Legacy 恢复和 SubWorld Projection 分别生成两份能力定义。
3. MainWorld skill port 根据 compiled definition 建立 SkillLibV3 技能容器并添加 `TagOccupied`；SubWorld skill port 只投影同一 definition 暴露的 capability。
4. 以道统 `RevisionId` 作为动态 `CultibookAsset.id`，避免覆盖原始功法资产。
5. 写入全部稳定字段，调用功法规则合成器完成规范化。
6. 将动态功法加入 `CultibookLibrary`，由角色 `Master()` 引用计数保活。
7. 中途失败时释放本次已经创建的 MainWorld 技能容器，不向动态库留下半成品；共享 `CompiledSkillDefinition` 仍由平台按签名管理。

同一 `RevisionId` 在一个运行时只物化一次。多个角色掌握同一修订时共享同一个不可变 `CultibookAsset`，各自保存独立掌握度。

### 步骤 2：建立世界道统目录与角色持有记录

#### 世界道统目录

新增 `LegacyWorldDocument`，序列化到 `MapStats.custom_data` 的固定 key：

```text
Cultiway.Legacy.World
```

首阶段文档包含：

```text
SchemaVersion
DoctrineRevisions[]
HistoryEntries[]
```

每个 `DoctrineRevisionRecord` 保存：

- `LineageId`、`RevisionId`、`ParentRevisionId`。
- 古修祖师姓名快照、来源类型和创建年份。
- 完整度；首阶段固定为 `1.0`。
- `CultibookBlueprint`。
- 代表法术在法术池中的索引。

`LegacyWorldStore` 是世界目录的唯一写入口。注册新修订时先按 `RevisionId` 去重，再持久化当前文档。`MapBox.clearWorld()` 时只清理运行时索引和物化缓存，不清除存档对象。

#### 角色持有记录

角色获得道统后，在 `ActorData.custom_data_string` 保存 `ActorLegacyHoldings`：

```text
SchemaVersion
Holdings[]
  RevisionId
  Mastery
  IsMainCultibook
  LearnedRepresentativeSkillIds[]
  AcquiredAt
  SourceSiteId
```

该记录只保存对世界道统目录的引用，不重复整份功法蓝图。角色首次建立 `ActorExtend` 时，`LegacyHoldingRestoreService` 根据 `RevisionId` 解析或物化动态功法，经共享 compiler 和 MainWorld skill port 恢复 `Master()`、主修状态和已经授予的代表法术；恢复入口不解释技能效果。

恢复必须幂等：同一个 `ActorExtend` 重复调用恢复入口不会重复增加掌握度、重复学习技能或重复增加功法引用计数。

### 步骤 3：注册完整遗府入口与小世界实例

在 `Buildings` 中注册 `Cultiway.LegacyEstate`，建议从原版 `monolith` 克隆并改为非城市建筑：

- 可在合法陆地单点放置。
- 不属于城市或文明，不参与建筑升级和城市建造队列。
- 可被世界灾害摧毁。
- 活跃期间保持 `BuildingState.Normal`。
- `has_ruin_state=true`，耗尽或摧毁后才进入原版废墟状态。
- `auto_remove_ruin=false`，让已发生的历史在地图上保留。

`BuildingData.custom_data_string` 使用固定 key 保存 `LegacySiteRecord`。它只描述主世界入口：

```text
SiteId
RevisionId
SubWorldId
State
Integrity
PlayerRevealed
CreatedAt
Discoverers[]
ReservedActorId
WinnerActorId
ClaimedAt
```

创建入口时同时通过 `SubWorldService.CreateInstance()` 建立休眠归档，使用 Template `Cultiway.Legacy.AncientEstate`。实例创建参数保存 `SiteId`、`RevisionId`、资格规则和可选的 `ContentRef<ArtifactInstanceSnapshot>`、`ContentRef<MagicScrollSnapshot>`、`ContentRef<TalismanSnapshot>`；法宝可放在核心室，魔法卷轴与符箓放在外围真实容器，全部以稳定 `ItemId` 物化为 SubWorld 唯一物品，不写入 SiteRecord。

首个模板采用确定性布局：

```text
入口 -> 封禁门 -> 外围室 -> 核心室 -> 出口
```

内部地形、封禁门、容器、物品、Projection、核心目标和结算状态全部由 `SubWorldArchive` 保存。创建时只生成归档，不启动 Runtime；首次参与者进入才激活实例。

Generator 的地面、墙体、入口和出口必须从 `IWorldBoxTerrainCatalog` 选择原版 `TileTypeBase` Asset 字符串 ID，并按 `TerrainPalette` 保存引用。`Cultiway.Legacy.AncientEstate` 只注册房间布局和遗府 `TerrainThemeOverrideId`；override 可以按 `SourceLayer + AssetId` 绑定石室 sprite、overlay 与局部材质，但不能复制一套 Legacy 基础 terrain 定义，也不能改写原 catalog 的通行、阻挡或环境语义。

首阶段状态只使用：

```text
Dormant -> Known -> Opening -> Claimed -> Exhausted
```

`LegacySiteService` 是入口与消息状态的唯一写入口；`LegacySiteRepository` 只提供按 Site ID、Building ID 和空间分桶的查询。`SubWorldRuntime` 是内部状态唯一写入口。世界加载后扫描 `Buildings.LegacyEstate.buildings` 重建索引，并用 `SubWorldId` 校验对应归档，不能把 Building 或 ECS ID 写入世界道统目录。

遗府基础建筑使用低调的封石或山岩画面。`PlayerRevealed=false` 时不显示 Tooltip 详情、小地图颜色或额外世界标记；不依赖切换 BuildingAsset 来表达显露状态。

### 步骤 4：实现古修遗府与显露天机神力

注册两个正式 World Tool：

| God Power ID | 显示名 | 点击语义 |
| --- | --- | --- |
| `Cultiway.PlaceAncientLegacyEstate` | 古修遗府 | 在合法地块创建一座完整且对玩家已显露的古修遗府 |
| `Cultiway.RevealLegacySites` | 显露天机 | 显露笔刷范围内已经存在的遗府，不把消息授予角色 |

两个 Power 都通过 `WorldboxGodPowers.SetupWorldToolPower` 注册，`hold_action=false`。显露天机设置固定 Brush 范围，复用原版光标高亮。

`LegacyAncientDoctrineFactory` 创建古修来源：

1. 从当前 `CultibookLibrary` 中筛选能够完整导出的功法。
2. 排除法术池为空、修炼方式失效或 Blueprint 验证失败的候选。
3. 从合格集合选择一部作为内容来源，导出后使用新的 `LineageId` 与 `RevisionId`。
4. 生成古修祖师姓名和简短来源描述，不将其伪装成当前世界角色。
5. 若内容目录中存在可由已注册 portable codec 完整物化的法宝、魔法卷轴或符箓，可以分别生成稳定 `ItemId` 与 `ContentRef<ArtifactInstanceSnapshot>`、`ContentRef<MagicScrollSnapshot>`、`ContentRef<TalismanSnapshot>` 写入 SubWorld 创建参数；古修物品以 Archive 为初始权威，没有 MainWorld 源 Entity，也不在创建或内部拾取时取得 `ItemLease`，只有实际带出并开始返回提交时才取得 Lease。内容和所有权都不写入 DoctrineRevisionRecord 或 SiteRecord。两个技能载体只保存嵌套 `StoredSkillPayloadSnapshot`，不保存 SkillContainer Entity 或 CompiledSkillDefinition 副本。
6. 先向 `LegacyWorldStore` 注册修订，再创建 Building、SiteRecord 和对应 `SubWorldArchive`。
7. 任一前置不满足时不消耗地块，并显示本地化失败原因。

Power、自然死亡和未来宗门遗址必须共用 `LegacySiteService.Create()` 的入口事务，并统一调用 `SubWorldService.CreateInstance()` 创建实例与 `SubWorldArchive`，不能各自复制入口、实例和存档初始化逻辑。

### 步骤 5：实现单人发现、寻访与进入实例

#### 发现

在 `ActorJobSelectionRegistry` 注册低频遗府 selector。只有满足以下条件的角色进入发现检查：

- 已经拥有仙道修炼体系。
- 当前不在战斗、突破、集体活动或不可中断任务中。
- 附近空间桶存在 `Dormant` 或 `Known` 遗府。
- 角色尚未记录该 Site ID。

发现概率首阶段只使用现有能力：

- 智力。
- 神识。
- `Effect.Perception` 语义净分。
- 与遗府的实际距离。

不读取尚未初始化的 `Qiyun`。发现成功后向 SiteRecord 添加角色稳定 `ActorData.id`，状态从 `Dormant` 进入 `Known`，并写发现日志。

#### 单人预约

首阶段不允许多人同时开启。遗府从已发现且满足最低境界与元素要求的存活角色中选择一名预约者：

- 基础相性采用现有元素契合与功法语义契合。
- 距离和当前任务只决定是否能够出发，不进入道统相性。
- 预约写入 `ReservedActorId`；其他角色保留消息但暂不前往。
- 预约者死亡、失去修炼体系或连续超时后释放预约。

预约者获得 `Cultiway.SeekLegacyEstate` 工作，设置 `beh_building_target` 并复用 `BehGoToBuildingTarget`。这段主世界行为在抵达入口时结束，随后由 `LegacyEntryService.TryEnterSingle()`：

1. 取得该 Actor 的 `ExpeditionLease`。
2. 通过 `SubWorldService.AddParticipants()` 加入 SiteRecord 指向的实例。
3. 在内部入口生成 `ExpeditionProjection` 并切换到小世界探索 AI。
4. 把 Site 外部摘要切换为 `Opening`。

入口 `step_action` 不推进封禁、不授予奖励。租约生效后主世界本体留在入口地块并暂停渲染、AI、伤害、饥饿、年龄、状态和模组定时系统。

### 步骤 6：实现内部探索、核心目标与返回恢复

首阶段核心资格：

```text
境界在功法 MinLevel..MaxLevel 内
ElementReq.Check(root) == true
综合相性 >= 0.3
```

综合相性复用现有解析器：

```text
Compatibility = 0.7 * ElementAffinity + 0.3 * SemanticAffinity
```

Projection 使用小世界导航和交互系统执行最小探索序列：

1. 从入口移动到封禁门，使用 Projection 上由 `ISkillDefinitionRegistry` 解析、经 shared skill execution ports 暴露的 `CompiledSkillDefinition` 神识/破禁 capability 执行交互；Legacy 不建立试炼技能解释器。
2. 进入外围室并自行决定是否打开容器、拾取法宝、魔法卷轴、符箓或其他已注册 typed 物品；载体物品只有实际拾取并撤离后才能提交。
3. 到达核心室，和 `LegacyCoreObjective` 交互并检查境界、元素与综合相性。
4. 通过后由目标写入唯一 Winner，并生成待冻结进 `OutcomeDelta` 的功法、代表技能 `SkillBlueprint` 引用和掌握度结果；代表技能在 MainWorld/SubWorld 两侧都经同一 `ISkillDefinitionRegistry` 解析到同一 `CompiledSkillDefinition`。
5. 若核心室存在镇府法宝，Winner 仍需走到物品旁拾取；实际拾取只更新 Archive 中的 SubWorld item holder，不提前创建 `ItemLease`，核心目标不能远程把物品塞入 `OutcomeDelta`。
6. Projection 到达出口后冻结 `OutcomeDelta`，以稳定 `CommitId` 写入 `PendingOutcome`，等待统一返回提交。

`OutcomeDelta` 是冻结后待提交的数据值，包含资源增量、角色状态、技能与机缘扩展字段、portable item 所有权变化和死亡结果。`PendingOutcome` 只表示这份 `OutcomeDelta` 尚未完成提交；失败或读档后继续使用原 `CommitId`，不创建另一种提交对象。

`SubWorldOutcomeCommitService` 是按稳定 `CommitId` 幂等提交 `OutcomeDelta` 的唯一入口，返回顺序固定为：

1. 读取 `PendingOutcome`，确认该 `CommitId` 尚未完成。
2. 为实际带出的 Archive 原生物品取得本次 `CommitId` 的 `ItemLease`，先销毁或卸载其 SubWorld Runtime materialization；Archive 与 `PendingOutcome` 继续权威持有最终 snapshot/holder。
3. 按 `ItemId + CommitId` 查询 MainWorld ownership；没有本次结果时调用对应 `IPortableItemCodec.Materialize(targetStore, snapshot, factory)` 创建同一 ItemId 并绑定目标 holder，已经物化并绑定时不重复创建。已消耗或销毁物品不 Materialize。
4. 再提交资源、角色状态和机缘扩展字段；其中机缘字段只通过 `LegacyOutcomeAdapter` 应用。
5. 死亡结果最后提交，避免提前销毁 Actor 阻断前述字段。
6. 在同一主线程提交边界持久化 `CommitId` 与 MainWorld ownership 后，删除对应 Archive item record/snapshot 引用，移除 `PendingOutcome`，释放本次完成的 `ItemLease`，最后释放 Actor 的 `ExpeditionLease`。

`LegacyOutcomeAdapter` 只由 `SubWorldOutcomeCommitService` 调用，并应用以下机缘字段：

1. 从世界目录解析并物化对应功法修订，其中全部 `SkillBlueprint` 先解析为共享 `CompiledSkillDefinition`。
2. 调用 `ActorExtend.Master()` 写入初始掌握度。
3. 从代表技能中选择与角色语义最匹配的一项，经 `MainWorldSkillAdapter` 授予同一 compiled definition 对应的运行时技能；SubWorld 试炼只使用 `SharedSkillExecutor` 和共享 ports，不复制定义。
4. 仅当新功法对当前灵根的修炼效率高于现有主修时，调用 `SetMainCultibook()`。
5. 写入 `ActorLegacyHoldings`、Site 的 Winner 摘要和世界历史；Site 只记录获选事实，不记录物品。

`LegacyOutcomeAdapter` 不创建或物化物品，不独立提交 `OutcomeDelta`，也不自建幂等状态；portable item、`CommitId` 和 Lease 都由 `SubWorldOutcomeCommitService` 处理。

初始掌握度按相性映射到 `10..30`，不能直接满掌握。传承给予修行入口和一项代表法术，不替代后续修炼。

返回提交完成后遗府进入 `Claimed`。实例中不再存在可拾取内容且没有参与者时，入口才进入 `Exhausted` 并转为原版废墟表现。世界道统目录、小世界历史与角色持有记录继续保留，所以删除入口建筑不会删除功法或传人状态。

### 步骤 7：补齐日志、Tooltip、地图表现与验收

#### WorldLog

首阶段注册两类高价值日志：

- 某修士发现某古修遗府。
- 某修士在某地获得某道统传承。

日志绑定角色并保存地块坐标，允许从日志跳转。预约、赶路和资格不足不写 WorldLog，避免刷屏。

#### Tooltip 与地图

- 光标位于已显露遗府时，通过原版 `RawTip` 显示名称、完整度、当前阶段和道统名称。
- 未显露时不显示遗府身份，只保留低调建筑画面。
- `mini_0.png` 只在 `PlayerRevealed=true` 时返回状态颜色。
- 已显露遗府使用对象池世界标记，样式复用现有 Realm Indicator 的渲染生命周期。
- 状态变化后标记占用地块 dirty，立即刷新小地图。
- Tooltip 提供“查看内部”命令，打开主世界 HUD 上的小世界 RenderTexture 浮窗；主世界继续运行和接受操作，玩家查看不替角色揭开迷雾。

#### 存读档顺序

读档恢复顺序固定为：

1. 读取 `LegacyWorldDocument` 并建立修订索引。
2. 读取 `SubWorldArchive` 并恢复实例归档。
3. 扫描遗府 Building，恢复 Site Repository 并重连 `SubWorldId`。
4. 恢复 `ExpeditionLease`、MainWorld 来源或已开始返回提交的 `ItemLease`、Projection，以及 `PendingOutcome` 中冻结的 `OutcomeDelta` 与稳定 `CommitId`；未开始返回的古修 Archive 原生物品没有 Lease。
5. Actor 首次创建 Extend 时读取 `ActorLegacyHoldings`。
6. 按需物化功法，并通过共享 `CompiledSkillDefinition` 与 MainWorld skill port 恢复角色技能和掌握。

世界清理时清空修订物化缓存、Site Repository、空间桶与待恢复集合。切换世界后不能继续解析上一个世界的 `RevisionId`。

## 验收标准

### 功能

- 古修遗府只能放在合法地块，同一点击只创建一个 Building、一个 SiteRecord 和一个 SubWorldArchive。
- 每个遗府引用一个存在于当前世界目录中的完整修订。
- 不可完整导出的功法不会生成缺字段遗府。
- 附近修士能在没有玩家指定角色的情况下发现并前往入口、取得 Lease、投影进入实例。
- 同一时刻只有预约者进入寻访工作，预约失效后可由其他发现者接替。
- Projection 会在内部经过封禁门、外围室和核心室，不能从入口直接取得奖励。
- 遗府 MapRecord 的 `TerrainPalette` 全部来自 `IWorldBoxTerrainCatalog` 的原版 `TileTypeBase` Asset 字符串 ID；删除 `TerrainThemeOverrideId` 后仍能解析基础语义，Legacy 不注册第二套基础 terrain。
- 不满足境界、灵根或相性门槛者不能取得核心传承。
- 成功者获得功法掌握和一项代表技能；恢复和内部试炼使用同一 `CompiledSkillDefinition`，但不改变境界成果。
- 镇府法宝以 `ContentRef<ArtifactInstanceSnapshot>`、稳定 `ItemId` 和 `SubWorldItemRecord` 由 Archive 权威持有，开始返回提交前没有 `ItemLease`；未拾取时不会随核心目标自动进入角色库存。
- 外围魔法卷轴和符箓分别以 `ContentRef<MagicScrollSnapshot>`、`ContentRef<TalismanSnapshot>` 与稳定 `ItemId` 存在；二者保留各自载体语义，未拾取时不进入返回结果。
- 同一遗府只能提交一次 Winner；`SubWorldOutcomeCommitService` 对同一 `CommitId` 只应用一次冻结的 `OutcomeDelta`，不能复制奖励。
- 显露天机只改变玩家可见性，不把消息授予附近角色。

### 存档

- 在 `Dormant`、`Known`、Projection 探索中、核心已完成、待返回和 `Exhausted` 状态分别保存并读档，入口与实例保持一致。
- 读档后世界目录能重新物化功法和法术池。
- 获得传承的角色读档后仍掌握同一修订、掌握度和代表法术。
- 读档不会重复增加 `Master()` 引用、重复学习技能或重复写继承日志。
- 遗府耗尽并移除后，传人仍能通过世界目录恢复功法。
- 读档后 `ExpeditionLease` 能重新约束主世界 Actor 本体；Archive 原生物品从 snapshot/record 恢复，Projection、内部位置、物品和目标进度不丢失。
- `PendingOutcome` 能在读档后以原 `CommitId` 继续；已完成的 `CommitId` 不会再次物化 portable item。
- 同一 ItemId 只由 Archive 或已提交的 MainWorld ownership 之一权威持有；返回期间由 `PendingOutcome`、`ItemLease` 和 `CommitId` 保证幂等，所有提交动作只由 `SubWorldOutcomeCommitService` 执行。
- 切换世界后 Site、Doctrine 和 Actor 恢复缓存均为空。

### 构建与游戏验证

- `dotnet build Cultiway.csproj -c Debug` 无错误。
- 在空世界、已有大量角色的世界和读档世界各完成一次投放到继承闭环。
- 观察至少 20 名附近修士，确认发现检查不会逐帧遍历全部遗府。
- 验证小地图、世界标记和 Tooltip 只在玩家已显露时出现。
