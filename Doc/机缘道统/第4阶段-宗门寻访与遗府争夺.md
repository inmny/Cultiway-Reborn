# 第4阶段-宗门寻访与遗府争夺

本阶段让 Sect 把已知机缘转化为正式事务，组织成员集结、远行并投影进入同一遗府 SubWorld 实例。多个宗门可以共同破禁、争夺物品，并按主世界既有敌对关系发生战斗；核心传承的得主仍是具体修士。

本阶段所有实例和远征状态都只存在于当前会话内存。`SubWorldManager` 管理实例、参与者绑定、前后台调度和世界间同步转移；每个实例由常驻 `SubWorldRuntime` 直接持有地图、Projection、物品、制造过程、目标进度与 Winner。切换世界、返回主菜单或 Mod 重载时，这些状态全部清空。

## 具体说明

### 设计边界

- 宗门负责决策、选人、集结和共享探索成果，不直接成为核心功法持有者。
- 核心道统仍选择一个 Actor；获选者回宗后可以通过现有书籍和讲法机制把修订收入藏经阁。
- 每个宗门对同一遗府最多存在一支活动队伍。
- 每名角色同时最多参加一个遗府远征。
- 不建立新的 Sect 战争、仇恨或自动攻击系统。
- 不同宗门进入实例时映射为不同 Faction；来源 Kingdom 已经敌对时为 `Hostile`，其他关系为 `Competitive`。
- `SubWorldManager` 可以在后台调度多个实例，但实例创建后始终保留对应 `SubWorldRuntime`，直到实例结束或当前会话清理。
- Actor 隔离只使用 `RuntimeBinding` 与 occupancy。绑定期间主世界 Actor 停止接收任务和模拟更新，解除绑定后立即恢复。
- `StableItemId`、typed snapshot、`ContentRef<TSnapshot>` 和 `CultibookBlueprint` 都是当前会话内值对象，不承担跨会话身份。
- MainWorld 与 SubWorld 之间的 Actor、物品和气运变化均在同一主线程同步完成，不建立延迟提交或重复执行控制层。

### 步骤 1：建立宗门消息与寻访事务

#### 宗门消息

第三阶段创建 Sect Holder 后，机缘会话状态增加 `SectKnowledgeState`：

```text
SectId
KnowledgeLevel
ReportedByActorId
ReportedAt
Decision
DecisionAt
```

`Decision` 为：

```text
Pending -> Accepted / Rejected / Expired
```

只有宗门当前仍存活、上报者确属该宗门且消息至少达到 `Location` 时，才创建待决策状态。消息、决策和使用次数都随当前会话结束而清空。

#### 寻访事务

注册 `Cultiway.SectAffair.ExploreLegacySite`。事务读取：

- 遗府距离与可达性。
- 道统境界范围与宗门候选人的相性。
- 已知参与者和公开程度。
- `SubWorldRuntime` 当前目标状态、入口容量和内部期限摘要。
- 宗门当前是否已有远征。

接受条件不使用固定“见遗府必去”：

- 至少存在一名能通过最低门槛的候选人。
- 宗门能够组成最小队伍。
- 路程和预计耗时不超过遗府当前状态允许范围。
- 宗门没有更高优先级的生存危机。

事务由现有职位和权限体系决定谁可批准。普通弟子可以上报，但不能自行调动整个宗门。

### 步骤 2：建立探索队伍角色与成员评估

每支队伍由 `LegacySessionState.ActiveSectExpeditions[]` 中的 `SectLegacyExpeditionState` 表达：

```text
ExpeditionId
SiteId
SectId
State
LeaderActorId
MemberStates[]
RallyX
RallyY
StartedAt
RallyDeadline
TravelDeadline
EnteredActorIds[]
ReturnedActorIds[]
```

队伍状态：

```text
Recruiting -> Rallying -> Travelling -> Entering -> Exploring -> Returning -> Completed
                                       ↘ Failed / Cancelled
```

#### 队伍角色

| 角色 | 数量 | 主要评估 | 实际职责 |
| --- | ---: | --- | --- |
| 领队 | 1 | 宗门职位、境界、组织能力 | 发起活动、维持队伍和组织返程 |
| 破禁者 | 1 | 神识、智力、Perception | Projection 从 `ISkillDefinitionRegistry` 取得共享 `CompiledSkillDefinition`，经 execution ports 作用于封禁实体 |
| 护道者 | 1 至 3 | 战斗能力、生命与移动 | 保护途中成员，并在内部对抗危险或敌对 Projection |
| 传承候选 | 1 至 2 | 元素和语义相性、境界范围 | 在内部完成试炼并可能成为 Winner |

同一 Actor 可以兼任领队、破禁者或传承候选，但不会因兼任在 Contribution 中重复计分。队伍总人数上限为 6，避免宗门把全部成员拉离日常工作。

`SectLegacyExpeditionEvaluator` 只从当前 Sect 的存活成员中评分，并排除：

- 已加入其他 CoordinatedActivity 的角色。
- 已被其他 `SubWorldRuntime` 绑定的角色。
- 当前战斗、突破、重伤或不可中断任务中的角色。
- 无法到达集结地点的角色。
- 明确不满足核心最低门槛且又不能担任其他角色者。

### 步骤 3：接入多人集结与远行

每个 Expedition 创建一个 `CoordinatedActivityService` Session：

- `CoordinationGroupKey` 使用现有 `cultiway.sect` Provider。
- Activity Key 由 `SiteId + SectId` 在当前会话内唯一构造。
- 集结点优先宗门大殿；大殿无效时使用领队当前位置。
- 成员完成集结后统一前往遗府入口附近 Rally Tile。
- 每名抵达者分别向 `SubWorldManager.IssueCommand(SubWorldId, AddParticipantsCommand)` 提交参与命令，不把整个队伍压成一个虚拟参与者。
- 同一 Sect 使用相同 `FactionId` 和 `VisionGroupId`，共享已探索迷雾；不同 Sect 不共享视野。

`SubWorldManager` 在主线程处理 `AddParticipantsCommand` 时依次完成：

1. 为 Actor 建立指向目标 `SubWorldRuntime` 的 `RuntimeBinding`。
2. 标记主世界 occupancy，停止该 Actor 的任务、移动和其他活动分配。
3. 在 Runtime 中创建独立 Projection，并关联 SourceActorId、Sect Faction、VisionGroup 与 ExpeditionId。
4. 把允许携带的物品从 MainWorld holder/equipment 关系中移出，并立即加入 Runtime 的物品集合和 Projection 背包。
5. 把队员状态切换为 `Exploring`。

这些操作在一次主线程调用中完成。角色返回时按相反方向直接同步 Projection 状态、物品与位置，然后解除 binding 和 occupancy。

#### 时间限制

- 招募和宗门内集结最长 6 个月。
- 远行期限按实际路径估算，并附加固定缓冲。
- 进入遗府后沿用实例 `LocalTime` 的目标期限，不再由 Coordination Session 计时。
- 到期未集结的成员从队伍移除；低于最小人数时事务失败。

Session 只管理成员选择、集合、主世界移动、抵达入口和返回宗门。参与者位置、战斗、试炼、物品与 WinnerSelection 由常驻 `SubWorldRuntime` 和遗府 RuleSet 管理。

### 步骤 4：实现多宗门统一争夺

同一 Site 可以同时存在多个 Expedition Session，但它们都通过 `SubWorldManager.Get(SubWorldId)` 进入创建入口时已经建立的同一个常驻实例：

1. 每个成员拥有独立 Projection，并携带 Sect Faction、VisionGroup 和 ExpeditionId。
2. 破禁贡献来自 Projection 对封禁实体实际执行的 capability 事件；能力效果和试炼伤害分别通过共享 `ISkillExecutionPorts` 与 `DamageResolver`。
3. `SubWorldRuntime` 直接持有完整 `SubWorldMapData`、EntityStore、Projection、物品、制造过程、交互状态和目标进度。
4. 外围物品由具体 Projection 拾取和携带。每件物品使用当前会话唯一的 `StableItemId`、实例内 `ExpeditionItemId`、typed `ContentRef<TSnapshot>` 与 Holder/Ground 状态。
5. MainWorld 来源物品在进入时同步转入 Runtime；实例原生物品在离开时同步物化到 MainWorld。任一时刻只有一个世界持有该物品。
6. 所有宗门的合格候选进入同一个 `SelectUniqueWinnerObjective`；目标和唯一 Winner 由 Runtime 直接更新。
7. 到达顺序、队伍规模和宗门身份不改变功法相性。

#### 宗门收益

核心选择的是个人，但宗门可以获得后续收益：

- 获选者完成返程后，使用 `BookManagerTools` 为该 Revision 写成功法书。
- 书籍进入 `SectScriptureCollection`，并在当前会话内关联 RevisionId。
- 宗门讲法与师徒传授使用同一修订，不复制新的 Lineage。
- 获选者死亡或叛离不删除已经存在于藏经阁的书。

角色未完成返程前，道统只存在于个人持有状态；不能在远征结束瞬间远程复制到宗门藏经阁。

#### 战斗关系

系统不因为两个 Sect 争夺同一地点而修改 Kingdom 敌对关系。进入时把主世界当前关系映射到小世界规则：

- 同一 Kingdom 或非敌对 Kingdom 的不同宗门为 `Competitive`，可以争抢路线、封禁贡献和物品，但不能互相造成伤害。
- 已处于战争的不同 Kingdom 为 `Hostile`，SubWorld 的 `ISkillWorldQuery/ICombatCommitPort` 与共享 `DamageResolver` 允许双方 Projection 战斗。
- Projection 死亡时，`SubWorldManager` 在主线程立即把死亡结果应用到 Source Actor，再解除其 occupancy 并更新队伍减员。
- 不调用原版 Actor 敌对搜索驱动内部战斗，也不新增仅对遗府生效的伪装战争。

### 步骤 5：管理实例生命周期与退出

多实例运行把逻辑 Tier 与 WorldView 可见性分开，不改变实例所有权：

- Active 实例执行完整固定 tick，Warm 实例只推进明确支持 elapsed 的模块。
- 主相机视野相交的全部 WorldView 同帧渲染；不相交视图只停止 Renderer 和视觉同步。
- 所有 Runtime 始终保留完整地图、实体、物品、制造、目标和参与者状态，不因离开视图而卸载。
- 再次通过底栏或事务命令聚焦实例时直接查看同一个 Runtime，不重建地图或目标。

退出规则：

- 领队死亡时从剩余成员中重新评估领队；没有合格者则远征失败。
- 候选全部死亡不立即取消队伍，实例内其他 Projection 仍可拾取外围物品并撤离。
- 核心已有 Winner 后，尚未进入的队伍结束远征；实例内成员继续撤离。
- 入口被摧毁时禁止新进入，实例内成员使用失效出口紧急返回。
- 正常返回通过 `SubWorldManager.IssueCommand(SubWorldId, RequestExitCommand)` 请求；所属 Runtime 完成当前 tick 后，Manager 在主线程同步角色状态和随身物品，并把 Actor 放回入口附近。

切换世界、返回主菜单或 Mod 重载时调用 `SubWorldManager.Clear()`：停止全部实例调度，取消远征 Session，解除 Actor binding/occupancy，并清空 Runtime、宗门远征和机缘知识状态。未完成的地图、制造、物品、目标和 Winner 不进入下一会话。

### 步骤 6：实现覆灭宗门遗址

注册 `Cultiway.SectLegacyRuin` 入口，并配套 `Cultiway.Legacy.SectRuin` 小世界模板。宗门覆灭时若仍有真实存在的镇宗道统或宝物，就在当前会话创建一个可进入的宗门遗址实例；它不使用原宗门建筑的 `BuildingState.Ruins`。

在 `Sect.triggerOnRemoveObject()` 中、`Treasures.Dispose()` 之前调用 `SectLegacyRuinBuilder.TryCreate()`：

1. 从 `SectScriptureCollection` 中筛选仍有效的功法修订。
2. 根据宗门创始人、历代掌门掌握和藏经阁讲法记录选出一部镇宗道统。
3. 从 `SectTreasureService` 中筛选仍属于宗门，且可由已注册 typed transfer adapter 完整表达的法宝、魔法卷轴和符箓。
4. 以宗门大殿或藏经阁位置为中心选择合法遗址地块。
5. 通过 `SubWorldManager.Create()` 创建包含残破山门、藏经阁、宝库和核心殿的常驻实例。
6. Generator 逐格写入 `SubWorldTile` 的原版 terrain Asset ID，并把完整地图直接交给 Runtime。
7. 以当前会话 `StableItemId` 和对应 typed snapshot，把最多两件真实宗门宝物在主线程直接转入 Runtime 宝库。
8. 从原宗门移除已转移宝物的 holder/equipment/craft 关系，再继续原有 Sect 清理。

没有有效功法和宝物的普通空宗门不生成遗址。未被选入遗址的宗门资产继续按原有解散规则处理，不复制到实例。

`Cultiway.Legacy.SectRuin` 的 Generator 直接逐格写入 `SubWorldTile` 的原版 terrain Asset ID：石室首版把 `soil_low` 写入 Main、把 `wall_ancient` 写入墙格 Top，没有 Top 的格子写空 `TopAssetId`。残破山门、藏经阁、宝库与核心殿通过布局、交互实体和独立 overlay/VFX 区分。

宗门遗址入口的当前会话状态只包含：

- 宗门名称、SectId、创建与覆灭年份。
- 最后一任宗主姓名快照。
- 镇宗道统 RevisionId。
- 对应 `SubWorldId`。
- 原大殿和 GeoRegion 信息。

地图、Projection、物品 typed snapshot、Holder、制造过程、目标和 Winner 只由对应 `SubWorldRuntime` 持有。宗门遗址随当前会话清理，不在下一会话重新出现。

### 步骤 7：补齐宗门表现

#### 宗门事务展示

复用现有 Sect 事务列表，展示：

- 目标遗府名称和消息可信度。
- 当前远征阶段。
- 领队、破禁者和候选人。
- 集结人数与期限。
- 核心是否已经被他人取得。

不新增独立远征管理窗口。玩家点击事务中的地点命令可跳转至主世界入口；实例已经激活时可以调用 `Focus(SubWorldId)` 聚焦周边 WorldView，主世界远征和其他事务继续运行。

#### WorldLog

只记录：

- 某宗门正式派队寻访公开或重大遗府。
- 两个以上宗门进入同一遗府争夺。
- 核心得主及其所属宗门。
- 某宗门覆灭后形成遗址。

普通招募、成员迟到和远征取消留在事务详情，不写公共日志。相关日志只描述当前会话中已经发生的玩法事件。
