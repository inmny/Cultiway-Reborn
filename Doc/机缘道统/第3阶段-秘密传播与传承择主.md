# 第3阶段-秘密传播与传承择主

本阶段把单人预约扩展为局部消息传播和多人 SubWorld 探索。发现者可以保密、求助或上报；多名 Projection 在同一实例内真实移动、破禁、承压、制造和拾取，外围收获可以分散带回，但核心道统只选择一名传人。本阶段依赖机缘道统第 1、2 阶段，以及 SubWorld 第 1 至第 4 阶段：第 2 阶段提供稳定 ItemId、六种 typed snapshot、portable codec、`ItemLease`、`OutcomeDelta`、`PendingOutcome`、`CommitId` 和 `SubWorldOutcomeCommitService`，第 3 阶段提供唯一 `ICraftProcessKindRegistry`、`ICraftDomainService` 与 `CraftProcessSnapshot`，第 4 阶段提供 `CompiledSkillDefinition`、shared capability 与 `DamageResolver`。

## 具体说明

### 设计边界

本阶段处理个人和师徒之间的秘密，不组织宗门队伍。宗门成员可以把消息上报并形成宗门知情记录，但真正的宗门决策、集结与跨宗门竞赛放到第四阶段。

本阶段完成后：

- 遗府不会在一人发现后立刻变成全世界公共目标。
- 第一位抵达者只开启遗府，不自动获得核心。
- 多名角色可以投影进入同一个 `SubWorldId`，在内部取得不同外围收获。
- 核心功法和镇府法宝只提交给一名合格传人。
- Projection、内部位置、物品归属、目标进度和胜者经过保存读档保持一致。
- 外围和核心物品只使用带已注册 codec 的 typed `ContentRef<TSnapshot>`；生成、拾取和制造产物以 Archive 为初始权威，由 `SubWorldItemRecord` 记录且不提前取得 `ItemLease`，实际开始返回提交时才取得 Lease；撤离时把所有权变化冻结进 `OutcomeDelta`，只由 `SubWorldOutcomeCommitService` 提交。
- 内部制造只开放 `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting`，Legacy 不注册 Process Kind 或 handler。

### 步骤 1：建立分层消息记录

将第一阶段的简单 `Discoverers[]` 扩展为 SiteRecord 内的 `LegacyKnowledgeRecord[]`：

```text
HolderKind
HolderId
KnowledgeLevel
SourceKind
SourceId
AcquiredAt
LastSharedAt
```

#### 消息层级

| 层级 | 含义 | AI 能力 |
| --- | --- | --- |
| `Clue` | 只知道某个 GeoRegion 存在异常 | 可以进入区域搜索，不能直接把 Building 设为目标 |
| `Location` | 知道遗府准确位置 | 可以独自前往、求助或上报 |
| `Opened` | 知道遗府正在开启 | 可以直接加入尚未结束的争夺 |
| `Public` | 消息已经公开 | 所有满足基本资格的附近修士都可评估 |

`HolderKind` 首先支持 Actor 与 Sect。Actor、Sect 使用各自稳定世界 ID；`SourceKind` 记录直接感知、师徒告知、宗门上报、队伍目击或开启外泄。

SiteRecord 是遗府入口消息的权威来源。运行时 `LegacyKnowledgeIndex` 建立“角色知道哪些遗府”和“遗府有哪些知情者”两个反向索引；读档后从 SiteRecord 重建，不把同一消息再写一份进 Actor ECS。进入后的参与者、探索和奖励状态不放进该记录。

角色死亡时删除其私有消息记录；已经由其传出的其他记录保持。Sect 失效时删除对应宗门知情记录，但不撤回成员已经亲自得知的消息。

### 步骤 2：实现保密、求助与消息外泄

角色取得 `Location` 后由 `LegacyDisclosurePlanner` 做一次明确决策：

#### 独自保密

满足以下条件时优先独自前往：

- 角色通过遗府最低境界和灵根要求。
- 估算的破禁难度不显著高于自身神识与修为。
- 当前没有必须先完成的集体活动或生存任务。
- 目的地可达。

独自保密不是永久状态。角色连续尝试失败或重伤退出后会重新评估是否求助。

#### 师徒求助

角色无法独立完成时，优先从现有师徒关系中选择一名：

- 仍存活且可达。
- 境界、神识或相性能够补足当前短板。
- 尚未知晓该 Site。

告知后双方获得 `Location`，来源记录指向告知者。师父不会自动取得核心优先权，仍要参加试炼。

#### 宗门上报

角色属于 Sect 且师徒求助不足时，可以创建 Sect `Location` 记录。第三阶段只保存消息并允许宗门内少量高职位成员知道，不创建集结活动。

#### 外泄

消息只在有真实原因时升级，不执行无来源的每月随机广播：

- 求助或上报增加知情者。
- 两名以上角色先后进入同一个活跃实例，消息升为 `Opened`。
- 实例持续活跃超过期限、参与者返回主世界后进入城市或再次求援，会增加一条外泄记录。
- 参与者达到公开阈值后，地点进入 `Public`。
- 玩家“显露天机”只设置 `PlayerRevealed`，不改变上述消息层级。

私密发现不立即写公开 WorldLog。首次进入 `Public` 或出现核心得主时才创建可跳转日志，避免日志本身泄露秘密。

### 步骤 3：建立多人进入与内部参与状态

移除第一阶段的单一 `ReservedActorId`。主世界 Actor 分别到达入口并取得 Lease，`LegacyEntryService` 把他们加入 SiteRecord 指向的同一个 `SubWorldId`。SiteRecord 只保留实例活跃、参与人数和 Winner 的外部摘要。

每名进入者使用小世界平台的 `SubWorldParticipantRecord`，并由遗府 RuleSet 扩展以下稳定数据：

```text
SourceActorId
FactionId
VisionGroupId
JoinedAt
EntryOrder
CompatibilitySnapshot
ContributionEvents[]
TrialFlags
State
```

参与状态为：

```text
Entering -> Exploring -> Qualified -> Returning -> Returned
                    ↘ Withdrawn / Disqualified / Dead
```

`ProjectionId` 只在实例运行时解析，不进入 SiteRecord。保存时记录稳定 Participant ID、当前位置、生命、背包、行为状态和目标事件，读档后由 `SubWorldArchive` 重建 ECS Entity。

#### 探索窗口

- 第一名 Projection 生成后，入口摘要从 `Known` 进入 `Opening`。
- 第二名 Projection 进入后摘要进入 `Contested`，但所有实际状态仍在实例内。
- 核心封禁在首次进入后维持 6 个小世界月；期限由实例 `LocalTime` 推进，并通过封禁裂纹和环境效果显示。
- 最多允许 8 名活跃 Projection；达到容量后，后续角色在主世界入口等待，不创建半参与记录。
- 已进入者可以随时从出口撤离，其他人继续探索。
- 无人留在实例时保留地图、已开启门、已取物品和目标状态，不重置探索成果。

首位进入只记录一次低权重的发现事件，不能通过早到覆盖相性与内部试炼。

### 步骤 4：实现内部外围遗藏与共享制造

外围遗藏由 Template 生成到具体房间，不保存为 `SiteRecord` 奖励表。每一件实体物品都使用平台 `SubWorldItemRecord { ExpeditionItemId, StableItemId, ContentRef, Holder, Ground, State }`；typed snapshot 存在 Archive snapshot store，`StableItemId` 等于共享 `PortableItemIdentity.ItemId`。Archive 原生物品在内部跨 holder 移动时不需要 Lease；只有开始跨世界返回提交时，`ItemLease` 才记录该 ItemId 的转移与幂等状态。SiteRecord 只保留人数、核心和外部摘要。

#### Typed ContentRef 与可携带物

首批消费类型如下：

| 类型 | typed ContentRef | 内部来源与取得 | `SubWorldOutcomeCommitService` 提交结果 |
| --- | --- | --- | --- |
| 材料 | `ContentRef<IngredientSnapshot>` | 发现隐藏容器或地面材料，开启并拾取真实 snapshot | 以同一 `StableItemId` 交给撤离 Actor 或指定接收容器 |
| 丹方 | `ContentRef<ElixirRecipeBlueprint>` | 在书室、残卷或容器中发现已注册丹方 blueprint | 以 recipe snapshot 写入接收者的可用配方来源，不直接生成丹药 |
| 丹药 | `ContentRef<ElixirItemSnapshot>` | 既有丹药遗藏，或通过共享 CraftProcess 制成 | 由 Elixir portable codec Materialize 同一 `StableItemId` 和实例状态 |
| 法宝 | `ContentRef<ArtifactInstanceSnapshot>` | 核心镇府物品、外围遗物或共享炼器产物 | 由 Artifact portable codec Materialize 同一 `StableItemId`，再绑定新所有者 |
| 魔法卷轴 | `ContentRef<MagicScrollSnapshot>` | 书室、残卷、既有真实遗物或 `magic_scroll_crafting` 产物 | 由 MagicScroll codec 提交；按载体资格执行现有学习/施放语义，并保留寿命 |
| 符箓 | `ContentRef<TalismanSnapshot>` | 符室、既有真实遗物或 `talisman_crafting` 产物 | 由 Talisman codec 提交；保留仙道资格、使用者力量换算和一次性施放语义 |

因此，首批六种顶层类型 `IngredientSnapshot`、`ElixirRecipeBlueprint`、`ElixirItemSnapshot`、`ArtifactInstanceSnapshot`、`MagicScrollSnapshot`、`TalismanSnapshot` 都可以按用途成为遗藏或内部制造内容；没有 codec 的具体类型不能进入。动态丹药能以 `ElixirItemSnapshot` 进入，通用 `SpecialItem` 则必须先解析到已注册的具体 typed snapshot；不能用总类绕过 codec，也不能把无 codec 对象强行转成通用奖励。

`MagicScrollSnapshot` 与 `TalismanSnapshot` 只共享嵌套 `StoredSkillPayloadSnapshot { SkillBlueprint, Signature, Strength, PowerLevel }`。Archive 不保存 `SkillContainer` Entity、`CompiledSkillDefinition` 副本或通用技能载体 payload，也不为任一载体臆造 `UseCount`。

容器开启、物品归属和道痕消耗由 SubWorld 命令与事件记录：

1. Projection 走到对象交互范围，发现并开启容器。
2. `InteractCommand` 校验对象仍存在且未被消耗；物品在场景 Commit 时已经取得 `StableItemId`、`ExpeditionItemId` 和 ContentRef，开箱只把 Holder 从隐藏 `ContainerSlot` 改为可见槽位，不重新生成内容。
3. 物品进入 Projection 背包时，Holder 改为 `ProjectionInventory(ParticipantId)`；转交、掉落和死亡分配只移动同一 StableItemId 的 Holder/Ground，不创建副本，也不为 Archive 内部移动取得 Lease。
4. 撤离时 Capture 最终 snapshot，并把 holder 和所有权变化冻结进 `OutcomeDelta`，由 `PendingOutcome` 保存这份 `OutcomeDelta` 与稳定 `CommitId`；开始提交时为实际带出的 Archive 原生物品取得 `ItemLease`。`SubWorldOutcomeCommitService` 先卸载 SubWorld Runtime materialization，再调用对应 codec 在 MainWorld Materialize 同一 ItemId 并绑定目标 holder；持久化 `CommitId` 与 MainWorld ownership 后才删除 Archive 引用并释放 Lease。丹方只提交 recipe 来源，丹药必须是实际存在的 `ElixirItemSnapshot`。
5. `SiteRecord` 永远不写入物品、snapshot、ItemId 或提交状态；未提交或未拾取内容继续留在 `SubWorldArchive`。

同一 Projection 可以携带多个不同物品，但同一 StableItemId 同一时刻只有一个 typed Holder 或 Ground tile。取得外围内容不要求通过核心试炼；未能撤离的携带物仍留在实例中，不会因核心目标完成而远程发放。

返回期间 Archive 与 `PendingOutcome` 保持权威，`ItemLease` 记录跨世界转移，稳定 `CommitId` 保证幂等；MainWorld ownership 提交后才删除 Archive 引用。codec 与所有权服务的调用都由 `SubWorldOutcomeCommitService` 发起。

#### 炉台与 CraftProcess

遗府 Template 可以在外围室、材料室或核心前厅放置炼丹炉、炼器台、符台和魔法卷轴工位。它们只是 SubWorld `Interactable`/station 实体与视觉绑定，`CraftCapabilities[]` 分别保存稳定 Kind ID `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting`，不包含机缘系统自建的配方、资源、品质、材料消耗或产出规则。

参与者在真实探索中发现对应 typed recipe、取得 `IngredientSnapshot`，并把材料带到已发现且支持该 Kind 的工作台后，由 SubWorld craft adapter 调用共享 `ICraftDomainService.Start(CraftStartRequest, CraftContext, IDeterministicRandom)` 创建 `CraftProcessSnapshot`，再用同一服务的 `Advance/Interrupt` 推进或中断：

1. 服务按 `ProcessKindId` 经唯一 registry 解析该 Kind 的 typed recipe/state codec 与 `ICraftProcessKindHandler<TRecipe,TState>`，再验证 recipe、材料类型/数量、参与者资格和工作台能力；未知 ID 直接失败。
2. `CraftContext` 包含参与者的 `CraftResourcePoolSnapshot[] { ResourceId, Current, Maximum }`。魔法卷轴与符箓 handler 分别检查并实际扣除其现有规则要求的资源，领域结果返回明确 `DeductCraftResourceCommand`。
3. 输入材料的 Holder 改为 `Process(ProcessId)`；唯一性由 Archive record 保证，MainWorld 来源输入沿用入场 Lease，Archive 原生输入不为工序内部移动新增 Lease。每个固定 tick 的 `ProcessKindId`、typed state、Progress、RandomState、失败和中断状态写入 Archive 中同一 `CraftProcessSnapshot`。
4. 完成时服务按 Kind 返回 `ElixirItemSnapshot`、`ArtifactInstanceSnapshot`、`TalismanSnapshot` 或 `MagicScrollSnapshot`；adapter 为产物建立新 `StableItemId`/`ExpeditionItemId` 与对应 typed ContentRef，并把 Holder 设为 `WorkbenchOutput(WorkbenchId, Slot)`。产物以 Archive 为初始权威，不创建 MainWorld Entity，也不在返回提交前取得 Lease。
5. Projection 必须实际到场拾取产物并带到出口；撤离时把输入与资源消耗、输出物品写入同一冻结的 `OutcomeDelta`，由 `SubWorldOutcomeCommitService` 提交。

MainWorld 的 `BehCraftElixir`、`BehCraftArtifact`、`BehCraftTalisman`、`BehCraftMagicScroll` adapter 与 SubWorld workbench adapter 调用同一个 registry/domain。两侧只提供不同的工作台、`ITimeSource`、库存、资源池和环境 `CraftContext`；相同 Kind、typed 输入、上下文和 RNG 得到一致领域结果。未完成的 `CraftProcessSnapshot` 随 SubWorldArchive 保存，工作台被破坏或参与者退出时由共享服务返回同一种 `CraftFailure`/中断结果。AIGC 名称和 60% 城市/个人分配只属于 MainWorld adapter，不进入遗府领域结果。

### 步骤 5：实现实体化试炼房间

#### 共享技能、能力与伤害路径

道统、`MagicScrollSnapshot` 和 `TalismanSnapshot` 继续保存 `SkillBlueprint`，但运行时能力只由共享编译链生成：`SkillBlueprint -> SkillBlueprintCompiler -> CompiledSkillDefinition`。`ISkillDefinitionRegistry` 按 ID/签名保存唯一 definition；卷轴学习/施放与符箓施放都解析该 definition，共享 portable item handler 负责两个 carrier 各自的资格和强度换算，`MainWorldSkillAdapter`/`SubWorldSkillAdapter` 再经 `SharedSkillExecutor` 和 `ISkillExecutionPorts` 授予或执行。神识破禁、悟法共鸣、护道攻击和试炼中的主动能力都从该 definition 暴露，不创建 Legacy/SubWorld 专属技能解释器或另一份只供试炼使用的效果描述。

试炼和敌对 Projection 的伤害通过共享 `DamageResolver` 完成。SubWorld port 提供 Projection 的攻击上下文、目标状态、Faction 关系和 RuleSet modifiers；MainWorld port 提供 Actor 的对应上下文。机缘 RuleSet 只能决定门槛、环境参数和允许的 modifier，不复制伤害公式或另建战斗结算器。

#### 相性

进入实例时从主世界角色快照计算一次资格基础：

```text
Compatibility = 0.7 * ElementAffinity + 0.3 * SemanticAffinity
```

- 硬门槛仍是境界处于功法范围且 `ElementRequirement.Check()` 通过。
- `ElementAffinity` 复用 `ElementRootAffinityResolver`。
- `SemanticAffinity` 使用功法 `SemanticDescriptor` 与 `ActorSemanticContributorService` 汇总的角色画像。
- 气运、到达顺序和单纯境界数值不加入相性。

#### 内部房间与对象

| 试炼 | 内部表现 | 实际行为 | 记录事实 |
| --- | --- | --- | --- |
| 灵根叩门 | 入口后的属性门 | Projection 走到门前交互；不合格者无法进入核心路线 | 门检查结果与元素基础分 |
| 神识破禁 | 带完整度和反馈的封禁实体 | 参与者持续施放由共享 `CompiledSkillDefinition` 暴露的破禁 capability，可合作削减封禁 | 有效作用量、耗时和贡献事件 |
| 道痕承压 | 连续危险地块与状态源 | Projection 真实穿越区域，并由共享 `DamageResolver` 结算小世界伤害、减速或退行 | 承受量、通过时间和是否退出 |
| 悟法共鸣 | 核心前的道痕台 | 到场后维持交互，受袭、移动或失去意识会中断 | 完成度与共鸣结果 |

试炼使用实例 `LocalTime`、SubWorld 规则、共享 capability 和 `DamageResolver`。打开、折叠或关闭浮窗不停止当前活跃实例；局部暂停和倍速只作用于该实例，主世界始终保持自己的暂停与速度状态。主世界 Actor 不承担逐帧伤害，内部伤势冻结进 `OutcomeDelta`，由 `SubWorldOutcomeCommitService` 返回结算。

#### 认可分

```text
Recognition = 0.55 * Compatibility
            + 0.30 * TrialResult
            + 0.15 * Contribution
```

`TrialResult` 来自门、封禁、危险区和悟法台的事件；`Contribution` 来自发现房间、有效破禁、协助同伴和实际抵达核心，不接受入口旁等待时间。评分只比较已经到达核心并完成全部硬门槛的 Projection。

### 步骤 6：实现唯一核心目标与返回事务

核心室注册 `SelectUniqueWinnerObjective`，它是实例内唯一能够产生择主结果的写入口：

1. 收集已经到达核心且完成四类内部事实的候选。
2. 在全部候选完成或核心封禁期限结束时冻结候选快照。
3. 计算认可分，从前 8 名中执行带权选择并生成唯一 `WinnerSelectionId`。
4. 给 Winner Projection 写入待冻结的 `OutcomeDelta` 机缘扩展字段，包括功法 `SkillBlueprint`、代表技能引用和掌握度，并解锁 `ContentRef<ArtifactInstanceSnapshot>` 镇府法宝实体；法宝仍须实际拾取。
5. 其他参与者不再参与核心目标，但可以继续取得剩余外围内容并从出口撤离。
6. Winner 到达出口后冻结最终 item snapshot/holder 到 `OutcomeDelta` 并建立 `PendingOutcome`。`SubWorldOutcomeCommitService` 按稳定 `CommitId` 幂等执行：为带出的 Archive 原生物品取得 ItemLease，卸载对应 SubWorld Runtime Entity，按 `ItemId + CommitId` Materialize/绑定尚未提交的存活物品；再提交资源与角色字段，并调用 `LegacyOutcomeAdapter` 应用 `ActorLegacyHoldings`、代表技能、Winner 摘要和世界历史，死亡最后。成功持久化 `CommitId` 与 MainWorld ownership 后删除 Archive item 引用、移除 `PendingOutcome`，再释放 `ItemLease` 与 `ExpeditionLease`。

`LegacyOutcomeAdapter` 不创建物品，不独立提交 `OutcomeDelta`，也不维护幂等记录；它只能由 `SubWorldOutcomeCommitService` 在机缘字段步骤调用。

SiteRecord 不自行选人，也不保存第二份试炼分数或任何物品状态。入口只有收到 Winner 的 `OutcomeDelta` 已提交结果后才进入 `Claimed`；实例内没有参与者和可取得内容后才进入 `Exhausted`。

### 步骤 7：补齐表现、日志与验收

#### Tooltip

已显露遗府 Tooltip 展示：

- 地点名称、来源与完整度。
- 当前消息状态和玩家是否只通过天机看见。
- 实例内部期限和运行状态摘要。
- 参与人数、可见外围剩余数量和核心状态。
- 已知时显示道统名称；未知时不泄露功法内容。
- “查看内部”打开 HUD 小世界浮窗，玩家可以同时观察和操作主世界，但观察不替任何 Projection 揭开迷雾。

#### 世界表现

- `Opening`：入口出现微弱脉动，内部由封禁实体显示状态。
- `Contested`：入口只显示多人进入提示；具体 Projection、房间和试炼在小世界视图中表现，不显示内部评分数字。
- `Claimed`：短暂播放道统认可反馈并淡化地点标记。
- `Exhausted`：转入 Building 废墟状态并停止 AI 查询。

#### 日志

只记录三类公开事件：遗府消息公开、多人正式开启、核心传承择主。个人求助、单次试炼失败和外围领取不写 WorldLog。

## 验收标准

### 消息

- 私密发现不会自动授予其他角色或全世界准确位置。
- 无力独自探索者会沿真实师徒或 Sect 关系求助，不凭空生成知情者。
- 玩家显露遗府后，附近 AI 仍需自行发现或获得消息。
- 开启、求援和多人目击能够逐步扩大知情范围。
- 角色或 Sect 消失后，其私有消息记录会清理，不影响已经传播出的记录。

### 探索与奖励

- 第一位参与者激活实例和 6 个小世界月期限，但必须完成内部路线才能接触核心。
- 最多 8 名 Projection 同时进入，超出者在主世界入口等待。
- 外围物品位于具体房间，各自带 StableItemId、ExpeditionItemId 和 typed ContentRef，只能有一个 Holder/Ground，可以由不同角色带回；Archive 原生物品开始返回前没有 ItemLease，返回时由 `PendingOutcome`、Lease 和 CommitId 保证唯一且只由 `SubWorldOutcomeCommitService` 调用对应 portable codec 提交。
- 不合格角色可以取得合法外围内容，但不能进入核心候选。
- 发现的 Ingredient、ElixirRecipe、Elixir、Artifact、MagicScroll 和 Talisman 只有在具体类型有已注册 portable codec 时才可进入；动态丹药使用 `ElixirItemSnapshot`，通用 SpecialItem 必须解析为已注册 typed snapshot。
- 四种工作台中的 recipe、材料、资源和产物必须依次真实发现或具备、制造、拾取和撤离；`CraftProcessSnapshot` 按 `ProcessKindId` 由共享 `ICraftDomainService.Start/Advance/Interrupt` 推进，Legacy 不维护制造规则。
- `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting` 的同输入、`CraftContext` 和 RNG 结果与 MainWorld adapter 一致；魔法卷轴和符箓制造都有明确资源扣减 command。
- 道统恢复、魔法卷轴学习/施放、符箓施放和神识破禁解析到同一 `CompiledSkillDefinition`；共享 portable item handler 保留 carrier 资格与强度换算，Legacy/SubWorld 内容代码不存在专属技能解释器。
- 道痕承压和 Hostile 战斗通过共享 `DamageResolver` 与 SubWorld combat ports 结算，不维护试炼伤害公式。
- 相性不读取气运、到达顺序或隐藏声望。
- 认可分来自相性和真实发生的门、破禁、危险区、悟法台与探索事件，核心只产生一个 WinnerSelection。
- 主世界入口不会在 Winner 的 `OutcomeDelta` 成功提交前提前显示已传承。

### 存档与游戏验证

- 在消息私密、多人处于不同房间、封禁半开、物品已拾取、核心已选择和 `PendingOutcome` 状态分别保存读档，所有记录保持一致。
- 读档后不会复制已拾取物品、重置已消耗道痕或重新选择第二名 Winner；`PendingOutcome` 中冻结的 `OutcomeDelta`、相关 `ItemLease` 和 `ExpeditionLease` 可按原 `CommitId` 继续。
- 让至少 20 名修士先后获知同一遗府，确认运行时索引和任务数量有界。
- 验证暂停、加速、候选死亡、候选重伤退出和遗府被摧毁。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
