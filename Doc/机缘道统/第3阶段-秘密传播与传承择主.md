## 具体说明

### 设计边界

本阶段处理个人和师徒之间的秘密，不组织宗门队伍。宗门成员可以上报消息并形成宗门知情状态，但真正的宗门决策、集结与跨宗门竞赛放到第四阶段。

本阶段完成后：

- 遗府不会在一人发现后立刻变成全世界公共目标。
- 第一位抵达者只开启遗府，不自动获得核心。
- 多名角色可以通过各自的 `ExpeditionBinding` 进入同一个 `SubWorldId`，在内部取得不同外围收获。
- 核心功法只授予一名合格传人；镇府法宝仍由实际拾取者带回，默认只有 Winner 能解除其封禁。
- Projection、内部位置、物品 Holder、目标进度和胜者直接属于当前 `SubWorldRuntime` 与其 ECS。
- 外围和核心物品只使用带已注册 transfer adapter 的 typed `ContentRef<TSnapshot>`；内部生成、拾取和制造产物直接物化为 Runtime Entity。
- 参与者从出口撤离时，在同一主线程调用中完成物品跨 EntityStore 转移和角色结果应用。
- 内部制造只开放 `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting`，Legacy 不注册 Process Kind 或 handler。

所有消息、参与状态、内部实体和结果只服务于当前游戏会话。切换到另一主世界、返回主菜单或 Mod 重载时全部清除。

### 步骤 1：建立分层消息状态

将第一阶段的简单 `Discoverers[]` 扩展为 `LegacySiteState.Knowledge`：

```text
LegacyKnowledgeState
  HolderKind
  HolderId
  KnowledgeLevel
  SourceKind
  SourceId
  AcquiredAt
  LastSharedAt
```

#### 消息层级

| 层级 | 含义 | AI 能力 |
| --- | --- | --- |
| `Clue` | 只知道某个 GeoRegion 存在异常 | 可以进入区域搜索，不能直接把 Building 设为目标 |
| `Location` | 知道遗府准确位置 | 可以独自前往、求助或上报 |
| `Opened` | 知道遗府正在开启 | 可以直接加入尚未结束的争夺 |
| `Public` | 消息已经公开 | 所有满足基本资格的附近修士都可评估 |

`HolderKind` 首先支持 Actor 与 Sect。`HolderId` 使用当前世界的 Actor/Sect ID；`SourceKind` 记录直接感知、师徒告知、宗门上报、队伍目击或开启外泄。

`LegacySiteState.Knowledge` 是入口消息的权威来源。运行时 `LegacyKnowledgeIndex` 建立“角色知道哪些遗府”和“遗府有哪些知情者”两个反向索引；两者随每次消息变更同步更新，不把消息复制进 Actor ECS。

角色死亡时删除其私有消息；已经由其传出的其他消息保持。Sect 失效时删除对应宗门知情状态，但不撤回成员已经亲自得知的位置。

### 步骤 2：实现保密、求助与消息外泄

角色取得 `Location` 后由 `LegacyDisclosurePlanner` 做一次明确决策。

#### 独自保密

满足以下条件时优先独自前往：

- 角色通过遗府最低境界和灵根要求。
- 估算的破禁难度不显著高于自身神识与修为。
- 当前没有必须先完成的集体活动或生存任务。
- 目的地可达。

独自保密不是永久状态。角色连续尝试失败或重伤退出后会重新评估是否求助。

#### 师徒求助

角色无法独立完成时，优先从现有师徒关系中选择一名：

- 仍存活且可达。
- 境界、神识或相性能够补足当前短板。
- 尚未知晓该 Site。

告知后双方获得 `Location`，来源指向告知者。师父不会自动取得核心优先权，仍要进入 Runtime 并参加试炼。

#### 宗门上报

角色属于 Sect 且师徒求助不足时，可以创建 Sect `Location` 消息。第三阶段只允许宗门内少量高职位成员从该消息得知地点，不创建集结活动。

#### 外泄

消息只在有真实原因时升级，不执行无来源的每月随机广播：

- 求助或上报增加知情者。
- 两名以上角色先后进入同一个活跃 Runtime，消息升为 `Opened`。
- Runtime 持续活跃超过期限、参与者返回主世界后进入城市或再次求援，会增加外泄来源。
- 参与者达到公开阈值后，地点进入 `Public`。
- 玩家“显露天机”只设置 `PlayerRevealed`，不改变上述消息层级。

私密发现不立即写公开 WorldLog。首次进入 `Public` 或出现核心得主时才创建可跳转日志，避免日志本身泄露秘密。

### 步骤 3：建立多人进入与内部参与状态

移除第一阶段的单一 `ReservedActorId`。主世界 Actor 分别到达入口后，`LegacyEntryService` 通过 `SubWorldManager.Get(SubWorldId)` 取得同一 Runtime，并为每名 Actor 建立独立 `ExpeditionBinding` 与 Projection。`LegacySiteState` 只持有参与人数、运行状态和 Winner 对外摘要。

每个 Projection Entity 挂载遗府专用 `LegacyParticipantComponent`：

```text
LegacyParticipantComponent
  SourceActorId
  FactionId
  VisionGroupId
  JoinedAt
  EntryOrder
  CompatibilityValue
  ContributionEvents[]
  TrialFlags
  State
```

参与状态为：

```text
Entering -> Exploring -> Qualified -> Returning -> Returned
                    ↘ Withdrawn / Disqualified / Dead
```

位置、生命、背包 Holder、行为状态和目标事件都是 Projection Entity 的普通运行时组件。Projection 的 ECS ID 只在对应 EntityStore 内使用，不进入入口状态或道统目录。

#### 探索窗口

- 第一名 Projection 生成后，入口摘要从 `Known` 进入 `Opening`。
- 第二名 Projection 进入后摘要进入 `Contested`，但所有实际状态仍在 Runtime 内。
- 核心封禁在首次进入后维持 6 个小世界月；期限由 Runtime `LocalTime` 推进，并通过封禁裂纹和环境效果显示。
- 最多允许 8 名活跃 Projection；达到容量后，后续角色在主世界入口等待，不建立 Binding 或 Projection。
- 已进入者可以随时从出口撤离，其他人继续探索。
- 无人留在内部时，Runtime 继续持有地图、已开启门、剩余物品和目标状态，仅把 tick 降到最低频率。

首位进入只获得一次低权重发现贡献，不能通过早到覆盖相性与内部试炼。

### 步骤 4：实现外围遗藏与共享制造

外围遗藏由 Template 直接生成到 Runtime 的具体房间，不在 `LegacySiteState` 中建立奖励表。每一件实体物品都在 SubWorld EntityStore 中拥有：

```text
PortableItemComponent
  StableItemId
  ContentRef<TSnapshot>

ItemHolderComponent
  ContainerSlot / ProjectionInventory / WorkbenchInput / WorkbenchOutput / Ground
```

typed snapshot 是当前会话内的不可变值，随物品 Entity 一起由 Runtime 持有。Entity 的创建、拾取、转交、掉落、消耗和销毁直接修改 Runtime ECS；`LegacySiteState` 只通过只读查询取得数量摘要。

#### Typed ContentRef 与可携带物

首批消费类型如下：

| 类型 | typed ContentRef | 内部来源与取得 | 撤离后的 MainWorld 结果 |
| --- | --- | --- | --- |
| 材料 | `ContentRef<IngredientSnapshot>` | 发现隐藏容器或地面材料，开启并拾取真实实体 | 以同一 `StableItemId` 交给 Actor 或指定接收容器 |
| 丹方 | `ContentRef<ElixirRecipeBlueprint>` | 在书室、残卷或容器中发现已注册丹方 Blueprint | 以当前会话值加入接收者的可用配方来源，不直接生成丹药 |
| 丹药 | `ContentRef<ElixirItemSnapshot>` | 既有丹药遗藏，或通过共享 CraftProcess 制成 | 由 Elixir transfer adapter 物化同一 `StableItemId` 和实例状态 |
| 法宝 | `ContentRef<ArtifactInstanceSnapshot>` | 核心镇府物品、外围遗物或共享炼器产物 | 由 Artifact transfer adapter 物化同一 `StableItemId`，再绑定新所有者 |
| 魔法卷轴 | `ContentRef<MagicScrollSnapshot>` | 书室、残卷、真实遗物或 `magic_scroll_crafting` 产物 | 由 MagicScroll transfer adapter 物化；保留资格、学习/施放语义与寿命 |
| 符箓 | `ContentRef<TalismanSnapshot>` | 符室、真实遗物或 `talisman_crafting` 产物 | 由 Talisman transfer adapter 物化；保留仙道资格、力量换算和一次性施放语义 |

六种顶层类型 `IngredientSnapshot`、`ElixirRecipeBlueprint`、`ElixirItemSnapshot`、`ArtifactInstanceSnapshot`、`MagicScrollSnapshot`、`TalismanSnapshot` 都可以成为遗藏或内部制造内容；没有 transfer adapter 的具体类型不能进入。动态丹药使用 `ElixirItemSnapshot`，通用 `SpecialItem` 必须先解析到已注册的具体 typed snapshot。

`MagicScrollSnapshot` 与 `TalismanSnapshot` 只共享嵌套 `StoredSkillPayloadSnapshot { SkillBlueprint, Signature, Strength, PowerLevel }`。Runtime 不复制 `SkillContainer` Entity 或 `CompiledSkillDefinition`，也不为任一载体臆造 `UseCount`。

容器开启和物品归属由 SubWorld 命令直接更新 ECS：

1. Projection 走到对象交互范围，发现并开启容器。
2. `InteractCommand` 校验对象仍存在且未被消耗；开箱只把 Holder 从隐藏 `ContainerSlot` 改为可见槽位，不重新生成内容。
3. 物品进入 Projection 背包时，Holder 改为 `ProjectionInventory(ProjectionEntity)`；转交、掉落和死亡分配只移动同一 StableItemId 的 Holder/Ground。
4. Projection 到达出口时，返回协调器捕获背包物品值，逐件移除 SubWorld 源物化并在 MainWorld 创建相同 ItemId 的目标物化。
5. 某件目标创建失败时，立即清理不完整目标并在 Runtime 中重新创建该物品；如果此前已有物品移出，则按逆序移回 Runtime。整个 Actor 返回失败，Binding 与 Projection 保持有效。

同一 Projection 可以携带多个不同物品，但同一 StableItemId 同一时刻只有一个物化和一个 Holder/Ground。取得外围内容不要求通过核心试炼；未能撤离的携带物仍属于 Runtime，不会因核心目标完成而远程发放。

#### 炉台与 CraftProcess

遗府 Template 可以在外围室、材料室或核心前厅放置炼丹炉、炼器台、符台和魔法卷轴工位。它们是 Runtime 中的 `Interactable`/station Entity，`CraftCapabilities[]` 分别声明稳定 Kind ID `alchemy`、`artifact_refining`、`talisman_crafting`、`magic_scroll_crafting`，不包含机缘系统自建的配方、资源、品质、材料消耗或产出规则。

参与者在真实探索中发现对应 typed recipe、取得 `IngredientSnapshot`，并把材料带到已发现且支持该 Kind 的工作台后，由 SubWorld craft adapter 调用共享 `ICraftDomainService.Start(CraftStartRequest, CraftContext, IDeterministicRandom)` 创建当前 Runtime 的 `CraftProcessSnapshot`，再用同一服务的 `Advance/Interrupt` 推进或中断：

1. 服务按 `ProcessKindId` 经唯一 registry 解析 typed recipe/state 与 `ICraftProcessKindHandler<TRecipe,TState>`，再验证 recipe、材料类型/数量、参与者资格和工作台能力；未知 ID 直接失败。
2. `CraftContext` 包含参与者的 `CraftResourcePoolSnapshot[] { ResourceId, Current, Maximum }`。魔法卷轴与符箓 handler 分别检查并实际扣除其现有规则要求的资源，领域结果返回明确 `DeductCraftResourceCommand`。
3. 输入材料的 Holder 改为 `Process(ProcessEntity)`；每个固定 tick 的 Process Kind、typed state、Progress、RandomState、失败和中断状态直接由工序 Entity 持有。
4. 完成时服务按 Kind 返回 `ElixirItemSnapshot`、`ArtifactInstanceSnapshot`、`TalismanSnapshot` 或 `MagicScrollSnapshot`；adapter 为产物分配新 `StableItemId`，创建对应物品 Entity，并把 Holder 设为 `WorkbenchOutput(WorkbenchEntity, Slot)`。
5. Projection 必须实际到场拾取产物并带到出口；输入消耗、资源扣减和输出都已经在 Runtime ECS 中发生，返回流程只移动仍然存在且由 Projection 携带的产物。

MainWorld 的 `BehCraftElixir`、`BehCraftArtifact`、`BehCraftTalisman`、`BehCraftMagicScroll` adapter 与 SubWorld workbench adapter 调用同一个 registry/domain。两侧只提供不同的工作台、`ITimeSource`、库存、资源池和环境 `CraftContext`；相同 Kind、typed 输入、上下文和 RNG 得到一致领域结果。AIGC 名称和 60% 城市/个人分配只属于 MainWorld adapter，不进入遗府领域结果。

### 步骤 5：实现实体化试炼房间

#### 共享技能、能力与伤害路径

道统、`MagicScrollSnapshot` 和 `TalismanSnapshot` 持有 `SkillBlueprint`，但运行时能力只由共享编译链生成：

```text
SkillBlueprint -> SkillBlueprintCompiler -> CompiledSkillDefinition
```

`ISkillDefinitionRegistry` 按 ID/签名持有当前会话内唯一 definition。卷轴学习/施放与符箓施放都解析该 definition，共享 portable item handler 负责两个载体各自的资格和强度换算，`MainWorldSkillAdapter`/`SubWorldSkillAdapter` 再经 `SharedSkillExecutor` 和 `ISkillExecutionPorts` 授予或执行。

神识破禁、悟法共鸣、护道攻击和试炼中的主动能力都从同一 definition 暴露，不创建 Legacy/SubWorld 专属技能解释器或另一份只供试炼使用的效果描述。

试炼和敌对 Projection 的伤害通过共享 `DamageResolver` 完成。SubWorld port 提供 Projection 的攻击上下文、目标状态、Faction 关系和 RuleSet modifiers；MainWorld port 提供 Actor 的对应上下文。机缘 RuleSet 只能决定门槛、环境参数和允许的 modifier，不复制伤害公式或另建战斗结算器。

#### 相性

进入实例时从主世界 Actor 捕获资格基础：

```text
Compatibility = 0.7 * ElementAffinity + 0.3 * SemanticAffinity
```

- 硬门槛仍是境界处于功法范围且 `ElementRequirement.Check()` 通过。
- `ElementAffinity` 复用 `ElementRootAffinityResolver`。
- `SemanticAffinity` 使用功法 `SemanticDescriptor` 与 `ActorSemanticContributorService` 汇总的角色画像。
- 气运、到达顺序和单纯境界数值不加入相性。

#### 内部房间与对象

| 试炼 | 内部表现 | 实际行为 | Runtime 中的事实 |
| --- | --- | --- | --- |
| 灵根叩门 | 入口后的属性门 | Projection 走到门前交互；不合格者无法进入核心路线 | 门组件中的检查结果与元素基础分 |
| 神识破禁 | 带完整度和反馈的封禁 Entity | 参与者持续施放 shared capability，可合作削减封禁 | 封禁生命、有效作用量、耗时和贡献事件 |
| 道痕承压 | 连续危险地块与状态源 | Projection 真实穿越区域，由 `DamageResolver` 结算伤害、减速或退行 | Projection 状态、承受量、通过时间和退出结果 |
| 悟法共鸣 | 核心前的道痕台 | 到场后维持交互，受袭、移动或失去意识会中断 | 交互组件中的完成度与共鸣结果 |

试炼使用 Runtime `LocalTime`、SubWorld 规则、共享 capability 和 `DamageResolver`。相机聚焦、离开遗府或 WorldView 裁剪不停止当前 Active 实例；底栏局部暂停和倍速只作用于当前 FocusedRuntime，主世界始终保持自己的暂停与速度状态。

MainWorld Actor 不承担逐帧内部伤害。Projection 从出口离开时，返回协调器在物品全部转移成功后同步应用最终伤势；Projection 在内部死亡时同步执行 MainWorld Actor 的死亡结果并解除 `ExpeditionBinding`。

#### 认可分

```text
Recognition = 0.55 * Compatibility
            + 0.30 * TrialResult
            + 0.15 * Contribution
```

`TrialResult` 来自门、封禁、危险区和悟法台的运行时事件；`Contribution` 来自发现房间、有效破禁、协助同伴和实际抵达核心，不接受入口旁等待时间。评分只比较已经到达核心并完成全部硬门槛的 Projection。

### 步骤 6：实现唯一核心目标与同步返回

核心室创建唯一 `SelectUniqueWinnerObjective` Entity。它是当前 Runtime 中唯一能够产生择主结果的写入口：

1. 查询已经到达核心且完成四类内部事实的 Projection。
2. 在全部候选完成或核心封禁期限结束时复制候选当前值，结束本次候选收集。
3. 计算认可分，从前 8 名中执行带权选择，并在 Objective 组件中写入唯一 `WinnerSelectionId` 与 Winner Projection。
4. 给 Winner Projection 的结果组件写入 Revision ID、代表技能索引和掌握度，并解除镇府法宝 Entity 的核心封禁；法宝仍须实际拾取。
5. 其他参与者不再进入核心候选，但可以继续取得剩余外围内容并从出口撤离。
6. 任一 Projection 到达出口后，调用 `ExpeditionReturnCoordinator.Return()` 同步移动其物品并应用角色结果。

Winner 的返回顺序为：

1. 捕获 Projection 伤势、资源、背包物品与机缘结果值。
2. 逐件执行“移除 SubWorld 源物化、创建 MainWorld 目标物化并绑定 Holder”。
3. 任一物品失败时在当前调用内回移全部已转物品，Winner 继续留在 Runtime，核心选择不重新执行。
4. 全部物品成功后，`LegacyResultApplier` 调用 `ActorExtend.Master()`、授予代表技能，并更新 `LegacyWorldState.ActorHoldings`。
5. 应用伤势或死亡结果，销毁 Projection，解除 `ExpeditionBinding`。
6. 更新 `LegacySiteState` 的 Winner 与 `Claimed` 摘要，并向当前会话历史和 WorldLog 添加择主事件。

`LegacyResultApplier` 不创建物品，不选择 Winner，也不维护独立返回状态。普通参与者使用相同返回流程，但没有核心功法字段。

`LegacySiteState` 不自行选人，也不持有第二份试炼分数或任何物品状态。Runtime 中没有参与者和可取得内容后，入口进入 `Exhausted`；`SubWorldManager.Destroy()` 释放内部地图与 ECS，地点的最终摘要继续存在于当前 `LegacyWorldState`，直到世界生命周期结束。

### 步骤 7：补齐表现、日志与会话清理

#### Tooltip

已显露遗府 Tooltip 展示：

- 地点名称、来源与完整度。
- 当前消息状态和玩家是否只通过天机看见。
- Runtime 内部期限和运行状态摘要。
- 参与人数、可见外围剩余数量和核心状态。
- 已知时显示道统名称；未知时不泄露功法内容。
- “聚焦内部”把主相机移动到遗府 WorldView；玩家随后可以连续拖回主世界，但观察不替任何 Projection 揭开迷雾。

#### 世界表现

- `Opening`：入口出现微弱脉动，内部由封禁 Entity 显示状态。
- `Contested`：入口只显示多人进入提示；具体 Projection、房间和试炼在小世界视图中表现，不显示内部评分数字。
- `Claimed`：短暂播放道统认可反馈并淡化地点标记。
- `Exhausted`：转入 Building 废墟状态并停止 AI 查询。

#### 日志

只记录三类公开事件：遗府消息公开、多人正式开启、核心传承择主。个人求助、单次试炼失败和外围领取不写 WorldLog。

#### 会话清理

切换到另一主世界、返回主菜单或 Mod 重载时：

1. 清除 `LegacyKnowledgeIndex` 与全部 `LegacySiteState.Knowledge`。
2. 解除所有 `ExpeditionBinding`，丢弃尚未同步带回的 Projection 结果。
3. `SubWorldManager.Clear()` 销毁 Projection、物品、容器、工序、试炼、目标、地图、WorldView 与空间槽位。
4. `LegacyWorldState.Clear()` 清除地点摘要、角色掌握、道统修订和当前会话历史。

清理后，上一主世界中的消息、参与关系、Winner 与物品位置均不再存在。
