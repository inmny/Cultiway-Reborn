# 第2阶段-坐化与战殁遗产

本阶段让当前世界中的真实修士自然留下道统。寿元将尽者生前寻地安排完整遗府，突然战死者只留下未被夺走的遗物与残缺知识；两者都会创建来源不同、布局和规则不同的 SubWorld 归档，而不是只改变入口建筑和奖励表。本阶段建立在机缘道统第 1 阶段之上，要求 SubWorld 第 1 至第 4 阶段已提供原版 terrain catalog、稳定 ItemId/portable item、共享技能与战斗；本阶段直接消费第 2 阶段的 `ArtifactInstanceSnapshot`、`MagicScrollSnapshot`、`TalismanSnapshot` codec、`ItemLease`、`OutcomeDelta`、`CommitId` 和 `SubWorldOutcomeCommitService`。

## 具体说明

### 设计边界

本阶段新增三种自然结果：

| 角色状态 | 死亡情况 | 结果 |
| --- | --- | --- |
| 已完成临终准备 | 任意死亡 | 预定地点激活完整遗府入口与完整内部模板，不再复制核心战场残卷 |
| 未完成准备但寿终 | `AttackType.Age` | 在合法附近地点形成完整度略低、规模较小的临终洞府实例 |
| 未完成准备且突然死亡 | 战斗或其他非寿终死亡 | 在死亡地点附近形成破损、危险且局部坍塌的战殁残迹实例 |

本阶段仍沿用第一阶段的单人进入与内部探索，不加入多人争夺和宗门行动。重点是来源、模板参数、快照和物权正确性。

### 死亡物权提交顺序

当前 `Actor.checkDeath()` 会先进入击杀者 `newKillAction()`，随后才进入 `Actor.die` 与 `ActorExtend.Dispose()`；若继续在 `Actor.die` Prefix 才处理遗物，城市、击杀者或 Dispose 已可能先改变和回收源 Entity。本阶段必须把 portable relic 提取前移到同一主线程死亡物权提交窗口，固定顺序为：

1. 判定死亡类型、遗产资格、宗门借物与击杀者/城市既有分配规则，先确定哪些个人物品进入遗府，哪些继续交给原死亡流程。
2. 在 `ActorExtend.NewKillAction()`、城市接收和 `ActorExtend.Dispose()` 处理这些物品前，对选定遗物调用对应 `IPortableItemCodec.Capture()`，取得 typed snapshot 与稳定 `ItemId`。
3. 创建并持久化 `SubWorldArchive` snapshot、`SubWorldItemRecord` 和唯一 `ItemLease`。
4. 在同一提交边界移除死者 holder、装备与 craft 关系并回收这些源 Entity；提交边界前任一步失败都不移除源，边界完成后只依赖 Archive 与 Lease 恢复。
5. 未选入遗府的物品再按原有击杀者、城市、宗门归还和 Dispose 规则处理；已归档 ItemId 不得再次进入这些接收路径。

`Actor.die` Prefix 仍可冻结人物、功法与死亡来源快照，但不再依赖此时仍存在 portable item Entity。战殁残迹所谓“击杀者已取得的物品不重复生成”，由步骤 1 的唯一分配决定，而不是允许击杀者先转移后再从残余对象猜测。

同一个 Actor 的尸体销毁阶段还会再次调用 `die(pDestroy:true)`。遗产入口必须要求 `actor.isAlive()`，确保只处理首次死亡。

### 步骤 1：建立留道资格与遗产快照规则

#### 资格规则

资格不使用声望或随机抽奖，而由实际成就决定：

| 境界 | 留道规则 |
| --- | --- |
| 元婴 | 只要存在可导出的主修功法即具备资格 |
| 金丹 | 主修功法可导出，并满足功法掌握、代表法术或个人法宝中的任一成就条件 |
| 筑基、炼气 | 必须拥有自创或改良功法修订，或者拥有达到指定品质且能由已注册 portable codec 完整封存的个人法宝 |

`LegacyWorthEvaluator` 读取以下实际内容形成可解释结果：

- 当前仙道境界。
- 主修功法掌握度。
- 功法是否属于角色创建或改良的动态修订。
- 已学且可导出的代表法术数量。
- `CoreFormationSnapshot.quality_score` 与代表法术。
- 完全属于个人且可由 `IPortableItemCodec<ArtifactInstanceSnapshot>` 导出的法宝品质。

Evaluator 返回 `Eligible`、主要理由和建议遗府规模，不返回一个难以解释的总声望值。元婴的境界资格不能绕过“必须存在可传承内容”。

#### 人物快照

遗产中保存 `LegacyFounderSnapshot`：

```text
ActorId
Name
RaceAssetId
KingdomId
CityId
SectId
Realm
CoreFormationName
MainCultibookName
CreatedAt
DiedAt
DeathKind
```

Actor、City、Sect 运行时对象不进入快照。ID 只用于当前世界内尝试解析，姓名与关键描述即使对象消失仍然保留。

#### 道统来源

如果角色主修功法已经属于 `LegacyWorldDocument` 中的某个修订，遗产沿用其 `LineageId` 和 `RevisionId`。普通静态或尚未登记的动态功法则先完整导出，创建新的根道统。

完整洞府引用完整修订；战殁残迹根据原修订创建一个残篇子修订：

- 保留相同 `LineageId`。
- 新建 `RevisionId`，`ParentRevisionId` 指向死亡时的完整修订。
- 只保留部分法术池条目。
- 使用固定 Fragment Composer 按完整度缩减属性和法术领悟率。
- 保存 `Integrity`，供后续补全和谱系展示。

残篇变化必须由明确 composer 完成，不能在死亡处理代码里散落随机删字段。

### 步骤 2：实现临终准备记录与寻地任务

#### 触发窗口

增加低频 `LegacyPreparationSelector`。每月只检查：

- 已具备留道资格。
- 尚无有效 `LegacyPreparationRecord`。
- 当前年龄已经进入最大寿命前 5 年。
- 不在战斗、突破、集体行动或长期不可中断任务中。

寿命判断直接使用原版 `getAge()` 与 `getMaxAge()`，不复制原版寿命公式。

#### 准备记录

准备过程可能跨越存读档，因此保存到 `ActorData.custom_data_string`：

```text
LegacyPreparationRecord
  SchemaVersion
  Stage
  TargetX
  TargetY
  RevisionId
  PreparedAt
  CompletedAt
```

阶段为：

```text
Selecting -> Travelling -> Sealing -> Completed
```

道统修订在开始准备时注册进世界目录；完成封印时再次比较主修功法。如果人物已经改良出新修订，则更新准备记录引用，不保留错误的旧版本。

#### 选址

`LegacySiteLocator` 只选择角色真实可达的合法陆地：

- 不在液体、岩浆或世界边缘。
- 当前没有 Building，且满足遗府建筑 footprint。
- 不在城市建筑密集区。
- 与其他活跃遗府保持最小距离。
- 优先同一陆块、当前地理区域或所属宗门附近的荒野。
- 距离不能近到像城市附属建筑，也不能远到临终角色无法抵达。

选址完成后角色执行 `Cultiway.PrepareLegacyEstate`，使用 tile target 前往并停留一个月完成封印。此时只保存位置与道统计划，不提前创建 Building，也不提前移走物品。这样遗府不会在主人尚未死亡时被探索或摧毁。

### 步骤 3：实现寿终后的完整洞府

死亡物权提交窗口把 `AttackType pType` 传给 `LegacyDeathService.TryCreateLegacy()`；人物与道统快照仍可由 `Actor.die` Prefix 补齐。当 `pType == AttackType.Age` 时：

#### 已完成准备

1. 读取 `LegacyPreparationRecord`。
2. 确认目标地块仍可建造；若环境已变化，在原目标附近重新选择合法地块。
3. 从角色当前个人物品中选择仍然存在、且有稳定 `ItemId` 和已注册 portable codec 的预定遗物，并在任何城市、击杀者或 Dispose 回收前 Capture typed snapshot。
4. 创建 `Cultiway.LegacyEstate`，关联准备好的完整修订。
5. 使用 `Cultiway.Legacy.PreparedEstate` 模板创建 `SubWorldArchive`，把完整度、道统语义和祖师快照作为确定性生成参数；遗物按真实类型以 `ContentRef<ArtifactInstanceSnapshot>`、`ContentRef<MagicScrollSnapshot>` 或 `ContentRef<TalismanSnapshot>` 作为独立内容输入。
6. 由共享 portable item 服务为每件遗物取得 `ItemLease`，持久化同一 `ItemId` 的 snapshot 与 `SubWorldItemRecord`；在同一提交边界移除 MainWorld holder/装备/craft 关系并回收源 Entity。Dormant Archive 不需要物化内部 Entity，`SiteRecord` 不接收物品字段。
7. 入口进入 `Dormant`，实例保持 `Dormant`，默认不对玩家和角色显露。

#### 未完成准备

寿终者只要仍满足留道资格，就在死亡地块附近创建“临终洞府”：

- 使用死亡时完整功法修订。
- 完整度固定低于生前完成封印的洞府。
- 地点优先同一 GeoRegion 的可用荒地。
- 只封存死亡时仍属于个人、且已有稳定 `ItemId` 与已注册 portable codec 的物品；首批遗物可包括法宝、魔法卷轴和符箓。
- 使用 `Cultiway.Legacy.LastMinuteEstate` 模板，房间更少、封禁较弱且外围容器容量较低。

这条规则保证元婴不会因为寻路尚未完成而完全失去道统，但生前完成准备仍具有更高完整度和更好的遗物容量。

已经完成准备的角色即使后来战死，也只激活预定完整遗府；战场可以留下普通材料或尸身，但不再生成第二份核心功法残卷。

### 步骤 4：实现战死后的残破遗地

注册第二个活跃建筑 `Cultiway.LegacyRemnant`。它使用残破石碑、断裂洞口或散落卷轴的画面，但交互期间仍保持 `BuildingState.Normal`。耗尽后才进入自己的 `ruin_0` 终态。

突然死亡满足留道资格且没有已完成准备时：

1. 在击杀者、城市和 `ActorExtend.Dispose()` 回收前完成唯一分配，排除宗门借物与明确交给击杀者的战利品，并选出仍属于死者个人遗产的 portable relic。
2. Capture 人物、修炼知识与选定遗物的 typed snapshot；portable item 不依赖稍后的 `Actor.die` Prefix 仍保留源 Entity。
3. 从完整功法修订生成一个残篇子修订。
4. 在死亡地块或最近合法地块创建 `LegacyRemnant`。
5. 使用 `Cultiway.Legacy.BattleRemnant` 模板创建 SubWorld Archive，写入遗物 snapshot、`SubWorldItemRecord` 与 ItemLease，生成破损入口、坍塌区、暴露残卷和由死亡类型决定的危险区域。
6. 在同一主线程提交边界移除选定遗物的 MainWorld holder/装备/craft 关系并回收源 Entity；未选物品随后继续原死亡分配。
7. SiteRecord 只记录攻击类型、击杀者 ID、残篇完整度和 `SubWorldId`；内部布局、遗物和危险状态由 Archive 保存。

战殁完整度由可解释事实决定：

- 原功法掌握越高，保留的知识越多。
- 死亡攻击越具破坏性，完整度越低。
- 已完成临终准备时不走残篇规则。
- 击杀者夺走多少物品只影响物品列表，不凭空降低知识完整度。

残篇至少保留一项有效修炼内容；无法形成有效功法或代表法术时不创建空遗地。

### 步骤 5：接入共享可携带物快照与唯一物品转移

本阶段不新增机缘专属 item snapshot 或 codec。法宝、魔法卷轴和符箓分别使用 SubWorld 平台提供的 `ArtifactInstanceSnapshot`、`MagicScrollSnapshot`、`TalismanSnapshot`，并通过 `PortableItemCodecRegistry` 中各自已注册的 `IPortableItemCodec<TSnapshot>` Capture/Materialize。三者都是 `IPortableItemSnapshot` 的独立实现并携带同一稳定 `ItemId`；机缘只决定真实遗物被放入哪个 Template 内容槽位。

两个技能载体只共享嵌套 `StoredSkillPayloadSnapshot { SkillBlueprint, Signature, Strength, PowerLevel }`。`MagicScrollSnapshot` 必须保留魔法资格、学习/施放与寿命数据，`TalismanSnapshot` 必须保留仙道资格、使用者力量换算与一次性施放语义；均不保存 `SkillContainer` Entity 或 `CompiledSkillDefinition` 副本。

原 `OwnerHistory` 语义统一收敛为通用 `ItemProvenance`：历任所有者、取得年份、来源地点和跨世界转移事件由 portable item 核心随 snapshot 维护；这份历史不属于机缘目录或任何 Legacy 私有 codec。

#### 可导出条件

遗物选择器调用共享 portable codec 的导出验证：

- 法宝的完整实例状态能够表示为 `ArtifactInstanceSnapshot`，且 snapshot 保留原稳定 `ItemId`；器形、材料、品质、能力、操控参数、外观、器灵稳定成长状态和稳定资源 ID 储藏均由 codec 支持。
- 魔法卷轴能够完整表示为 `MagicScrollSnapshot`，包括嵌套技能 payload、资格和 `AliveTimer/AliveTimeLimit` 寿命数据。
- 符箓能够完整表示为 `TalismanSnapshot`，包括嵌套技能 payload、仙道资格和使用者力量换算所需的稳定数据；一次性施放是载体 handler 语义，不以臆造的使用次数保存。
- 当前装备关系、旧主人认主 Binder、冷却、充能中的短时活动、持续施法会话和未注册的运行时组件不进入 snapshot。
- 存在未注册组件时该物品不能进入遗府；不生成退化的普通法宝副本，也不改写原物品类型。

#### OutcomeDelta 与物品所有权路径

自然遗府封存采用共享物品服务的唯一转移事务：

1. 在死亡处理的物权窗口内解析当前真实所有者，按实际类型调用 `IPortableItemCodec<ArtifactInstanceSnapshot>`、`IPortableItemCodec<MagicScrollSnapshot>` 或 `IPortableItemCodec<TalismanSnapshot>` 的 `Capture()` 导出 typed snapshot，并取得其稳定 `ItemId`。
2. 在移除 holder、装备或工序关系前取得唯一 `ItemLease`，并通过与实际类型一致的 typed `ContentRef<TSnapshot>` 把同一 snapshot、`SubWorldItemRecord { ExpeditionItemId, StableItemId, ContentRef, Holder=ContainerSlot, Ground, State }` 写入 `SubWorldArchive`。
3. Archive snapshot、item record 与 Lease 持久化后，在同一主线程提交边界移除 MainWorld holder/equipment/craft 关系并回收源 Entity。边界前失败不得移除源；边界后 Archive 是唯一权威，恢复不查找死者、击杀者或城市中的旧 Entity。
4. Projection 必须在内部找到并拾取物品；每次拾取、转交或掉落只改变 Archive 内该 `ItemId` 的 holder/ground 状态，不能创建新 ID。
5. Projection 撤离时，把最终 typed snapshot、holder、portable item 所有权变化、角色伤势、技能和死亡结果冻结进 `OutcomeDelta`，并以稳定 `CommitId` 写入 `PendingOutcome`。`SubWorldOutcomeCommitService` 先销毁或卸载对应 SubWorld Runtime materialization，Archive 与 PendingOutcome 继续权威；物品存活时由同一 portable codec 和显式目标 `EntityStore` 的 `ISpecialItemFactory` Materialize 同一 `ItemId` 并绑定接收者，已消耗或销毁时不 Materialize。
6. 全部变化成功后，`SubWorldOutcomeCommitService` 在同一提交边界持久化 `CommitId` 与 MainWorld ownership，随后删除对应 Archive item record/snapshot 引用、移除 `PendingOutcome`，再释放本次完成的 `ItemLease` 与参与者的 `ExpeditionLease`。未拾取的物品继续由 `SubWorldArchive` 持有；提交失败则保留 Archive、Lease 和冻结的 `OutcomeDelta`，并按 `ItemId + CommitId` 识别已物化结果后重试，不依赖源 Entity也不重复创建。

事务完成后，原角色、击杀者、宗门宝库、SubWorld 容器和返回后的新持有者之间只能有一个有效所有者。所有权由 Archive、`ItemLease`、`OutcomeDelta` 和 `CommitId` 共同决定，实际提交只由 `SubWorldOutcomeCommitService` 执行。`SiteRecord` 不保存 snapshot、ItemId、ContentRef 或 Lease，也不参与物品所有权判断；地点 Tooltip 的物品摘要从 SubWorldArchive 只读查询得到。

### 步骤 6：修正死亡物权顺序

本步骤只修正直接影响遗产正确性的现有问题：

#### 城市转移错误

`ActorExtend.OnDeath()` 当前城市分支再次调用 `Base.GetExtend()`，得到死者自身扩展，剩余物品随后被 `Dispose()` 回收。应改为明确调用城市扩展的物品接收入口；遗府服务必须在城市接收之前完成选定个人遗物的 Capture、Lease、Archive commit 和源 Entity 回收，城市入口只接收未选物品。

#### 宗门借用法宝

带 `SectTreasureRelation` 的法宝属于宗门，不属于借用角色：

- `ActorExtend.NewKillAction()` 不得把它转给击杀者。
- 死亡时优先由 `SectTreasureService.ReturnBorrowedOnDeath()` 归还。
- 遗产选择器必须排除此关系。
- 宗门已经解散时，物品归属由后续宗门遗址规则处理，不自动变为个人遗产。

个人遗物也必须在 `ActorExtend.NewKillAction()` 接收前完成唯一分配。选入 Archive 的 ItemId 先完成 Capture/Lease/Archive commit 并回收源 Entity，击杀者只处理未选且按原规则属于战利品的物品。

#### 特殊物品过滤

遗产与击杀转移都继续排除：

- `TagOccupied`
- `TagConsumed`
- `TagUncompleted`
- `TagRecycle`

原版装备、城市资源和普通 `ActorBag` 不进入本系统，继续由原版死亡流程管理。

### 步骤 7：补齐表现、历史与验收

#### 历史记录

生前准备完成时只写入 `LegacyWorldDocument` 内部历史，不发公开 WorldLog，避免玩家从日志直接得知秘密位置。

遗府被发现后，公开日志可以说明：

- 遗府来自哪位已故修士。
- 该修士是寿终、战死还是古修来源。
- 地点是完整洞府还是战殁残迹。

战殁遗地的 Tooltip 在玩家显露后展示击杀者姓名快照，但不保证击杀者仍然存活。

#### 地点命名

完整洞府优先使用祖师姓名、道统语义和 GeoRegion 名称组合，例如“青玄真人遗府”“赤霞剑洞”。战殁残迹使用“某某遗痕”“断法战场”等差异化词干。名称生成只影响展示，不作为 Site ID。

## 验收标准

### 留道与地点

- 有有效主修功法的元婴进入寿命窗口后会主动寻地并完成准备。
- 普通低阶修士不会因为死亡大量生成空遗地。
- 拥有自创功法或高品质个人法宝的低阶修士可以形成小型遗藏。
- 完成准备的角色无论寿终或战死都只激活一座完整遗府入口和一个完整小世界归档。
- 未准备的寿终者形成临终洞府实例，未准备的战死者形成残篇遗地实例，内部布局和危险明显不同。
- 不合法、被占用或环境变化的目标地块不会生成重叠建筑。
- 同一角色首次死亡只生成一次自然遗产，尸体销毁不会重复生成。

### 内容与物权

- 完整遗府保存死亡时完整功法修订。
- 战殁残迹保存同一 Lineage 下的新残篇修订，并能正常修炼。
- 击杀者已经取得的特殊物品不会再次出现在遗地。
- 被封存的个人法宝在城市、击杀者和 Dispose 回收前完成 `ArtifactInstanceSnapshot` Capture、typed `ContentRef`、原稳定 `ItemId`、Archive record 与 ItemLease 提交，随后解除原关系并回收源 Entity；Projection 拾取并返回时，`SubWorldOutcomeCommitService` 按 `OutcomeDelta` 和稳定 `CommitId` 只物化并绑定一次新所有者。
- 被封存的魔法卷轴与符箓在同一死亡物权窗口分别以 `MagicScrollSnapshot`、`TalismanSnapshot`、对应 typed `ContentRef`、原稳定 `ItemId` 和 ItemLease 转入 Archive，源 Entity 随后回收；卷轴寿命及两种载体的资格、强度与使用语义读档后不变。
- 宗门借用法宝不会被击杀者或个人遗府取得。
- 没有已注册 portable codec 或存在未知组件的专属法宝不会进入遗府，也不会退化成普通法宝副本。
- `ItemProvenance` 会随三种具体 snapshot 的 Core 保留所有权历史；Legacy 不创建 OwnerHistory 字段或私有 codec。
- SiteRecord 不保存任何物品 snapshot、ItemId、ContentRef 或 Lease；Archive 才是内部物品状态的唯一来源。
- 提交失败或中途读档时，`PendingOutcome` 保留冻结的 `OutcomeDelta` 与原 `CommitId`，不会提前删除 Archive 引用或释放 Lease；重试按 `ItemId + CommitId` 不重复 Materialize 或绑定物品。
- 原版装备和城市资源的死亡分配行为不受影响。

### 存档与游戏验证

- 在 `Selecting`、`Travelling`、`Completed` 三个临终准备状态保存读档后能继续正确行为。
- 自然遗府和战殁残迹的祖师、死亡类型、功法、内部布局、危险与遗物读档后保持一致。
- 分别验证寿终、被 Actor 击杀、无 Actor 攻击者死亡、准备完成后战死和携带宗门借物死亡。
- `dotnet build Cultiway.csproj -c Debug` 无错误。
