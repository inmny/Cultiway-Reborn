本阶段定义首批可直接接入原版成就窗口的修仙成就。成就只观察注册完成后发生的真实领域事件，不扫描旧世界、不补发历史，也不改变任何玩法结果。完成本阶段后，玩家可以在原版成就窗口中看到独立“修仙”分组，并通过炼气至元婴、丹器生产、越境战斗、宗门建设和师徒传承逐步点亮 18 项账号级成就。

## 具体说明

### 设计边界

本阶段采用以下固定边界：

- 成就总数为 18，其中 14 项明示、4 项隐藏。
- 所有成就均为纯荣誉，`unlocks_something = false`，不绑定任何 `BaseUnlockableAsset`。
- 成就状态属于原版账号进度，不属于当前世界；一旦解锁，切换世界后仍保持完成。
- 只有成就注册完成后发生的领域事件可以解锁。载入世界、打开成就窗口、重载 Mod 和查看角色都不是事件源。
- 不遍历世界补判既有修士、宗门、师徒关系、丹药、法宝或器灵。
- 不新增进度计数器。五名弟子、二十名门人等阈值只在相关成功事件发生时即时检查当前对象。
- 状态合法即可参与判定，包括注册后由神力直接授予并产生正常进阶提交的结果；`ProgressionMode.Synchronize` 不算新事件。
- 化神及以后境界不在本阶段范围内。
- UI 完全复用原版 `AchievementWindow`、`AchievementGroup`、`AchievementButton`、Tooltip 和 `AchievementPopup`。

### 通用判定规则

#### 事件时间边界

`CultivationAchievements` 完成资产注册并绑定全部事件后，设置一次只读的 `Ready` 状态。只有 `Ready == true` 后收到的事件可以进入判定。

以下操作不得调用任何成就检查：

- `MapBox.on_world_loaded`。
- 成就窗口 `OnEnable()` 或 `showList()`。
- Mod `OnReload()`。
- 角色信息页刷新。
- 世界保存与读取。
- 对全体角色、宗门或物品的周期扫描。

内容初始化时如果 `GameProgress.instance` 尚不可用，则该成就内容库初始化失败并记录明确错误；不延迟进入 `Ready`，也不缓存或补处理初始化期间的事件。

#### 形成有效性

真气、仙基、金丹和元婴成果必须满足：

- 组件存在。
- `CoreFormationSnapshot.IsValid == true`。
- `CoreFormationSnapshot.IsFinalized == true`。
- 品阶的 `Stage` 与 `Level` 落在 `ItemLevel` 支持范围内。

“一脉天成”按同一角色在结婴事件后的四份快照检查：

1. `QiRefinementState.formation`。
2. `XianBase.formation`。
3. 结婴后保留为只读归档的 `Jindan.formation`。
4. `Yuanying.formation`。

任意一份缺失、未定型或低于地阶都不解锁。不得用当前元婴品阶代替前三份谱系成果。

#### 多项同时解锁

同一事件按照成就目录顺序检查。账号进度先全部幂等写入，再由展示队列逐个播放弹窗。例如：

- 天阶金丹依次解锁“一粒金丹吞入腹”和“金丹天成”。
- 满足四境高品质的混沌灵根九转结婴，依次检查“九转功成”“紫府婴成”“一脉天成”“混沌初开”。
- 地阶法宝依次解锁“百炼成器”和“天工开物”。

已解锁项立即跳过，不重复排队。

#### 诅咒世界

当 `WorldLawLibrary.world_law_cursed_world.isEnabled()` 为真时，本地解锁网关拒绝本次事件。拒绝项不进入账号进度，也不进入内存队列。关闭法则不会补发，必须等待新的合格事件。

### 步骤 1：注册分组与十八项成就资产

新增 `Source/Content/CultivationAchievements.cs`，作为本功能的唯一资产注册者和稳定目录所有者。它向原版 `AssetManager.achievements` 添加 18 个 `Achievement`，并向 `AssetManager.achievement_groups` 添加一个分组：

```text
Group ID: cultiway_cultivation
Locale key: achievement_group_cultiway_cultivation
Title: 修仙
Color: #78D7B2
```

原版 `AchievementGroupLibrary.linkAssets()` 在 Mod 内容初始化之前已经执行，不能依赖它为后注册资产建立关系。`CultivationAchievements` 必须维护一份显式 `OrderedAchievements` 列表，并按成就目录的 1 至 18 顺序把资产加入 `AchievementGroupAsset.achievements_list`。

每项资产统一设置：

```text
id            = Cultiway.Achievement.<Name>
locale_key    = 与 id 相同
icon          = cultiway/icons/achievements/<stable_name>
group         = cultiway_cultivation
hidden        = 仅四项隐藏成就为 true
unlocks_something = false
```

描述键由原版 `Achievement.getDescriptionID()` 解析为 `<locale_key>_description`。资产 `action` 固定返回 `false`，避免其他代码误调用原版 `Achievement.check()` 时把无条件成就解锁；所有正式判定只接受类型明确的领域事件。

初始化必须验证：

- 分组 ID 尚未存在。
- 18 个成就 ID 均唯一且尚未存在。
- `OrderedAchievements.Count == 18`。
- 隐藏项数量恰为 4。
- 每项分组、图标路径、本地化键和隐藏状态完整。

任一目录错误应让该内容库初始化失败并输出明确日志，不能只注册半组资产。

### 步骤 2：实现本地解锁与弹窗队列

新增内部 `CultivationAchievementUnlockService`，提供唯一入口：

```text
TryUnlock(Achievement achievement)
```

处理顺序固定为：

1. 检查模块已 `Ready`、资产非空且 `GameProgress.instance` 可用。
2. 检查诅咒世界法则。
3. 用 `GameProgress.isAchievementUnlocked(id)` 幂等过滤。
4. 调用 `GameProgress.unlockAchievement(id)` 立即写入账号进度。
5. 将成功写入的资产加入展示队列。
6. 在原版成就弹窗空闲时调用 `AchievementPopup.show(achievement)`，并随该项展示调用一次 `MapBox.aye()` 复用原版解锁反馈。

不得调用：

- `Achievement.check()`。
- `AchievementLibrary.unlock()`。
- `SteamAchievements.TriggerAchievement()`。
- 官方 Analytics 成就事件。

展示队列只协调原版弹窗，不创建新弹窗 prefab。队列缓存并复用场景中的原版 `AchievementPopup`，仅在其根对象未激活时展示下一项；账号持久化不等待动画。世界退出或 Mod 卸载时可以清空尚未展示的提示，但已经写入的完成状态不能回滚。

原版窗口的总数和分组计数直接读取 `AssetManager.achievements` 与 `GameProgress`，无需额外 UI 适配。

### 步骤 3：接入仙道进阶与道果判定

#### 统一成功进阶通知

当前 `ProgressionService` 只在大境界提交后发布 `ProgressionCommittedEvent`，小境界成功会提前返回。为了让第九次金丹淬炼在发生时立即解锁，应把发布点统一移动到成功变换、奖励和属性脏标记都完成之后，使 `ProgressionKind.Minor` 与 `ProgressionKind.Major` 都能发布。

保持以下语义：

- `ProgressionMode.Natural` 与直接授予模式可以发布。
- `ProgressionMode.Synchronize` 不发布，不把读档同步当成新进阶。
- 失败和无进展不发布。
- 小境界事件的 `FromLevel` 与 `ToLevel` 可以相同，具体步骤由 `Kind` 和 `TransitionId` 区分。

同步更新 `ProgressionCommittedEvent` 与 `ProgressionLifecycle` 的注释，使其表示“成功进阶提交”，不再声称只代表主等级。审查现有订阅者：

- `BreakthroughVisualTrigger` 保持显式 `Kind == Major`。
- `KnightBloodline` 增加 `Kind == Major`，避免未来小境界重复建立血脉快照。
- `KnightTechniqueSkills` 增加 `Kind == Major`，保持原有学习时点。
- `CoreFormationSkillBridge` 可以响应全部仙道成功提交，使三、六、九转后的形成效果立即同步。

#### 仙道成就检查

新增一个仙道事件处理器，只读取 `evt.Actor`，不遍历其他角色：

- 筑基提交：检查“一朝筑基”。
- 结丹提交：依次检查“一粒金丹吞入腹”和“金丹天成”。
- 金丹小境界提交：当前转数达到 9 时检查“九转功成”。
- 结婴提交：依次检查“九转功成”“紫府婴成”“一脉天成”“混沌初开”。

通过神力逐级授予境界时，只要服务产生正常的非同步成功提交，就按同一规则判定；直接写组件或载入同步不算。

#### 灵根初醒

“灵根初醒”必须在仙道体系实际接入后检查，不能仅凭角色持有灵根触发。将检查放在：

- 新角色调用 `RecheckAvailableCultisyses` 并成功获得仙道之后。
- 既有角色因灵根变化重新检查准入，并在本次调用中新增仙道体系之后。

如果角色在成就模块进入 `Ready` 前已经拥有灵根和仙道，不做补判。

### 步骤 4：接入丹药与法宝最终定型事件

现有 `ArtifactProductionResultEvent` 在最终品阶写入之前发布，并允许法宝能力修改 `QualityBonus` 与 `YieldMultiplier`。成就不能读取这个中间状态，也不能改变该事件的既有职责。

新增同步、只读的生产完成通知：

```text
ProductionCompletedEvent
  Producer: ActorExtend
  Process: string
  Recipe: object
  Product: Entity
  FinalLevel: ItemLevel
  OutputCount: int
```

由一个轻量 `ProductionLifecycle` 维护完成观察者。通知在主线程同步发布，不进入异步 `EventSystemHub`，避免成品实体在延迟处理前被转移或销毁。

#### 炼丹完成时点

`ElixirAsset.Craft()` 按以下顺序处理：

1. 完成丹药固有效果。
2. 派发原有生产结果上下文和法宝能力上下文。
3. 应用全部质量加成并写入最终 `ItemLevel`。
4. 计算实际产量并将原件、副产物放入接收者库存。
5. 发布一次 `ProductionCompletedEvent`。

无论实际产量是多少，一次炼制只发布一次。处理器先检查“丹火初燃”，再以 `FinalLevel.Stage >= 2` 检查“妙手丹成”。

#### 炼器完成时点

`BehCraftArtifact` 按以下顺序处理：

1. 应用生产结果中的质量加成。
2. 删除材料与未完成标记。
3. 移除 `CraftingArtifact`，写入正式 `Artifact`。
4. 创建副产物并完成原件装备。
5. 发布一次 `ProductionCompletedEvent`。

处理器先检查“百炼成器”，再以 `FinalLevel.Stage >= 2` 检查“天工开物”。配方预览、开工、工序推进、失败回收、直接生成成品和库存转移都不能发布完成事件。

符箓生产可以使用同一完成通知，但首批成就不消费 `TalismanCrafting` 流程。

### 步骤 5：接入战斗、器灵、宗门与师徒事件

#### 逆行伐仙

复用 `ActorExtend.RegisterActionOnKill`。在死者对象仍可读取时检查：

1. 击杀者和死者均有效、不是同一角色。
2. 双方都持有仙道体系。
3. 读取击杀瞬间的 `CurrLevel`。
4. `deadLevel - killerLevel >= 1`。

环境伤害、无归属投射物、召唤物没有解析到真实击杀者、同境界击杀和低境击杀均不计。只比较仙道大境界，不使用综合战力、细分境界、装备或临时属性。

#### 器有真灵

在 `ArtifactSpiritService.Awaken()` 中，仅当状态从未觉醒变为觉醒并准备返回 `true` 时调用成就检查。重复附加器灵能力、载入已有觉醒状态、器灵升级、显化和复苏均不计。

#### 开宗立派与名门大宗

`SectManager.BuildSect()` 在 `Sect.Setup()` 全部完成并得到有效宗门后检查“开宗立派”。失败选址、资格不足和创建中途异常不计。

“名门大宗”只在两个可能让条件从假变真的真实玩法事件中，检查事件关联的单个宗门：

- `Sect.JoinSect()` 成功完成成员加入之后。
- `BehBuildSectTarget` 中 `building.updateBuild(...)` 返回 `true`，确认一座宗门建筑实际完工之后。

不得把检查挂在 `SectManager.updateDirtyBuildings()` 上。`loadFromSave()` 会把所有载入宗门标记为建筑脏数据，随后执行的清单重建不是新建造事件，会导致旧世界被错误补判。

判定要求：

- `GetLivingMembers()` 数量至少 20。
- 各有至少一座 `Buildings.SectHall`、`Buildings.SectScripturePavilion`、`Buildings.SectTreasurePavilion`。
- 三座计入建筑均未损毁且不处于施工状态。

成员加入事件直接使用已经重建的宗门建筑列表。建筑完工事件把本次 `building` 作为候选项，与宗门列表中其他已登记建筑合并检查，不能为了判成就主动执行一次全世界建筑重建。

载入时已有的合格宗门不解锁；它后续发生新成员加入或新的宗门建筑实际完工时，可以基于这次新事件重新判定。

#### 桃李满门与薪火相传

`MasterApprenticeTools.TryRecruit()` 在关系写入、师父状态更新和可选入宗处理全部成功后，检查本次师父当前可解析的在世弟子列表。数量至少 5 时解锁“桃李满门”。仅依赖可能失真的缓存计数不够，最终条件以有效关系和在世角色为准。

`MasterApprenticeTools.TryGraduate()` 在出师资格确认、关系移除和师父计数更新全部成功后，发布一次包含师父与弟子的成功通知并解锁“薪火相传”。失败尝试、师父失效和仅达到资格但尚未执行出师都不计。
