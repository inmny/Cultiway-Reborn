# 第1阶段-组合表达与视觉内核

本文所说的**表现型**，就是“这只生物当前真正长出来并生效的身体”。第 0 阶段已经能按身体规则整理组合；本阶段要让整理结果真正改变生物单位的属性、生物特征、主动能力、受击反应、固定形态和外观。本阶段不决定虫群或妖兽为什么获得某个器官。

## 具体说明

### 步骤 1：身体变化提交

任何玩法都不能直接改写生物单位身上的当前身体数据。共用提交服务是当前身体记录的唯一写入者。

虫群出生或蜕变时，可以直接提交已经确定的完整身体方案。妖兽不同：启灵、炼化、返祖、切换形态和读档恢复，必须先由妖兽身体服务更新或读取 `YaoBody`，再把其中当前活动形态交给共用提交服务。`YaoBody` 始终是妖兽所有永久身体方案的唯一记录，当前生效的身体不能反过来覆盖它。

程序对应：

```text
YaoBody                              // 妖兽永久身体总表，唯一记录
YaoFormPlanService                   // 妖兽身体总表的唯一写入者
CreatureExpressionService            // 当前生效身体的唯一写入者
CreaturePhenotype                    // 当前生效身体
```

每次身体变化按固定顺序完成：

1. 整理新的完整身体方案。
2. 固定形态变化时，切换对应的生物单位模板。
3. 一次性替换当前身体记录，数组使用完整副本。
4. 对照新旧来源，移除已经不存在的属性、能力、持续状态和外观。
5. 刷新属性、生物特征、技能、战斗规划和图形缓存。
6. 发布“身体已经变化”事件。

程序中的固定顺序：

```text
CreaturePhenotypePlan
CreaturePhenotype
CreaturePhenotypeExpressedEvent
Signature    // 组合指纹
Revision     // 身体变更序号
```

普通查询、界面和绘制系统都不能调用提交服务。虫群或妖兽应先在自己的玩法内形成完整候选，再在允许改结构的时机提交。

### 步骤 2：属性与生物特征

#### 属性

共用模块只注册一次属性入口。它检查生物单位是否有当前身体数据，然后读取已经整理好的固定属性列表，按稳定顺序合并。它不能读取虫群母巢或妖兽修炼状态，不能临时创建字典，也不能在属性计算中重新整理身体。

身体变化提交后，只把该生物单位的属性缓存标记为需要刷新。每种器官不能各自注册一份属性回调。

程序对应：

```text
ActorExtend.RegisterCachedStatsBuilder(
  CreaturePhenotypeStatsContributor.Contribute)

CreaturePhenotype
CompiledIndex
BaseStats
MarkCultiwayStatsDirty()
```

#### 生物特征

固定形态和器官提供长期、天生的生物特征，例如水生、龙属、毒性和再生倾向。临时排异、劫伤和消化不算当前身体的长期特征，应由持续状态或妖兽玩法自己提供。

共用特征入口使用固定编号和确定的执行顺序注册。每条特征需要保留可追查来源。现有来源结构只能保存“哪个系统提供”以及一个定义编号，因此把身体方案、固定形态、槽位和器官编号组合成一个稳定字符串，不扩展底层来源结构。

身体变化后只标记特征缓存需要刷新，不主动扫描所有使用者。

程序对应：

```text
CreaturePhenotypeSemanticContributor : IActorSemanticContributor
Id = content.creature_phenotype
Priority = deterministic
Contribute(ActorExtend, SemanticProfileBuilder)
SemanticScope.Intrinsic
SemanticSourceRef
asset_id = BodyPlanId/MorphId/SlotId/OrganId
SemanticContributorService
```

### 步骤 3：主动能力

器官使用项目现有技能系统。每个器官引用的技能容器在内容初始化时只建立一次，并由现有来源技能登记处长期持有。不能为每只生物单位、每次出生或每次能力检查重新创建技能容器。

同一个共用能力入口同时承担两件事：

1. 向战斗和世界行动公开当前可用的主动能力。
2. 向技能详情界面公开这些能力的名称、图标和说明。

它必须分别注册到主动能力服务和来源技能服务，并实现两个不同的收集方法。

程序对应：

```text
SkillContainerBuildMode.SourceGranted
SourceGrantedSkillRegistry

CreaturePhenotypeActiveAbilityProvider
  : IActiveAbilityProvider
  , ISourceGrantedSkillProvider

ActiveAbilityService.Register(provider)
SourceGrantedSkillService.Register(provider)

IActiveAbilityProvider.Collect(
  ActorExtend,
  ICollection<ActiveAbilityHandle>)

ISourceGrantedSkillProvider.Collect(
  ActorExtend,
  ICollection<SourceGrantedSkillPresentation>)
```

每项能力使用稳定来源：

```text
ProviderId = content.creature_phenotype
Source     = ActorExtend.E
EntryId    = SlotId + "/" + OrganId + "/" + AbilityId
```

主动能力入口必须完整回答：

- 这只生物当前有哪些能力，只读现有整理结果，不能顺便改身体。
- 能力属于战斗还是世界行动；首版器官能力主要用于战斗。
- 能力名称、图标、目标方式和施放时能否移动。
- 当前器官、形态、资源、冷却和目标关系是否允许准备。
- 实际距离和目标是否允许本次使用。
- 自动行为此刻使用它的意愿有多高，不能所有能力都给固定高分。
- 它偏向输出、防御、控制还是资源作用，适合什么距离。
- 实际施放距离和效果半径；没有固定范围预览时，效果半径返回 0。
- 最终通过现有技能系统开始技能，不能直接生成投射物或直接结算伤害。

对应接口方法：

```text
Collect
GetChannels
Describe
CanPrepare
CanUse
ResolveAiWeight
ResolveTacticalProfile
ResolveRange
ResolveEffectRadius
TryUse
```

同类能力来自多个器官时，必须在静态定义中选择一种合并规则：

| 合并方式 | 规则 | 程序值 |
| --- | --- | --- |
| 只取最高级 | 只保留最高等级来源 | `HighestRank` |
| 合并强度 | 只显示一个能力，并在上限内合并强度 | `MergePotency` |
| 分别保留 | 只有定义明确允许且没有超过主动能力上限时才分别显示 | `Independent` |

妖兽首版每只最多两个常规战斗主动能力；虫群可以在自己的身体方案中设置更低上限。

### 步骤 4：被动反应

所有组合器官共用一组稳定入口。单个器官不能自己注册全局受伤、击杀或定时回调，否则初始化顺序不同就可能改变结果。

需要处理的事件：

- 常规适应与器官减伤。
- 在护盾和单次伤害上限之后判断致命伤的保命阶段。
- 常规保命失败后的最后手段阶段。
- 实际伤害结算完成、造成伤害、击杀和死亡。
- 技能施放完成。
- 低频生命过程更新。

程序对应：

```text
CreatureOrganEffectDispatcher
PassiveEffects[]

FinalDamageStage.Adaptation
FinalDamageStage.Survival
FinalDamageStage.LastResort

EventKind -> EffectFamilyId -> Rank -> SlotId -> OrganId
```

同类器官效果按“事件、效果类别、等级、槽位、器官编号”的稳定顺序执行。

#### 保命必须当场生效

普通数值减伤可以直接修改本次伤害。会阻止死亡的器官则必须在“保命”或“最后手段”阶段同步完成以下步骤：

1. 再次确认这次伤害确实会致命。
2. 检查器官仍然存在，次数、妖力或其他资源足够。
3. 直接从效果所属玩法的数据中消费一次机会；凤凰涅槃次数和九尾尾命等首版次数保存在 `Yao` 中。
4. 立刻把本次伤害改成非致命或无效。

不能把“阻止这次死亡”本身放进后果队列。否则队列处理时，生物单位可能已经正式死亡。

程序对应：

```text
FinalDamageStage.Survival
FinalDamageStage.LastResort
```

共用层不增加通用生命过程组件。它只负责在正确的伤害阶段分发效果；具体次数由玩法自己的数据保存。妖兽首版直接使用 `Yao` 中的涅槃次数和尾命次数，虫群能力则使用虫群自己的数据。

#### 后果队列

保命机会已经同步预留后，或者其他器官反应需要改变结构时，再把后续动作放进数量受限的队列。以下操作必须延后：

- 增加或删除运行时组件和关系。
- 切换固定形态或替换器官。
- 创建持续状态、召唤物或世界对象。
- 进入涅槃、脱壳、断尾或后续复生过程。
- 在伤害结算完成后才能改变的资源。

队列条目保存生物单位编号、身体变更序号、效果类别、来源槽位、目标编号和已经算好的数值。身体变更序号用来丢弃不再属于当前身体的过期条目。同一生物单位同类未处理后果最多一条；清理世界时直接清空。

程序对应：

```text
CreatureConsequenceQueue
ActorId
Revision
EffectFamilyId
```

#### 跟随器官撤销的持续状态

某些自身状态应在器官消失时一起移除，例如甲壳姿态、蓄能和临时翼化；已经施加给敌人的中毒或燃烧则可以自然到期。需要额外记录该状态由哪个器官和哪次身体变更产生。

程序对应：

```text
CreatureEffectStatusSource
  OwnerActorId
  PhenotypeRevision
  SlotId
  OrganId
  EffectFamilyId
  RemovalPolicy

PersistUntilExpiry       // 来源消失后仍自然到期
RemoveWhenSourceMissing  // 来源消失时立刻移除
StatusRelation           // 现有持续状态关系
```

不能假设现有持续状态关系已经包含器官来源。

### 步骤 5：固定形态切换

固定形态切换沿用现有生物转换服务保留身份、关系、物品和资源比例，但必须先为它增加明确选项，解决旧出生特性累积的问题。

程序对应：

```text
ActorTransformationService

ActorTransformationOptions
  ApplyTargetBirthTraits
  ReconcileOwnedTraits
  RecheckCultisyses
```

必须遵守：

- 固定形态尽量通过当前身体贡献能力，不依赖无法撤销的原版出生特性。
- 共用层必须记录自己授予的形态特性，只移除自己拥有的旧来源。
- 不能只按特性编号粗暴删除，因为同名特性可能来自其他玩法。
- 切换生物单位模板后，重新设置亚种、飞行状态、阴影、主体图形和原版属性缓存。
- 妖兽切换形态时默认不重新检查可获得的修炼体系。化成人形不能因此意外获得仙道或其他体系。
- 转换后保留生物单位编号、家庭、阵营、装备、妖兽或虫群运行时状态、妖丹、血脉、母巢归属和对照试验关系。

程序中的原名：

```text
ActorAsset
Subspecies
Trait
HiveMembership
Trial
```

### 步骤 6：视觉表达

新增共用器官附加图层系统，只处理当前可见且拥有当前身体数据的生物单位。

外观定义：

```text
CreatureVisualRigAsset
  FrameSetId
  AnchorsByBaseFrame[]
  LayerOrder[]

CreatureVisualLayerAsset
  Id
  RigCompatibility[]
  Channel
  FramesByBaseFrame[]
  Anchor
  Offset
  Scale
  TintPolicy
```

实现要求：

- 每个主体动画帧预先对应附加图层帧，绘制时不能临时拼资源路径或搜索资源。
- 附加图层跟随主体当前图片、位置、左右翻转、大小、跳跃高度、可见性和前后顺序。
- 只给当前可见生物单位借用绘制对象；不可见、死亡或离开视野后立刻归还对象池。
- 每只生物单位最多三层可见附加图层。同一通道只显示一个胜出者，按器官等级、优先级和稳定编号选择。
- 九尾、巨翼、龟甲和蛇尾使用合并图片，不能按尾巴或甲片数量创建多个对象。
- 武器腺主要通过攻击准备动作、发射点、弹体和命中特效表现；内部代谢器官默认只在详情界面显示。
- 对照试验、器官来源和候选状态不进入永久世界外观，只能在选中单位或开发模式中显示轻量标记。

程序对应：

```text
CreatureOverlayRenderSystem
ActorBinder
CreaturePhenotype
MonoObjPool
SpriteRenderer
```

详情界面预览和世界绘制可以共用同一份只读外观解析结果，但使用各自的绘制对象。界面不能借用世界绘制对象池。
