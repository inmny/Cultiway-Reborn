# 第7阶段-持久化表现与长时平衡

本阶段不再增加新的核心玩法，而是保证现有妖兽系统可以长期游玩：保存和读取后不会丢失修炼过程；详情界面能解释妖兽为什么变成现在这样；大量虫群与妖兽同时活动时，游戏仍能稳定运行。

## 具体说明

### 步骤 1：正常存档与读取

玩家保存世界后，应当保住一只妖兽真正重要的成长结果：身份与境界、血脉、全部身体与器官来源、吞噬进度、妖丹，以及正在进行的天劫或涅槃。读取后，它仍然是原来那一只妖兽，而不是重新随机生成一只相似单位。

#### 每只动物自己的存档

凡兽只要已经积累启灵机会或带有潜伏血脉，也要保存这些内容。已经启灵的妖兽最多长期保存五类数据。`Yao` 和 `YaoBody` 必有，另外三类只在确实有内容时存在。程序由 `YaoPersistence` 负责；每一只场上单位在程序中称为 `Actor`，当前存档格式版本称为 `Schema`。

凡兽启灵前的资料：

```text
YaoAwakeningPotential                    // 尚未启灵时已经积累的启灵机会
YaoGenome                                // 可能已经携带的潜伏血脉
```

启灵后允许长期保存的数据最多五类：

```text
Yao                                      // 身份、原始物种、启灵时间、境界、妖力、凝丹准备、涅槃累计次数、剩余尾命和通用冷却
YaoBody                                  // 全部形态、当前形态、切换冷却，以及带来源的器官资料
YaoGenome                                // 主血脉、隐性血脉与器官位点
YaoDigestion                             // 已领取精华、消化进度、排异与对应冷却
YaoCore                                  // 妖丹、裂痕、品质和元素路线
```

正在进行的过程按需附加在妖兽单位上：

```text
YaoTribulation                           // 仅渡劫期间存在，结束即移除
Nirvana                                  // 仅涅槃期间存在，结束即移除
```

`YaoTribulation` 和 `Nirvana` 活动时可以随所属妖兽一起保存。它们不是长期妖兽数据。

保存规则：

- 只保存稳定编号、数值、有明确上限的列表和世界模拟时间。实际写入位置为 `ActorData.custom_data_string["cultiway.yao"]`，不能覆盖其他玩法使用的键。
- `YaoBody` 是全部永久身体的唯一存档来源。每个形态的器官列表统一叫 `Organs`，其中每份资料保存位置、器官、等级和来源。生成当前共用身体时，再转换成不带来源的 `CreatureOrganEntry`。
- 当前外观、属性和能力的快速读取结果 `CreaturePhenotype` 不单独保存，读取后从 `YaoBody` 的活动形态重建。
- 编译位置 `CompiledIndex`、静态定义 `Asset`、技能容器 `SkillContainer`、图片 `Sprite`、运行时数据对象 `Entity` 和场上单位引用 `Actor` 都不进入存档。
- 当前行动、寻路、尸体对象、劫云和粒子不保存。已经被妖兽领取的精华保存在 `YaoDigestion` 中；尚未领取的精华读取后消失。
- 领地、栖息地、迁徙和繁殖情况不另存一份妖兽生态数据。需要这些信息时，根据当前位置、当前行动、`YaoBody`、`Yao` 中的资源和原版繁殖资料现算。
- 所有形态方案和基因列表都要保存自己的完整副本，不能让两只妖兽共用同一份可修改列表。出生时临时使用的 `YaoBirthPayload` 不进入存档。

#### 读取顺序

1. 原版准备保存单位时，`Actor.prepareForSave` 的前置补丁把当前妖兽记录写入同一份原版单位数据。
2. 原版读取出场上单位后，`ActorManager.loadObject` 的后置处理先恢复凡兽的启灵积累和潜伏血脉。
3. 对已经启灵的妖兽，恢复必有的 `Yao` 和 `YaoBody`；存档中确实存在血脉、消化或妖丹内容时，再恢复 `YaoGenome`、`YaoDigestion` 或 `YaoCore`。
4. 如果保存时正在渡劫或涅槃，再恢复 `YaoTribulation` 或 `Nirvana`。
5. `YaoFormPlanService` 读取 `YaoBody` 的活动形态，由 `CreatureExpressionService` 重建当前快速读取结果 `CreaturePhenotype`。
6. 全部单位读取完成后，重新统计稀有谱系数量和精华领取记录；领地、栖息和繁殖展示在需要时现算。

#### 临时世界物件不另存

首版不建立第二份妖兽世界存档，也不把运行时世界根对象 `StoreRoot` 当作存档。长期状态尽量归属到具体妖兽，临时画面和临时目标不进入存档。

- 尚未领取的精华 `YaoEssenceDeposit`、劫云、落雷、粒子、寻路和外观绘制租约都是临时世界物件，不另存。
- 正在进行的天劫使用 `YaoTribulation`，正在进行的涅槃使用 `Nirvana`；它们随所属妖兽保存，过程结束后立即移除。突破准备放入 `Yao`，已经领取的精华放入 `YaoDigestion`。读取后只重建尚未发生的表现。
- 稀有谱系数量和出生预算从已恢复妖兽重新统计，不保存临时字典（`Dictionary`）。领地和行动安排直接根据当前世界情况重新产生。

虫群仍然不保存母巢（`Hive`）、进化试验（`Trial`）和生物质（`Biomass`）状态。所有虫群单位资产都设置 `skip_save`，让原版跳过这些单位；母巢核心和附属建筑（`Building`）在原版收集存档内容（`SavedMap`）时也必须过滤。这样读取世界后不会留下失去母巢状态的虫群残件。共享身体的重建能力不能被误当成完整虫群存档。

### 步骤 2：界面与日志

玩家点开一只妖兽时，应当先看懂“它是谁、现在是什么形态、器官从哪里来、正在做什么、付出了什么代价”，而不是先看到程序编号和公式。正式界面只负责查看，不提供安装、替换或升级器官的编辑按钮。

实现前仍须遵守 `Prompts/UI.md`。界面只读取一份不可修改的展示副本，程序中称为 `ReadModel`；它不能直接持有运行时数据对象 `Entity`、可写列表或可修改的静态定义 `Asset`。

#### 妖躯详情页

在现有生物信息窗口 `CreatureInfo` 中增加“妖躯”页：

| 区域 | 玩家看到的内容 |
| --- | --- |
| 总览 | `Yao` 中的身份、境界、妖力、剩余尾命、当前形态和当前行动 |
| 身体 | 身体结构（`BodyPlan`）、固定形态（`Morph`）、承载使用量和稳定度 |
| 器官 | 从 `YaoBody` 当前形态的 `Organs` 读取按身体位置排列的器官、等级、来源、收益、代价和当前是否休眠 |
| 血脉 | 主血脉、隐性血脉、纯度、显性/隐性位点和代数 |
| 吞噬 | 最多三个消化条目、可选结果、进度、排异和压制情况 |
| 妖丹 | 路线、品质、元素、稳定度、裂痕和神通 |
| 天劫/化形 | 活动中的 `YaoTribulation`、化形准备、备用形态和 `YaoBody` 的切换冷却 |
| 生态 | 根据当前位置、当前行动、身体能力、妖力和原版繁殖资料现算的栖息、食性、迁徙与繁殖信息 |

这里的当前行动在程序中称为 `Job`。生态区域不读取单独的长期生态数据，而是在打开界面时根据当前位置、当前行动、`YaoBody`、`Yao` 资源和原版繁殖资料生成。它只用于解释妖兽正在狩猎、休养、渡劫还是繁殖，不要求玩家管理工作队列。

布局要求：

- 复用现有生物信息页和公共滚动列表。程序组件包括 `CreatureInfo`、`UiScrollPane`、分段条、池化列表行 `Row` 和悬停说明 `Tooltip`。
- 器官、血脉和消化列表使用固定高度的行，不在一个信息卡内再嵌套另一张卡。
- 超长器官名、长本地化说明、八个器官槽全部占用、无血脉、无妖丹、渡劫中和形态休眠都要有清楚显示。
- 正式界面不显示随机种子、原始公式、缓存位置和完整决策评分。
- 正式界面没有安装、替换或提升器官的按钮。

#### 悬停说明

器官的悬停说明（程序控件为 `Tooltip`）展示：

- 器官类别、等级、占用位置和适用形态。
- 实际属性、语义、主动神通和受击反应。
- 来源、是否已经固化入血、能否遗传。
- 妖力、稳定度、速度或环境代价。

悬停说明只能绑定到固定图标或字段，不能绑定整条滚动列表行，否则会妨碍玩家滚动。

#### 世界日志

世界日志 `WorldLog` 记录：

- 凡兽启灵。
- 稀有器官炼化、严重排异和固血。
- 凝丹、裂丹、渡劫成功与死亡。
- 血脉返祖、首次蛟化和化形。
- 涅槃、九尾代命等稀有保命事件。
- 稀有血脉出生和谱系断绝。

每条日志都要写清主体、原因和结果。例如：“青涧灵蛇在雷劫中以水息肺卸去劫火，凝成下品水行妖丹。”不能只输出程序资产编号。

### 步骤 3：资源表现

画面只表现已经结算完成的事实。动画和特效可以帮助玩家看懂过程，但不能反过来决定器官、伤害或突破结果。

- 器官等级、固定形态和当前身体，由共享外观解析器根据已确认的身体方案显示。程序对应 `Rank`、`Morph` 和当前 `Form`。
- 消化和排异外观读取 `YaoDigestion`；天劫和涅槃外观分别读取活动中的 `YaoTribulation` 与 `Nirvana`。

必须覆盖的动画：

| 动画 | 对象 | 何时播放 | 程序对照 |
| --- | --- | --- | --- |
| 启灵 | 凡兽 | 启灵已经结算成功 | `YaoAwakenedEvent` |
| 吞噬/消化 | 妖兽 | 正在吞噬或消化 | 当前行动阶段与消化状态 |
| 器官显化 | 妖兽 | 新身体方案已经应用 | `CreaturePhenotype` 已提交 |
| 凝丹/裂丹 | 妖兽 | 妖丹结算完成 | `YaoCore` 结果 |
| 天劫 | 妖兽与劫云 | 妖兽单位挂有 `YaoTribulation` | `YaoTribulation` |
| 返祖 | 妖兽 | 返祖身体已经应用 | 返祖表现型已提交 |
| 化形/返真 | 妖兽 | 身体切换完成 | 当前形态 `Form` 已切换 |
| 涅槃 | 凤凰系 | 妖兽单位挂有 `Nirvana` | `Nirvana` 与结算结果 |
| 尾命代死 | 九尾狐系 | `Yao` 中的剩余尾命已经当场扣除 | 保命后果已提交 |

### 步骤 4：性能预算

目标不是让每只妖兽每一帧都思考全部事情，而是把启灵、消化、领地、繁殖和天劫分批处理。玩家看不到的单位也不应持续创建界面数据或外观绘制对象。

设计负载必须支持：

- 4096 个虫群组合个体。
- **1024 个活动妖兽**，其中最多 128 个达到妖丹境，最多 16 个同时进行长期突破准备。
- 每个身体方案最多 12 个器官槽，屏幕上每只可见单位最多三层器官外观。
- 每只妖兽最多三个消化条目、两个血脉、八个遗传位点和三个完整身体方案（`Form Plan`）。
- 当前世界最多缓存 8192 种不同的已编译身体组合。

单次工作的处理量：

| 操作 | 玩法要求 | 实现对照 |
| --- | --- | --- |
| 重算一次属性 | 只查看这只单位当前的固定槽位 | `O(当前固定槽位数)` |
| 处理一次器官受击反应 | 只查看已经编译的少量被动效果，并有固定上限 | `O(已编译被动效果数)` |
| 列出可用主动神通 | 只查看已经编译的少量主动能力 | `O(已编译主动能力数)` |
| 应用一次新身体 | 只处理槽位和静态贡献，并且只在身体真正变化时执行 | `O(槽位 + 静态贡献)` |
| 处理一个启灵候选 | 读取一份固定大小的经历摘要 | `O(1)`，表示不随世界人口增长 |
| 完成一次消化 | 只比较与样本相符的静态候选，并低频执行 | 有上限的候选集合 |
| 完成一次遗传 | 固定检查八个遗传位点 | `O(8 个位点)` |
| 构建一只妖兽的界面数据 | 只读取它自身有上限的状态 | `O(自身有界状态)` |

初始每帧预算：

| 工作 | 每帧最多处理数量 |
| --- | ---: |
| 启灵候选评估 | 8 |
| 妖兽常规低频更新 | 16 |
| 消化完成结算 | 4 |
| 身体方案应用 | 8 |
| 待处理后果 | 16 |
| 领地/繁殖评估 | 4 |
| 天劫推进 | 2 |
| 外观层处理 | 只处理当前可见的组合单位 |
