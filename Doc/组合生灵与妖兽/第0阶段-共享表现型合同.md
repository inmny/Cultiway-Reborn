# 第0阶段-共享表现型合同

## 具体说明

### 步骤 1：模块与目录

新增 `CreatureCompositionModule : ICanInit`，由现有 `Content.Manager` 扫描和初始化。它只组合定义库、编译器、共享 Contributor 和后续系统，不建立 Feature 注册器或独立消息总线。

建议目录：

```text
Source/Content/CreatureCompositions/
  CreatureCompositionModule.cs
  Components/
  Libraries/
  Models/
  Services/
  ActiveAbilities/
  Combat/
  Persistence/
  Presentation/
  Systems/
  Visuals/
```

本阶段只创建真实使用的 `Components`、`Libraries`、`Models` 和 `Services`。其他目录随对应阶段增加，不预建空类型。

依赖规则：

```text
Insects -> CreatureCompositions -> Core
Yao     -> CreatureCompositions -> Core
CreatureCompositions -X-> Insects / Yao
```

共享层可以引用通用修仙语义资产和 SkillV3 定义，但不能引用 `HiveGenome`、`InsectAdaptationProfile`、`YaoGenome`、`YaoCore` 或领域服务。

### 步骤 2：静态定义

#### 身体方案

```text
CreatureBodyPlanAsset
  Id
  SlotDefinitions[]
  AllowedMorphIds[]
  BaseComplexityCapacity
  MaximumOverlayLayers
  VisualRigId
  Tags[]
```

`CreatureBodySlotDefinition`：

```text
SlotId
AcceptedCategoryMask
Capacity
SymmetryMode
VisualChannel
Required
```

规则：

- 槽位 ID 在一个身体方案内唯一，并按定义顺序形成规范顺序。
- 身体方案最多 12 个槽位，单槽容量为有界小整数。
- `SymmetryMode` 只表达单体、成对或聚合表现，不为左右器官创建无限子槽。
- `VisualChannel` 只决定覆盖层竞争与排序，不参与器官选择。
- 虫群身体方案可定义五槽，妖兽身体方案可定义八槽，共享代码不硬编码两者。

#### 固定形态

```text
CreatureMorphAsset
  Id
  BodyPlanId
  ActorAssetId
  LocomotionKind
  LockedSlots[]
  AddedSlotCapacity[]
  BaseComplexityModifier
  VisualRigId
  Tags[]
```

`CreatureMorphAsset` 负责必须由 `ActorAsset` 承担的事实：飞行、水陆限制、碰撞、基础动画、体型和基础攻击。器官只能解锁或要求一个形态，不能直接在属性回调中篡改这些资产级能力。

#### 器官

```text
CreatureOrganAsset
  Id
  Category
  AllowedBodyPlanTags[]
  AllowedMorphTags[]
  SlotRequirements[]
  PrerequisiteOrganIds[]
  ConflictOrganIds[]
  Ranks[]
  Semantics
  EffectFamilyIds[]
```

`CreatureOrganRankDefinition`：

```text
Rank
ComplexityCost
StatValues[]
SkillContainerIds[]
EffectRanks[]
VisualLayerIds[]
UpkeepDescriptor
```

约束：

- 器官描述“表达什么”，不保存压力响应、Trial、样本需求、妖力消耗、血脉纯度或天劫条件。
- 多槽器官通过 `SlotRequirements` 锁定明确槽位容量，不在安装后动态扩张数组。
- 属性使用静态 ID 与值；复杂机制引用静态 Effect 或来源授予 Skill，不保存 C# 类型名、反射方法和脚本字符串。
- `UpkeepDescriptor` 是可供领域解释的静态代价说明；共享层只统计，不直接扣生物质或妖力。

### 步骤 3：运行时数据

领域向共享层提交不可变计划：

```text
CreaturePhenotypePlan
  Version
  BodyPlanId
  MorphId
  OrganStates[]
  Signature
```

```text
CreatureOrganState
  SlotId
  OrganId
  Rank
```

Actor ECS 上的权威表达快照：

```text
CreaturePhenotype : IComponent
  Version
  BodyPlanId
  MorphId
  OrganStates[]
  Signature
  Revision
  CompiledIndex
```

编译结果：

```text
CompiledCreaturePhenotype
  Signature
  Morph
  OrderedOrgans[]
  Stats[]
  Semantics[]
  ActiveAbilities[]
  PassiveEffects[]
  VisualLayers[]
  ComplexityUsed
```

所有数组必须满足：

- 创建时分配，之后由拥有者独占。
- 从模板、父母、母巢或存档创建时深拷贝。
- Query 和热路径只读，不原地增删。
- 表现型替换时构造新快照并整体提交，旧数组不再被其他对象引用。

`CompiledIndex` 只是当前世界的快速索引，不进入签名和存档；恢复后按签名重新编译并写回。

### 步骤 4：校验与签名

#### 静态链接校验

`CreatureCompositionValidator.LinkAndValidate()` 在内容初始化完成后一次性检查：

1. 身体方案槽位唯一、数量和容量合法。
2. 形态引用存在的身体方案和 `ActorAsset`。
3. 器官类别能被至少一个目标槽位接受。
4. Rank 连续、复杂度非负、属性和语义引用有效。
5. Skill、Effect、视觉层和 Rig 引用存在。
6. 前置和冲突引用存在，且没有自依赖或明确冲突环。
7. 固定形态的锁槽和增量容量指向存在的槽位。
8. 覆盖层数量和通道不超过身体方案硬上限。

定义错误直接中止该模块初始化并输出完整资产路径，不能在战斗时静默忽略。

#### 计划校验

`ValidatePlan()` 检查：

- BodyPlan、Morph 和每个 Organ/Rank 存在。
- Morph 属于 BodyPlan。
- 每个安装项占用合法槽位，且没有重复主槽。
- 多槽容量、锁槽、前置、冲突和形态兼容全部满足。
- 总复杂度不超过计划允许的结构容量。
- 同一 Effect Family 的多来源能按声明的合并规则归并。

领域层可以在调用共享校验前施加更严格预算，例如母巢生物质、妖兽境界、血脉纯度和身体稳定度。

#### 稳定签名

规范顺序：

```text
Version
BodyPlanId
MorphId
for slot in BodyPlan.SlotDefinitions:
  SlotId
  OrganId or empty
  Rank
```

签名使用稳定序列的哈希，不依赖 Dictionary 遍历、当前语言或运行时对象哈希。

明确排除：Actor ID、名字、时间、领域来源、母巢、基因世代、Trial、妖力、妖丹、冷却、Status 和视觉对象 ID。

调用方提供的 Signature 只用于校验；编译器始终重算并在不一致时拒绝计划，不能信任外部签名。

### 步骤 5：编译与所有权

`CreaturePhenotypeCompiler` 只执行纯读取：

1. 校验计划。
2. 按身体方案槽位顺序解析器官与 Rank。
3. 合并属性和语义。
4. 按 Effect Family 的静态策略归并能力和被动效果。
5. 选择每个视觉通道的胜出层。
6. 生成 `CompiledCreaturePhenotype` 和世界期 `CompiledIndex`。

缓存规则：

- 以完整 Signature 为键，不以 Actor 或领域为键。
- 只保存静态 Asset 引用和不可变紧凑数组，不保存 Actor、Building、Entity 或领域对象。
- 只允许在出生、蜕变、器官替换、返祖、形态切换和加载恢复时编译。
- 伤害、AI 枚举和渲染热路径只允许 `TryResolveCompiled`，未命中时记录不变量错误，不能现场编译。
- 当前世界最多 8192 个独特已编译表现型；超过上限视为内容或演化失控并拒绝新组合。
- 世界清理时清空动态组合缓存；静态资产库保留。

共享层不修改调用方模板。虫群的 `HiveGenome`、`BroodPhenotypePlan` 和妖兽的 `YaoGenome` 必须自行拥有深拷贝；共享编译器只返回新结果。

### 步骤 6：生命周期

初始化顺序：

```text
RegisterDefinitions
LinkAndValidate
RegisterSharedContributors
CreateCompilerCache
RegisterWorldClear
```

世界清理：

- Actor 上的 `CreaturePhenotype` 随长期 ECS Store sweep 删除。
- 编译缓存、待表达请求、诊断索引和后续视觉租约同步清空。
- 静态 BodyPlan、Morph、Organ、Effect 与来源授予 Skill 定义保留。
- 清理后 `CompiledPhenotypeCount`、`PendingExpressionCount` 和世界期索引必须为零。

本阶段不新增通用世界代次，也不把清理延迟到新世界首个 Tick。

### 步骤 7：验收

建立两个仅用于验证的定义夹具：

- 虫群五槽 BodyPlan：甲壳、运动、武器腺、代谢、神经。
- 妖兽八槽 BodyPlan：表被、运动、天生武器、吐息腺、感知、代谢、异质附肢、灵窍。

必须验证：

1. 两个领域能提交同一个共享 `CreaturePhenotypePlan` 类型。
2. 相同实际组合在不同 Actor、母巢、Trial 和来源下得到相同签名。
3. 槽位顺序不同但内容相同的输入被规范化为同一签名。
4. 重复槽、多槽超载、前置缺失、冲突和错误形态被明确拒绝。
5. 任一快照深拷贝后修改原数组不会改变副本。
6. 热路径未命中编译缓存时失败并诊断，不隐式构建。
7. 连续三次创建和清理世界后动态缓存与请求归零，静态定义仍有效。
