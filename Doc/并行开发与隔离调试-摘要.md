# 并行开发与隔离调试

分析日期：2026-11-17。状态：第一版技能与环境脚本已实现，正在进行实机验收。

## 后续讨论已确认的方向

采用一个随仓库分发的 skill 管理完整开发流程：创建或接入 worktree、准备环境、开发验证、提交 PR 和收尾。环境构造及清理交给可重复执行的脚本。

用户已确认默认回收时机：PR 交付后回收游戏副本，保留分支、worktree 和验证证据；PR 合并后再回收 worktree。具体职责与异常中断处理见 [技能与一键环境流程](并行开发与隔离调试/技能与一键环境流程.md)。实际使用见 [develop 技能](../.agents/skills/develop/SKILL.md)。下文保留最初的分析依据，实施结果单独记录。

## 结论

建议采用「一个开发任务一个 worktree 和功能分支，按需配一个独占的游戏环境，通过 PR 合并」的方式。worktree 负责分开代码；游戏副本、用户配置、调试连接和验证记录仍须另外分开。

当前真正的问题比端口冲突更广：DebugToolbox 已经由系统分配端口，但默认会话文件只有一份；加载器也把不同分支的 Cultiway 编译到同名缓存文件。只分开 Player.log 或者给每个任务安排固定端口，都不足以解决问题。

多人在各自电脑开发时，不会直接争用本机端口和日志；他们需要的是相同的环境准备入口、明确的依赖版本和可追溯的 PR 验证记录。同机多个开发任务则需要完整的运行隔离。

## 已确认的主要缺口

| 范围 | 当前情况 | 改革后的要求 |
|---|---|---|
| 代码 | 当前只有主工作目录，已有未提交修改 | 每个任务使用自己的分支和 worktree；现有修改另行归属 |
| DebugToolbox | 动态端口，但共用临时目录下的 `DebugToolbox/session.json`；退出还会删该文件 | 每次启动有独立会话，客户端明确选择，不自动寻找另一游戏 |
| 加载器 | 按模组编号写 `CompiledMods/CULTIWAY.dll`、编译记录和启用记录 | 每个运行环境有自己的加载器可写目录 |
| 日志 | Unity、原版资源加载、BepInEx、Cultiway 各有写入位置 | 游戏目录、当前工作目录和日志位置一起隔离 |
| 存档和设置 | 原版世界、自动存档、模组全局资料共用用户数据目录 | 每个环境独立配置；重启验证继续使用该环境的同一份资料 |
| 构建和脚本 | 默认从模组目录向上找游戏，向旁边找 DebugToolbox | 游戏和工具路径来自本机配置，适应任意 worktree 位置 |
| 验证记录 | 部分脚本已记版本，但运行中仍链接开发目录，且版本范围不完整 | 绑定实际运行的代码快照、环境版本和场景输入 |
| 画面和性能 | 鼠标、键盘、前台窗口、显卡仍然共享 | 操作画面和测性能单独占用；普通逻辑验证可按容量并行 |

## 推荐结构

```text
共享的本机依赖：指定版本的游戏、加载器和调试工具
    ├── 任务甲 worktree → 甲的游戏环境 → 甲的连接、存档和验证记录 → PR 甲
    └── 任务乙 worktree → 乙的游戏环境 → 乙的连接、存档和验证记录 → PR 乙
```

共享部分只作为准备环境的来源。游戏和模组会写入的文件属于各自环境。首版优先采用普通复制或写时复制；后者节省空间，修改时仍保留独立内容。不要把整个模组目录直接链接到开发目录，也不要把整个加载器目录做硬链接。

每个环境允许一个游戏进程和一个负责修改世界的任务。多个脚本即使都在游戏主线程执行，跨帧等待时仍可能交错，不能共同控制同一世界。

## 现有基础可以复用

`Scripts/SpellDemos/baseline_scenarios.py` 已经同时设置独立配置目录和临时目录，并核对进程号及实际存档位置；`benchmark_baselines.py` 已经准备私有加载器目录。它们应成为新入口的基础。

还需要解决四件事：移除安装位置假设、避免整个模组目录链接、加入同环境的启动与控制占用规则，以及让脚本的输入输出位置跟随明确选择的环境。

## 分阶段交付

1. **任意 worktree 可构建**：整理本机路径配置、依赖准备和环境检查，不启动游戏也能完成开发检查。
2. **两个任务可独立调试**：准备游戏快照，隔离配置、临时目录和日志；启动、连接、退出只作用于所属实例。先复用现有 DebugToolbox，通过环境变量隔离。
3. **调试连接与验证记录明确化**：在 DebugToolbox 独立仓库加入显式会话选择和身份核对；Cultiway 迁移共用脚本入口，先接正常流程和保存重启流程。
4. **接入 PR 日常开发**：添加评审模板与适当的自动检查；运行证据对应提交，合并后关闭环境并保留所需结果。

各阶段都能单独交付。不需要先搭建服务器、容器平台或集中调度系统；本地目录、少量配置和一个共用入口足以验证这套方式。
