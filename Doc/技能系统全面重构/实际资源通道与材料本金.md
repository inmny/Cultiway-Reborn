# 实际资源通道与材料本金

## 这批完成什么

推进4.01、10.13和12.04的支付基础。新构造不再只认识五个写死的余额字段，可以通过`AbilityDefinition.Resource`引用已经登记的实际资源编号。余额、是否可用、报价、扣费、容量和整数规则由资源所属玩法维护；学习同一构造不会额外生成人物体系。

这不是全部旧容器迁移。旧学习、词条、轨迹、法杖条件以及任选或同时支付多个资源的来源仍使用原有合同；本批让它们与新构造共用资源登记，没有把这些来源改成固定费用或真元。新构造目前仍是每次选择一个资源通道，多资源构造及各来源资料转换继续待办。

## 保存的需求与本次实际费用

`Cost`记录能力需要多少，不是永久缓存的一次报价。正式可用检查及本次启动向实际资源重新报价；已经开始的生成材料只持有本次费用形成的本金，之后目录或报价变化不能补写过去的支付。

例如自定义资源把需求3报价为6，实际支付6，按75%收束最多返还4.5。以后同一通道改为三倍报价，新施放支付9、形成9的本金；原有材料仍只有6，存读档不重新报价旧材料。

旧容器在调用资源报价之前仍按自身词条、范围和当前人物计算需求；构造已有自己的实际形状和需求，不重复套一遍旧容器范围。

## 精度、扣费与回收

资源余额和写入参数以双精度传递，保留原版整数的完整范围；原有真元、斗气和妖力仍按所属组件的单精度实际存储。报价不再要求旧技能实体：旧来源在外部先完成实际需求计算，新构造直接传自己的需求。

扣费与校准余额分开。支付调用专用扣费入口，真元与妖力沿用已有资源变化通知；支付不能顺带把已有超容量余额夹到上限。原版法力和体力使用整数运算，不能把大额余额先转成单精度再扣掉一个小费用。

生成材料以本次可表示的实际扣费为本金。单精度存量太大、费用实际没有扣下时，本金为零；后来降低余额也不能凭空获得退款。回收只进入原支付者的原资源，按当前实际容量入账；整数资源对累计结果取整，小数资源继续沿用向下取可表示值的份额规则。

后续补入[启动支付与真实本金](启动支付与真实本金.md)：先冻结报价并实际扣费，再以扣费前后的真实差额建立执行；启动未受理时撤销本次支付，正式开始之后按原结束规则处理。旧容器的单项、任选及全部支付使用同一入口，共用余额的别名合计费用。

世界材料保留原通道编号与本金，恢复不重新收费或更换资源。收束、共同回收、保存边界和日常需求都读取同一通道的容量及整数规则，不再各自维护一份资源名称清单。

## 接入新资源

复用`SkillCastResourceAsset.Configure`登记真实可用性、余额读取、余额写入和需求报价。必要时用`ConfigureSpending`提供专用扣费，用`ConfigureRecovery`登记实际容量和整数规则；然后在构造中填写通道稳定编号。无需增加玩家设置、构造专属余额或新的施法时钟。

若普通余额写入会按回能容量截断，需要用`ConfigureRestoring`提供启动撤销入口，完整恢复扣费前存量；真实余额别名使用`ShareBalanceWith`声明所属存量。两者均由资源所属玩法登记。

## 验证入口

- `Scripts/SpellDemos/verify_construction_resources.script`：正式施放、五类真实资源、自定义当前报价、实际收束、旧多资源支付以及材料保存。
- `Scripts/SpellDemos/verify_construction_resources_restart.script`：真正重启后恢复旧本金，验证报价变化只影响新施放，再次保存不重复材料。
- 原有`verify_recovery_resources.script`：大额整数、单精度未扣费、容量及目录改写边界。
- 原有`verify_world_use.script`：真实日常回收、净收益选择与永久材料保护。

新资源测试先完成原版新生初始化，再设置受控余额；隔离自然法力与体力恢复时暂时关闭两项原版增量，并在结束时恢复，避免把自然补满误认成收束结果。所有支付和收束均经过正式入口，退款以实际确认记录核对。

## 实测结果

首次运行24项、真正重启15项、原支付和回收边界36项、原日常自主回收37项，共112项通过。进程3444272保存、3448385恢复；旧材料真实本金6、实际返还4.5，新施放真实支付9，再次保存读取不叠加或改写本金，没有局部丢弃及备份错误。世界推进时钟按当前世界重建，核对保存内容时不把这个临时时钟冒充永久身份。

原边界检查覆盖大额整数精确扣费、差一点不足时拒绝、单精度未扣费不退款、满容量不入账以及运行中替换目录。旧的一项检查曾用人物总余额推测是否补发退款；实测总余额因自然恢复变为11.04102，现改为直接检查实际收束记录，避免把其他玩法恢复算作退款。
