## 具体说明

### 建立可嵌套构造与规则补全

定义形体与结构、材料与物态、运动与分布、变化过程、关联、作用与条件六类资料。部件可以包含其他构造，操作可作用于整体、命名部位、部件集合和过程；输出能继续作为其他操作的输入，保留来源、位置、速度和实际结果。

构形、分布、附着、聚合、生长、解体、流散、映照和转化等操作明确输入要求、输出结构、可修改状态、作用区与显示资料。具体原理由操作和对应玩法实现，不能只在资料中出现一个名称。

展开时依据部位、材料、连接和过程需求补齐必要步骤，明确默认值、玩家覆盖、冲突处理及缺失说明。词条修改构造和规则，不逐招复制变化代码；运行中的条件读取真实状态与结果，触发后续变化。

先用少量共用形体和操作生成原始用例及两种结构或行为不同的变体。至少一种变体在共用能力冻结后提出，并只改构造资料完成；若必须新增对应的整招类或按技能编号分支，则回到操作划分调整。

### 拆开作用投送与动作

基础招式声明作用、目标、投送方式、默认运动、动作、表现及可扩展部位。原有技能编号不再决定“永远只能近身或贴地”。

非战斗能力允许以物件、过程、地域、连接或世界条件为对象，不强制具有碰撞体或命中目标。一次动作可以启动长期工程、建立设施或改变规则，动作结束与结果结束分别定义。通用结构需满足第0阶段的跨尺度合同。

玩家改造、法宝材料或其他来源产生的变化，先形成明确构造，展开及补全后再编译成供执行使用的紧凑数据。执行还包括实际对象的生长、转化、关联和过程变化，不能只保留产生执行体、移动、命中和结束。不先实现通用可视化编程语言；这套构造资料面向模组能力，玩家沿用现有改造方式。

同一能力可以有多个执行体和持续区域，但仍是一次招式。多个已学技能的独立释放沿用自主施法目标，不建立跨技能固定配方。

### 编译跨形态和词条

以原地掌击改追踪飞掌作为必过的改造路径：

1. 保留伤害、击退等作用，投送方式变为离手飞行。
2. 选择追踪目标，生成飞掌主体、运动和对应作用形状。
3. 身体播放发掌动作，到释放时点产生飞掌；飞掌独立追踪和接触。
4. 巨大同步改变形体、作用形状和所需挂点偏移；齐射产生多个真实执行体；急速同步调整相关动作标记及运动参数。
5. 真实成本、冷却、持续、数量、重复命中和结束规则一次性确定。

不能只更换轨迹组件，留下原有近身判定和手部外观。跨形态应由可复用的改造规则完成，避免每帧按技能编号判断。

校验检查目标、执行体、作用区、动作和表现是否齐备。缺失时说明缺少哪项能力，不因旧类别不同直接拒绝。自由改造不等于宣称所有逻辑冲突都能自动生成合理画面；需要的资源和转换规则必须实际提供。

除掌击转飞掌外，至少再验证水浪改为环绕浪体、固定领域改为随执行体移动。作用保持还是改变必须明确：环绕浪体不会因改了轨迹就凭空获得护盾能力。轨迹、投送和作用的改造可联动，但不能悄悄混淆。

同一形体需有适合手持、离体、推进或区域形式的表现规则，尺寸、轨迹和时长连续变化时仍能维持轮廓与材质。跨形态验证不能靠为一个技能编号写特例通过。

词条还应能声明对象筛选、触发条件、转移方向、维护方式、结果保留和传播连接等变化。引流可改分流、固定作用可改附着、临时结构可改持续维持；这些改造的玩法、保存和表现需求必须一起进入编译结果，不能全部退回数量和大小倍率。

### 接入修士自主创法

正式目标是让修士生成未预先登记过的构造，成为可学习、使用、保存和继续改造的能力。创法生成描述，共用编译器负责补全与检查，运行系统执行当前计划；玩家改造使用同一入口。

当前入口已核对：`ActorExtendTools.TryComprehendSkill()` 从功法池学习，`EnhanceSkillRandomly()` 强化已有技能，`TryCreateBranchPrototype()` 从同系列已登记资产挑选分支；已学能力由 `LearnedSkillActiveAbilityProvider` 接入主动施法，`WorldObjectSaveService` 保存技能定义及已学关系。这些是后续接入点，尚不代表已经具备新构造生成能力。

创法按以下顺序处理：

1. 读取修士已有知识、功法、材料偏好和使用经历，形成对结构、变化及作用的选择倾向；具体偏好规则逐步增加，不先强制新建完整知识树。
2. 生成结构或改造已有构造，允许替换与嵌套部件、改变材料、接入变化、建立关联及修改作用条件。生成过程操作共用结构，不能仅抽取完整技能编号或随机几个倍率。
3. 编译检查部位、资源、过程、成本和执行规模，并比较已有能力的结构及作用，避免大量只改名称的重复能力。缺失资料明确记录原因，不无限重试。
4. 成功后确定稳定编号、创造者、实际构造、必要种子及版本，接入已学能力和正常施放。创法发生在领悟、修炼或突破等合适入口，使用有界工作量，战斗出手直接执行已有计划。
5. 保存并载入同一构造和已学关系，恢复后的行为保持一致。更新资源或操作时走明确资料转换，不能重新随机生成另一招覆盖旧能力。

首批优先复用现有领悟和强化活动入口。不同修士的选择倾向需有可观察差异，具体频率与收益在实际世界中调节；自主创法不增加固定多招配方或战况衔接系统。

验收需要自然触发和可重复的开发调用两种方式：确认修士确实生成新结构、学会并自主释放、作用与画面一致，保存载入后仍能使用；同时保留输入、种子和构造资料，便于复现。测试所用的共用操作冻结后再验证新的结构变体。

### 接入游戏内自由拓展

保留万法阁选词条、轨迹及参数的使用方式。必要时提供清楚的投送方式和作用说明；跨形态产生的变化由编译结果回显，玩家不需要手工连接节点。

预览、实际施放、能力消耗、范围说明和保存使用同一编译结果。运行中的施放固定使用原版本，编辑只影响之后的出手。新增词条或轨迹通过登记自身改变的数据接入，不在所有法术中逐一追加判断。

界面沿用公共控件、候选搜索和本地化；本阶段不新增组合编辑器，不向 mod.json 堆叠开发选项。

### 定义版本转换

保持正式能力、蓝图、词条、轨迹等稳定编号。旧资料按相邻版本转换成新定义，并保留玩家修改、已学关系和资源要求。旧运行对象、模型句柄和线程状态不入档。

构造描述、所引资源与操作的稳定编号、资料版本和必要随机种子可保存；编译结果作为缓存重建。长期对象与过程的真实状态仍由对应玩法保存，不能只存生成种子就覆盖已经发生的世界变化。

资料已删除或无法转换时，遵守既有约定：保留原档、提示并仅丢弃受影响部分，其他世界内容继续读取。版本转换完成后运行当前实现，不长期维护两套旧新行为。

验证包含改造保存再载入、历史蓝图迁移、来源专属能力、部分无法转换及原档不被回写。

## 资源说明

| 资源或资料 | 要求 |
|---|---|
| 构造定义 | 六类要素、嵌套部件、作用对象、来源和版本明确 |
| 共用操作 | 输入输出、部位要求、实际状态变化、作用区和显示资料明确 |
| 自主创法资料 | 生成输入、结构变化、创造者、稳定编号、版本、必要种子与失败原因 |
| 改造规则 | 声明输入需求与输出变化，定义相互覆盖和计算顺序 |
| 飞掌资源 | 使用第一阶段实际通过的主体、动作和材质 |
| 变化说明 | 能说明从近身到飞行、目标与作用时点的变化 |
| 旧资料夹具 | 覆盖已学法术、玩家改造、法宝来源和旧轨迹 |
